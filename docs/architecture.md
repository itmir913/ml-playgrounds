# 아키텍처

`CLAUDE.md` §2의 상세 문서. 큐·워커·자원 관리·디렉터리 구조를 건드릴 때 읽는다.

**배포 경로가 둘이고 빌드 산출물은 하나다** (CLAUDE.md §1.1).

```
① GitHub Pages (공식)              ② 도커 (자가호스팅, 학교가 설치)

   Vue 3 (브라우저)                    Vue 3 (브라우저)
        │                                   │
   브라우저 내 학습                  ┌───────┴───────┐
   IndexedDB                        │               │
   .mlpx                     브라우저 내 학습    WebSocket (같은 오리진)
                                                    │
   서버 없음                                 FastAPI Gateway
                                                    │
                                            Job Queue (추상화)
                                                    │
                                              Worker Pool
                                                    │
                                          scikit-learn / pandas
```

같은 `dist/`가 양쪽에 들어간다. 프런트엔드는 시작할 때 **같은 오리진**의 헬스 엔드포인트를
찔러 서버 유무를 판정한다(§7.3). Pages에서는 404가 나고 브라우저 전용으로 동작한다.

**백엔드 주소를 설정 가능하게 만들지 마라.** CORS, mixed content(Pages는 https, 교실 서버는
대개 http), 교사가 고쳐야 할 설정 파일이 한꺼번에 생긴다. 같은 오리진이면 셋 다 없다.

## 1. 작업 큐

큐는 반드시 인터페이스 뒤에 둔다.

```python
# backend/app/jobs/base.py
class JobQueue(Protocol):
    async def enqueue(self, job: JobSpec) -> JobId: ...
    async def get_status(self, job_id: JobId) -> JobStatus: ...
    async def cancel(self, job_id: JobId) -> None: ...
```

**V1 — `InProcessQueue`** (asyncio.Queue + ProcessPoolExecutor)

sklearn으로 수천 행 CSV를 학습하는 데는 대개 1초도 걸리지 않는다. 진짜 병목은 학습이 아니라
동시 업로드와 메모리다. Redis를 처음부터 넣는 것은 과설계다.

**V2 이후 — `CeleryQueue`** (Redis broker)

이미지·음성 등 장시간 작업이 들어오는 시점(V5 예정)에 전환한다.
전환 시 `JobQueue` 구현체만 갈아끼우면 되도록 지금 설계한다.

### 1.1 큐 라우팅

나누는 기준은 **작업 크기**와 **데이터 타입** 두 가지다.

- 크기: `small` / `large` — 작은 작업이 큰 작업 뒤에서 굶지 않게 한다.
- 타입: `tabular` / `image` / `audio` / `text` — 이미지 학습이 CSV 학습을 막지 않게 한다.

V1에서는 `tabular-small`, `tabular-large` 둘만 있으면 된다.
그러나 **라우팅 로직은 처음부터 넣는다.**

### 1.2 V1의 확장 한계 (알려진 제약)

`InProcessQueue`는 백엔드 프로세스 안에 큐가 있으므로 **워커 수평 확장이 불가능하다.**
또한 백엔드를 다중 인스턴스로 띄우면 WebSocket의 `jobId` 구독이 특정 인스턴스에 묶인다
(작업을 처리한 인스턴스만 진행 상황을 안다).

V1은 단일 백엔드 인스턴스를 전제한다. 이 전제를 깨야 할 때가 `CeleryQueue` 전환 시점이다.
그 전까지는 로드 밸런서에 스티키 세션을 걸지 말고, 아예 인스턴스를 늘리지 마라.

## 2. 자원 관리

### 2.1 업로드 수용 판단

업로드를 **받기 전에** 판단한다. 다 받고 나서 거부하면 이미 디스크를 쓴 것이다.

1. 클라이언트가 `Content-Length` 또는 사전 요청으로 예상 크기를 알린다.
2. 서버가 `shutil.disk_usage()`로 가용 공간을 확인한다.
3. `free - DISK_RESERVE_MB < 예상크기 × SAFETY_FACTOR` 이면 `SERVER_DISK_INSUFFICIENT` 반환.
4. 통과하면 수락하고 스트리밍으로 임시 디렉터리에 쓴다.

**주의: `Content-Length`는 클라이언트가 속일 수 있다.** 사전 확인만으로는 부족하다.
스트리밍 중에도 누적 바이트를 세고, 신고한 크기나 `MAX_UPLOAD_MB`를 넘는 순간
연결을 끊고 부분 파일을 삭제해야 한다.

### 2.2 세션 수명주기

**세션 = WebSocket 연결 하나.** 학생이 데이터를 한 번 올리고 설정을 바꿔가며
여러 번 학습하는 동안 전체가 하나의 세션이다.

```
업로드 → /tmp/mlp/{sessionId}/ → 학습 N회 (설정만 바꿔 반복) → WS 종료 → 전부 삭제
                                   └ 예측도 여기서 즉시 처리
```

세션 동안 서버가 들고 있는 것:

| 대상 | 이유 |
|---|---|
| 원본 데이터셋 파일 | 재업로드 회피 |
| 파싱된 DataFrame | 재파싱 비용 회피 (200,000행이면 무시 못 한다) |
| 직전 학습 모델 | 예측 요청을 즉시 처리 |

**세션 종료를 감지하는 네 가지 경로.** 하나만 믿으면 반드시 샌다.

1. WebSocket `close` 이벤트 → `try/finally`에서 즉시 정리
2. **heartbeat(ping/pong) 실패** → half-open 연결 정리.
   TCP만 믿으면 끊긴 줄 모르는 연결이 데이터를 붙들고 남는다
3. **유휴 타임아웃** → 연결은 살아 있으나 N분간 요청이 없으면 정리.
   탭을 열어두고 하교하는 학생을 막는다
4. **고아 파일 청소기** → 위 셋이 모두 실패했을 때의 안전망.
   기준 시각은 디렉터리의 마지막 접근 시각이지 생성 시각이 아니다

- 정리는 `try/finally`에서 수행한다. 실패해도 반드시 지운다.
- 컨테이너의 작업 볼륨은 크기 제한을 걸어라(tmpfs 또는 quota).
  코드 버그가 호스트 디스크를 채우면 안 된다.

**받아들인 대가**

- 브라우저 새로고침 = 세션 소실 = 데이터 재업로드. grace period로 재접속을 허용하는 방안은
  서버에 상태를 남기는 쪽으로 미끄러지므로 채택하지 않았다.
- **디스크 점유가 "작업 중"에서 "접속 중"으로 늘어난다.** 30명 학급이 각 50MB를 올리면
  1.5GB가 상주한다. 여러 학급이 겹치면 그만큼 곱해진다.
  → 세션 상한값을 반드시 걸어야 한다 (`open-decisions.md` #9)

### 2.3 상한값

> **이 표는 임시다.** `backend/app/config.py`(Pydantic Settings)를 구현하는 시점에
> 아래 값을 코드로 옮기고 **이 절은 삭제한다.** 이후 단일 출처는 `config.py`다.

| 항목 | 초기 기본값 | 환경 변수 |
|---|---|---|
| 업로드 최대 크기 | 50 MB | `MAX_UPLOAD_MB` |
| 최대 행 수 | 200,000 | `MAX_ROWS` |
| 최대 열 수 | 200 | `MAX_COLUMNS` |
| 학습 최대 시간 | 120 초 | `MAX_TRAIN_SECONDS` |
| 작업당 최대 메모리 | 2048 MB | `MAX_MEMORY_MB` |
| 디스크 예비 공간 | 2048 MB | `DISK_RESERVE_MB` |
| 동시 실행 작업 수 | CPU 코어 수 | `MAX_CONCURRENT_JOBS` |

시간·메모리 상한은 **워커 프로세스 수준에서** 강제한다
(별도 프로세스 + `resource.setrlimit`, 또는 컨테이너 제한).
파이썬 코드 안의 체크만으로는 막지 못한다.

**미해결 문제:** `MAX_MEMORY_MB` × `MAX_CONCURRENT_JOBS`가 호스트 메모리를 넘을 수 있다
(8코어면 16GB 요구). CLAUDE.md §1.5와 충돌한다. → `open-decisions.md`

## 3. 브라우저 내 학습 — V1의 기본 실행 위치

**공식 배포에는 서버가 없으므로 이것이 유일한 실행 위치다.** 더 이상 "나중에 붙이는 것"이
아니라 V1이 성립하는 조건이다.

### 3.1 결과 일치는 여전히 제약이다 — 자리가 옮겨졌을 뿐

서버가 없어졌으니 "브라우저 vs 서버"를 맞출 필요가 없어 보이지만, **배포 경로가 둘이라
"Pages 결과 vs 도커 결과"가 그 자리를 대신한다.** 그리고 이쪽이 더 위험하다.

```
학생이 집에서 Pages로 학습 → .mlpx 제출
→ 교사가 도커 설치본에서 열고 재실행 대조
→ 엔진이 달라 숫자가 안 맞음
→ 무고한 학생이 위조를 의심받는다
```

수행평가에서 이건 이 프로젝트가 낼 수 있는 최악의 실패다.

### 3.2 그래서 재실행 대조는 엔진을 넘지 않는다

각 run에 **엔진 종류와 버전을 기록**하고(`mlpx-spec.md` §4), 대조는 그 run을 만든 엔진으로만
한다. 다른 엔진밖에 없으면 "대조할 수 없음"이지 "불일치"가 아니다.

이 규칙 덕분에 **엔진 선택과 검증 설계가 분리된다.** 엔진은 순수하게 다운로드 크기와 정확도로
고르면 되고, 나중에 엔진을 바꿔도 옛 파일의 검증 의미가 깨지지 않는다.

### 3.3 엔진은 둘이다

**순수 JS가 기본이고 scikit-learn은 학생이 켜는 선택지다**(`open-decisions.md` "브라우저 학습
엔진은 둘 다 간다"). 실측값과 지표 차이는 그쪽에 있다. 여기서는 구조만 적는다.

핵심은 **무거운 엔진의 로딩 시점을 화면 최상단의 상태 점검이 쥔다**는 것이다. 자동으로 받으면
교사가 부하 타이밍을 통제할 수 없고, 26MB와 15초가 수업 중간에 예고 없이 터진다.

**"동등성 보장"이라고 말하지 마라.** 엔진이 다르면 숫자가 갈리는 것은 실측으로 확인됐고
(로지스틱 회귀 0.9667 대 0.8667), 같은 sklearn이라도 WASM과 네이티브는 BLAS와 스레드 수가
달라 마지막 자리가 갈린다. 트리 계열은 `random_state` 고정 시 대개 같다. UI는 자릿수를
제한해 표시하고, 대조는 정확 일치가 아니라 **허용 오차**로 판정한다(`open-decisions.md` #12).

### 3.4 학습은 Web Worker에서 돈다

**화면이 얼면 안 된다** (`open-decisions.md` "학습은 언제나 백그라운드다"). 스피너를 띄우는
것으로는 부족하다 — 메인 스레드가 막히면 진행률도 취소 버튼도 같이 죽는다.

```
메인 스레드          Worker                    서버 (자가호스팅)
  [학습] 클릭  ──▶  postMessage        또는  ──▶ WebSocket
  진행률 표시  ◀──  progress 이벤트          ◀── progress 이벤트
  취소         ──▶  terminate                ──▶ cancel
```

**두 경로의 모양이 같다.** 그래서 `TrainingBackend`가 하나로 유지되고 화면은 어디서
도는지 몰라도 된다. 엔진 시동(scikit-learn 15.4초)도 같은 워커에서 한다.

`terminate`가 유일하게 확실한 취소 수단이다. 메인 스레드에서 도는 루프는 멈출 방법이 없고,
45분 수업에서 잘못 누른 학습을 못 멈추는 것은 그 자체로 실패다.

### 3.5 실행 방법은 하나의 목록이다

`computedBy`(browser/server)와 `engine.kind`는 직교하지만 **화면에는 하나의 목록으로 낸다.**
드롭다운 두 개는 중학생에게 던질 질문이 아니다.

어휘는 이렇게 대응한다.

| 화면 | `computedBy` | `engine.kind` | 실행 방법 id |
|---|---|---|---|
| 순수 JS | `browser` | `mljs` | `mljs` |
| scikit-learn (내 컴퓨터) | `browser` | `pyodide-sklearn` | `pyodide-sklearn` |
| scikit-learn (학교 서버) | `server` | `sklearn` | `server-sklearn` |

**화면은 이 목록을 알고리즘마다 다시 묻지 않는다.** 묶음 기본을 위에서 한 번 고르고,
바꾸고 싶은 모델만 개별로 바꾼다.

```
실행 방법(기본):  ● 순수 JS   ○ scikit-learn(내 컴퓨터)   ○ 학교 서버

학습할 모델
  ☑ 결정 트리        순수 JS ▾            ← 기본 그대로
  ☑ 랜덤포레스트     scikit-learn ▾       ← 학생이 바꿈
  ☑ SVM             학교 서버 ▾           ← 순수 JS에 없어서 자동으로 옮겨짐(표시된다)
```

판정은 `frontend/src/ml/backend.ts`의 순수 함수 하나가 하고, **상단 상태 패널과 모델 선택
화면이 같은 결과를 본다.** 두 곳이 각자 판정하면 반드시 어긋난다.
자동 이동은 없어지는 것이 아니라 **그 칸의 기본값을 채우는 동작**이 된다(§0.1) — 그러면
"왜 이건 딴 데서 돌지"가 화면에 그냥 보인다. **콕 집어 고른 칸은 옮기지 않는다.**

**같은 알고리즘을 여러 실행 방법으로 나란히 둘 수 있다.**

```
  ☑ SVM             순수 JS ▾
  ☑ SVM             scikit-learn ▾     ← 같은 SVM, 다른 엔진
  ☑ SVM             학교 서버 ▾
```

"같은 SVM인데 왜 숫자가 다른가"를 한 묶음 안에서 보는 것이 목적이다. 그리고 이것이
위의 "콕 집은 칸은 안 옮긴다" 규칙이 필요한 이유다 — 옮기면 셋이 같은 곳으로 몰려
**똑같은 줄 세 개**가 나오고 비교하려던 것이 사라진다.

**묶음이 보장하는 것은 같은 데이터·전처리·분할이다. 엔진은 그 목록에 없다.**
그래서 엔진이 섞여도 비교는 성립하고, 대신 각 run이 무엇으로 만들어졌는지 남긴다(§3.2).
서버로 가는 모델이 섞여 있으면 화면이 **몇 개가 서버로 가는지 요약해 줘야 한다** —
교사가 부하 타이밍을 쥘 수 있어야 하기 때문이다.

## 5. 로컬 개발

**도커는 필요 없다.** 도커 이미지·nginx 설정·`docker-compose.yml`은 배포 단계에서 만든다
(`open-decisions.md` #10).

```bash
# 백엔드 (backend/)
uv sync                                          # 최초 1회, uv.lock 생성
uv run uvicorn app.main:app --reload --port 8000
uv run ruff check . && uv run mypy . && uv run pytest

# 프런트엔드 (frontend/)
npm install
npm run dev
npm run lint && npm run typecheck && npm test
```

`package.json`과 `pyproject.toml`의 버전은 상한 없는 캐럿 범위다.
최초 `npm install` / `uv sync` 후 실제로 해결된 버전을 락파일로 고정한다.
**`uv.lock`과 `package-lock.json`은 커밋한다.** 재현성이 이 프로젝트의 요구사항이다.

## 6. 데이터 타입 확장 (V5~V7)

V1은 표 데이터만 다루지만, 최종 목표는 학생이 이미지·음성·텍스트로도 포트폴리오를
만드는 것이다. **표 데이터 전용 가정을 계약에 새겨 넣지 마라.**

이미 준비된 확장 지점:

| 지점 | 어떻게 확장되는가 |
|---|---|
| `manifest.dataType` | `tabular` / `image` / `audio` / `text` |
| 큐 라우팅 | 타입 축이 이미 있다. 이미지 학습이 CSV 학습을 막지 않는다 |
| `dataset/` 레이아웃 | 타입별 구조가 명세돼 있다 (`mlpx-spec.md` §1) |
| `registry` | 알고리즘을 등록만 하면 된다 |
| `TrainingBackend` | 실행 위치를 갈아끼운다 |

**아직 없는 확장 지점 — 만들 때 함께 설계할 것:**

- **지표 선택**: 현재는 분류 지표만 상정한다. `taskType`(classification / regression /
  clustering)에 따라 지표 집합이 완전히 달라진다. `evaluate.py`에도 알고리즘 registry와
  같은 방식의 **지표 registry**가 필요하다. `if taskType == ...` 분기를 만들지 마라.
- **전처리 파이프라인**: 표 데이터의 결측치·스케일링·인코딩은 이미지·음성에 그대로 대응되지
  않는다(리사이즈, 정규화, 특징 추출). `preprocess.py`를 dataType별 파이프라인으로 나눠야 한다.
- **업로드 형태**: 이미지·음성은 파일 하나가 아니라 라벨 디렉터리 묶음이다.
  `routes_train.py`의 요청 스키마가 단일 CSV를 전제하지 않도록 한다.

## 7. 운영 비용과 실행 위치 정책

**아무도 공용 백엔드를 운영하지 않는다.** 공식 배포는 GitHub Pages 정적 페이지이고,
백엔드는 도커로 배포되어 **필요한 학교가 직접 설치한다**(CLAUDE.md §1.1).

이 절이 원래 전제했던 "개인이 Oracle 프리티어에 공용 서버를 띄운다"는 폐기됐다.
아래 §7.1은 그 판단의 근거로 남긴다 — 숫자가 결론을 그대로 지지한다.

### 7.1 공용 서버는 왜 불가능한가

교실에서 실제로 쓰는 데이터는 작다. 붓꽃 5 KB, 타이타닉 60 KB, 학생이 만든 데이터도 대개 수 MB 이하다.
50 MB는 상한이지 전형값이 아니다. 학습도 수천 행이면 1초 미만이다.

| 상황 | 부하 | 판정 |
|---|---|---|
| 한 학급 30명, 각 1 MB, 동시 학습 | 메모리 수백 MB, CPU 몇 초 | 여유 |
| 한 학급 30명이 상한(50 MB)을 실제로 사용 | 세션 상주 메모리 6 GB 이상 | 위험 |
| 같은 교시에 100개 학급 = 3,000명 | 어떤 계산으로도 불가능 | **불가** |

한국 학교는 시간표가 정렬돼 있어 부하가 교시 시작에 몰린다.
**전국 단위로 퍼지면 서버 학습만으로는 구조적으로 버틸 수 없다.**

그리고 계산이 버티더라도 남는 문제가 셋이다.

1. 공개 URL에 인증이 없으면 **익명 사용자에게 개인 부담 연산을 무제한 열어주는 것**이다.
   로드맵은 계정·로그인을 명시적으로 범위 밖에 뒀다.
2. 막으려고 계정을 두면 개인정보를 다루게 되어 §1.1의 "인적사항을 받지 않는다"와 충돌한다.
3. **수행평가 도중 서버가 죽으면 그 실패는 교사가 뒤집어쓴다.** 개인이 질 책임이 아니다.

### 7.2 결론: 공식 배포는 정적, 서버는 학교가 설치

| 누가 | 무엇을 | 어디서 | 우리 서버 비용 |
|---|---|---|---|
| 학생 | 모든 학습 | 브라우저 | **0** |
| 학생 | 큰 데이터·무거운 알고리즘 | 학교가 설치한 서버 | **0** (학교 부담) |
| 교사 | 제출물 재실행 대조 | 브라우저 | **0** |

연산 부담이 **그 연산의 혜택을 받는 곳**에 놓인다. 강한 장비가 필요한 학교는 컴퓨터실에
직접 띄우고, 그렇지 않은 대다수는 정적 페이지만으로 수업을 끝낸다.

자가호스팅 서버는 세션 동안 데이터셋·DataFrame·직전 모델을 캐시한다(§2.2). 학교 안에서
도는 서버이므로 데이터가 학교 밖으로 나가지 않는다 — 공용 서버였을 때의 개인정보 압박이
여기서는 성립하지 않으므로 세션 상한(`open-decisions.md` #9)을 넉넉하게 잡아도 된다.

**다만 세션을 넘어선 영구 보관은 하지 않는다.** §1.2(브라우저가 저장소다)와 §1.3(하나의
파일이 제출물이다)이 흔들리고, 서버가 죽으면 학생 작업물이 날아간다. 모델은 서버가
내려보내고 **클라이언트가 `.mlpx`에 담는다.**

### 7.3 서버가 없는 것이 기본 상태다

공식 배포에는 서버가 아예 없다. 그러므로 "서버 없음"은 예외 처리가 아니라 **정상 경로**다.

- 프런트엔드는 시작할 때 **같은 오리진**의 헬스 엔드포인트를 찔러 `ServerStatus`를 정한다.
  Pages에서는 404가 나고 `unavailable`로 굳는다. 탐지 타임아웃은 짧게 잡아 정적 배포
  사용자가 기다리지 않게 한다.
- 모델 선택 화면은 알고리즘마다 **실행 위치**를 함께 보여준다.
- 서버가 없으면 서버 실행 옵션을 비활성화하되 **왜 못 쓰는지 이유를 함께 보여준다.**
  이유 없이 회색으로 죽어 있는 버튼은 학생에게 고장으로 보인다.
- 판정 로직은 `frontend/src/ml/backend.ts`의 `runtimeOptions()`에 있다. 순수 함수이고 테스트로 덮여 있다.
- 확인 전 상태(`unknown`)는 서버를 열어 주지 않는다. 낙관적으로 켰다가 실패하는 것보다
  처음부터 브라우저로 가는 편이 낫다.

### 7.4 브라우저 학습 엔진의 전송량

기본 엔진(순수 JS)은 gzip 25 KB라 사실상 없는 비용이다. scikit-learn 엔진은 **gzip 26.3 MB**이고
**이걸 GitHub Pages가 서빙한다** — 우리가 부담하는 전송량은 0이고, Pages는 CDN이 붙어 있어
학교 회선에서도 빠르다. 개인 서버로 이만한 정적 자산을 서빙하지 않아도 되는 것이 정적 배포의
부수 효과다.

- 불변 자산으로 긴 캐시 헤더를 붙인다. 학기 중 같은 학생이 반복 접속하는 패턴에 잘 맞는다.
- 서비스 워커로 캐시하면 두 번째 수업부터는 다운로드가 없다. 다만 **학교 PC는 재이미징되는
  경우가 있어** 캐시를 전제로 설계하지 마라.
- **캐시가 지우지 못하는 비용이 따로 있다.** WASM 시동과 첫 `import sklearn`이 개발 PC에서도
  15.4초이고 이건 페이지를 열 때마다 다시 든다. 다운로드만 캐시된다.
- 그래서 **로딩 시점을 상태 점검이 쥔다**(§3.3). 수업 시작 시각에 30명이 동시에 받는 것은
  막을 수 없지만, **언제 그 30명이 받을지를 교사가 정할 수 있게** 하는 것이 요점이다.

### 7.5 검증은 브라우저에서 끝난다

서명이 없으므로 "미검증"이라는 상태 자체가 없다. 교사는 제출물을 열어 **재실행 대조**로
지표가 재현되는지 확인하고, 그 계산은 교사의 브라우저에서 일어난다
(`mlpx-spec.md` §7). 서버도, 채점 시점의 서버 비용도 필요 없다.

대조는 **run을 만든 엔진으로만** 한다(§3.2). 교사 환경에 그 엔진이 없으면
"대조할 수 없음"이며 "불일치"가 아니다.

## 8. 프런트엔드 셸

화면 하나하나가 아니라 **화면들이 놓이는 틀**을 정한다. 여기 적힌 것은 개별 화면을
만들면서 흔들리면 안 되는 결정들이다.

### 8.1 라우팅은 해시 모드다

`createWebHashHistory`를 쓴다. 주소는 `#/project/{id}/train` 모양이다.

- **GitHub Pages에는 SPA 재작성 규칙이 없다.** history 모드로 두면 `/project/abc/train`을
  새로고침하는 순간 404가 난다. 학생이 F5를 누르는 것은 예외 상황이 아니다.
- 같은 `dist/`가 Pages와 도커 양쪽에 들어간다(§7). 해시 모드는 **어느 쪽에서도 서버 설정이
  필요 없다.** 한쪽만 되는 방식을 고르면 배포 경로마다 다른 산출물이 생긴다.
- 404.html로 우회하는 방법이 있지만, 그건 새로고침할 때마다 리다이렉트가 한 번 끼는
  것이고 주소창이 잠깐 튄다. 얻는 것은 `#` 하나가 사라지는 것뿐이다.

### 8.2 라우트는 워크플로 단계다

**단계를 컴포넌트 안의 상태로 두지 않는다.** 단계 하나가 라우트 하나다.

```
/                          프로젝트 목록
/project/:id/data          데이터
/project/:id/preprocess    전처리·모델 설정
/project/:id/train         학습
/project/:id/results       결과 분석
/project/:id/predict       예측
/project/:id/portfolio     포트폴리오
```

이 순서는 **학생이 프로젝트를 만들어 가는 워크플로**다. 수행평가 진행 순서가 아니다 —
이 도구는 수행평가를 대체하지 않는다.

라우트로 두면 얻는 것:

- 브라우저 뒤로가기가 그대로 동작한다. 단계를 상태로 두면 뒤로가기가 앱을 통째로 벗어난다.
- 상단 단계 탭바가 곧 네비게이션이다. 별도의 단계 상태를 둘 이유가 없다.
- 학생이 주소를 복사해 자기 다른 기기에서 열 수 있다 (프로젝트는 그 기기의 IndexedDB에 있어야 한다).

### 8.3 가드는 컴포넌트 밖의 순수 함수다

데이터 없이 `/train`에 들어가는 것 같은 판단은 **컴포넌트 안에 두지 않는다.**
입력을 받아 "여기 들어가도 되는가 / 아니면 어디로 보내는가"를 돌려주는 순수 함수로 두고,
라우터 가드는 그 함수를 호출하기만 한다.

이유는 하나다 — **단계 진입 조건은 화면을 띄우지 않고 테스트할 수 있어야 한다.**
컴포넌트 안에 두면 조건 하나를 확인하려고 화면 전체를 마운트해야 한다.

### 8.4 겉모습은 토큰 한 겹 뒤에 둔다

색·모서리·그림자·간격을 컴포넌트에 직접 쓰지 않는다. `src/style.css`의 `@theme`에
**의미 있는 이름**으로 정의하고 컴포넌트는 그 이름만 쓴다 (`--color-surface`이지
`--color-white`가 아니다).

디자인은 교체가 예정돼 있다. 토큰을 두면 교체가 **값을 바꾸는 일**이 되고, 안 두면
**전부 다시 쓰는 일**이 된다. 이건 나중에 할 리팩터링이 아니라 지금 두는 이음매다.

### 8.5 글꼴은 자체 호스팅한다

Pretendard Variable **동적 서브셋**을 저장소에 넣고 우리가 서빙한다.

- **CDN을 쓰지 않는다.** 학교망이 CDN을 막는 경우가 실재하고, 그러면 글꼴만 깨지는 게
  아니라 화면 폭이 통째로 달라진다.
- 동적 서브셋은 유니코드 범위별로 잘린 파일들이고 브라우저가 **화면에 실제로 뜬 글자의
  범위만** 받는다. 전체를 한 파일로 받으면 첫 화면에서 1 MB가 넘는다.
- `font-display: swap`. 글꼴을 기다리느라 글자가 안 보이는 시간을 만들지 않는다.
- **글꼴 스택에 일본어 대체를 처음부터 넣는다.** ja를 추가할 때 스택을 고치는 일이
  없어야 한다 (CLAUDE.md §3).

### 8.6 셸은 웹페이지가 아니라 작업실이다 (2026-08-05)

**앞의 §8.1~8.5는 그대로 두고, 화면을 담는 껍데기만 다시 정했다.** 첫 구현은 강의노트형
참고물을 따라 히어로 + 세로 스크롤로 만들어졌는데, 이 도구는 **읽으러 온 사람이 아니라
한 시간 넘게 작업하는 사람**을 위한 것이다.

상시 존재하는 영역은 **넷뿐이다.** 나머지는 전부 작업 공간이 바뀌는 것이다.

```
┌──────────────────────────────────────┐
│ 상단 바 (52px)                        │  프로젝트 이름 · 전역 동작 · 상태 버튼
├───┬──────────────────────────────────┤
│레일│                                  │
│ 📂│                                  │
│ ⚙ │        작업 공간                  │  라우트가 바꾸는 유일한 곳
│ 🧪│                                  │
│ 📈│                                  │
├───┴──────────────────────────────────┤
│ 상태 표시줄                           │  저장 상태 · 내보내기 · 크기 · 언어
└──────────────────────────────────────┘
```

**목록 화면도 이 셸 안에 있다.** 별도의 홈이 없다 — 앱을 열면 이미 작업실이고, 가운데만
"새 프로젝트 / 프로젝트 열기"로 채워진다. 프로젝트를 만들어도 다른 페이지로 가지 않고
같은 자리의 내용이 바뀐다. 그래야 웹사이트가 아니라 프로그램처럼 느껴진다.

**단계 이동은 왼쪽 레일이 쥔다. 상단 바는 안 쥔다.** 둘 다 두면 같은 것이 두 군데 있고,
학생은 둘이 다른 것인 줄 안다. 상단 바에 남는 것은 프로젝트 이름, 저장·열기·내보내기
같은 전역 동작, 그리고 상태 버튼이다.

**레일은 아이콘만 남긴다**(56~64px). 표와 그래프가 이 앱의 본체이고, 그것들이 쓸 수 있는
가로 폭이 넓을수록 좋다. 못 가는 단계는 지우지 않고 **이유와 함께** 흐리게 둔다(§8.2).

**휴대폰에서는 레일이 아래로 내려간다.** 좁은 화면에서 세로 레일은 이미 부족한 가로 폭을
더 깎는다. `sm` 미만에서 하단 바로 바뀌고 상태 표시줄은 접힌다. 모바일에서도 동작해야
한다는 것은 타협 대상이 아니다(`open-decisions.md` "모바일에서도 동작한다").

**상태 팝오버.** 상단 바의 상태 버튼을 누르면 지금 무엇을 하는 중인지, 다음이 무엇인지,
단계가 어디까지 왔는지가 작은 팝오버로 뜬다. 모달도 사이드 패널도 아니다 — 작업을
가리지 않고 잠깐 떴다 사라지는 것이어야 한다.

### 8.7 화면이 다음에 할 일을 말한다

**이 도구가 IDE와 갈라지는 지점이다.** JetBrains도 VS Code도 Figma도 "사용자가 이미
어디에 뭐가 있는지 안다"를 전제한다. 우리 사용자는 **머신러닝을 처음 만나는 학생**이다.

그렇다고 튜토리얼이 되면 안 된다. 학생이 "이제 뭘 하지?"를 묻지 않게 하되, 물어보지도
않은 설명을 늘어놓지 않는다.

**단계마다 그 단계 안의 할 일 목록을 보여준다.**

```
데이터        ☑ 파일 올리기   ☐ 시트 고르기   ☐ 열 확인하기
전처리        ☐ 예측할 값 고르기   ☐ 특성 고르기   ☐ 빈 칸 처리   ☐ 스케일링
학습          ☐ 알고리즘 고르기   ☐ 설정 조정   ☐ 학습 시작
결과          ☐ 묶음 견주기   ☐ 지표 읽기
```

**이 목록은 §8.3의 잠금 조건과 같은 것을 다른 각도에서 보여주는 것이다.** 그러므로
**같은 순수 함수에서 나와야 한다.** 두 벌로 만들면 "체크는 다 됐는데 다음 단계가 잠겨
있다"가 생기고, 그건 학생이 고칠 방법이 없는 고장이다.

### 8.8 저장 상태를 늘 보여준다

**학교 컴퓨터실 PC는 전원을 끄면 디스크가 되돌아간다**(`open-decisions.md` "컴퓨터실 PC는
리셋을 전제한다"). 그래서 상태 표시줄이 이 프로젝트에서 장식이 아니라 **핵심 기능**이다.

상태 표시줄에 상시 있는 것:

- **IndexedDB 저장 상태와 마지막 저장 시각** — 자동 저장이 돌고 있다는 것을 보여준다
- **내보내기 상태** — `.mlpx`로 내보낸 적이 있는가, 그 뒤로 고쳤는가
- 프로젝트 크기, 현재 언어

**"아직 내보내지 않았습니다"가 상시 보이는 것이 이 도구가 리셋 문제에 주는 답이다.**
차시가 끝날 때 잔소리하는 배너보다 낫다 — 배너는 닫히고, 상태 표시줄은 늘 거기 있다.

**내보낸 시각은 `.mlpx`에 적지 않는다.** 그건 **이 기기의 사정**이지 파일의 내용이
아니다. 파일이 존재한다는 것 자체가 내보내졌다는 뜻이고, 그 파일에 "나는 내보내졌다"를
적는 것은 아무것도 더해 주지 않는다. IndexedDB의 프로젝트 레코드에만 남긴다.

### 8.9 화면마다의 방향 (2026-08-05)

셸이 정해진 뒤에 나온 것들이다. 해당 화면을 만들 때 여기부터 읽는다.

**작업 공간 머리.** 단계마다 작은 머리 영역을 둔다 — 이 단계가 무엇을 하는 곳인지 한 줄,
그리고 지금의 맥락(어떤 파일, 몇 행 몇 열). **길잡이 역할은 하지 않는다.** 이동은 레일이
쥔다(§8.6). 히어로는 쓰지 않는다.

**빈 화면은 고장처럼 보이면 안 된다.** 모든 빈 상태가 둘을 갖는다 — **왜 비어 있는지**와
**무엇을 하면 열리는지.** "결과가 없습니다"로 끝내지 않고 "학습을 한 번 하면 여기에
지표가 나옵니다"까지 간다. 이건 §8.2의 "이유 없이 회색이면 고장으로 본다"와 같은 규칙이다.

**데이터 화면은 표가 주인공이다.** 카드를 쌓지 않는다. 순서는 표 > 데이터 정보 >
열 검사기이고, 검사기는 필요할 때만 나오는 보조 영역이다. 열이 수십 개인 표를 카드 안에
가두면 가로 스크롤 상자 안에서만 볼 수 있게 된다.

**결과 화면은 순위표가 아니라 변경 이력이다.** 이 도구의 차별점은 "가장 좋은 모델"이
아니라 **"무엇을 바꿨더니 왜 달라졌는가"**다. 묶음마다 직전 대비 무엇이 바뀌었는지를
`batch.changed`가 이미 들고 있다(`mlpx-spec.md` §4). 지표 옆에 `스케일링 OFF → ON`처럼
붙여 **git diff를 읽듯** 보게 한다. 순위는 그다음이다.

**예측 화면은 표의 한 줄을 채우는 것이다.** 별도의 폼이 아니라 데이터 화면과 같은
머릿속 모형을 쓴다 — 학생이 이미 본 그 표에 새 줄을 하나 넣는 일이어야 한다.

**포트폴리오는 마크다운 편집기가 아니라 보고서를 쓰는 자리다.** 원시 마크다운을 다루는
느낌을 최소화한다. 문항이 먼저 보이고 그 아래에 쓰는 칸이 있는 모양이다.

**체크리스트에 없는 상태를 지어내지 않는다.** §8.7의 목록은 프로젝트에서 **읽어낼 수
있는 사실**만 담는다. "시트 고르기"는 시트가 여럿인 엑셀에만 있는 일이라 항목이 아니라
그 순간의 선택지이고, "빈 칸 처리"와 "스케일링"은 기본값이 이미 있어 영원히 체크된
상태다. 그런 것들은 체크박스가 아니라 **"지금 이렇게 되어 있습니다" 요약 줄**로 보여준다.
체크할 수 없는 체크박스는 안내가 아니라 방해다.

### 8.10 문구도 등록부에서 나온다 (2026-08-05, 아직 구현 안 됨)

**`if (dataType === 'image')`를 금지한 규칙을 코드가 아니라 문장이 어기고 있었다.**

- "데이터를 불러오고 **어떤 열이 있는지** 확인합니다" — 이미지·음성에는 열이 없다
- "**예측할 값** 고르기" — 군집화에는 예측할 값이 없다

단어를 바꿔서 될 일이 아니다. 조합마다 맞는 문장이 다르므로 **문구가 등록부에서
나와야 한다.** 아래 둘을 그렇게 정했다.

**단계 설명문은 데이터 종류 등록부가 갖는다.** `data/kinds.ts`의 판이 자기 설명문 키를
함께 들고, 화면은 그것을 읽는다. 이미지 판을 더할 때 문구가 같이 따라오고, 빠뜨리면
컴파일이 깨진다.

**단계별 체크리스트는 없앤다.** 분류·회귀·군집·이미지에 **모두** 맞는 문구는
"학습에 쓸 것 정하기"처럼 막연해져서 안내 구실을 잃는다. 조합마다 문구를 두면
번역할 문장이 곱으로 늘고(3개 언어 × 조합), **어느 조합의 문구가 이상한지 CI가 못
잡는다** — §3이 "검사가 못 잡는 것은 번역이 됐는가"라고 적어 둔 것과 같은 함정이다.

같은 정보는 이미 두 곳이 전달한다 — 레일의 잠금 상태와 각 단계 화면 자체.
`ProjectFacts`와 잠금 조건(§8.7)은 **그대로 남는다.** 사라지는 것은 화면에 뜨는
목록(`StepChecklist`, `tasks.*`, 프로젝트 홈의 항목 나열)뿐이다.

### 8.11 레일 글자는 두 줄까지다 (2026-08-05)

규칙 자체는 `CLAUDE.md` §3 규칙 9에 있다. 여기에는 **왜 그 규칙이 필요했는지**와
레일에서 실측한 값을 남긴다. 다른 좁은 칸(탭·배지)을 만들 때 같은 계산을 다시 한다.

레일은 `--spacing-rail` 4.5rem(72px)이고 칸의 좌우 여백을 빼면 **안쪽이 64px**이다.
`text-base` 16px에 `style.css`의 자간 `-0.01em`이 붙어 **한글 한 자가 약 15.8px**이다.

- 보통 굵기: 네 자 = 63.4px. 64px에 0.6px 남기고 들어간다.
- 굵은 글씨: 네 자가 안 들어간다.

**그래서 활성 칸을 굵게 하지 않는다.** 굵게 하면 "대시보드"가 안 눌렸을 때 한 줄,
눌렀을 때 두 줄이 되어 **칸을 누를 때마다 레일 전체가 튄다.** 활성 표시는 흰 면과
브랜드 색과 경계선이 이미 하고 있고(§8.6), 굵기는 거기에 아무것도 더하지 않으면서
레이아웃만 흔든다. 영어 `Training`도 같은 경계에 있었다.

**끊는 자리를 잡을 때의 기준은 세 자다.** 네 자는 0.6px 여유라 글꼴 지표가 조금만
달라져도 넘친다. `대시​보드`(2/2), `포트​폴리오`(2/3)가 여기서 나왔다.

영어는 `hyphens: auto`가 **실측에서 하이픈을 만들지 않았다.** `word-break`를 바꿔도
결과가 같았으므로 브라우저에 하이픈 사전이 없는 것이고, `Dashboar/d` `Portfoli/o`처럼
아무 데서나 끊겼다. 소프트 하이픈을 넣어 `Dash-/board` `Port-/folio`로 잡았다.
`Pre­pro­cess­ing`처럼 **여러 자리를 열어 두면 브라우저가 들어가는
것을 고른다** — 한 자리만 열면 그 뒤가 여전히 넘칠 수 있다.

검증은 브라우저에서 각 라벨의 `scrollWidth > clientWidth`와 줄 수를 재서 했다.
눈으로 보는 것보다 정확하고, 언어를 바꿔 가며 반복할 수 있다.
