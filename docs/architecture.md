# 아키텍처

`CLAUDE.md` §2의 상세 문서. 큐·워커·자원 관리·디렉터리 구조를 건드릴 때 읽는다.

**배포 경로가 둘이고 빌드 산출물은 하나다** (CLAUDE.md §1.1).

```
① GitHub Pages (공식)              ② 도커 (자가호스팅, 학교가 설치)

   Vue 3 (브라우저)                    Vue 3 (브라우저)
        │                                   │
   브라우저 내 학습                  ┌───────┴───────┐
   IndexedDB                        │               │
   .mlpx                     브라우저 내 학습    WebSocket (같은 오리진)
                                                    │
   서버 없음                                 FastAPI Gateway
                                                    │
                                            Job Queue (추상화)
                                                    │
                                              Worker Pool
                                                    │
                                          scikit-learn / pandas
```

같은 `dist/`가 양쪽에 들어간다. 프런트엔드는 시작할 때 **같은 오리진**의 헬스 엔드포인트를
찔러 서버 유무를 판정한다(§7.3). Pages에서는 404가 나고 브라우저 전용으로 동작한다.

**백엔드 주소를 설정 가능하게 만들지 마라.** CORS, mixed content(Pages는 https, 교실 서버는
대개 http), 교사가 고쳐야 할 설정 파일이 한꺼번에 생긴다. 같은 오리진이면 셋 다 없다.

## 1. 작업 큐

큐는 반드시 인터페이스 뒤에 둔다.

```python
# backend/app/jobs/base.py
class JobQueue(Protocol):
    async def enqueue(self, job: JobSpec) -> JobId: ...
    async def get_status(self, job_id: JobId) -> JobStatus: ...
    async def cancel(self, job_id: JobId) -> None: ...
```

**V1 — `InProcessQueue`** (asyncio.Queue + ProcessPoolExecutor)

sklearn으로 수천 행 CSV를 학습하는 데는 대개 1초도 걸리지 않는다. 진짜 병목은 학습이 아니라
동시 업로드와 메모리다. Redis를 처음부터 넣는 것은 과설계다.

**V2 이후 — `CeleryQueue`** (Redis broker)

이미지·음성 등 장시간 작업이 들어오는 시점에 전환한다.
전환 시 `JobQueue` 구현체만 갈아끼우면 되도록 지금 설계한다.

### 1.1 큐 라우팅

나누는 기준은 **작업 크기**와 **데이터 타입** 두 가지다.

- 크기: `small` / `large` — 작은 작업이 큰 작업 뒤에서 굶지 않게 한다.
- 타입: `tabular` / `image` / `audio` / `text` — 이미지 학습이 CSV 학습을 막지 않게 한다.

V1에서는 `tabular-small`, `tabular-large` 둘만 있으면 된다.
그러나 **라우팅 로직은 처음부터 넣는다.**

### 1.2 V1의 확장 한계 (알려진 제약)

`InProcessQueue`는 백엔드 프로세스 안에 큐가 있으므로 **워커 수평 확장이 불가능하다.**
또한 백엔드를 다중 인스턴스로 띄우면 WebSocket의 `jobId` 구독이 특정 인스턴스에 묶인다
(작업을 처리한 인스턴스만 진행 상황을 안다).

V1은 단일 백엔드 인스턴스를 전제한다. 이 전제를 깨야 할 때가 `CeleryQueue` 전환 시점이다.
그 전까지는 로드 밸런서에 스티키 세션을 걸지 말고, 아예 인스턴스를 늘리지 마라.

## 2. 자원 관리

### 2.1 업로드 수용 판단

업로드를 **받기 전에** 판단한다. 다 받고 나서 거부하면 이미 디스크를 쓴 것이다.

1. 클라이언트가 `Content-Length` 또는 사전 요청으로 예상 크기를 알린다.
2. 서버가 `shutil.disk_usage()`로 가용 공간을 확인한다.
3. `free - DISK_RESERVE_MB < 예상크기 × SAFETY_FACTOR` 이면 `SERVER_DISK_INSUFFICIENT` 반환.
4. 통과하면 수락하고 스트리밍으로 임시 디렉터리에 쓴다.

**주의: `Content-Length`는 클라이언트가 속일 수 있다.** 사전 확인만으로는 부족하다.
스트리밍 중에도 누적 바이트를 세고, 신고한 크기나 `MAX_UPLOAD_MB`를 넘는 순간
연결을 끊고 부분 파일을 삭제해야 한다.

### 2.2 세션 수명주기

**세션 = WebSocket 연결 하나.** 학생이 데이터를 한 번 올리고 설정을 바꿔가며
여러 번 학습하는 동안 전체가 하나의 세션이다.

```
업로드 → /tmp/mlp/{sessionId}/ → 학습 N회 (설정만 바꿔 반복) → WS 종료 → 전부 삭제
                                   └ 예측도 여기서 즉시 처리
```

세션 동안 서버가 들고 있는 것:

| 대상 | 이유 |
|---|---|
| 원본 데이터셋 파일 | 재업로드 회피 |
| 파싱된 DataFrame | 재파싱 비용 회피 (200,000행이면 무시 못 한다) |
| 직전 학습 모델 | 예측 요청을 즉시 처리 |

**세션 종료를 감지하는 네 가지 경로.** 하나만 믿으면 반드시 샌다.

1. WebSocket `close` 이벤트 → `try/finally`에서 즉시 정리
2. **heartbeat(ping/pong) 실패** → half-open 연결 정리.
   TCP만 믿으면 끊긴 줄 모르는 연결이 데이터를 붙들고 남는다
3. **유휴 타임아웃** → 연결은 살아 있으나 N분간 요청이 없으면 정리.
   탭을 열어두고 하교하는 학생을 막는다
4. **고아 파일 청소기** → 위 셋이 모두 실패했을 때의 안전망.
   기준 시각은 디렉터리의 마지막 접근 시각이지 생성 시각이 아니다

- 정리는 `try/finally`에서 수행한다. 실패해도 반드시 지운다.
- 컨테이너의 작업 볼륨은 크기 제한을 걸어라(tmpfs 또는 quota).
  코드 버그가 호스트 디스크를 채우면 안 된다.

**받아들인 대가**

- 브라우저 새로고침 = 세션 소실 = 데이터 재업로드. grace period로 재접속을 허용하는 방안은
  서버에 상태를 남기는 쪽으로 미끄러지므로 채택하지 않았다.
- **디스크 점유가 "작업 중"에서 "접속 중"으로 늘어난다.** 30명 학급이 각 50MB를 올리면
  1.5GB가 상주한다. 여러 학급이 겹치면 그만큼 곱해진다.
  → 세션 상한값을 반드시 걸어야 한다 (`open-decisions.md` #9)

### 2.3 상한값

> **이 표는 임시다.** `backend/app/config.py`(Pydantic Settings)를 구현하는 시점에
> 아래 값을 코드로 옮기고 **이 절은 삭제한다.** 이후 단일 출처는 `config.py`다.

| 항목 | 초기 기본값 | 환경 변수 |
|---|---|---|
| 업로드 최대 크기 | 50 MB | `MAX_UPLOAD_MB` |
| 최대 행 수 | 200,000 | `MAX_ROWS` |
| 최대 열 수 | 200 | `MAX_COLUMNS` |
| 학습 최대 시간 | 120 초 | `MAX_TRAIN_SECONDS` |
| 작업당 최대 메모리 | 2048 MB | `MAX_MEMORY_MB` |
| 디스크 예비 공간 | 2048 MB | `DISK_RESERVE_MB` |
| 동시 실행 작업 수 | CPU 코어 수 | `MAX_CONCURRENT_JOBS` |

시간·메모리 상한은 **워커 프로세스 수준에서** 강제한다
(별도 프로세스 + `resource.setrlimit`, 또는 컨테이너 제한).
파이썬 코드 안의 체크만으로는 막지 못한다.

**미해결 문제:** `MAX_MEMORY_MB` × `MAX_CONCURRENT_JOBS`가 호스트 메모리를 넘을 수 있다
(8코어면 16GB 요구). CLAUDE.md §1.5와 충돌한다. → `open-decisions.md`

## 3. 브라우저 내 학습 — V1의 기본 실행 위치

**공식 배포에는 서버가 없으므로 이것이 유일한 실행 위치다.** 더 이상 "나중에 붙이는 것"이
아니라 V1이 성립하는 조건이다.

### 3.1 결과 일치는 여전히 제약이다 — 자리가 옮겨졌을 뿐

서버가 없어졌으니 "브라우저 vs 서버"를 맞출 필요가 없어 보이지만, **배포 경로가 둘이라
"Pages 결과 vs 도커 결과"가 그 자리를 대신한다.** 그리고 이쪽이 더 위험하다.

```
학생이 집에서 Pages로 학습 → .mlpx 제출
→ 교사가 도커 설치본에서 열고 재실행 대조
→ 엔진이 달라 숫자가 안 맞음
→ 무고한 학생이 위조를 의심받는다
```

수행평가에서 이건 이 프로젝트가 낼 수 있는 최악의 실패다.

### 3.2 그래서 재실행 대조는 엔진을 넘지 않는다

각 run에 **엔진 종류와 버전을 기록**하고(`mlpx-spec.md` §4), 대조는 그 run을 만든 엔진으로만
한다. 다른 엔진밖에 없으면 "대조할 수 없음"이지 "불일치"가 아니다.

이 규칙 덕분에 **엔진 선택과 검증 설계가 분리된다.** 엔진은 순수하게 다운로드 크기와 정확도로
고르면 되고, 나중에 엔진을 바꿔도 옛 파일의 검증 의미가 깨지지 않는다.

**이것은 갈리는 것이 바람직하다는 말이 아니다 (2026-08-11에 덧붙인다).** 목표는 두 엔진이
같은 답을 내는 것이고, V2 감사 1단계가 그쪽으로 크게 옮겨 놓았다 — 닫힌 식 계열은 1e-13
수준 일치, 로지스틱 회귀도 수렴하면 라벨 완전 일치(§3.3). 그러므로 이 규칙은 **불일치를
허용하는 선언이 아니라, 일치가 아직 실물로 검증되지 않은 동안**(scikit-learn 엔진은
V3에 붙는다) **학생을 보호하는 장치다.**

**검증된 뒤에도 규칙은 남는다.** 일치는 실측된 사실이지 계약이 아니고, 반복 예산에서
멈추는 자리처럼 **정당하게 갈리는 경우가 실재하기** 때문이다(`mlpx-spec.md` §5.9).
"대조 못 함"을 "불일치"로 읽는 순간 그 자리에서 무고한 학생이 위조를 의심받는다.

### 3.3 엔진은 둘이다

**순수 JS가 기본이고 scikit-learn은 학생이 켜는 선택지다**(`open-decisions.md` "브라우저 학습
엔진은 둘 다 간다"). 실측값과 지표 차이는 그쪽에 있다. 여기서는 구조만 적는다.

핵심은 **무거운 엔진의 로딩 시점을 화면 최상단의 상태 점검이 쥔다**는 것이다. 자동으로 받으면
교사가 부하 타이밍을 통제할 수 없고, 26MB와 15초가 수업 중간에 예고 없이 터진다.

**"동등성 보장"이라고 말하지 마라.** 엔진이 다르면 숫자가 갈릴 수 있다 — 랜덤포레스트는
배깅 난수가 달라 **붓꽃에서 sklearn 0.9667 대 우리 0.9333**이었고, 로지스틱 회귀와
SVM은 반복 예산 안에 멈추지 못하면 경로 중간의 서로 다른 지점에 선다
(`mlpx-spec.md` §5.9). 같은 sklearn이라도
WASM과 네이티브는 BLAS와 스레드 수가 달라 마지막 자리가 갈린다. UI는 자릿수를 제한해
표시하고, 대조는 정확 일치가 아니라 **허용 오차**로 판정한다(`open-decisions.md` #12).

**다만 "갈린다"의 폭이 V2 감사 1단계에서 크게 좁혀졌다 (2026-08-11).** 답이 하나뿐인
알고리즘(선형 회귀·가우시안 나이브 베이즈·KNN·동점 없는 의사결정트리)은 sklearn과 1e-13
수준으로 일치하고, 로지스틱 회귀도 **수렴하면** 예측 라벨이 완전히 같다. 남은 차이는
전부 이름이 붙어 있다 — 배깅 난수, 수렴 경로. **그래도 보장이라고는 말하지 않는다**:
일치는 실측된 사실이지 계약이 아니고, 상한 근처처럼 수렴이 안 되는 자리가 실재한다.

**위 숫자의 출처는 `frontend/tests/fixtures/sklearn/`이다** — 붓꽃 150행, 120/30 분할,
`randomState` 42. **저장소 안에서 재현되고 CI가 지키는 유일한 실측**이라 인용은 여기서
한다. `open-decisions.md`의 2026-08-04 표에는 같은 붓꽃인데 다른 숫자가 있다(랜덤포레스트
sklearn 0.9000 / 우리 0.9667). **틀린 것이 아니라 분할이 다른 별개의 실험이다** —
둘을 나란히 놓고 모순으로 읽지 마라. 그래서 여기서는 분할을 함께 적는다.

### 3.4 학습은 Web Worker에서 돈다

**화면이 얼면 안 된다** (`open-decisions.md` "학습은 언제나 백그라운드다"). 스피너를 띄우는
것으로는 부족하다 — 메인 스레드가 막히면 진행률도 취소 버튼도 같이 죽는다.

```
메인 스레드          Worker                    서버 (자가호스팅)
  [학습] 클릭  ──▶  postMessage        또는  ──▶ WebSocket
  진행률 표시  ◀──  progress 이벤트          ◀── progress 이벤트
  취소         ──▶  terminate                ──▶ cancel
```

**두 경로의 모양이 같다.** 그래서 `TrainingBackend`가 하나로 유지되고 화면은 어디서
도는지 몰라도 된다. 엔진 시동(scikit-learn 15.4초)도 같은 워커에서 한다.

`terminate`가 유일하게 확실한 취소 수단이다. 메인 스레드에서 도는 루프는 멈출 방법이 없고,
45분 수업에서 잘못 누른 학습을 못 멈추는 것은 그 자체로 실패다.

### 3.5 실행 방법은 하나의 목록이다

`computedBy`(browser/server)와 `engine.kind`는 직교하지만 **화면에는 하나의 목록으로 낸다.**
드롭다운 두 개는 중학생에게 던질 질문이 아니다.

어휘는 이렇게 대응한다.

| 화면 | `computedBy` | `engine.kind` | 실행 방법 id |
|---|---|---|---|
| 순수 JS | `browser` | `mljs` | `mljs` |
| scikit-learn (내 컴퓨터) | `browser` | `pyodide-sklearn` | `pyodide-sklearn` |
| scikit-learn (학교 서버) | `server` | `sklearn` | `server-sklearn` |

**화면은 이 목록을 알고리즘마다 다시 묻지 않는다.** 실험 기본을 위에서 한 번 고르고,
바꾸고 싶은 모델만 개별로 바꾼다.

```
실행 방법(기본):  ● 순수 JS   ○ scikit-learn(내 컴퓨터)   ○ 학교 서버

학습할 모델
  ☑ 의사결정트리        순수 JS ▾            ← 기본 그대로
  ☑ 랜덤포레스트     scikit-learn ▾       ← 학생이 바꿈
  ☑ SVM             학교 서버 ▾           ← 순수 JS에 없어서 자동으로 옮겨짐(표시된다)
```

판정은 `frontend/src/ml/backend.ts`의 순수 함수 하나가 하고, **상단 상태 패널과 모델 선택
화면이 같은 결과를 본다.** 두 곳이 각자 판정하면 반드시 어긋난다.
자동 이동은 없어지는 것이 아니라 **그 칸의 기본값을 채우는 동작**이 된다(§0.1) — 그러면
"왜 이건 딴 데서 돌지"가 화면에 그냥 보인다. **콕 집어 고른 칸은 옮기지 않는다.**

**같은 알고리즘을 여러 실행 방법으로 나란히 둘 수 있다.**

```
  ☑ SVM             순수 JS ▾
  ☑ SVM             scikit-learn ▾     ← 같은 SVM, 다른 엔진
  ☑ SVM             학교 서버 ▾
```

"같은 SVM인데 왜 숫자가 다른가"를 한 실험 안에서 보는 것이 목적이다. 그리고 이것이
위의 "콕 집은 칸은 안 옮긴다" 규칙이 필요한 이유다 — 옮기면 셋이 같은 곳으로 몰려
**똑같은 줄 세 개**가 나오고 비교하려던 것이 사라진다.

**실험이 보장하는 것은 같은 데이터·전처리·분할이다. 엔진은 그 목록에 없다.**
그래서 엔진이 섞여도 비교는 성립하고, 대신 각 run이 무엇으로 만들어졌는지 남긴다(§3.2).
서버로 가는 모델이 섞여 있으면 화면이 **몇 개가 서버로 가는지 요약해 줘야 한다** —
교사가 부하 타이밍을 쥘 수 있어야 하기 때문이다.

### 3.6 군집화는 분할하지 않는다 (V3, 2026-08-11)

**비지도학습에는 정답이 없으므로 "보지 않은 데이터에서 성능을 확인한다"는 전제가
성립하지 않는다.** sklearn도 `fit(X)` → `score(X)`이지 `fit(X_train)` →
`score(X_test)`가 표준 용법이 아니다. 전체 데이터로 학습하고 전체 데이터에 대해
지표를 낸다.

**스키마 관점에서는 `trainIndices`에 전체 행이, `testIndices`는 빈 배열이다.**
`split` 설정은 군집일 때 무시된다 — 분할 방법에 별도 값을 추가하는 대신
실험 실행 경로(`ml/experiment.ts`)가 `taskType === 'clustering'`일 때 분할을
건너뛴다.

**이건 등록이 아니라 분기다** (2026-08-11에 고쳐 적는다). 예전에 "이 조합에 등록된
분할기가 없다는 사실"이라고 적혀 있었는데 `SPLIT_BY_METHOD` 등록부는 그대로이고
`experiment.ts`가 `isClustering`으로 가른다. 문서가 코드보다 강한 주장을 하면 다음
사람이 없는 등록부를 찾는다. **그리고 이 분기는 등록으로 풀 것이 아니다** — 여기서
갈리는 것은 알고리즘 선택(CLAUDE.md §2가 금지하는 자리)이 아니라 **타깃이 있는가
없는가**이고, 그건 이 프로젝트의 설계 선택이 아니라 지도학습과 비지도학습의 구조적
차이다.

교실에서 "왜 나누지 않나요?"는 비지도학습을 이해하는 좋은 질문이고, 그것을
설명할 자리가 생기는 것이 교육적 가치다.

### 3.7 군집 지표는 시그니처가 다르다 (V3, 2026-08-11)

분류·회귀의 `Evaluator`는 `(actual, predicted) => Evaluation`이다. 군집은
정답이 없으므로 **같은 시그니처를 쓸 수 없다** — `actual`에 빈 배열을 넣는
꼼수를 쓰면 타입이 거짓말을 한다.

`ClusterEvaluator`를 별도 타입으로 만들고 등록부를 분리한다. `EVALUATORS`는
분류·회귀만 갖고, `CLUSTER_EVALUATOR`가 따로 있다.

**가르는 것은 부르는 쪽이다** (2026-08-11에 고쳐 적는다). 예전에 "`evaluate()`가
`taskType`으로 갈라서 각각의 등록부를 부른다"고 적혀 있었는데 `evaluate()`와
`evaluateCluster()`는 **밖으로 둘 다 노출된 별개 함수**이고, 가르는 것은
`experiment.ts`의 `taskType === 'clustering'`이다. 등록부가 둘인 이유는 시그니처가
둘이기 때문이고, 이 분기는 **`Evaluator` 타입이 하나가 될 수 없다는 사실의 표현**이다.
`evaluate()`에 군집을 넘기면 등록부에 없어 던진다 — 조용히 빈 지표를 내지 않는다.

지표는 **실루엣 계수(Silhouette Coefficient)**와 **이너셔(Inertia)** 둘이다
(`open-decisions.md` #29). 실루엣은 −1~1이고 높을수록 좋다. 이너셔는 K-Means의
목적함수이고 낮을수록 좋지만 k를 올리면 무조건 내려가므로 **단독으로 "좋다"를
말할 수 없다** — k를 바꿔 가며 비교하는 것이 교실 활동의 핵심이다.

| `backend/app/jobs/` | `JobQueue` 뒤에 구현이 숨는다. 부르는 쪽은 어느 큐인지 모른다 |
| `frontend/src/ml/` | **Vue를 모른다.** 워커와 서버 학습 양쪽에 그대로 쓰이기 때문이다 |

| `frontend/src/composables/` | 프레임워크를 아는 이음매. `toRaw` 같은 것이 여기 산다 |
| `scripts/` | CI가 부르는 검사. 사람이 지키길 기대하지 않는 것들이다 |

**도커는 필요 없다.** 도커 이미지·nginx 설정·`docker-compose.yml`은 배포 단계에서 만든다

# 백엔드 (backend/)

uv run ruff check . && uv run mypy . && uv run pytest

# 프런트엔드 (frontend/)
npm install
npm run dev
npm run lint && npm run typecheck && npm test

`package.json`과 `pyproject.toml`의 버전은 상한 없는 캐럿 범위다.
최초 `npm install` / `uv sync` 후 실제로 해결된 버전을 락파일로 고정한다.
**`uv.lock`과 `package-lock.json`은 커밋한다.** 재현성이 이 프로젝트의 요구사항이다.

## 7. 운영 비용과 실행 위치 정책

**아무도 공용 백엔드를 운영하지 않는다.** 공식 배포는 GitHub Pages 정적 페이지이고,
백엔드는 도커로 배포되어 **필요한 학교가 직접 설치한다**(CLAUDE.md §1.1).

이 절이 원래 전제했던 "개인이 Oracle 프리티어에 공용 서버를 띄운다"는 폐기됐다.
아래 §7.1은 그 판단의 근거로 남긴다 — 숫자가 결론을 그대로 지지한다.

### 7.1 공용 서버는 왜 불가능한가

교실에서 실제로 쓰는 데이터는 작다. 붓꽃 5 KB, 타이타닉 60 KB, 학생이 만든 데이터도 대개 수 MB 이하다.
50 MB는 상한이지 전형값이 아니다. 학습도 수천 행이면 1초 미만이다.

| 상황 | 부하 | 판정 |
|---|---|---|
| 한 학급 30명, 각 1 MB, 동시 학습 | 메모리 수백 MB, CPU 몇 초 | 여유 |
| 한 학급 30명이 상한(50 MB)을 실제로 사용 | 세션 상주 메모리 6 GB 이상 | 위험 |
| 같은 교시에 100개 학급 = 3,000명 | 어떤 계산으로도 불가능 | **불가** |

한국 학교는 시간표가 정렬돼 있어 부하가 교시 시작에 몰린다.
**전국 단위로 퍼지면 서버 학습만으로는 구조적으로 버틸 수 없다.**

그리고 계산이 버티더라도 남는 문제가 셋이다.

1. 공개 URL에 인증이 없으면 **익명 사용자에게 개인 부담 연산을 무제한 열어주는 것**이다.
   로드맵은 계정·로그인을 명시적으로 범위 밖에 뒀다.
2. 막으려고 계정을 두면 개인정보를 다루게 되어 §1.1의 "인적사항을 받지 않는다"와 충돌한다.
3. **수행평가 도중 서버가 죽으면 그 실패는 교사가 뒤집어쓴다.** 개인이 질 책임이 아니다.

### 7.2 결론: 공식 배포는 정적, 서버는 학교가 설치

| 누가 | 무엇을 | 어디서 | 우리 서버 비용 |
|---|---|---|---|
| 학생 | 모든 학습 | 브라우저 | **0** |
| 학생 | 큰 데이터·무거운 알고리즘 | 학교가 설치한 서버 | **0** (학교 부담) |
| 교사 | 제출물 재실행 대조 | 브라우저 | **0** |

연산 부담이 **그 연산의 혜택을 받는 곳**에 놓인다. 강한 장비가 필요한 학교는 컴퓨터실에
직접 띄우고, 그렇지 않은 대다수는 정적 페이지만으로 수업을 끝낸다.

자가호스팅 서버는 세션 동안 데이터셋·DataFrame·직전 모델을 캐시한다(§2.2). 학교 안에서
도는 서버이므로 데이터가 학교 밖으로 나가지 않는다 — 공용 서버였을 때의 개인정보 압박이
여기서는 성립하지 않으므로 세션 상한(`open-decisions.md` #9)을 넉넉하게 잡아도 된다.

**다만 세션을 넘어선 영구 보관은 하지 않는다.** §1.2(브라우저가 저장소다)와 §1.3(하나의
파일이 제출물이다)이 흔들리고, 서버가 죽으면 학생 작업물이 날아간다. 모델은 서버가
내려보내고 **클라이언트가 `.mlpx`에 담는다.**

### 7.3 서버가 없는 것이 기본 상태다

공식 배포에는 서버가 아예 없다. 그러므로 "서버 없음"은 예외 처리가 아니라 **정상 경로**다.

- 프런트엔드는 시작할 때 **같은 오리진**의 헬스 엔드포인트를 찔러 `ServerStatus`를 정한다.
  Pages에서는 404가 나고 `unavailable`로 굳는다. 탐지 타임아웃은 짧게 잡아 정적 배포
  사용자가 기다리지 않게 한다.
- 모델 선택 화면은 알고리즘마다 **실행 위치**를 함께 보여준다.
- 서버가 없으면 서버 실행 옵션을 비활성화하되 **왜 못 쓰는지 이유를 함께 보여준다.**
  이유 없이 회색으로 죽어 있는 버튼은 학생에게 고장으로 보인다.
- 판정 로직은 `frontend/src/ml/backend.ts`의 `runtimeOptions()`에 있다. 순수 함수이고 테스트로 덮여 있다.
- 확인 전 상태(`unknown`)는 서버를 열어 주지 않는다. 낙관적으로 켰다가 실패하는 것보다
  처음부터 브라우저로 가는 편이 낫다.

### 7.4 브라우저 학습 엔진의 전송량

기본 엔진(순수 JS)은 gzip 25 KB라 사실상 없는 비용이다. scikit-learn 엔진은 **gzip 26.3 MB**이고
**이걸 GitHub Pages가 서빙한다** — 우리가 부담하는 전송량은 0이고, Pages는 CDN이 붙어 있어
학교 회선에서도 빠르다. 개인 서버로 이만한 정적 자산을 서빙하지 않아도 되는 것이 정적 배포의
부수 효과다.

- 불변 자산으로 긴 캐시 헤더를 붙인다. 학기 중 같은 학생이 반복 접속하는 패턴에 잘 맞는다.
- 서비스 워커로 캐시하면 두 번째 수업부터는 다운로드가 없다. 다만 **학교 PC는 재이미징되는
  경우가 있어** 캐시를 전제로 설계하지 마라.
- **캐시가 지우지 못하는 비용이 따로 있다.** WASM 시동과 첫 `import sklearn`이 개발 PC에서도
  15.4초이고 이건 페이지를 열 때마다 다시 든다. 다운로드만 캐시된다.
- 그래서 **로딩 시점을 상태 점검이 쥔다**(§3.3). 수업 시작 시각에 30명이 동시에 받는 것은
  막을 수 없지만, **언제 그 30명이 받을지를 교사가 정할 수 있게** 하는 것이 요점이다.

### 7.4.1 첫 화면이 받는 양 (2026-08-05 실측)

**청크 하나의 크기와 첫 화면이 받는 양은 다른 문제다.** 빌드가 500kB 경고를 내지만
그건 청크 하나를 보는 값이고, 우리에게 중요한 것은 앞의 것이다.

| 첫 화면이 받는 것 | gzip |
|---|---|
| index (vue · pinia · 라우터 · 셸) | 73 kB |
| vue-i18n | 61 kB |
| CSS | 21 kB |
| 글꼴 서브셋 (화면에 뜬 범위만) | 44 kB |
| **합계** | **약 200 kB** |

**무거운 것은 전부 그 뒤에 있다.** 라우트는 전부 `() => import(...)`이고, 엑셀
라이브러리 둘(ExcelJS 930kB, SheetJS 492kB)은 `data/xlsx.ts`에서 `await import`로만
닿는다 — 학생이 엑셀 파일을 열 때까지 안 내려온다. SheetJS는 한 발 더 뒤에 있어
ExcelJS가 실패한 한셀 파일에서만 쓴다. 데이터 종류별 판도 같다(`data/kinds.ts`).

**앞으로 무거운 것을 더할 때도 같은 자리에 둔다.** 브라우저 학습 엔진(§7.4의
scikit-learn 26MB)과 zip 처리가 그렇다. 첫 화면에 얹히면 학교 PC와 휴대폰이 기준이라는
전제(CLAUDE.md §0)가 그 자리에서 깨진다.

빌드의 경고 기준은 엑셀 라이브러리 위로 올려 뒀다(`vite.config.ts`). 무시할 경고를
계속 띄우면 진짜 경고도 같이 무시하게 된다.

### 7.5 검증은 브라우저에서 끝난다

서명이 없으므로 "미검증"이라는 상태 자체가 없다. 교사는 제출물을 열어 **재실행 대조**로
지표가 재현되는지 확인하고, 그 계산은 교사의 브라우저에서 일어난다
(`mlpx-spec.md` §7). 서버도, 채점 시점의 서버 비용도 필요 없다.

대조는 **run을 만든 엔진으로만** 한다(§3.2). 교사 환경에 그 엔진이 없으면
"대조할 수 없음"이며 "불일치"가 아니다.

---

### 7.6 주소로 백엔드를 건네는 방안 — 제안, 아직 결정 아님 (2026-08-05)

> **이 절은 결정이 아니다.** 지금 문서에 있는 규칙(`CLAUDE.md` §2, 이 문서 머리)은
> **"백엔드 주소를 설정 가능하게 만들지 마라"**이고, 아래는 그것을 뒤집자는 제안이다.
> 채택되면 `CLAUDE.md` §2를 함께 고쳐야 한다. 그 전에는 구현하지 마라.

**제안.** `https://<pages>/?backend=http://192.168.0.1` 처럼 주소로 백엔드를 넘기면,
프런트엔드가 그 주소를 저장해 두고 그쪽으로 헬스 체크를 보낸다. 도커로 프런트엔드와
백엔드가 같은 오리진에 함께 떠 있으면 필요 없는 이야기이고, **GitHub Pages로 배포된
프런트엔드에서도 다른 백엔드에 붙을 길을 주자**는 것이다. 쓰임새는 서버를 여럿 운영하거나
아는 사람에게만 주소를 따로 건네는 경우다.

**막히는 것 넷.** 순서대로 무겁다.

1. **혼합 콘텐츠 — 이것 하나로 순진한 형태는 성립하지 않는다.** Pages는 https이고 교실
   서버는 대개 http다. 브라우저는 https 페이지에서 http로 나가는 요청을 **경고가 아니라
   차단**한다. `?backend=http://…`는 그냥 동작하지 않는다. 학교 서버에 https를 붙이면
   자체 서명 인증서가 되고, 그러면 학생 기기마다 경고를 눌러 넘겨야 한다 — 수업 시작
   5분을 그걸로 쓴다.
2. **CORS.** 백엔드가 Pages 오리진을 허용해야 한다. 풀 수 있지만 백엔드가 오리진 목록을
   알아야 하고, 그건 교사가 고치는 설정 파일이 하나 생긴다는 뜻이다.
3. **주소가 곧 신뢰다.** 링크 하나로 앱이 임의의 서버에 말을 걸게 된다. 누가 학생에게
   자기 서버를 가리키는 링크를 보내면 **학생이 올린 데이터가 그리로 간다.** §1.1이
   "데이터가 학교 밖으로 나가지 않는다"를 근거로 세워 둔 것이 조용히 깨진다.
   붙기 전에 확인을 받고, 지금 어느 서버에 붙어 있는지가 화면에 늘 보여야 한다.
4. **저장하면 들러붙는다.** 한 번 누른 링크가 계속 살아 있으면 학생은 자기가 어디에
   연결돼 있는지 모른 채 쓴다. 무엇에 붙어 있는지 보고 끊는 자리가 반드시 필요하다.

**그래서 채택한다면 최소한 이렇다.** 주소를 받아도 **바로 쓰지 않고 물어본다.**
받아들인 주소는 상태 표시줄과 실행 방법 목록에 **호스트가 그대로 보인다**(§7.3이 이미
실행 위치를 늘 보여주기로 했다). 끊는 것은 한 번에 되어야 한다. 그리고 https가 아닌
주소는 Pages에서 **애초에 받지 않는다** — 받아 봐야 차단되므로, 되는 척하는 것보다
"이 주소는 여기서 못 쓴다"고 말하는 편이 낫다.

먼 이야기다. 자가호스팅 백엔드(V6, `roadmap.md`) 자체가 아직 없다.

## 8. 프런트엔드 셸

화면 하나하나가 아니라 **화면들이 놓이는 틀**을 정한다. 여기 적힌 것은 개별 화면을
만들면서 흔들리면 안 되는 결정들이다.

### 8.1 라우팅은 해시 모드다

`createWebHashHistory`를 쓴다. 주소는 `#/project/{id}/train` 모양이다.

- **GitHub Pages에는 SPA 재작성 규칙이 없다.** history 모드로 두면 `/project/abc/train`을
  새로고침하는 순간 404가 난다. 학생이 F5를 누르는 것은 예외 상황이 아니다.
- 같은 `dist/`가 Pages와 도커 양쪽에 들어간다(§7). 해시 모드는 **어느 쪽에서도 서버 설정이
  필요 없다.** 한쪽만 되는 방식을 고르면 배포 경로마다 다른 산출물이 생긴다.
- 404.html로 우회하는 방법이 있지만, 그건 새로고침할 때마다 리다이렉트가 한 번 끼는
  것이고 주소창이 잠깐 튄다. 얻는 것은 `#` 하나가 사라지는 것뿐이다.

**해시 뒤는 앵커가 아니라 경로다.** `#data`나 `#preprocess`처럼 한 낱말로 두지 않는다.
이유가 둘이고, 둘 다 짧은 주소보다 무겁다.

- **경로가 값을 실어야 한다.** `#data`는 *어느 프로젝트의* 데이터인지 담지 못한다.
  프로젝트 id가 주소에 있어야 §8.2가 얻어 둔 것(주소를 복사해 다른 기기에서 열기)과
  §8.3이 요구하는 것(가드가 컴포넌트 밖에서 판정하기)이 성립한다. 담으려면
  `#project/{id}/data`가 되고, 그건 이미 경로다.
- **한 낱말짜리 해시는 문서 안 앵커의 자리다.** 브라우저도 스크린리더도 사용자도 그것을
  "페이지 안에서 이동"으로 읽는다. `#/`로 시작하는 것이 그 충돌을 피하는 관행이고,
  `createWebHashHistory`가 만드는 모양도 그것이다 — 라우트를 `data`라고 적어도
  라우터가 `#/data`로 정규화한다.

### 8.2 라우트는 워크플로 단계다

**단계를 컴포넌트 안의 상태로 두지 않는다.** 단계 하나가 라우트 하나다.

```
/                          프로젝트 목록
/project/:id/data          데이터
/project/:id/preprocess    전처리 — 데이터를 학습에 넣을 모양으로 만든다
/project/:id/train         학습 — 기계학습 유형과 모델을 고르고 돌린다
/project/:id/results       결과 분석
/project/:id/predict       예측
/project/:id/portfolio     포트폴리오
```

이 순서는 **학생이 프로젝트를 만들어 가는 워크플로**다. 수행평가 진행 순서가 아니다 —
이 도구는 수행평가를 대체하지 않는다.

**전처리와 학습의 경계는 데이터와 모델이다** (2026-08-05). 전처리에서 정하는 것은 전부
데이터의 성질이고(타깃·특성·결측치·스케일링·인코딩·분할), 모델의 성질은 전부 학습에
있다(기계학습 유형·모델·실행 방법). 이 절은 한때 전처리를 "전처리·모델 설정"이라고
적어 두었는데 그게 틀렸다 — 자세한 근거는 `open-decisions.md` "기계학습 유형은 모델을
고르는 자리에서 고른다".

라우트로 두면 얻는 것:

- 브라우저 뒤로가기가 그대로 동작한다. 단계를 상태로 두면 뒤로가기가 앱을 통째로 벗어난다.
- 상단 단계 탭바가 곧 네비게이션이다. 별도의 단계 상태를 둘 이유가 없다.
- 학생이 주소를 복사해 자기 다른 기기에서 열 수 있다 (프로젝트는 그 기기의 IndexedDB에 있어야 한다).

### 8.3 가드는 컴포넌트 밖의 순수 함수다

데이터 없이 `/train`에 들어가는 것 같은 판단은 **컴포넌트 안에 두지 않는다.**
입력을 받아 "여기 들어가도 되는가 / 아니면 어디로 보내는가"를 돌려주는 순수 함수로 두고,
라우터 가드는 그 함수를 호출하기만 한다.

이유는 하나다 — **단계 진입 조건은 화면을 띄우지 않고 테스트할 수 있어야 한다.**
컴포넌트 안에 두면 조건 하나를 확인하려고 화면 전체를 마운트해야 한다.

### 8.4 겉모습은 토큰 한 겹 뒤에 둔다

색·모서리·그림자·간격을 컴포넌트에 직접 쓰지 않는다. `src/styles/theme.css`의 `@theme`에
**의미 있는 이름**으로 정의하고 컴포넌트는 그 이름만 쓴다 (`--color-surface`이지
`--color-white`가 아니다).

디자인은 교체가 예정돼 있다. 토큰을 두면 교체가 **값을 바꾸는 일**이 되고, 안 두면
**전부 다시 쓰는 일**이 된다. 이건 나중에 할 리팩터링이 아니라 지금 두는 이음매다.

**어두운 배색이 그 이음매가 실제로 값을 한 첫 사례다** (2026-08-05). `@media
(prefers-color-scheme: dark)`에 값 세트를 하나 더 얹는 것으로 끝났고 **화면 코드는 한 줄도
안 고쳤다.** 밝기 순서(surface > canvas > sunken)는 두 배색이 같게 두고, 브랜드와 상태색은
색상을 유지한 채 명도만 올린다. `color-scheme`을 함께 선언해야 브라우저가 직접 그리는
것들(선택 상자, 스크롤 막대)이 따라온다.

지금은 시스템 설정을 따라가기만 한다. **화면에서 직접 고르는 것은 언어와 같은 방식으로**
(IndexedDB에 저장, §8.5의 언어 선택과 같은 자리) 붙인다 — 값 층이 이미 있으므로 그때 할
일은 스위치뿐이다.

### 8.5 글꼴은 자체 호스팅한다

Pretendard Variable **동적 서브셋**을 저장소에 넣고 우리가 서빙한다.

- **CDN을 쓰지 않는다.** 학교망이 CDN을 막는 경우가 실재하고, 그러면 글꼴만 깨지는 게
  아니라 화면 폭이 통째로 달라진다.
- 동적 서브셋은 유니코드 범위별로 잘린 파일들이고 브라우저가 **화면에 실제로 뜬 글자의
  범위만** 받는다. 전체를 한 파일로 받으면 첫 화면에서 1 MB가 넘는다.
- `font-display: swap`. 글꼴을 기다리느라 글자가 안 보이는 시간을 만들지 않는다.
- **글꼴 스택에 일본어 대체를 처음부터 넣는다.** ja를 추가할 때 스택을 고치는 일이
  없어야 한다 (docs/i18n.md).

### 8.6 셸은 웹페이지가 아니라 작업실이다 (2026-08-05)

**앞의 §8.1~8.5는 그대로 두고, 화면을 담는 껍데기만 다시 정했다.** 첫 구현은 강의노트형
참고물을 따라 히어로 + 세로 스크롤로 만들어졌는데, 이 도구는 **읽으러 온 사람이 아니라
한 시간 넘게 작업하는 사람**을 위한 것이다.

상시 존재하는 영역은 **넷뿐이다.** 나머지는 전부 작업 공간이 바뀌는 것이다.

```
┌──────────────────────────────────────┐
│ 상단 바 (52px)                        │  프로젝트 이름 · 전역 동작 · 상태 버튼
├───┬──────────────────────────────────┤
│레일│                                  │
│ 📂│                                  │
│ ⚙ │        작업 공간                  │  라우트가 바꾸는 유일한 곳
│ 🧪│                                  │
│ 📈│                                  │
├───┴──────────────────────────────────┤
│ 상태 표시줄                           │  저장 상태 · 내보내기 · 크기 · 언어
└──────────────────────────────────────┘
```

**목록 화면도 이 셸 안에 있다.** 별도의 홈이 없다 — 앱을 열면 이미 작업실이고, 가운데만
"새 프로젝트 / 프로젝트 열기"로 채워진다. 프로젝트를 만들어도 다른 페이지로 가지 않고
같은 자리의 내용이 바뀐다. 그래야 웹사이트가 아니라 프로그램처럼 느껴진다.

**단계 이동은 왼쪽 레일이 쥔다. 상단 바는 안 쥔다.** 둘 다 두면 같은 것이 두 군데 있고,
학생은 둘이 다른 것인 줄 안다. 상단 바에 남는 것은 프로젝트 이름, 저장·열기·내보내기
같은 전역 동작, 그리고 상태 버튼이다.

**레일은 아이콘만 남긴다**(56~64px). 표와 그래프가 이 앱의 본체이고, 그것들이 쓸 수 있는
가로 폭이 넓을수록 좋다. 못 가는 단계는 지우지 않고 **이유와 함께** 흐리게 둔다(§8.2).

**휴대폰에서는 레일이 아래로 내려간다.** 좁은 화면에서 세로 레일은 이미 부족한 가로 폭을
더 깎는다. `sm` 미만에서 하단 바로 바뀌고 상태 표시줄은 접힌다. 모바일에서도 동작해야
한다는 것은 타협 대상이 아니다(`open-decisions.md` "모바일에서도 동작한다").

**상태 팝오버.** 상단 바의 상태 버튼을 누르면 지금 무엇을 하는 중인지, 다음이 무엇인지,
단계가 어디까지 왔는지가 작은 팝오버로 뜬다. 모달도 사이드 패널도 아니다 — 작업을
가리지 않고 잠깐 떴다 사라지는 것이어야 한다.

### 8.7 화면이 다음에 할 일을 말한다

**이 도구가 IDE와 갈라지는 지점이다.** JetBrains도 VS Code도 Figma도 "사용자가 이미
어디에 뭐가 있는지 안다"를 전제한다. 우리 사용자는 **머신러닝을 처음 만나는 학생**이다.

그렇다고 튜토리얼이 되면 안 된다. 학생이 "이제 뭘 하지?"를 묻지 않게 하되, 물어보지도
않은 설명을 늘어놓지 않는다.

**단계마다 그 단계 안의 할 일 목록을 보여준다.**

```
데이터        ☑ 데이터 불러오기
전처리        ☐ 타깃 정하기   ☐ 특성 정하기
학습          ☐ 기계학습 유형 정하기   ☐ 모델 선정하기   ☐ 모델 학습하기
포트폴리오     ☐ 포트폴리오 작성하기
```

**이 목록은 §8.3의 잠금 조건과 같은 것을 다른 각도에서 보여주는 것이다.** 그러므로
**같은 순수 함수에서 나와야 한다.** 두 벌로 만들면 "체크는 다 됐는데 다음 단계가 잠겨
있다"가 생기고, 그건 학생이 고칠 방법이 없는 고장이다.

### 8.8 저장 상태를 늘 보여준다

**학교 컴퓨터실 PC는 전원을 끄면 디스크가 되돌아간다**(`open-decisions.md` "컴퓨터실 PC는
리셋을 전제한다"). 그래서 상태 표시줄이 이 프로젝트에서 장식이 아니라 **핵심 기능**이다.

상태 표시줄에 상시 있는 것:

- **IndexedDB 저장 상태와 마지막 저장 시각** — 자동 저장이 돌고 있다는 것을 보여준다
- **내보내기 상태** — `.mlpx`로 내보낸 적이 있는가, 그 뒤로 고쳤는가
- 프로젝트 크기, 현재 언어

**"아직 내보내지 않았습니다"가 상시 보이는 것이 이 도구가 리셋 문제에 주는 답이다.**
차시가 끝날 때 잔소리하는 배너보다 낫다 — 배너는 닫히고, 상태 표시줄은 늘 거기 있다.

**내보낸 시각은 `.mlpx`에 적지 않는다.** 그건 **이 기기의 사정**이지 파일의 내용이
아니다. 파일이 존재한다는 것 자체가 내보내졌다는 뜻이고, 그 파일에 "나는 내보내졌다"를
적는 것은 아무것도 더해 주지 않는다. IndexedDB의 프로젝트 레코드에만 남긴다.

### 8.9 화면마다의 방향 (2026-08-05)

셸이 정해진 뒤에 나온 것들이다. 해당 화면을 만들 때 여기부터 읽는다.

**작업 공간 머리.** 단계마다 작은 머리 영역을 둔다 — 이 단계가 무엇을 하는 곳인지 한 줄,
그리고 지금의 맥락(어떤 파일, 몇 행 몇 열). **길잡이 역할은 하지 않는다.** 이동은 레일이
쥔다(§8.6). 히어로는 쓰지 않는다.

**빈 화면은 고장처럼 보이면 안 된다.** 모든 빈 상태가 둘을 갖는다 — **왜 비어 있는지**와
**무엇을 하면 열리는지.** "결과가 없습니다"로 끝내지 않고 "학습을 한 번 하면 여기에
지표가 나옵니다"까지 간다. 이건 §8.2의 "이유 없이 회색이면 고장으로 본다"와 같은 규칙이다.

**데이터 화면은 표가 주인공이다.** 카드를 쌓지 않는다. 열이 수십 개인 표를 카드 안에
가두면 가로 스크롤 상자 안에서만 볼 수 있게 된다.

**열 검사기는 넓은 화면에서 표 옆에 선다** (2026-08-06). 원래 이 자리에는 "검사기는
필요할 때만 나오는 보조 영역이다"라고 적혀 있었고 화면은 `<details>`로 접어 두었다.
**접어야 할 이유가 자리가 없다는 것 하나였는데, 자리를 세로로만 찾아서 없었던 것이다.**

접어 둔 것의 대가가 둘이었다.

- **펼치면 표가 먹힌다.** 작업 공간은 `h-full` 세로 flex라 검사기가 펼쳐지는 만큼 표의
  자리를 가져간다. 표는 여전히 스크롤되지만 **보이는 창이 몇 줄로 줄어서**, 학생이 얻는
  것은 "열 정보를 보려면 데이터를 포기하라"는 맞바꿈이다. 둘은 **함께 봐야 하는 것**이다 —
  검사기의 결측 수를 보는 이유가 표의 그 열을 보기 위해서다.
- **접힌 목록은 없는 것과 같다** (`AppChoices`의 머리말과 같은 이유다). 자기 데이터에
  빈 칸이 몇 개인지는 전처리 화면에 가기 전에 알아야 하는 사실인데, 그것이 접혀 있으면
  안 열어 본 학생에게는 존재하지 않는다.

그러므로 §8.10.1을 여기에도 적용한다 — **`md` 이상에서 표가 왼쪽, 검사기가 오른쪽이다.**
검사기는 늘 열려 있고 `<details>`가 사라진다. 열이 많으면 검사기가 **자기 열 안에서**
세로로 스크롤하므로 표의 자리는 어떤 경우에도 안 줄어든다. `md` 미만에서는 1열이고
(§8.10.1은 타협 대상이 아니다) 거기서는 접는다 — 좁은 화면에서는 세로가 진짜로 부족하다.

**대시보드는 [바로가기]가 맨 위 오른쪽이다** (2026-08-05). 그 아래에서 단계 목록과
프로젝트 요약이 **같은 높이에서 시작한다.** 이 버튼이 왼쪽 열 안에 있으면 오른쪽
요약이 그만큼 위로 떠서 두 열의 머리가 어긋나고, 눈이 훑을 기준선이 없어진다. 그리고
단계 줄의 [들어가기]는 **경계선을 가진다** — 면색만으로 구분한 버튼은 카드 위에서
경계가 흐려져 누를 수 있는 것으로 안 보인다.

**전처리 화면은 데이터 얘기만 한다** (2026-08-05). 타깃·특성·결측치·스케일링·인코딩·분할이
전부이고 모델은 없다 (§8.2, `open-decisions.md` "기계학습 유형은 모델을 고르는 자리에서
고른다"). 한 열로 접혔을 때의 순서가 곧 작업 순서다 — 타깃·특성 → 다듬기 → 나누기.

**타깃과 특성은 같은 표에서 고른다.** 드롭다운 하나와 체크박스 목록을 따로 두지 않는다.
고르는 대상이 같은 열들이고, 판단 재료(자료형·결측 수·값 종류)가 그 자리에 있어야 한다 —
"값이 한 종류뿐인 열을 타깃으로 골랐다"가 [학습]을 눌러야 드러나면 안 된다.
**표가 이 화면에서 가장 넓은 것이므로 넓은 쪽 열을 준다** — 반쪽 칸에 가두면 그 안에서만
옆으로 스크롤하게 된다(§8.9의 "데이터 화면은 표가 주인공이다"와 같은 이유다).

**분할 설정이 여기 있다.** 학습용과 평가용으로 나누는 것은 데이터에 하는 일이고,
결과 화면의 변경 이력에서 `split.testSize`가 학생이 자주 움직이는 축이 된다.

**전처리는 원본을 건드리지 않는다.** 정본 `dataset/data.csv`는 가져오기 시점에 확정된 뒤
아무도 손대지 않고(§7의 규칙), 변환은 학습할 때 메모리에서만 일어난다. 파일에 남는 것은
변환된 데이터가 아니라 **파라미터**다(`model/preprocessor-experiment-N.json`). 그래서
스케일링을 켰다 꺼도 되돌아온다. 화면이 이것을 말할 필요는 없지만, 여기를 고치는 사람은
알고 있어야 한다.

**학습 화면은 기계학습 유형에서 시작한다** (2026-08-05). 순서는 유형 → 모델 선정 →
실행 방법 → [학습]이다. 유형이 모델 목록을 좁히므로 위에 있어야 하고, **기본값이 없으므로
아무것도 안 골라진 채로 시작한다** — 학생이 고른 분류와 아무도 안 고른 분류는 다르다.
셋은 **한 카드 안의 세 축**이고 서로를 좁힌다 (§8.12).

**성립하지 않는 조합은 선택을 되돌리지 않고 그 자리에서 말한다** (`mlpx-spec.md` §0.1).
회귀에 문자 타깃이면 학습 화면이 그 자리에서 말한다 — 유형이 나중에 정해지므로 학생이
방금 한 선택의 옆이 거기다. 다만 **유형을 바꾸면 그 유형에서 뜻을 잃은 모델 선택은
지우고 알린다** — 선택을 뒤집는 것이 아니라 유형이 바뀌면서 의미가 없어진 것이고,
데이터를 바꿀 때 없어진 열을 선택에서 빼는 것과 같은 처리다(`project/dataset.ts`).

**결과 화면은 순위표가 아니라 변경 이력이다.** 이 도구의 차별점은 "가장 좋은 모델"이
아니라 **"무엇을 바꿨더니 왜 달라졌는가"**다. 실험마다 직전 대비 무엇이 바뀌었는지를
`experiment.changed`가 이미 들고 있다(`mlpx-spec.md` §4). 지표 옆에 `스케일링 OFF → ON`처럼
붙여 **git diff를 읽듯** 보게 한다. 순위는 그다음이다.

**예측 화면은 표의 한 줄을 채우는 것이다.** 별도의 폼이 아니라 데이터 화면과 같은
머릿속 모형을 쓴다 — 학생이 이미 본 그 표에 새 줄을 하나 넣는 일이어야 한다.

**포트폴리오는 마크다운 편집기가 아니라 보고서를 쓰는 자리다.** 원시 마크다운을 다루는
느낌을 최소화한다. 문항이 먼저 보이고 그 아래에 쓰는 칸이 있는 모양이다.

**체크리스트에 없는 상태를 지어내지 않는다.** §8.7의 목록은 프로젝트에서 **읽어낼 수
있는 사실**만 담는다. "시트 고르기"는 시트가 여럿인 엑셀에만 있는 일이라 항목이 아니라
그 순간의 선택지이고, "빈 칸 처리"와 "스케일링"은 기본값이 이미 있어 영원히 체크된
상태다. 그런 것들은 체크박스가 아니라 **"지금 이렇게 되어 있습니다" 요약 줄**로 보여준다.
체크할 수 없는 체크박스는 안내가 아니라 방해다.

### 8.10 문구도 등록부에서 나온다 (2026-08-05, **절반 구현됨**)

> **어디까지 됐나 (2026-08-06).** **체크리스트 쪽은 돌고 있다** — `router/steps.ts`의
> `factAppliesTo`가 과제 유형에 해당하는 사실만 남기고, 잠금과 할 일 목록이 같은 함수를
>쓴다. **안 된 것은 단계 설명문이다** — `data/kinds.ts`에 문구 키가 없고 화면은 아직
> `steps.*.purpose` 로케일을 직접 읽는다. 이미지 판을 더할 때 문구가 따라오지 않는다.

**`if (dataType === 'image')`를 금지한 규칙을 코드가 아니라 문장이 어기고 있었다.**

- "데이터를 불러오고 **어떤 열이 있는지** 확인합니다" — 이미지·음성에는 열이 없다
- "**예측할 값** 고르기" — 군집화에는 예측할 값이 없다

단어를 바꿔서 될 일이 아니다. 조합마다 맞는 문장이 다르므로 **문구가 등록부에서
나와야 한다.** 아래 둘을 그렇게 정했다.

**단계 설명문은 데이터 종류 등록부가 갖는다.** `data/kinds.ts`의 판이 자기 설명문 키를
함께 들고, 화면은 그것을 읽는다. 이미지 판을 더할 때 문구가 같이 따라오고, 빠뜨리면
컴파일이 깨진다.

**체크리스트도 같은 등록부에서 나온다. 없애지 않는다.**

> **뒤집힌 결정 (2026-08-05).** 이 절은 원래 "단계별 체크리스트는 없앤다"였다.
> 근거가 둘이었는데 **하나가 논거가 아니었다.**
>
> 버린 논거는 "모두에 맞는 문구는 막연해진다"이다. 그건 번역 품질 문제이지
> 구조 문제가 아니고, 잘 쓴 문구는 그 문제를 안 겪는다. 실제로 이 문서가 근거로
> 든 두 문장("어떤 열이 있는지", "예측할 값")은 **문구를 고쳐서 해결됐다.**
>
> 남은 논거는 "조합마다 문구를 두면 곱으로 는다"인데, 세어 보면 V1에서 안 터진다.
> 갈리는 것은 `targetChosen`·`featuresChosen` 둘뿐이다. 폭발은 이미지·음성이
> 들어올 때 일어나고, **그때 필요한 것은 없애는 것이 아니라 등록부다** —
> 이 절이 단계 설명문에 처방한 것과 똑같은 처방이 체크리스트에도 통한다.
>
> 그리고 반대편에 §8.7이 있다. "화면이 다음에 할 일을 말한다"가 이 도구가 IDE와
> 갈라지는 지점이라고 적혀 있고, **체크리스트가 그것을 하는 유일한 물건이다.**
> 지우면 길 잃은 학생에게 남는 것은 레일의 회색 아이콘뿐이다.

그러므로 **항목의 집합이 과제 유형에서 나온다.** `ProjectFacts`의 어떤 사실이 이
과제 유형에 해당하는지를 등록부가 말하고, `stepTasks`가 그것으로 거른다.
**군집화에는 타깃이 없으므로 `targetChosen`이 항목이 아니다** — 문구를 바꾸는 것이
아니라 항목 자체가 없다. 이건 V3를 기다리는 이야기가 아니라 지금 참인 사실이다.

**군집화 문구를 미리 쓰지 마라** — 는 V3 이전의 규칙이었다. **V3에서 K-Means를
등록했으므로 지금은 군집화 문구를 쓴다.** 쓸 대상(등록된 알고리즘)이 있고 화면에
실물이 있다. 이 절의 원래 의도 — "등록부에 없는 것의 문구를 만들지 마라" — 는
그대로이고, 다음 대상은 이미지(V4)다.

지금 만드는 것은 **이음매뿐이다.** 과제 유형 칸을 빠뜨리면 컴파일이 깨지고,
군집화 칸은 비어 있는 것이 눈에 보이게 둔다.

### 8.10.1 넓은 화면은 세로로 늘리지 않는다 (2026-08-05)

**작업 공간을 가로로 쌓기만 하면 넓은 화면이 여백이 된다.** 대시보드가 그 상태였다 —
카드 여섯 장이 위에 몰리고 화면 아래 3분의 2가 비었다. 그건 웹사이트 문법이지
작업실 문법이 아니다(§8.6).

**앞으로 만드는 모든 화면에 적용한다.**

- `md` 이상에서는 **2열을 기본으로 놓고** 무엇을 어느 쪽에 둘지 정한다. 왼쪽은 지금
  하는 일, 오른쪽은 그 일을 판단하는 데 필요한 맥락이 기본 배치다.
- `md` 미만에서는 **무조건 1열이다.** 좁은 화면에서 2열은 둘 다 못 읽게 만든다.
  타협 대상이 아니다(`open-decisions.md` "모바일에서도 동작한다").
- **세로로만 자라는 화면을 만들지 마라.** 스크롤로 미루기 전에 옆에 놓을 수 있는지
  먼저 본다.

`text-base` 하한(CLAUDE.md §4) 때문에 우리 화면은 같은 정보를 담는 데 남보다 넓은
자리를 쓴다. **그래서 가로를 쓰는 것이 선택이 아니라 조건이다.**

### 8.10.2 IndexedDB도 `.mlpx`와 같은 문을 지난다 (2026-08-05)

**프로젝트가 들어오는 입구는 둘이다** — `.mlpx` 파일과 IndexedDB. 그런데 마이그레이션과
스키마 검사는 파일 쪽에만 걸려 있었다. `storage.ts`는 스키마를 **타입으로만** 가져오고
저장된 값을 그대로 `ProjectDocument`라고 단정했다.

그래서 `runs.json`의 `batches`를 `experiments`로 바꾸자 리네임 전에 저장돼 있던
프로젝트가 **흰 화면**으로 죽었다. `experiments`가 `undefined`라 `.some(...)`이 던졌고,
렌더 중 예외라 그 프로젝트만이 아니라 앱 전체가 멈췄다. 스키마에 `.default([])`가
있으므로 **파싱만 거쳤다면 스스로 나았을 상황이다.**

배포 뒤에는 이것이 더 나빠진다. GitHub Pages는 자동으로 갱신되고 집 PC의 IndexedDB는
남는다. 학생이 집에서 하던 프로젝트를 우리가 형식을 바꾼 뒤 열면 **처리된 에러가 아니라
흰 화면**을 본다. §1.2가 IndexedDB에 맡긴 일(새로고침·크래시 복구)의 탈출구까지 같이
막힌다 — 목록 화면에 못 가면 `.mlpx`를 열어 되살릴 수도 없다.

**그러므로 읽기 경로가 같은 함수를 지난다.** `loadProject`가
`migrateProjectDocument` → `parseProjectDocument`를 거친다. 상위 `formatVersion`은
파일과 같은 규칙으로 거부한다(`PROJECT_FILE_VERSION_TOO_NEW`).

**못 읽는 레코드를 조용히 버리지 않는다.** 학생 눈에는 프로젝트가 사라진 것으로 보이고,
그건 우리가 만들 수 있는 최악의 인상이다. 대신 이렇게 다룬다.

- **여는 순간**: 에러를 던지고 스토어가 받아 알림을 띄운다. 그 프로젝트만 못 열고
  앱은 산다. 레코드는 지우지 않는다.
- **목록에서**: 요약을 못 만들면 이름 대신 "열 수 없음"으로 두고 **열기만 막는다.**
  지우기는 열어 둔다 — 학생이 스스로 정리할 수 있어야 한다.

### 8.11 레일 글자는 두 줄까지다 (2026-08-05)

규칙 자체는 `docs/i18n.md` 규칙 9에 있다. 여기에는 **왜 그 규칙이 필요했는지**와
레일에서 실측한 값을 남긴다. 다른 좁은 칸(탭·배지)을 만들 때 같은 계산을 다시 한다.

레일은 `--spacing-rail` 4.5rem(72px)이고 칸의 좌우 여백을 빼면 **안쪽이 64px**이다.
`text-base` 16px에 `styles/base.css`의 자간 `-0.01em`이 붙어 **한글 한 자가 약 15.8px**이다.

- 보통 굵기: 네 자 = 63.4px. 64px에 0.6px 남기고 들어간다.
- 굵은 글씨: 네 자가 안 들어간다.

**그래서 활성 칸을 굵게 하지 않는다.** 굵게 하면 "대시보드"가 안 눌렸을 때 한 줄,
눌렀을 때 두 줄이 되어 **칸을 누를 때마다 레일 전체가 튄다.** 활성 표시는 흰 면과
브랜드 색과 경계선이 이미 하고 있고(§8.6), 굵기는 거기에 아무것도 더하지 않으면서
레이아웃만 흔든다. 영어 `Training`도 같은 경계에 있었다.

**끊는 자리를 잡을 때의 기준은 세 자다.** 네 자는 0.6px 여유라 글꼴 지표가 조금만
달라져도 넘친다. `대시​보드`(2/2), `포트​폴리오`(2/3)가 여기서 나왔다.

영어는 `hyphens: auto`가 **실측에서 하이픈을 만들지 않았다.** `word-break`를 바꿔도
결과가 같았으므로 브라우저에 하이픈 사전이 없는 것이고, `Dashboar/d` `Portfoli/o`처럼
아무 데서나 끊겼다. 소프트 하이픈을 넣어 `Dash-/board` `Port-/folio`로 잡았다.
`Pre­pro­cess­ing`처럼 **여러 자리를 열어 두면 브라우저가 들어가는
것을 고른다** — 한 자리만 열면 그 뒤가 여전히 넘칠 수 있다.

### 8.12 고르는 축은 미니 카드로 늘어놓는다 (2026-08-05)

**드롭다운은 목록을 접어서 감춘다.** 우리 학생은 무엇이 있는지 모르는 상태로 온다.
접힌 목록은 "그런 게 있는 줄도 몰랐다"를 만들고, 그건 §8.2가 "못 가는 단계도 지우지
않는다"로 막으려던 것과 같은 실패다. 그리고 **드롭다운은 서로 좁히는 것을 보여주지
못한다** — 유형을 바꿔서 모델 목록이 달라져도 학생은 열어 보기 전까지 모른다.

그러므로 **고를 것이 손에 꼽히는 축은 미니 카드를 나란히 늘어놓는다.** 학습 화면의
세 축(기계학습 유형 · 모델 · 실행 방법)이 첫 사례다.

**축들은 서로를 좁히고, 그 좁혀짐이 눈에 보여야 한다.** 한 축에서 하나를 고르면 나머지
축에서 성립하지 않는 칸이 그 자리에서 꺼진다 — 순수 JS를 고르면 서포트 벡터 머신이
꺼지고, 회귀를 고르면 분류 모델이 꺼진다. **판정은 이미 있는 순수 함수가 한다**
(`ml/algorithms.ts`의 `algorithmOptions`, `ml/backend.ts`의 `runtimeOptions`). 화면은
그리기만 한다 — 축이 셋이라고 판정을 세 벌 만들면 서로 어긋난다.

**한 축의 카드는 크기가 같다.** 격자에 넣고 행 높이를 맞춘다. 글자 수대로 넓이가
제각각이면 목록이 아니라 부스러기로 보이고, **언어를 바꾸면 그 들쭉날쭉이 또 달라진다.**
다만 고정 너비는 주지 않는다(docs/i18n.md 규칙 7) — 칸이 화면 폭을 나눠 갖고 글자는 그
안에서 접힌다. 좁은 화면에서는 칸 수가 줄 뿐이다.

**축과 축 사이는 점선으로 가른다.** 셋이 세로로 붙어 있으면 어디까지가 한 축인지 안
보이고, 그러면 축이 서로를 좁힌다는 것도 읽히지 않는다. **[추가]도 같은 선으로 가른다** —
그것만 고르는 일이 아니라 담는 일이다.

**꺼진 칸은 지우지 않고, 누르면 축 아래 한 줄로 사유가 뜬다.**

- 카드마다 사유를 늘 붙이면 처음 들어온 학생이 회색 문장 예닐곱 줄을 먼저 만난다.
  서버가 없는 것은 예외가 아니라 정상 상태다(§1.1) — 그걸 화면 가득 늘어놓을 이유가 없다.
- 그래서 `disabled`가 아니라 `aria-disabled`다. `disabled`는 클릭 자체가 안 잡혀
  **사유에 도달할 방법이 없어진다.** hover에 맡길 수도 없다 — 휴대폰에는 hover가 없다
  (`open-decisions.md` "모바일에서도 동작한다").
- 사유 문장은 이미 `client.*` 로케일에 있다. 화면이 새로 짓지 않는다.

**담는 것은 여전히 [추가] 버튼이다.** 마지막 축을 누르는 것이 곧 담기가 되면, "지금
고른 것"과 "담은 것"이 한 물건에 겹친다. 파일은 **(모델, 실행 방법) 쌍을 여러 줄** 담고
같은 모델이 엔진만 다르게 두 줄 들어가는 것이 이 도구의 핵심 수업 장면이므로
(`open-decisions.md` "실행 방법은 하나의 목록이다"), 축의 현재 선택과 담긴 목록은
서로 다른 것으로 남아야 한다.

**넓은 화면에서는 축이 왼쪽, 담긴 목록이 오른쪽이다** (§8.10.1). 축은 지금 하는 일이고
담긴 목록은 그 판단의 맥락이다.

**미니 카드가 라디오 버튼보다 항상 나은 것은 아니다.** 전처리 화면의 결측치·스케일링은
지금 라디오이고 그대로 둔다 — 거기는 축이 서로를 좁히지 않는다. 이 절이 답하는 문제는
**"고를 수 있는 것이 다른 선택에 따라 달라진다"**이지 "라디오가 촌스럽다"가 아니다.

검증은 브라우저에서 각 라벨의 `scrollWidth > clientWidth`와 줄 수를 재서 했다.
눈으로 보는 것보다 정확하고, 언어를 바꿔 가며 반복할 수 있다.

### 8.13 결과 화면은 세로줄로 읽는다 (2026-08-06)

§8.9가 "순위표가 아니라 변경 이력이다"라고 정해 둔 것을 화면 모양으로 옮긴다.

**두 열이다** (§8.10.1). **왼쪽이 실험 목록, 오른쪽이 고른 실험의 속**이다. 왼쪽이
지금 하는 일(어느 실험을 보는가)이고 오른쪽이 그 판단의 맥락이다.

**왼쪽 세로줄이 이력 그 자체다.** 최신이 위. 줄마다 실험 번호 · 시각 · **직전 대비 바뀐
것** · **그 실험의 최고 성적 하나**를 둔다. 숫자를 하나로 제한하는 것이 규칙이다 —
목록은 훑는 자리이고, 여기에 지표를 여럿 늘어놓으면 그 순간 순위표가 된다. 어느 모델이
그 점수를 냈는지는 오른쪽에서 본다.

**오른쪽은 위에서부터 이렇게 쌓인다.**

1. **바뀐 것.** `스케일링 껐다 → 켰다`처럼 전후를 나란히. 첫 실험에는 직전이 없다.
2. **분할을 껐으면 그 사실.** 지표 표 **위에** 둔다 — 표 전체에 걸리는 말이다.
   줄마다 배지를 붙이면 같은 문장이 모델 수만큼 반복된다
   (`open-decisions.md` "분할 `none`은 학습에 쓴 데이터로 점수를 매긴다").
3. **성공한 run 표.** 모델 · 실행 위치 · 지표들.
4. **고른 run의 속.** 맨 위가 **그 run에 먹인 하이퍼파라미터**, 그다음이 등록부가 고른
   패널들이다(분류면 혼동 행렬과 클래스별 지표). **회귀면 패널이 0개이고, 그때 화면은
   아무 말도 안 한다** — 없는 것을 이름으로 말하지 않는다(§9.2의 같은 이름 절).
   **표 줄 안에서 펼치지 않는다.** 표 안에 표를 넣으면 열 폭이 무너진다.
5. **실패한 run은 접어서 맨 아래.** `failure.code`로 문장을 쓰고 `params.detail`의
   라이브러리 원문은 그 안에서 한 겹 더 접는다 — 그건 학생이 아니라 교사와 우리가 볼
   것이다.

**성공한 run에 붙는 경고는 그 run의 속 맨 위다** (2026-08-06). `run.warning`이 있는
run은 지표가 다 나왔지만 그 숫자가 어떻게 나왔는지에 조건이 붙어 있다(지금은 SMO가
수렴하지 못한 경우 하나다, `mlpx-spec.md` §5.9). **숫자보다 위에 둔다** — 이 문장이
걸리는 대상이 아래의 모든 숫자이고, 다 읽은 뒤에 알게 되면 이미 늦다. 표의 줄에는 안
붙인다: 위 규칙대로 목록은 훑는 자리이고, 여기 배지가 붙기 시작하면 열이 는다.

**그 run이 무엇으로 돌았는지도 속 맨 위다** (2026-08-07). 경고 바로 아래, 혼동 행렬을
비롯한 지표들보다 위다. **`직전 학습에서 바뀐 것`이 이 자리를 대신하지 못한다** — 그것은
두 실험의 *차이*라서 안 바꾼 값은 안 나오고, 첫 실험에는 아예 아무것도 안 나온다. 학생이
지표를 보며 묻는 것은 "직전보다 뭘 바꿨나"가 아니라 **"이 숫자를 낸 모델이 어떤 설정이었나"**이고,
둘은 다른 질문이다.

**값의 출처는 `run.hyperparameters` 하나다.** `settings.hyperparameters`가 아니다 — 그쪽은
학생이 화면에서 고른 값이고, 실행 방법이 자동으로 넘어갔으면(`open-decisions.md` "실행
방법은 하나의 목록이다") 실제로 먹인 것과 다르다. run에 박힌 값은 **학습 직전에 기본값까지
채워 확정한 것**이라(`mlpx-spec.md` §3) 학생이 아무것도 안 건드린 모델도 깊이 몇으로
돌았는지 답한다 — 그게 이 자리가 있는 이유다.

**이름과 순서는 손잡이 등록부에서 온다** (`ml/hyperparams.ts`의 `parametersFor`). 실행 방법은
`run.engine.kind`로 되짚는다(`whereTrainedKeyOf`와 같은 길). **등록부가 모르는 키도 버리지
않는다** — 서버 엔진이나 남의 파일에서 올 수 있고, 그때는 엔진이 받는 키를 그대로 보여준다.
번역된 이름이 없다고 값을 감추면 화면이 파일보다 적게 말하게 된다.

**손잡이가 없는 모델도 그 사실을 적는다** (나이브 베이즈·선형 회귀). 빈 자리는 고장으로
보인다(§8.9). 문장은 학습 화면이 같은 상황에서 쓰는 것을 그대로 쓴다 — 같은 사실을 두
화면이 다른 낱말로 말할 이유가 없다.

**지표 패널 등록부(`ml/metric-panels.ts`)에 넣지 않는다.** 그 등록부가 답하는 질문은
"이 (데이터 종류, 과제 유형) 조합에서 무엇을 그리나"인데(§9.3), 이건 축과 무관하게
**모든 run에 언제나 있다.** 축을 안 보는 항목을 축의 등록부에 넣으면 다음 사람이 이미지
데이터를 더할 때 이것까지 판단해야 한다. 판정 자체는 화면 밖 순수 함수에 둔다(§9.1) —
등록부를 되짚고 모르는 키를 뒤에 붙이는 규칙은 눈으로 확인하기 어렵다.

**세로줄에서 실험을 고르면 오른쪽으로 스스로 스크롤한다** (2026-08-07). 좁은 화면에서는
두 열이 위아래로 접히므로(§8.10.1) **고른 결과가 화면 밖에 있다** — 눌렀는데 아무 일도
안 일어난 것처럼 보이고, 학생은 같은 카드를 한 번 더 누른다. 넓은 화면에서도 실험마다
속의 길이가 달라 오른쪽이 중간까지 내려가 있을 수 있으므로, 고른 순간 그 실험의 머리로
올려 준다. **실험 안에서 모델 줄을 고를 때 이미 같은 것을 하고 있다**(`ExperimentDetail`) —
한 화면에서 "고르면 그리로 데려간다"가 두 층 모두에 걸린다.

**변경 이력에서 이름은 배지, 값은 plaintext다** (2026-08-07). 하이퍼파라미터 변경에만
모델 배지(`의사결정트리 · ml.js · 내 컴퓨터`)가 붙어 있었고 나머지 줄은 통째로 plaintext라,
**같은 목록 안에서 줄마다 위계가 달랐다.** 무엇이 이름이고 무엇이 바뀐 값인지가 줄마다
다른 방식으로 읽히면 목록을 훑는 눈이 매번 다시 자리를 잡아야 한다.

> **그 줄이 무엇에 대한 것인지(모델 · 설정 이름)는 회색 배지, 바뀐 값은 plaintext.**

**여러 줄일 때는 불릿 목록이다** (2026-08-07). 배지가 줄마다 서면서 어디까지가 한 줄인지가
오히려 흐려졌다 — 한 변경이 두 줄로 접히면 다음 항목의 시작과 구별이 안 된다. 불릿은
`list-outside`라 **글머리표가 글자 바깥에 서고, 접힌 둘째 줄은 첫 줄과 나란히 들여쓰인다.**
번호는 안 매긴다: 변경들 사이에 순서나 우열이 없다.

`설정을 바꾸지 않고 다시 학습했습니다`·`처음 학습입니다`처럼 **줄 전체가 문구인 것도 배지**다.
그 자리에 있는 것이 값이 아니라 상태의 이름이기 때문이다 — plaintext로 두면 그것만
"바뀐 값"처럼 읽힌다.

**배지는 컴포넌트 하나에서 나온다** (`AppBadge`). 같은 회색 알약이 네 자리에 서는데
클래스 문자열을 네 번 적으면 그중 하나만 고쳐지는 날이 오고, 그때 어긋난 것을 아무도
못 잡는다 (§8.4).

**이름을 배지로 빼면서 문장이 둘로 갈린다** — `{label}: {from} → {to}`가 배지의 `{label}`과
`{from} → {to}`가 된다. **이것은 문장 조각 잇기가 아니다**(`i18n.md` 규칙 3). 조각 잇기가
막는 것은 *한 문장*을 나눠 이어 붙이는 것이고, 여기서 배지에 들어가는 것은 문장의 일부가
아니라 **이름 그 자체**다 — 모델 배지를 문장 밖에 둔 것과 같은 이유이고(조사가 생기는 자리를
없앤다), 이름 다음에 값이 오는 순서는 세 언어에서 모두 같다.

**용어는 눌러야 설명이 나온다** (2026-08-07). 지표 이름(`정확도` · `F1 점수` · `정밀도` ·
`재현율` · `실제 데이터 수`)과 혼동 행렬의 칸을 누르면 팝오버가 열린다. **제목은 그 용어,
본문은 두세 줄 설명**이다.

**상시 설명을 깔지 않는 이유**는 §8.7·`copy.md`가 이미 정해 두었다 — 이 도구는
튜토리얼이 아니고, 설명은 묻지 않은 것까지 가지 않는다. **누르는 것은 묻는 행위이고,
그때만 답한다.**

**hover 툴팁으로 만들지 마라.** 이 저장소가 이미 겪었다 — `save.exportWarning`이
`title` 속성으로만 있어서 **터치 기기에서는 영원히 안 뜨는 문장**이었다(§8.8). 설명이
가장 필요한 학생이 휴대폰으로 보고 있을 수 있다.

**혼동 행렬 칸은 문장으로 쓰지 않는다.** `모델이 {A}라고 예측하였고`는 값 종류가
**학생의 데이터**라 조사가 갈리고(`{A}라고`/`{B}이라고`), `i18n.md` 규칙 5는 회피형까지
금지한다. 그래서 §8.16의 문법을 그대로 쓴다 — **이름은 배지, 값은 plaintext**로 세 줄
(`예측한 값` · `실제 값` · `데이터 수`)을 세우고, 맞았는지 틀렸는지만 한 줄로 덧붙인다.
조사가 생길 자리가 없어지고 화면 문법도 한 벌로 남는다.

**수식은 CSS로 쌓는다. 수식 라이브러리를 넣지 않는다** (2026-08-07). 설명 위에
`정밀도 = 옳게 분류된 수 / 예측한 수`를 교과서처럼 분자·분모로 세운다 — 글로 푼 세 문장보다
이 한 줄이 먼저 읽힌다.

**KaTeX·MathJax는 기각한다.** 우리가 그릴 것은 **가로줄 하나에 낱말 둘**이고, 그걸 위해
글꼴까지 딸린 수백 KB를 첫 화면에 얹을 이유가 없다(§8.5가 글꼴을 자체 호스팅하는 것과 같은
계산이다 — 저사양 학교 PC와 휴대폰이 기준이다). CDN에서 받아 오는 것은 애초에 불가능하다.

**MathML도 안 쓴다.** 의존성은 없지만 우리 수식에는 **수식 문법이 필요 없다** — 분수 하나에
`<math>` 트리를 세우면 로케일 문자열이 마크업 안으로 흩어지고, 번역하는 사람이 태그를 만지게
된다. 지금 필요한 것은 **낱말 두 개와 가로줄 하나**다.

**분자·분모는 각각 한 키다.** 문장을 쪼개 잇는 것(`i18n.md` 규칙 3)이 아니라 **수식의 두
자리**이고, 어순이 다른 언어에서도 분수의 위아래는 그대로다. `=`와 `×`는 번역하지 않는다.

**설명문은 지표 옆이 아니라 로케일에 있고, 키는 자리마다 정적으로 쓴다.** 화면이
`if (정밀도)`로 문장을 고르면 §9.1 위반이지만, 반대로 키를 코드에서 조립하면
**로케일에 없는 키를 화면에 흘려도 CI가 못 잡는다**(`i18n.md`의 정적 `t()` 검사).
그래서 부르는 자리가 `t('metricHelp.precision')`처럼 **적어 두고**, 공통 껍데기는
제목·본문을 **이미 번역된 문자열로** 받는다.

**표를 정렬하지 않는다. 담은 순서 그대로다.** 대신 **지표별 최고값만 굵게** 한다. 정렬은
비교를 순위로 바꾸는 장치이고, 이 화면이 하려는 일은 그 반대다.

**열 순서는 sklearn의 `classification_report`를 따른다** (`open-decisions.md` "파이썬 표준
관행을 따른다"). 범주별 점수표가 `정밀도 · 재현율 · 특이도 · F1 점수 · 실제 데이터 수`인
것은 그 넷의 상대 순서를 그대로 두고 특이도만 끼운 결과다. **여기를 다시 배열하려는
사람은 그 문서를 먼저 읽어라** — 근거가 교과서가 아니라 다음에 만날 도구다.

**갈리지 않으면 아무것도 강조하지 않는다** (2026-08-07). 붓꽃처럼 범주별 점수가 전부
100%인 실험에서 **첫 줄만 노랗게 칠해지고 있었다** — 최저값을 `reduce`로 고르니 전부
같을 때 첫 항목이 남았고, 그래서 화면이 **없는 차이를 있다고 말했다.** 강조는 "여기를
다시 보라"는 신호인데 다시 볼 것이 없는 자리를 가리킨 셈이다.

> **최저(최고)가 최고(최저)와 같으면 그 지표는 건너뛴다. 같은 값이 여럿이면 전부 짚는다.**

뒷문장도 같은 이유다. 셋 중 둘이 나란히 가장 낮은데 **먼저 담긴 하나만** 짚으면, 화면이
고른 그 하나에 학생의 눈이 가고 나머지 하나는 멀쩡한 것처럼 보인다. 어느 쪽도 우리가
고를 근거가 없다.

이 규칙은 **모델 비교표(`bestByMetric`)와 범주별 점수표(`weakestPerClass`) 양쪽에 같이
걸린다.** 둘은 "무엇이 이겼나"와 "무엇이 가장 약한가"로 방향만 다를 뿐 같은 장치다 —
한쪽만 고치면 다음 사람이 다른 쪽에서 같은 버그를 다시 만난다.

**지표에는 표시 등록부가 필요하다.** `ml/metrics.ts`는 값만 내고 **무엇을 먼저 보일지,
높을수록 좋은지 낮을수록 좋은지, 백분율인지를 아무도 모른다.** 최고값을 굵게 하려면
방향이 있어야 한다. 그러므로 `EVALUATORS`와 **같은 파일에 같은 모양으로** 표를 하나 더
두고, 두 표의 과제 유형 집합이 어긋나면 테스트가 빨개지게 한다 — 지표를 늘리면 화면이
따라오고 빠뜨리면 잡힌다. `r2`는 백분율로 쓰지 않는다. **음수가 될 수 있어서** `-234%`가
뜬다.

**변경 서술의 경로와 값은 한 곳에서 나온다.** `experiment.changed`는 경로만 들고 있어서
(`preprocessing.scaling`) 전후 값은 두 실험의 설정 스냅샷에서 읽어야 하는데, **경로 모양을
정한 것은 `ml/experiment.ts`의 `comparable()`이다** — 하이퍼파라미터를 `알고리즘:실행방법`
으로 묶고 `trainIndices`를 뺀 것이 그 함수다. 값을 딴 데서 읽으면 **경로 규칙이 두 벌이
되어 반드시 어긋난다.** 그래서 그 함수를 내보내 **같은 객체에서 경로로 값을 꺼낸다.**

**등록부에 없는 경로가 와도 버리지 않는다.** 남의 파일이나 나중 버전에서 올 수 있다.
경로를 괄호에 담아 그대로 보여준다 — 우리가 모르는 것을 아는 척하지 않는다
(docs/i18n.md 규칙 5는 값이 무엇일지 모를 때 괄호로 빼라고 이미 말한다).

**실험은 지울 수 없다** (2026-08-06). `project/attach.ts`가 덧붙이기만 하는 것이 그
결정의 구현이다. 이력이 주인공인 화면에서 지우기를 먼저 주면 학생은 **실패한 실험부터
지운다** — 그러면 무엇을 바꿨더니 왜 나아졌는지가 파일에서 사라지고, 지워진 실험을
직전으로 삼던 `changed`도 가리킬 곳을 잃는다. 한 차시에 실험이 수십 개 쌓이는 문제는
목록이 먼저 실물을 갖고 난 뒤에 다시 본다.

**이번 범위 밖 셋.** **특성 중요도**는 스키마에 자리는 있으나 **어떤 엔진도 만들지 않는다** —
화면이 아니라 엔진 쪽 작업이다. **실험을 가로지르는 비교표**는 목록이 선 뒤에 무엇이
부족한지 보고 정한다. **정렬·필터**는 위와 같은 이유로 안 넣는다.

### 8.13.1 예측 화면은 표의 한 줄을 채우는 것이다 (2026-08-06)

§8.9가 한 줄로 정해 둔 것을 화면 모양으로 옮긴다. **별도의 폼이 아니라 학생이 이미 본
그 표에 새 줄을 하나 넣는 일**이어야 한다.

**왼쪽이 입력 한 줄, 오른쪽이 모델들의 답이다** (§8.10.1). 입력이 지금 하는 일이고
답이 그 판단의 결과다.

**칸은 특성마다 하나이고, 데이터가 칸의 모양을 정한다.** 수치 열은 숫자 칸, 범주형 열은
**학습 때 본 값들 중에서 고르는 칸**이다. 자유 입력으로 두면 학생이 오타를 내고 그 값은
전처리에서 조용히 미지의 범주가 된다 — 화면이 답을 내주는데 그 답이 무의미해진다.

**빈 칸으로 시작하고 [데이터에서 한 줄 가져오기]를 준다.** 처음부터 채워 두면 학생이
그대로 [예측]을 눌러 **자기가 학습에 쓴 행을 다시 맞히는 것**을 본다. 그건 아무것도
가르치지 않는다. 그러나 열이 스무 개인 데이터에서 전부 손으로 채우게 하는 것도 벽이라,
가져와서 **한두 칸만 바꿔 보는 길**을 함께 연다 — 이 도구가 주려는 장면이 그것이다.

**여러 모델에 같은 값을 동시에 넣는다** (`mlpx-spec.md` §0). 예측은 밀리초라 나눌 이유가
없고, "같은 값인데 모델마다 답이 다르다"가 결과 화면의 비교와 짝을 이룬다.

**예측 결과는 파일에 기록하지 않는다** (`mlpx-spec.md` §0). 여기는 플레이그라운드이지
보고서가 아니다. **다만 학생이 올린 `predict.csv`는 남는다** — 막는 것은 산출물이지
학생의 데이터가 아니다(`open-decisions.md` "일괄 예측은 `행 × 모델` 매트릭스다").
그래서 이 화면이 프로젝트를 고치는 경우는 **파일을 올릴 때 하나뿐이고**, 예측을
누르는 것으로는 아무것도 바뀌지 않는다.

**예측은 언제나 브라우저다** (`mlpx-spec.md` §0.2). 서버에서 학습한 모델이라도 실행은
여기서 한다 — 그래서 파일만 있으면 서버 없이 시연이 된다.

**쓸 수 없는 모델은 지우지 않고 사유와 함께 끈다** (§8.2). 사유는 셋이고 전부 다른
말이다 — 이 빌드가 모르는 형식, **원본 데이터가 필요한데 없음**(`mlpx-spec.md` §5.0),
파일에 모델이 안 담김(`modelOmitted`). 셋 다 학생이 할 수 있는 일이 다르다.

#### 확률을 내는 모델은 확률도 보여준다 (2026-08-07)

**로지스틱 회귀 카드에는 범주 옆에 클래스별 확률이 함께 선다**(`mlpx-spec.md` §5.4).
범주만 보여주면 이 알고리즘을 교실에 넣은 이유의 절반이 빠진다 — 학생이 값을 조금씩
바꾸며 **확률이 넘어가는 지점**을 보는 것이 이 화면에서 가장 좋은 장면이다.

**능력은 등록부가 선언한다** (§9). 해석기에 `loadProba`가 있으면 확률을 내는 모델이고,
없으면 아닌 것이다. **불리언 플래그를 따로 두지 않는다** — 플래그와 실제 구현이 갈라질
자리를 만들지 않기 위해서다. `includesPreprocessing`·`needsTrainingRows`가 불리언인 것은
그 둘이 **모델을 읽기 전에** 판정에 쓰이기 때문이고(꺼진 줄을 그리려면 그 전에 알아야
한다), 확률에는 그런 사전 판정이 없다.

**로지스틱 회귀만의 이야기가 아니다.** sklearn에서는 의사결정트리(잎의 클래스 빈도)와
나이브 베이즈도 `predict_proba`를 갖는다. 지금 그 둘에 없는 것은 아직 안 만든 것이지
성질이 아니라서, **이음매를 형식 하나에 박아 넣지 않는다.**

**일괄 예측 표에서는 한 칸에 괄호로 붙인다** — `FALSE (100%)`. 범주마다 열을 세우면
정작 비교할 모델 열이 화면 밖으로 밀린다(아래 "특성 값은 기본으로 숨기고 펼쳐서 본다"와
같은 문제다). 그래서 표에 서는 것은 **답으로 나온 범주 하나의 확률**이고, 나머지 범주를
다 보려면 한 줄 예측으로 간다.

**내려받는 CSV에서는 반대로 열을 나눈다** (`predictDownloadGrid`). 모델 열 바로 뒤에
`{모델} 확률`이 서고 값은 비율 그대로다. 화면의 `FALSE (100%)`는 **사람이 읽는 모양**이라
파일에 그대로 넣으면 엑셀에서 정렬도 계산도 안 되는 문자열이 되는데, 그건 그 함수가
"예측할 수 없음" 같은 문장을 파일에 안 넣는 것과 같은 이유다 — **저기는 눈이고 여기는
데이터다.** sklearn의 `predict_proba`를 열로 받는 모양과도 같아진다.

**붙는 숫자는 확률의 최댓값이 아니라 그 답의 확률이다** (`chosenProbability`). 포화
구간에서는 argmax와 라벨이 갈릴 수 있고(`mlpx-spec.md` §5.4), 최댓값을 쓰면 표가
"FALSE라고 답해 놓고 TRUE의 확률"을 쓴다. 화면과 CSV가 **같은 함수**로 그 범주를 찾는다.

#### 화면보다 먼저 만들 이음매 둘 (2026-08-06)

**둘 다 화면 밖 순수 함수이고 테스트로 덮는다.** 화면 코드 안에 넣으면 검증할 방법이
없어지는데, **여기는 틀려도 에러가 안 나는 자리**다 — 행 하나만 밀려 잡아도 그럴듯한
예측이 나오고 아무도 못 알아챈다. 이 저장소가 규정한 최악이 정확히 그것이다.

**① 학습 행을 만든다.** 참조형(`mlpx-reference-v1`)이 `needsTrainingRows: true`라,
그 모델로 예측하려면 **그 실험의** `trainIndices`로 `dataset/`에서 원본 행을 찾아
**그 실험의 전처리기**로 변환해야 한다. 계약은 `LoadContext`에 정해져 있다
(`mlpx-spec.md` §5.0). **"그 실험의"가 두 번 나오는 것이 핵심이다** — 실험마다 전처리기가
다르므로 다른 실험 것을 쓰면 좌표계가 어긋난 채로 답이 나온다.

**② 입력 한 줄을 특성 벡터로 바꾼다.** 학생이 칸에 넣은 값을 **학습 때 쓴 바로 그
전처리기**로 변환한다. 원-핫으로 늘어난 열의 순서까지 같아야 한다 — `preprocessor`의
`featureNames` 순서가 곧 행렬의 열 순서다(`ml/preprocess.ts`).

**모델을 고를 때 실험도 함께 고르는 셈이다.** 화면이 "모델 목록"을 보여주지만 각 줄이
실제로 매달려 있는 것은 (실험, run) 쌍이고, 위 둘이 전부 그 실험에서 나온다.

#### 칸은 실험들의 합집합이다 (2026-08-06)

**입력은 한 줄인데 모델은 여러 실험에서 온다.** 학생이 특성을 바꿔가며 학습하므로 실험마다
열 목록이 다를 수 있는데, 화면의 칸은 하나뿐이다.

**합집합을 쓴다.** 교집합으로 하면 열을 하나 더 쓴 실험의 모델이 통째로 못 쓰게 되고,
그러면 **"같은 값인데 모델마다 답이 다르다"라는 이 화면의 목적 자체가 사라진다.** 어느
실험이 그 칸을 실제로 보는지는 각자의 전처리기가 정한다 — 안 쓰는 칸은 그 실험의
벡터에 아예 안 들어간다. 범주 목록도 합친다: 학습셋이 달라 못 본 범주가 있을 수 있고,
그 값을 고른 학생에게 그 모델은 미지의 범주로 답한다(전처리의 규칙 그대로다).

**[데이터에서 한 줄 가져오기]는 평가에 쓴 행부터 준다.** 학습 행을 주면 학생이 보는 것이
**모델이 이미 외운 답**이고, 그건 이 버튼을 만든 이유와 정반대다.

**어느 표에서 뽑는지가 실험마다 다르다.** `testIndices`가 가리키는 정본이 `split.method`에
따라 갈리기 때문이다 — `holdout`이면 `data.csv`이고 `provided`면 `test.csv`다
(`mlpx-spec.md` §1.1). 실험이 아니라 화면이 이것을 정하면 **조용히 다른 줄을 채운다.**

**평가 행 중에서 무작위로 하나 준다** (2026-08-06에 뒤집었다). 원래는 순차였고 그 근거를
"난수를 넣으면 재현 가능성에 구멍이 생긴다"라고 적어 두었는데, **다시 보니 그 규칙을 잘못
넓혀 적용한 것이었다.** `randomState`가 지키는 것은 **파일에 기록되고 재실행 대조가 다시
돌리는 것**(분할과 학습)이다. 이 버튼은 입력 칸을 채울 뿐이고 예측 결과는 파일에 남지
않으므로(`mlpx-spec.md` §0) 재현할 대상 자체가 없다. 그리고 순차로 두면 **반에서 모두가
첫 줄로 같은 행을 본다** — 둘러보라고 만든 버튼이 매번 같은 예시를 준다.

**직전에 준 줄은 빼고 뽑는다.** 눌렀는데 화면이 그대로면 학생은 버튼이 고장 났다고 읽는다.
뽑을 것이 하나뿐이면 그것을 다시 준다 — 없는 것을 지어내지 않는다.

**난수원은 인자로 받는다.** 순수 함수로 남아야 테스트가 어느 줄을 뽑았는지 확인할 수 있다.

#### 입력은 양자택일이다 — 한 줄이거나 파일이거나 (2026-08-06)

**왼쪽 입력 영역이 라디오로 갈린다.** 전처리의 `테스트 데이터(Test Data)`와 같은 모양이고
같은 이유다 — 묻는 것이 하나("이 모델들에 무엇을 넣을까")인데 답하는 길이 둘이다.
**새 탭이나 새 화면을 만들지 않는다.**

**파일 쪽의 결과는 `행 × 모델` 표다.** 1열이 행 번호, 2열부터 모델이다. 특성 값은 기본으로
숨기고 펼쳐서 본다 — 특성이 스물이면 정작 비교할 모델 열이 화면 밖으로 밀린다.

**파일 쪽에서는 그 표가 폭을 전부 갖는다.** 오른쪽 답 목록(`AnswerList`)이 하던 일을
표가 대신하기 때문이다 — 같은 것을 둘로 보여줄 이유가 없고, 표를 왼쪽 칸 폭에 가두면
모델 열이 가로 스크롤 안으로 사라진다. 그래서 "왼쪽은 붙박이다"는 ①에만 걸린다.

**100줄씩 끊고, 계산도 그만큼만 한다.** 페이지네이션이 여기서 하는 일은 화면 정리가
아니라 **연산 억제**다(저사양 학교 PC가 기준이다). 한 번 계산한 페이지는 캐시하고,
파일·모델 선택·전처리 설정 중 하나라도 바뀌면 통째로 버린다.

상세(무엇을 남기고 무엇을 안 남기는지, 내려받는 CSV의 모양, 빈 칸이 있는 행)는
`open-decisions.md` "일괄 예측은 `행 × 모델` 매트릭스다"에 있다.

#### 왼쪽은 붙박이다 (2026-08-06)

**입력 칸은 `sticky`로 화면 위에 붙는다.** 오른쪽 답 목록은 실험이 쌓일수록 길어지는데,
왼쪽 입력은 짧다. 붙박이가 아니면 답을 보려고 내려 스크롤하는 순간 값을 바꿀 입력이
화면 밖으로 사라져, "한두 칸만 바꿔서 다시 예측해 보는" 이 화면의 핵심 동작
(위 "칸은 실험들의 합집합이다")이 스크롤 왕복이 된다.

#### 모델 이름에 학습한 곳까지 적는다 (2026-08-06)

**`{알고리즘} · {학습한 곳}`이다.** 결과 화면이 "이번 학습 결과입니다" 카드에서 같은
정보를 보이는 것과 같은 이유다(§8.13의 `RunDetail`) — 브라우저 안에도 순수 JS와
scikit-learn(Pyodide) 둘이 있어서, 그걸 안 보이면 같은 알고리즘인데 다른 엔진으로 학습한
두 모델이 화면에서 구분이 안 되고 비교가 부정확해진다. `ml/results.ts`의
`whereTrainedKeyOf`를 그대로 가져다 쓴다 — 같은 판정을 두 화면이 각자 하면 반드시
어긋난다.

#### 답을 거르고 세어 본다 (2026-08-06)

**필터는 실험(학습 차수) × 모델(알고리즘)의 다중 선택이다.** 실험이 쌓이고 알고리즘이
늘수록 목록이 길어져 "3번째 학습의 결과만 보고 싶다", "의사결정트리끼리만 비교하고 싶다"가
생긴다.

**필터는 돌릴 모델도 줄인다.** 보이지도 않는 모델을 계산할 이유가 없다. 예측이
균일하게 싸다면 상관없을 텐데 **참조형이 그 가정을 깬다** — `mlpx-reference-v1`은 답을
내기 전에 그 실험의 학습셋 전체를 전처리해야 하고(`trainingRowsFor`), 그건 실험마다
한 번씩이다. 저사양 학교 PC가 기준인 이상 안 보이는 것을 위해 그걸 돌지 않는다.

**필터를 바꾸면 지금까지의 답을 지운다.** 안 지우고 새로 보이는 것만 채우는 편이
빠르지만, 그러면 **아래의 불변식이 깨진다** — 답이 있는 카드와 없는 카드가 섞이고,
집계표의 합계가 화면의 카드 수와 안 맞는다. 지우면 **[예측]을 누른 뒤에는 보이는 카드가
전부 답을 가진 상태**가 보장된다. 입력값이 바뀌면 지우는 기존 규칙과 한 줄로 합쳐진다 —
**화면의 구성이 바뀌면 답을 지운다.**

**칸도 필터를 따라간다 — 다만 학생이 넣은 값은 안 지운다.** 칸은 여전히 합집합이되,
합치는 대상이 **지금 보이는 쓸 수 있는 모델들**이다. 한 실험으로 좁혔는데 다른 실험이
쓰던 열까지 채워야 [예측]이 켜지면, **아무 모델도 안 보는 값을 요구하는 셈**이다.
[예측]의 잠금 조건(빈 칸)이 실제로 돌 모델들과 맞아야 한다. 값 자체는 이름을 키로
남겨 두므로 필터를 넓히면 아까 넣은 값이 그대로 돌아온다 — 화면을 좁혔다는 이유로
학생이 친 것을 버리지 않는다.

**[데이터에서 한 줄 가져오기]도 보이는 것 중 첫 모델의 실험을 쓴다.** 지금은 쓸 수 있는
첫 모델의 실험에서 평가 행을 꺼내는데, 그 실험이 필터에 걸려 안 보이면 **화면에 없는
실험의 분할을 따라 행을 주게 된다.**

**전부 끄면 카드가 없고 [예측]도 꺼진다. 이유를 함께 준다** — 이유 없이 꺼진 버튼은
학생에게 고장으로 보인다(§8.2). 필터는 **전부 켠 상태로 시작한다**: 처음 온 학생에게
아무것도 안 보이는 화면을 주지 않는다.

**계산이 도는 동안에는 필터를 못 바꾼다.** 도중에 대상이 바뀌면 어느 집합에 대한 답인지가
흐려진다. 그런데 **끄려면 예측이 비동기여야 한다** — 동기로 도는 함수는 메인 스레드를
통째로 막아서 꺼진 상태가 화면에 그려질 틈이 없고, 그건 "화면이 멈추면 안 된다"는 규칙
자체를 어기는 것이기도 하다(§3.4의 같은 판단). 그러므로 [예측]은 `@click`이 아니라
**`AppButton`의 `action`**이고(CLAUDE.md §4 — `@click`은 두 번 눌리는 것을 못 막는다),
모델 사이에서 화면에 양보한다. 참조형이 낀 파일에서 이것은 실제로 오래 걸리는 버튼이다.

**분류 답에는 값별 집계와 강조가 붙는다. 회귀에는 없다.** 분류는 같은 라벨이 여러
모델에서 정확히 겹칠 수 있어 "1로 답한 모델 3개, 2로 답한 모델 1개"가 뜻이 있다.
**회귀는 다르다** — 답이 연속값이라 부동소수 두 개가 정확히 같을 일이 실질적으로 없고,
그러면 "n개 모델이 3.14159를 냈다"는 사실상 항상 1이라 집계표가 통째로 장식이 된다.
그래서 회귀에는 이 표와 강조를 만들지 않는다. 값이 아니라 흩어진 정도(범위 등)를
보여주는 것이 맞겠지만 그건 범위 밖이다.

**집계와 강조는 필터를 따라간다.** 위에서 필터가 실행 대상을 줄이므로 실은 따라갈 수밖에
없지만, 그게 아니더라도 그래야 한다 — **표의 숫자가 화면의 카드와 맞아떨어져야 한다.**
"1로 답한 모델 3개"인데 보이는 카드가 둘이면 학생이 세어서 확인할 수가 없고, 이 나이대에게
집계표의 값어치는 **직접 세어 맞춰 보는 것**에 있다. **답을 낸 모델만 센다** — 사유와 함께
꺼진 모델과 예측이 실패한 모델은 목록에 남지만 표에는 안 들어간다. 표가 세는 것은
"답"이지 "카드"가 아니다.

#### 값마다 다른 색이다 — `과반수`도 이분법도 아니다 (2026-08-06)

**처음에는 최다 답만 `info`로 강조하고 나머지 전부를 `caution` 하나로 묶었는데,
그러면 갈림표 칩의 "B: 2개"와 카드가 같은 색인지를 학생이 표에서 못 찾았다.** 값이
셋 이상으로 갈리면 "다른 답"이 전부 같은 caution이라 그 안에서 또 뭐가 뭔지 안 보였다.
그래서 **값마다 고유한 색을 하나씩 매긴다** — 카드와 갈림표 칩이 같은 값이면 항상 같은
색이다.

**등수는 매기지만 등수와 색의 대응은 고정하지 않는다.** 갈림표 칩과 카드가 같은
등수 하나를 같은 색으로 봐야 어긋나지 않으므로, "몇 번째로 많이 나온 값인가"
(`rankAnswers`, `ml/predict.ts`)가 등수의 유일한 출처인 것은 맞다. 그런데 **1등이
항상 chart-1로 고정되면 그 색만 늘 쓰인다** — 분류는 대개 두세 갈래라 chart-1·2만
매번 나오고 나머지 다섯은 사실상 죽은 색이 된다. 그래서 등수 → 색의 대응
자체는(`AnswerList.vue`의 `CHART_CLASSES`) **화면이 뜰 때 한 번 섞는다.** 답이
갱신되는 동안은 다시 안 섞는다 - 방금 보던 카드의 색이 [예측]을 다시 누를 때마다
바뀌면 무엇이 무엇이었는지 놓친다. **동점이어도 등수를 매긴다** — 예전의 "과반수
강조"는 승자를 뽑는 일이라 동점에 색을 얹으면 없는 승자를 지어내는 것이었지만,
지금은 색이 **정체성일 뿐 승패가 아니다.** "몇 등인지"는 몰라도 "그 값들이 서로
다른 색인지"만 있으면 된다.

- **전부 같은 답이면 강조하지 않는다.** 보여줄 갈림이 없다(`rankAnswers`는 값이
  하나뿐이면 `null`을 준다).
- **색은 일곱 개뿐이다.** Okabe-Ito 색맹 안전 팔레트에서 가져왔다(`styles/theme.css`).
  값 종류가 이보다 늘면 여덟째부터는 등수를 매기지 않고 회색 하나로 묶는다 — 색이
  여덟아홉 개를 넘으면 팔레트를 더 늘려도 눈으로 못 가르고, 늘어난 값 하나하나에
  뜻을 둘 만큼 이 표가 정밀한 도구도 아니다.
- **`positive`/`danger`가 아니라 이름 없는 순서색이다.** 옳고 그름을 말하는 상태색을
  쓰면 그 순간 정답 발표로 읽힌다. 그래서 이 팔레트는 `--color-chart-1`처럼 뜻이 아니라
  순서로만 부른다 - §8.4가 말하는 "이름은 쓰임새로 짓는다"의 예외이지만, 여기서
  쓰임새는 정확히 "구분"이지 "상태"가 아니므로 이름을 붙일 상태가 애초에 없다.
- **문자열을 이어 붙여 클래스 이름을 만들지 않는다.** `` `border-chart-${n}` `` 은
  Tailwind가 소스에서 못 찾아 그 색이 빌드에서 빠진다. 일곱 개를 배열에 통째로 적어
  둔다(`AnswerList.vue`의 `CHART_CLASSES`).

**이 표는 판정 도구가 아니라 관찰 도구다.** 답하는 질문은 "정답이 무엇인가"가 아니라
**"얼마나 갈렸나"**이고, 문구도 그 선을 넘지 않는다.

**모델들은 독립적인 투표자가 아니다.** 같은 데이터·같은 전처리·같은 분할을 봤고, 무엇보다
목록이 (실험, run) 쌍이라 **설정을 거의 안 바꾸고 세 번 학습하면 같은 의견이 세 표가 된다.**
여론조사가 아니다. 이것이 기능을 뺄 이유는 아니지만, **필터가 그 해독제라는 점이 중요하다** —
한 실험으로 좁히면 그 안의 서로 다른 알고리즘끼리 비교가 되고 그게 실제로 뜻이 있는
비교다. 필터는 편의 기능이 아니라 이 표를 의미 있게 만드는 장치다.

**필터·집계·강조는 화면 밖 순수 함수다** (`ml/predict.ts`). 이 화면이 이미 규정한
최악과 같은 이유다 — 여기는 틀려도 에러가 안 나는 자리이고, 화면 코드 안에 넣으면
확인할 방법이 없어진다.

#### 일괄 예측 표의 셀도 값별로 다른 색이다 — 등수가 아니라 처음 본 순서다 (2026-08-07)

**위의 "값마다 다른 색"(카드·갈림표)과 같은 목적, 다른 규칙이다.** 일괄 예측 표는
`행 × 모델`이라 셀이 수백 개고, 같은 타깃(예: `Iris-setosa`)이 여러 행·여러 열에
흩어져 나온다 - 셀마다 같은 값이면 같은 색이면 표를 눈으로 훑기가 훨씬 쉽다.

**그런데 카드·갈림표의 "등수(개수 순)" 방식을 그대로 못 쓴다.** 이 표는
`PREDICT_PAGE_SIZE`행씩 끊어서 계산한다(연산 억제, 위 "칸도 필터를 따라간다"
문단). 즉 **화면은 지금 페이지가 계산되기 전까지 파일 전체의 값 분포를 모른다.**
등수로 색을 매기면 1페이지에서 최다였던 값이 2페이지에서는 최다가 아닐 수 있고,
그러면 **같은 값인데 페이지마다 색이 바뀌는** 사고가 난다 - 이 기능을 만든 이유
(같은 값을 눈으로 맞춰 보는 것) 자체를 어긴다.

그래서 **등수가 아니라 "처음 본 순서"로 배정한다** (`assignAnswerColors`,
`ml/predict.ts`).

- 화면 상태로 값 → 색 인덱스 맵을 하나 들고, **페이지를 계산할 때마다 그 페이지에서
  처음 보는 값에만** 다음 빈 색을 준다. 이미 배정된 값은 절대 안 바꾼다 - 페이지를
  앞뒤로 오가도 같은 값은 항상 같은 색이다.
- 파일을 바꾸거나 보이는 모델이 바뀌면(`signature` 변경) 이 맵도 함께 비운다 -
  `pageCache`를 버리는 자리와 같다. 값의 세계 자체가 바뀐 것이라 이전 배정을
  들고 있을 이유가 없다.
- 일곱 개를 넘는 값은 계속 색이 없다("값마다 다른 색"과 같은 제한). **어떤 값이
  일곱 개 안에 드는지는 페이지를 넘긴 순서에 달려 있다** - 결정적이지 않고, 감수한
  트레이드오프다.
- 카드·갈림표의 셔플 팔레트와 **공유하지 않는다.** `AnswerList`(한 줄 입력)와 이
  화면(파일)은 `PredictView.vue`에서 `v-if`/`v-else`로 갈려 동시에 안 보이므로,
  같은 값이 두 화면에서 같은 색일 이유가 없다. 각자 뜰 때 따로 섞는다.
- **표는 촘촘해서 배경색 대신 글자색만 쓴다** (`text-chart-N`). 카드는 넓어서
  `border + bg-soft`가 자연스러웠지만, 표는 이미 지브라 줄무늬
  (`odd:bg-surface even:bg-surface-sunken`)가 있어 셀마다 배경까지 칠하면 시끄러워진다.

**미결정.** 위 트레이드오프는 값 종류가 일곱을 넘는 데이터가 드물다는 전제로 받아들인
것이다. 자주 넘으면 등수 기반으로 바꿀 수 있다 → `open-decisions.md` #24.

#### 군집의 답에는 이웃이 딸린다 (V3, 2026-08-11)

**군집 번호만 주는 답은 학생에게 정수 하나다.** `2번 군집`이라는 답을 받은 학생의 다음
말은 "그래서 이거랑 비슷한 게 뭔데"이고, 그 답을 못 하면 이 화면에서 군집은 아무것도
가르치지 않는다.

**답 카드에 `0`이라고 쓰지 마라.** 해석기가 돌려주는 것이 문자열 `"0"`이라 그대로 쓰면
카드에 `0`만 뜬다 — 분류의 라벨 `0`이나 회귀의 값 `0`과 **글자가 같아서 구별되지 않는다**
(2026-08-11에 화면에서 그렇게 났다). `0번 군집`으로 쓴다. **그 판정을 화면이 하지
않는다** — `ml/predict.ts`가 "이 모델의 답이 군집 번호인가"에 답하고, 화면은 그것만 본다
(§9.1, `answerRank`가 분류에만 등수를 주는 것과 같은 모양이다).

**그리고 군집 번호는 그 모델 안에서만 뜻이 있다.** 1번째 학습의 `0번 군집`과 2번째
학습의 `0번 군집`은 **같은 군집이 아니다** — 번호는 초기화 순서가 매긴 이름일 뿐이다.
카드 둘이 나란히 `0번 군집`이라고 적혀 있으면 학생은 "둘 다 같은 답"으로 읽으므로
**그 사실을 한 줄로 말한다.** 같은 이유로 **갈림표가 군집을 안 센다** — 세면 서로 다른
것을 같은 칸에 담게 된다(집계가 `분류 모델의 답만 셉니다`라고 말하는 자리가 그것이다).

**그래서 답 옆에 그 군집의 요약과 입력에 가까운 행 몇 개가 선다.** 정렬은 **입력과의
거리**이지 중심점까지의 거리가 아니다 — 결과 화면의 구성원 표(전형적인 것부터)와는 다른
질문에 답한다 (`open-decisions.md` #28-6).

**데이터가 없으면 답은 나오고 표만 없다** (§9.5). `mlpx-kmeans-v1`은
`needsTrainingRows: false`라 중심점만으로 군집 번호를 답한다. 여기서 모델을 통째로 끄면
(위 `MODEL_NEEDS_DATASET`) **지금 되던 것이 안 되게 된다.**

**비용은 참조형과 다르다.** KNN이 무거운 것은 *예측 행마다* 학습셋 전체와 거리를 재기
때문인데(`MLJS_KNN_ROW_LIMIT`의 근거), 여기는 **입력 한 줄 대 학습 행 전체**라 한 번이다.

**그리고 그림이 함께 선다** (#28-7). 이웃 표가 "비슷하다"고 말한 것을 **점 하나로
보여주는 자리**다 — 입력한 데이터는 **흰 테두리를 두른 마름모**이고 색은 답으로 나온
군집의 색이다. 빨강을 쓰지 않는 이유는 그것이 `danger`의 자리라 학생이 "내 데이터가
잘못됐다"로 읽기 때문이다. **그림 자체는 결과 화면과 같은 부품이다**
(`components/ClusterScatter.vue`) — 두 벌로 두면 축 규칙과 색 규칙이 한쪽에서만
고쳐질 자리가 생긴다.

### 8.13.2 군집 결과 패널은 셋을 함께 보인다 (V3, 2026-08-11)

**결과 화면에 `if (taskType === 'clustering')`을 만들지 마라.** 군집 결과는
`ml/metric-panels.ts`에 한 줄로 등록한다 — 혼동 행렬이 분류 전용인 것과 같은 방식이고,
그래야 이미지가 들어오는 날 고칠 파일이 등록부 하나다 (§9.1).

자리는 "고른 run의 속"이다(§8.13의 4번). 결정과 근거는 `open-decisions.md` #28에 있고,
여기 적는 것은 **화면 쪽 규칙**이다.

**패널 하나가 셋을 보인다 — 산점도 · 군집 요약표 · 구성원 표.** 그림만으로는 "이 군집은
어떤 애들인가"에 답할 수 없다 (#28-6). **셋이 한 패널인 이유는 재료가 하나이기 때문이다** —
전체 행의 군집 배정 하나에서 셋이 다 나온다. 등록부에 줄을 셋 세우면 같은 계산을 세 번
하게 되고, **그 셋이 서로 다른 배정을 들고 있을 자리**가 생긴다.

1. **축 선택은 그림 위 왼쪽, 좁은 화면에서 세로로 쌓인다** (§8.10.1). 특성이 2개
   이하면 자리 자체가 없다 (§9.2).
2. **군집은 요약표의 줄을 눌러 고르고, 그 아래 구성원 표가 펼쳐진다.** 점수 표의 줄을
   눌러 `RunDetail`이 펼쳐지는 것과 같은 문법이다(§8.13) — 한 화면에서 같은 동작이 두
   문법을 갖지 않는다.
3. **패널이 뜨는 조건은 축이 아니라 담김이다** (§9.5). `run.model`이 없으면 그릴 재료가
   없으므로 패널이 없고, 화면은 아무 말도 안 한다 — 사유(`run.modelOmitted`)는 다른
   자리가 이미 말한다.
4. **재료를 만드는 계산은 화면 밖 순수 함수다** (§8.3). 배정 되계산 · 스케일 되돌리기 ·
   표본 뽑기 · 거리 정렬이 전부 `ml/` 아래에 있고, 패널은 받은 것을 그리기만 한다. 눈으로
   확인할 수 없는 규칙이라 vitest가 덮는 쪽에 있어야 한다 (CLAUDE.md §4).
5. **차트 설정도 그 계산에 든다** (`ml/cluster-chart.ts`, 2026-08-11에 화면에서 뺐다).
   처음에는 `chartData`/`chartOptions`를 화면에 두었는데, **거기서 규칙 둘이 조용히
   깨졌다** — 데이터셋을 배열 끝에 넣으면 맨 아래에 그려져 중심점이 점 수천 개에
   묻혔고(Chart.js는 정렬 후 역순으로 그린다), 애니메이션 기본값이 켬이라 축 한 번
   바꾸기가 1만 점에서 799ms였다. **둘 다 눈으로만 보이는 종류라 사용자가 화면에서
   잡았다.** 빼고 나니 캔버스 없이 검사가 붙는다 — 그리는 차례 · 흰 테두리의 자리 ·
   범례와 툴팁의 필터 · `animation`. **chart.js에서 타입만 가져오므로** 이 계층을 쓰는
   코드가 차트 라이브러리를 함께 받지 않는다.

**패널이 재료를 어디서 받는가는 계약이 하나 는다는 뜻이다.** 지금 패널은 `run` 하나만
받는데(`RunDetail`), 군집 패널은 전처리기와 모델과 데이터셋이 필요하다. **`run`에 담아
해결하지 않는다** — 그 값은 행마다 하나라 데이터가 클수록 커진다 (#28-4).

**넓히는 방법은 프롭 하나에 묶는 것이다. 개별 프롭으로 흩지 마라.** 흩으면 안 쓰는 패널이
그것을 선언하지 않게 되고, **선언하지 않은 객체 프롭은 `[object Object]`라는 어트리뷰트로
DOM에 그대로 박힌다**(2026-08-11에 재현해서 확인했다 — 조용히 사라지지도, 경고를 내지도
않는다). 그러면 계약이 넓어질 때마다 **패널 전부**를 고쳐야 하고, 하나를 빠뜨린 것은
컴파일도 검사도 못 잡고 학생이 화면에서 알게 된다 — §9.1이 등록부를 만든 이유와 같은
실패 모양이다.

**그리고 여기는 타입이 안 지켜 주는 자리다.** 호출부가 `<component :is>` 하나뿐이라
vue-tsc가 프롭을 검사하지 않는다. 그래서 **`tests/ui-rules.spec.ts`가 "패널은 프롭을
하나만 선언한다"를 강제한다** — 사람이 지키길 기대하지 않는다 (CLAUDE.md §4).

### 8.14 낮은 창에서 잘리지 않게 하는 규칙 (2026-08-06)

**`h-full`로 만든 작업 공간은 창이 낮으면 내용을 0으로 나눠 준다.** 데이터 화면과 결과
화면이 둘 다 그랬다 — 표가 머리만 남긴 채 **잘리는데 스크롤도 안 생겼다.**

원인이 둘로 겹쳐 있어서 눈으로는 못 짚는다.

1. 작업 공간이 `h-full`이면 높이가 바깥(`AppShell`의 `<main>`)과 **딱 같다.** 그러면
   바깥은 넘칠 것이 없다고 보고 스크롤 막대를 안 만든다. 안쪽만 짜부라진다.
2. `AppTable`은 **스스로 스크롤하는 상자**다. 거기에 `h-full`을 주면 부모가 얼마나 작든
   그만큼 따라 줄어들어, 표는 "내 자리가 이만큼"이라고 믿고 머리만 그린다.

그래서 규칙이 둘이다. **`tests/ui-rules.spec.ts`가 강제한다.**

- **작업 공간 래퍼는 `min-h-full`이다.** `h-full`을 쓰지 마라. 최소 높이면 낮은 창에서
  내용이 바깥을 넘치고, 그때 스크롤하는 것은 바깥이다.
- **표에 `h-full`을 주지 마라.** 자리는 부모가 flex로 주고 표는 `min-h-0 flex-1`로
  받는다. **그래야 최소 높이가 부모 한 군데에 모인다** — 표마다 흩어 두면 자리를
  나눠 갖는 규칙이 화면마다 달라진다.

세로로 자리를 나눠 갖는 칸(`flex-1`)에는 **최소 높이를 준다.** 이건 정규식으로 잡을 수
없어 검사가 없다 — 옆으로 나눈 두 열이 각자 스크롤하는 화면을 만들 때 사람이 지켜야
하는 유일한 항목이다.

### 8.15 확인 모달이 걸린 라디오는 그룹째 되돌린다 (2026-08-06)

**라디오는 `:checked`가 실제로 안 바뀌면 Vue가 DOM을 다시 안 써 준다.** 전처리
화면의 테스트 데이터 선택("훈련 데이터의 일부를 씁니다" / "별도 파일을 올립니다")이
그랬다 — 붙어 있던 테스트 데이터를 떼려면 확인 모달을 거치는데, **취소하면 라디오가
원래 자리로 안 돌아오고 아무것도 선택 안 된 채 남았다.**

원인이 둘로 겹쳐 있어서 눈으로는 못 짚는다.

1. `:checked="model === 'x'"`처럼 계산값에 매인 라디오는, 확인을 기다리는 동안
   실제 모델 값이 안 바뀐다. Vue는 이전 렌더와 계산 결과가 같으면 "바뀐 게 없다"고
   보고 그 DOM 프로퍼티를 다시 안 쓴다 — `v-model`도 같은 최적화를 한다.
2. 그런데 **브라우저는 클릭한 순간 이미 네이티브 라디오 그룹 전체의 `checked`를
   새 선택에 맞게 바꿔 둔 뒤다.** 방금 켠 것만 손으로 되돌리면 그룹의 나머지는
   여전히 브라우저가 꺼 둔 채로 남는다 — 결국 아무것도 안 켜진 것처럼 보인다.

그래서 **확인을 취소하면 그 라디오 하나가 아니라 그룹 전체를 실제 값에 맞게 다시
써야 한다.** `composables/useRadioGroupGuard.ts`가 이 되돌리기를 한다 — 값별로
노드를 등록해 두고, 취소 시점에 등록된 노드를 전부 훑어 실제 값과 비교해
`checked`를 다시 쓴다. **옵션이 몇 개든 이 훅을 고칠 필요가 없다.**

**확인 모달이 걸린 라디오 그룹은 전부 이 훅을 쓴다. `tests/ui-rules.spec.ts`가
강제한다** — `@change` 핸들러가 `request*` 함수(붙이거나 뗄 때 먼저 물어보는
기존 관례, `PreprocessView.vue`의 `requestApplyTest`/`requestRemoveTest`)를
부르는 라디오 그룹인데 그룹의 노드 중 하나라도 `useRadioGroupGuard`로 등록돼
있지 않으면 잡는다.

#### 8.15.1 잠기는 입력은 DOM을 스키마로 되돌린다 (2026-08-07)

**같은 함정이 체크박스에도 있고, 잠금이 걸리면 실패가 더 나쁘다.** §8.15의 원인 1번은
라디오만의 성질이 아니다 — `:checked`는 `v-model`이 아니라 **계산값이 안 바뀌면 Vue가
DOM 프로퍼티를 다시 안 쓴다.** 그런데 브라우저는 클릭한 순간 이미 `checked`를 뒤집어 둔
뒤다. 그래서 핸들러가 스키마를 못 고치면(파일이 없다·가드가 막았다·적용이 실패했다)
**화면과 파일이 갈린 채로 남는다.**

평소에는 "한 번 더 누르면 맞아진다"로 끝나는데, **잠기는 입력에서는 끝이 아니다.**
잠금 조건이 스키마를 보고 판정하므로 화면이 거짓말하는 동안 입력이 회색이 되면
**학생이 고칠 문이 없다.** 파일을 손으로 열어 고치는 것 말고는 방법이 없고, 그건
교실에서 없는 선택지다.

그래서 잠금이 걸린 입력의 `@change` 핸들러는 둘을 지킨다.

- **DOM을 읽지 않는다.** 의도는 스키마에서 뒤집는다 — `input.checked`는 우리가 만든
  결과가 아니라 브라우저의 짐작이다.
- **끝에 DOM을 스키마 값으로 다시 쓴다.** 정상 경로에서는 아무 일도 아니고
  (이미 같다), 못 고친 경로에서만 되돌린다. `useRadioGroupGuard.resync`가 하는 일과
  같은 것을 입력 하나에 대해 하는 셈이다.

**훅으로 만들지 않는다.** 잠기는 체크박스가 지금 하나뿐이고(전처리 화면의 층화),
구현이 하나뿐인 계약을 미리 설계하지 않는다(§9.2.1). 둘째가 생기는 날 `useRadioGroupGuard`
옆으로 옮긴다.

### 8.16 나열에서 이름은 배지, 값은 plaintext다 (2026-08-07)

**이름-값 쌍을 `gap`만 두고 이어 붙이면 어디서 한 값이 끝나고 다음 값이 시작하는지
안 보인다.** `StepHeader`의 맥락 줄("행 수 120 열 수 8")이 그랬다 — `gap-x-5`는
여백일 뿐 눈에 보이는 경계가 아니고, 이름은 흐리고 값은 볼드인 서식이 그룹마다
반복되니 오히려 "120 열"까지가 한 덩어리로 읽혔다.

처음에는 그룹 사이에 가운뎃점을 넣어 갈랐는데, **경계를 하나 더 그리는 대신 이름과 값의
생김새를 다르게 하는 편이 낫다** (2026-08-07에 뒤집었다). 점은 "여기서 끊긴다"만 말하고
**어느 쪽이 이름인지는 여전히 서식으로 알아내야 한다.** 결과 화면의 변경 이력이 같은
문제를 배지로 풀고 있었고(§8.13), 한 앱에서 같은 물건이 자리마다 다른 문법으로 서 있을
이유가 없다.

> **이름은 회색 배지(`AppBadge`), 값은 plaintext. 그리고 그 사이에 구분자는 없다.**

**가운뎃점은 하단 상태 표시줄에만 남는다.** 거기는 `<dl>`이 아니라 **한 줄로 이어 붙인
요약**이고(줄이 잘리면 앞부터 남는다) 배지가 설 자리가 없다 — 배지는 높이를 갖고,
그 줄은 높이를 늘릴 수 없다.

**이름이 안 보이는 쌍에는 배지도 없다.** 파일 이름이나 실험 개수처럼 `<dt>`가 `sr-only`인
자리가 그렇다 — 값 자체가 무엇인지 말하고 있어 이름을 보일 이유가 없고, 안 보이는 것에
배지를 씌울 수도 없다.

**볼드나 버튼 테두리처럼 굵기·상자 자체가 이미 경계인 줄에는 안 쓴다.** 잡는 것은
**plaintext 이름-값이 가로로 나열되는 자리**뿐이다 — `AnswerList`의 카드 세 줄은 각 줄이
이미 다른 글자 크기·색으로 나뉘어 있어 해당하지 않고, `ProjectSummary`처럼 **한 줄에 한
쌍씩 세로로 쌓는 표**도 아니다. 거기서는 줄 자체가 경계라 이름을 볼드로 세우는 것으로
충분하고, 배지를 씌우면 회색 알약이 열 줄 넘게 쌓여 값보다 눈에 띈다.

**`tests/ui-rules.spec.ts`가 둘을 강제한다** — 보이는 `<dt>`에 배지가 없으면 잡고,
`AppStatusBar` 밖에 가운뎃점이 있으면 잡는다. 앞의 것이 관례를 지키게 하고, **뒤의 것이
이 절이 뒤집힌 사실을 지킨다** — 옛 모양을 기억하는 사람이 점을 다시 넣는 것을 막는
자리가 있어야 한다.

### 8.17 학습 중에는 **담은 모델마다** 상태를 보인다 (2026-08-07)

**끝난 개수만으로는 어느 모델이 오래 걸리는지 알 수 없다.** 진행 줄은 `3개 중 1개째`를
말하는데, 그 말이 가리키는 것이 "1번이 도는 중"인지 "1번은 끝나고 2번이 도는 중"인지
문장만으로는 갈리지 않는다. 그리고 **어느 모델에서 멈췄는지는 아예 안 나온다** — 실제로
그 상태가 되면 학생이 할 수 있는 일은 **모델을 하나씩 빼 가며 다시 학습해 범인을 찾는 것**뿐이고,
그 시간에 배우는 것은 없다.

> **`담은 모델` 목록의 줄마다 지금 상태를 보인다 — 대기 · 학습 중 · 완료 · 실패.**

자리를 새로 만들지 않는다. 그 목록이 이미 "무엇을 돌릴 것인가"를 말하는 자리이고,
**돌린 결과도 같은 줄에서 읽히는 것이 맞다.**

**색과 글자를 함께 준다.** 테두리 색만으로 말하면 색각 이상이 있는 학생과 흑백으로
인쇄한 교사에게는 아무 말도 안 한 것과 같다. 색은 §8.4의 토큰을 그대로 쓴다 —
대기 `line`, 학습 중 `brand`, 완료 `positive`, 실패 `danger`.

**상태는 워커가 보고한 것만 쓴다. 화면이 추측하지 않는다.** "앞의 것이 끝났으니 다음
것이 돌고 있겠지"는 순차 실행일 때만 맞는 추론이고, 그 가정은 서버 학습이나 병렬 실행이
붙는 날 조용히 틀린다. 그래서 시작도 워커가 말한다 (`mlpx-spec.md` §0.3).

**줄과 보고를 잇는 것은 순서(index)다.** `담은 모델`은 같은 알고리즘이 실행 방법만 다르게
두 번 들어올 수 있어(`schema.ts`의 `selectedAlgorithms`) 알고리즘 이름은 키가 못 된다.
run이 `selectedAlgorithms`와 같은 순서로 만들어진다는 것은 이미 `comparable()`이 기대고
있는 사실이다.

**학습이 끝나면 상태는 사라진다.** 결과는 결과 화면이 말하는 것이고(§8.13), 학습 화면에
남겨 두면 같은 사실을 두 화면이 각자 들고 있게 된다. 이 목록이 말하는 것은 **지금 도는
학습 한 번**이다.

**모델별 실행 시간은 안 보인다.** 지금 화면이 답해야 하는 질문은 "누가 오래 걸리는가"이고
그건 `학습 중` 배지가 오래 떠 있는 것으로 이미 답이 된다. 초를 세어 보이면 그 순간
숫자가 비교 대상이 되고(§8.13이 순위표를 거부한 것과 같은 이유), 엔진과 기기가 다른
사이에서 그 비교는 아무 뜻이 없다.

## 9. 능력 선언 — 무엇이 무엇에서 되는가 (2026-08-06)

**이 도구의 거의 모든 것이 세 축에 걸려 있다.**

| 축 | 어디서 오는가 | 값 |
|---|---|---|
| `dataType` | 업로드한 데이터 | `tabular` / `image` / `audio` / `text` |
| `taskType` | **학생이 고른다** | `classification` / `regression` / `clustering` |
| `runtime` | **항목이 선언한다** — 어느 엔진에 구현이 있는가 | 순수 JS / pyodide / 서버 |

**`runtime`은 두 겹이다. 섞지 마라.** 등록부가 말하는 것은 *"이 알고리즘에 sklearn
구현이 있다"*는 **정적 사실**이고, *"지금 그 서버가 붙어 있다"*는 **동적 사실**이다.
앞의 것만 §9의 축이고, 뒤의 것은 `ml/backend.ts`가 지금 상태를 보고 판정해 §10의
gate로 들어간다. 등록부에 "서버가 켜졌는가"를 넣으면 정적인 표가 시간에 따라
변하게 되고, 그 순간 표를 신뢰할 수 없다.

K-NN은 분류에도 회귀에도 선다. 로지스틱 회귀는 표 데이터에서만 선다. 혼동 행렬은
분류에만 있다. 결측치 채우기는 이미지에 없다. **이 사실들은 전부 같은 모양의 사실이고,
같은 방식으로 적어야 한다.**

### 9.1 규칙: 사실은 능력 옆에 적는다

> **"X는 Y에서만 쓸 수 있다"는 X의 등록부 항목에 적는다. Y의 화면에는 절대 적지 않는다.**

혼동 행렬이 분류 전용이라는 사실은 **결과 화면이 아니라 혼동 행렬 옆**에 있어야 한다.
결측치 채우기가 표 전용이라는 사실은 **전처리 화면이 아니라 그 단계 옆**에 있어야 한다.

화면에 적으면 무슨 일이 생기는지가 이 규칙이 있는 이유다. 이미지가 들어오는 날,
고쳐야 할 파일이 **등록부 하나가 아니라 그 사실을 아는 화면 전부**가 된다. 그리고 그중
하나를 빠뜨렸다는 것은 **컴파일도 검사도 못 잡고 학생이 화면에서 알게 된다.**

따라서 **`v-if="dataType === 'tabular'"`도 `v-if="taskType === 'classification'"`도 금지다.**
`ml/algorithms.ts`가 알고리즘에, `ml/metrics.ts`가 지표 계산에 이미 이 규칙을 지킨다.
남은 두 곳이 **전처리 UI와 결과 지표 UI**이고, 그 둘을 같은 모양으로 옮긴다.

### 9.2 등록부의 모양은 하나다

새 등록부를 만드는 사람은 `data/kinds.ts`와 같은 모양을 쓴다. 모양이 갈리면 다음 사람이
어느 쪽을 흉내 낼지 고민하고, 고민한 곳에서 갈라진다.

등록부 항목은 **id, 축마다의 칸, 그리고 화면**을 갖는다. 축의 정확한 표기는 §9.3이
정한다 — 배열이 아니라 exhaustive Record이고, **그 이유가 이 등록부의 존재 이유 전체다.**

**축은 늘리지 말고 접는다.** 축이 넷이 되면 표가 곱으로 커지고 사람이 못 읽는다.
딥러닝이 들어와도 `runtimes`에 값이 하나 늘 뿐, 새 축이 생기지 않는다.

**모든 축을 반드시 적는다. 옵셔널 필드를 만들지 마라.**

결측치 채우기는 분류든 회귀든 똑같이 성립하므로 `taskTypes`를 생략하고 싶어진다.
생략하면 안 된다 — **옵셔널은 "이 축과 무관하다"와 "적는 걸 잊었다"를 타입이 구별하지
못한다.** 과제 유형이 하나 느는 날 생략된 항목은 컴파일러를 조용히 통과하고, 그 항목이
새 유형에서 성립하는지 **아무도 다시 보지 않는다.** 등록부가 짧아지는 대가로 얻는 것은
그것 하나뿐이고, 그 하나가 이 등록부를 만든 이유 전체다.

**화면을 갖는 항목은 지연 로딩한다** (`defineAsyncComponent`). 표만 쓰는 수업에서
이미지 판의 코드가 내려올 이유가 없다. `data/kinds.ts`가 이미 그렇게 한다.

### 9.2.1 `false`의 뜻은 하나다 (2026-08-06)

> **`false` = 이 조합에서는 성립하지 않는다.** 그것뿐이다.

"아직 안 만들었다"는 `false`가 아니다. **줄이 없는 것이다.** 등록부에 항목이 있다는
것은 그것이 만들어져 있다는 뜻이고, 만들다 만 것은 등록부에 올리지 않는다. 코드가
남아 있다면 지우거나 주석 처리한다.

그러므로 **"준비 중입니다" 같은 문구를 만들지 마라.** 학생 입장에서 *없어서 안 보이는
것*과 *만드는 중이라 못 쓰는 것*은 **똑같다** — 지금 할 수 없다는 사실 하나뿐이고,
우리 사정은 학생이 알아야 할 것이 아니다. §8.10이 "군집화 문구를 미리 쓰지 마라"고
한 것과 같은 규칙이고, 이유도 같다: 쓸 대상이 없는 문장은 아무도 화면에서 못 보고
검사도 못 잡는다.

**로드맵을 등록부에 넣지 마라.** `'planned'` 같은 세 번째 상태를 두고 싶어지는데,
그건 검증할 방법이 없는 선언이라 §9.3.2의 "잘못 판단한 칸"이 한 종류 늘 뿐이다.
무엇을 만들 예정인지는 `docs/roadmap.md`가 갖는다. **등록부는 지금 참인 것만 담는다.**

### 9.2.2 한 줄이 표현하는 것은 직사각형이다 (2026-08-07)

**축은 서로 독립이고 판정은 AND다.** 그래서 한 항목이 덮는 것은 켠 값들의 **곱집합**이지,
칸 하나하나가 아니다.

```
dataTypes  { tabular: true, image: true }
taskTypes  { classification: true, regression: false, clustering: false }
                    ↓
        classification  regression  clustering
tabular       ✅           ✕           ✕
image         ✅           ✕           ✕
```

이미지 + 군집이 안 서는 이유는 `clustering: false` 하나이고, **데이터 종류와 무관하게**
걸린다. 그것이 옳다 — 혼동 행렬이 군집에 성립하지 않는 이유는 정답 라벨이 없어서이지
데이터가 사진이어서가 아니다.

**그러므로 한 줄로는 "표+분류는 되고 이미지+분류는 안 된다"를 못 쓴다.**
`classification: true`를 켜는 순간 두 종류 모두에 걸린다.

> **그때 필요한 것은 새 필드가 아니라 새 줄이다.**

```ts
{ id: 'confusion-matrix',       dataTypes: { tabular: true, image: false }, … }
{ id: 'confusion-matrix-image', dataTypes: { tabular: false, image: true }, …, panel: 다른 화면 }
```

직사각형 여러 개를 겹치면 어떤 모양이든 나온다. **그리고 대개는 그렇게 나누는 것이
맞다** — 표의 혼동 행렬과 이미지의 혼동 행렬은 실제로 다른 화면이 된다(이미지 쪽은
틀린 사진을 칸마다 보여주는 것이 자연스럽다). 한 줄로 억지로 덮으려 할 때가
**사실은 두 기능이라는 신호**다.

**조합마다 값을 지정하는 매트릭스를 만들지 마라.** `Record<DataType, Record<TaskType,
boolean>>` 같은 것을 두면 축이 늘 때 칸이 곱으로 늘어 사람이 못 읽고, §9.2가 "축은
늘리지 말고 접는다"고 한 이유가 통째로 무너진다. 칸이 많아지는 쪽이 아니라 **줄이
많아지는 쪽으로 간다.**

#### 없는 것을 이름으로 말하지 않는다 (2026-08-07)

**등록부가 안 고른 것에 대해 화면이 한마디도 하지 않는다.** 결과 화면이 회귀에서
`회귀에는 혼동 행렬이 없습니다`라고 적고 있었는데, **그것이 §9.1 위반의 교과서적인
형태다** — 없다고 말하려면 그 화면이 혼동 행렬이라는 것을 알아야 하고, 아는 순간
`if (분류) 표 else 문장`이 화면에 생긴다. 등록부를 둔 이유가 통째로 사라지는 자리다.

증거는 축을 하나 늘려 보면 나온다. 이미지가 들어오는 날 그 문장은
`이미지에는 혼동 행렬이 없습니다`로 **한 줄 더 늘어난다.** 늘어나야 하는 것이
등록부의 줄인데 늘어나는 것이 화면의 분기라면, 그 문장은 처음부터 틀린 자리에 있었다.

> **패널이 0개면 그 자리는 없다. 왜 없는지 설명하지 않는다.**

§8.9의 "이유 없는 빈 자리는 고장으로 보인다"와 부딪히지 않는다. 그 규칙이 막는 것은
**있어야 할 것이 비어 있는 상태**이고, 여기는 애초에 그 자리가 없는 것이다 — 회귀 결과에
혼동 행렬 자리를 비워 두고 사과문을 붙이는 것이 아니라, 회귀 결과는 **지표와 설정으로
이미 완결되어 있다.** "이 모델에 쓴 설정"이 언제나 있으므로(§8.13) 카드가 통째로 비는
경우도 없다.

**이건 "안 담긴 것"과 다르다** (§9.5). 분류로 돌렸는데 혼동 행렬이 없는 파일은
**있어야 할 것이 없는** 상태라 할 말이 있다. 없는 것이 원래 없는 것과 같은 침묵으로
처리되면 안 되지만, 그 말도 화면이 아니라 그 패널이 해야 한다.

### 9.3 놓침은 사람이 아니라 컴파일러가 막는다

**축의 값이 늘어날 때 컴파일이 깨지지 않으면 그 등록부는 실패한 등록부다.**

`router/steps.ts`의 `FACTS_NOT_IN_TASK: Record<TaskType, …>`가 그 장치다. 군집화를
추가한 사람은 자기 칸을 채우지 않으면 빌드가 안 된다. **비어 있는 칸은 실수가 아니라
선언이다** — "군집화에는 빠지는 사실이 없다"고 사람이 명시적으로 적은 것이다.

**그런데 배열은 이걸 못 한다.** 이게 §9.2를 그대로 믿으면 안 되는 자리다.

```ts
taskTypes: readonly TaskType[]
```

여기에 `['classification', 'regression']`이 적혀 있고 나중에 `clustering`이 축에
추가되면, **컴파일은 아무 말도 안 한다.** 부분집합은 언제나 올바른 배열이기 때문이다.
`taskTypes: TASK_TYPES`라고 적어 둔 항목은 더 나쁘다 — **새 유형을 지원한다고 조용히
선언해 버린다.** 아무도 그 항목을 다시 보지 않는데 화면에는 나타난다.

그러므로 **축은 배열이 아니라 exhaustive Record로 적는다.**

```ts
interface Capability {
  readonly id: string
  readonly dataTypes: Readonly<Record<DataType, boolean>>
  readonly taskTypes: Readonly<Record<TaskType, boolean>>
  readonly panel: Component
}

// 결측치 채우기 — 표에서만, 과제 유형과는 무관하다
{
  id: 'missing-values',
  dataTypes: { tabular: true, image: false, audio: false, text: false },
  taskTypes: { classification: true, regression: true, clustering: true },
  panel: …,
}
```

길다. 길어서 얻는 것이 정확히 우리가 원하는 것이다 — **`DataType`에 `image`를 더하는
순간 모든 항목이 빨개지고, 넣는 사람이 항목마다 `true`/`false`를 판단해야 한다.**
배열이었다면 그 사람은 아무것도 안 했을 것이고, 이미지 데이터에서 결측치 채우기가
뜨거나 안 뜨는 것은 우연이 됐을 것이다.

**그런데 Record만으로는 부족하다. 타입 주석이 강제 장치의 나머지 절반이다**
(2026-08-06 tsc로 확인). 등록부 배열에 주석이 없으면 TypeScript는 리터럴을 그대로
추론하고, 축이 늘어도 **아무 말도 하지 않는다.**

```ts
export const X: readonly Capability[] = [ … ]   // 축이 늘면 깨진다
export const X = [ … ] as const                 // 조용하다. 강제가 없다
```

**등록부에 `as const`를 쓰지 마라.** 축의 리터럴 타입을 좁히려고 손이 가는 자리인데,
그 대가로 이 절 전체가 무의미해진다.

필터는 등록부가 감춘다(`capabilitiesFor(dataType, taskType)`). **부르는 쪽은 Record를
보지 않는다** — 장황함은 선언하는 자리에만 있고 쓰는 자리로 새지 않는다.

**타입으로 못 막는 것은 검사가 막는다.** 축 값의 존재 여부가 아니라 *조합의 결과*가
문제인 것들이다.

- **알고리즘이 하나라도 서는 조합에서 지표가 0개가 아닌가** — 학습이 되는데 볼 것이
  없는 상태만 금지한다. "모든 조합에서 0이 아니다"로 쓰면 안 된다. 이미지×회귀처럼
  **정당하게 아무것도 없는 조합**이 있고, 그런 조합까지 채우라고 하면 검사가 오탐으로
  울리다가 결국 꺼진다.

  **여기서 세는 것은 지표(`METRIC_DISPLAY`)이지 상세 패널이 아니다.** 혼동 행렬 같은
  패널은 **0개인 것이 정상인 조합이 있다** — 회귀가 그렇다. 맞고 틀림이 아니라 얼마나
  벗어났느냐이고, 그건 지표가 이미 전부 말했다. 패널 수를 세면 회귀에서 오탐이 난다.
- 등록부의 모든 `panel`이 **실제로 import되는가** — 파일을 지웠는데 줄이 남으면
  지연 로딩이라 런타임에서야 터진다.
- 등록부의 모든 `id`에 **로케일 키가 있는가** — `tests/i18n-usage.spec.ts`의 방식.

**타입과 검사 둘 다 없으면 등록부를 만들지 마라.** 규칙만 있고 강제가 없는 등록부는
규칙이 없는 것보다 나쁘다 — 지켜지고 있다고 믿게 만든다.

**이 규칙이 적용되는 등록부와 아닌 등록부가 있다.** 가르는 기준은 축이 항목의 **속성**인가,
항목을 **찾는 열쇠**인가다.

- **선언형 — Record로 쓴다.** 한 항목이 여러 축 값에 걸친다. `ml/algorithms.ts`,
  그리고 앞으로 만들 지표·전처리 등록부. 축이 늘면 **항목마다 판단이 필요하므로**
  컴파일이 깨져야 한다.
- **열쇠형 — 그대로 둔다.** 축 값 하나에 항목 하나가 대응한다. `data/kinds.ts`가
  그렇다(`dataType` → 그 종류를 다루는 판). 축에 `image`가 늘고 판이 아직 없으면
  **줄이 없는 것이 맞고**, 화면은 이미 "아직 못 다룬다"고 말한다. 여기에
  `Record<DataType, … | null>`을 씌우면 **없는 것에도 줄을 만들라**는 뜻이 되어
  §9.2.1과 정면으로 충돌한다.

열쇠형에서 놓치는 것(판을 만들고 등록을 잊는 것)은 타입이 못 잡는다. §9.3.2의 둘째
항목이고, 2층 검사가 맡는다.

> **지금 어긋나 있는 것 (2026-08-06).** `ml/algorithms.ts`는 선언형인데 축을 배열로
> 갖는다. 규칙을 세운 문서가 코드보다 늦게 나온 자리다. **새 등록부를 Record로 만들면서
> 이것도 함께 옮긴다** — 두 모양이 공존하면 다음 사람이 어느 쪽을 흉내 낼지 고민하고,
> 고민한 곳에서 갈라진다. `runtimes`도 같은 축이므로 함께 간다.

### 9.3.1 이 원칙을 앞으로 어떻게 관철하는가

강제는 세 층이고, **아래로 갈수록 약하다. 위층에서 막을 수 있는 것을 아래층에 미루지
마라.**

**1층 — 타입.** 축 값이 늘면 컴파일이 깨진다. 위의 Record 규칙, `Record<TaskType, …>`,
`Record<StepId, …>`가 여기 있다. **이 층을 무력화하는 목록은 다섯이다** —
`Partial<>`, `?`(옵셔널 필드), `[key: string]`, `as`/`as const`, 그리고
**타입 주석 생략.** 등록부에서 다섯 다 쓰지 마라. 마지막 둘은 "타입을 잘못 썼다"가
아니라 "타입을 안 썼다"라서 리뷰에서 제일 안 보인다.

**2층 — 검사.** 조합의 결과를 훑는다. `tests/ui-rules.spec.ts`(화면 규칙),
`tests/steps.spec.ts`(표 훑기)가 여기 있다. **검사기 자체를 먼저 검사한다** — 정규식이
아무것도 안 잡으면서 초록색이 되는 것이 제일 나쁜 상태다.

**3층 — 문서.** 이 절이다. **1·2층이 막는 것을 여기 또 쓰지 마라.** 문서에만 있는
규칙은 지켜지지 않는다고 가정하고, 지켜지지 않아도 되는 것만 여기 남긴다.

그리고 **새 축을 도입할 때가 유일하게 위험한 순간이다.** 축이 하나 늘면 기존 등록부
전부가 그 축에 대해 아무 말도 안 하는 상태가 된다. 그때 할 일은 정해져 있다.

1. 축을 `Record<새축, boolean>`으로 **모든 등록부에 동시에 추가한다.** 한 등록부만 먼저
   고치고 나머지를 나중에 하면, 그 사이에 축은 있는데 강제가 없는 상태가 된다.
2. 컴파일 에러를 **하나도 남김없이 손으로 판단한다.** 일괄 치환하지 마라 —
   일괄 치환은 이 층 전체를 무의미하게 만든다.
3. 검사를 먼저 돌려 **빨간 줄을 보고 나서** 고친다. 초록색으로 시작하면 검사가 그 축을
   안 보고 있다는 뜻이다.

### 9.3.2 이 장치가 못 막는 것

**적어 두지 않으면 지켜지고 있다고 믿게 된다** (`docs/i18n.md`가 같은 절을 갖는 이유다).
셋은 사람이 봐야 한다.

- **`true`/`false`를 잘못 판단한 것.** 타입은 칸을 채우라고만 하고, 채운 값이 맞는지는
  모른다. 이미지에서 결측치 채우기를 `true`로 두면 아무것도 울리지 않는다.
- **등록 자체를 잊은 것.** 새 지표 컴포넌트를 만들고 등록부에 안 넣으면, 존재하지 않는
  기능이 되어 조용히 사라진다. **없는 것을 못 잡는 것이 등록부 방식의 근본 한계다.**
  그래서 등록부 파일과 컴포넌트 디렉터리를 대조하는 검사가 2층에 있어야 한다.
- **화면이 등록부를 우회하는 것.** 컴포넌트가 등록부를 안 거치고 직접 그리면 타입은
  만족스럽다. 이것만은 2층 정규식(§10.3의 `v-if` 규칙)이 부분적으로 잡는다.

### 9.4 조합이 비면 화면이 그렇게 말한다

필터를 지나고 아무것도 안 남는 조합이 반드시 생긴다(이미지 + 회귀 같은 것). 그때
**빈 화면을 보여주지 마라.** 학생은 그것을 고장으로 읽는다.

`ml/algorithms.ts`가 이미 답을 갖고 있다 — **비활성화하되 숨기지 않고, 왜 못 쓰는지
이유를 함께 준다.** 이유의 우선순위도 같다: **데이터 타입 > 과제 유형 > 실행 위치.**
더 근본적인 것이 먼저다. 이미지에 회귀를 고른 학생에게 "서버가 없습니다"라고
답하면 안 된다.

지표 패널과 전처리 단계도 같다. 조합에 맞는 것이 하나도 없으면 **그 자리에 이유가 뜬다.**

### 9.5 축이 맞아도 담겨 있지 않을 수 있다 (2026-08-06)

**등록부의 축은 "이 조합에서 성립하는가"만 답한다.** 그런데 화면이 실제로 그릴 수 있느냐는
한 겹 더 있다 — 분류 실행인데 혼동 행렬이 안 담긴 `.mlpx`가 있다(옛 파일, 예산에서
밀린 것 → `mlpx-spec.md` §4.2).

그래서 **패널 항목은 축과 함께 "이 실행에 담겨 있는가"를 자기 옆에 갖는다.** 화면이
`run.confusionMatrix`를 직접 보면 §9.1을 어긴 것이다 — 혼동 행렬이 어느 필드에 담기는지는
혼동 행렬의 앎이지 결과 화면의 앎이 아니다.

**축과 이 판정을 한 필드로 합치지 마라.** 축은 등록부에 적힌 정적 사실이고 이것은 파일마다
다른 값이다. 합치면 "이 조합에서 원래 없는 것"과 "있어야 하는데 안 담긴 것"이 구별되지
않고, 그 둘은 화면이 할 말이 다르다.

## 10. 잠금은 gate 하나에서 나온다 (2026-08-06)

`[학습]` 버튼이 눌리려면 데이터가 있어야 하고, 타깃과 특성이 정해져야 하고, 과제 유형을
골라야 하고, 알고리즘을 하나 이상 골라야 하고, 그 알고리즘이 지금 실행 위치에서
돌아야 하고, 분리 비율이 성립해야 한다. **조건은 앞으로 줄지 않는다.**

### 10.1 조건을 prop으로 내리지 마라

`:disabled="!hasData || !hasTarget || !hasFeatures || …"`는 다음 셋을 동시에 만든다.

1. **조건을 하나 더할 때 고쳐야 할 파일이 늘어난다.** 버튼까지 내려가는 컴포넌트의
   시그니처가 전부 바뀐다. 놓침은 사라지지 않고 **자리만 옮겨진다.**
2. **테스트할 수 없다.** 조건 하나를 확인하려고 화면 전체를 마운트해야 하면 아무도
   그 조건을 테스트하지 않는다 (§8.3).
3. **학생이 왜 못 누르는지 모른다.** 이게 제일 나쁘다. 회색 버튼은 이유 없이는
   고장으로 보인다 (§9.4와 같은 이야기다).

### 10.2 규칙: 판정은 순수 함수가, 화면은 결과만

> **잠기는 것에는 gate 함수가 하나 있고, 그 함수는 boolean이 아니라 이유 목록을 반환한다.**

```ts
/** 비어 있으면 눌린다. 아니면 첫 번째 이유가 버튼 옆에 문장으로 뜬다. */
function trainGate(facts: ProjectFacts, selection: SelectionResult, runtime: RuntimeContext)
  : readonly BlockReason[]
```

- **컴포넌트 밖의 순수 함수다.** `router/steps.ts`의 `isStepUnlocked`, `ml/selection.ts`의
  issue/caution이 이미 그 물건이다. **새 개념을 만들지 말고 그 자리로 가져가라** —
  같은 판정이 두 벌이 되면 "체크는 다 됐는데 버튼이 잠겨 있다"가 생기고, 그건 학생이
  고칠 방법이 없는 고장이다.
- **화면이 받는 prop은 gate 결과 하나다.** 조건이 열둘이 되어도 시그니처는 그대로다.
- **이유는 코드다. 문장이 아니다** (CLAUDE.md §1.4와 같은 이유). 백엔드 응답과 같은
  모양을 쓴다 — `{ code: string; params?: Record<string, string | number> }`. 화면이
  `t(\`block.${code}\`, params)`로 문장을 만든다. **사용자 데이터는 문장 끝 괄호로 뺀다**
  (§3 규칙 4) — 열 이름이 문장 가운데 들어가면 조사가 앞 글자에 따라 갈린다.
- **우선순위가 있다.** 근본적인 것이 먼저다 — 데이터가 없으면 "알고리즘을 고르세요"라고
  말하지 않는다.

**아직 `trainGate`는 없다 (2026-08-07).** 만들지 않았고, 그것이 맞다.

세어 보니 `[학습]` 버튼이 지금 보는 조건은 **하나뿐이다** — 담은 모델이 0개인가
(`nothingToTrain`). 나머지는 이미 다른 자리에 흩어져 있고 **그게 옳은 자리다.**

- 데이터·타깃·특성이 없으면 **단계가 잠겨 이 화면에 못 온다** (`router/steps.ts`).
- 고른 모델이 지금 조합에서 안 서면 **학습이 돌고 run마다 사유가 남는다**
  (`ml/experiment.ts`). 실험 하나가 통째로 실패하는 일은 없다 (`mlpx-spec.md` §4.1).

즉 지금 코드는 이미 §10.2를 만족한다 — 조건 하나, 이유 한 줄. **구현이 하나뿐인 계약을
미리 설계하지 마라**(§9.2.1과 같은 이유). 두 번째 조건이 생기는 날 gate를 만들고,
그날을 §10.3의 검사가 알려 준다.

### 10.3 검사가 강제한다

`tests/ui-rules.spec.ts`에 규칙을 더한다. **사람이 지키길 기대하지 않는다.**

- **`:disabled` 바인딩에 `&&`나 `||`가 있으면 위반이다.** 막아야 할 죄는 **조합**이다.
  `!canSubmit`이나 `gate.length > 0`처럼 **한 군데를 가리키는 표현은 통과시킨다** —
  다이얼로그 확인 버튼 같은 국소 조건까지 잡으면 검사가 성가셔지고, 성가신 검사는
  꺼진다. 조합이 필요해진 순간이 gate 함수를 만들 순간이다.
- **화면 코드가 `dataType`·`taskType`을 문자열 리터럴과 비교하면 위반이다** (§9.1).
  **`=== undefined`는 뺀다** — 그건 "어느 종류인가"가 아니라 "아직 안 골랐는가"이고,
  안 고른 상태는 등록부가 답할 수 있는 것이 아니다. 잡힌 것을 옮길 자리는 화면 밖의
  순수 함수다 (`ml/predict.ts`의 `answerTone`이 그렇게 옮겨졌다).
- 검사기 자체를 먼저 검사한다 — 정규식이 아무것도 안 잡으면서 초록색이 되는 것이
  제일 나쁜 상태다. 기존 규칙들이 `violations`/`allowed` 예시를 갖는 이유가 그것이다.

### 10.4 새 기능을 넣는 사람이 자문할 것

> **"이걸 의존하는 요소는 무엇인가?"**

이 질문에 사람이 답하게 두면 언젠가 틀린다. 그래서 답이 **한 군데에 모여 있어야** 한다.

- 새 **능력**(알고리즘·지표·전처리 단계)을 넣는가 → §9의 등록부에 줄을 더한다.
  화면은 손대지 않는다. 손대야 한다면 등록부가 부족한 것이다.
- 새 **조건**(무언가가 준비되어야 다음이 열리는 것)을 넣는가 → `ProjectFacts`에 사실을
  더하고 gate에 넣는다. **그 사실이 할 일인지 결과인지 정해야 한다** (§8.10,
  `DERIVED_FACTS`). 어느 쪽도 아니면 검사가 막는다.
- 새 **축의 값**(데이터 타입·과제 유형)을 넣는가 → **컴파일이 깨지는 곳을 전부 따라가면
  그것이 의존 목록이다.** 안 깨졌다면 §9.3이 안 지켜진 등록부가 어딘가 있다는 뜻이고,
  그걸 찾는 것이 그 작업의 첫 번째 할 일이다.
