### 3-1. scikit-learn 엔진의 교실 실측 — 필요 시점: 엔진을 붙일 때
엔진 선택 자체는 결정됐다(아래). 남은 것은 **학교 PC에서 시동이 몇 초인가**다.
개발 PC에서 15.4초였으므로 학교 PC는 그보다 느리다. 40초면 "고급 선택지"로 성립하고
3분이면 성립하지 않는다 — 그때는 상태 패널의 문구와 안내 방식이 달라져야 한다.

학교 회선에서 26MB가 30명에게 동시에 내려갈 때의 시간도 함께 잰다.
**측정은 sklearn을 실제로 붙이는 시점에 한다.** 그전에 재봐야 결정이 바뀌지 않는다.

**휴대폰도 같이 잰다**(아래 "모바일에서도 동작한다"). 엔진 선택이 바뀌지는 않는다 —
학생이 명시적으로 켜는 선택지이고 못 켜면 순수 JS로 도니까. 정해야 하는 것은
**상태 패널이 기기를 보고 말을 바꿔야 하는가**다. LTE로 26MB를 받게 두는 것은
학생 요금제를 쓰는 일이기도 하다.

### ~~3-2. 배색 선택을 어디에 저장하나~~ — 결정됨 (2026-08-05)

**`localStorage`에 저장한다.** 언어는 IndexedDB에 두지만(§1.2, `i18n.ts`) 배색에는
언어에 없는 제약이 있다 — **첫 그림이 그려지기 전에 답이 나와야 한다.** IndexedDB는
비동기라 읽는 동안 화면이 이미 떠 버리고, 어두운 배색을 고른 학생이 새로 고칠 때마다
흰 화면을 한 번씩 본다. 언어는 늦게 바뀌어도 글자만 바뀌지만 **배색은 화면 전체가
번쩍인다.** 저장 수단이 둘이 되는 대가를 치른다.

**상태는 둘뿐이다 — 라이트 모드와 다크 모드.** "기기 설정을 따름"이라는 세 번째
상태는 두지 않았다. 중학생에게 설명하기 어렵고 아이콘 하나로 표현할 수도 없다.
저장된 값이 없을 때만 기기 설정을 따르고, 한 번 고르면 그 뒤로는 따라가지 않는다.

**CSS는 선택자가 하나다.** `@media (prefers-color-scheme: dark)`와 `[data-theme='dark']`에
같은 값을 두 벌 적으면 한쪽만 고쳤을 때 배색이 갈린다. 그래서 **기기 설정을 읽는 일을
`theme.ts`가 하고 `styles/dark.css`는 결과만 본다.**

남은 것 하나: `initTheme()`이 `app.mount()`보다 먼저 돌지만 **HTML 파싱 시점에는 아직
아니다.** 지금은 깜빡임이 관측되지 않았는데, 확실히 없애려면 `index.html`에 인라인
스크립트를 두어 CSS보다 먼저 `data-theme`을 채워야 한다. 그러면 판정 로직이 두 군데가
되므로, **깜빡임이 실제로 보이는 기기가 나오기 전에는 하지 않는다.**

### 23. 포트폴리오는 글상자가 아니라 **게시글이다** — 필요 시점: 포트폴리오 화면 착수 전

**§8이 그리는 것보다 크다** (2026-08-06). 사용자가 원하는 모양이 둘 더 있고, 둘 다
포맷과 화면을 함께 건드리므로 **정하기 전에는 착수하지 않는다.**

1. **학생이 이미지 등을 첨부한다.** 지금 `portfolio.answers`는 문항 id -> 문자열이다.
   첨부가 들어오면 zip에 엔트리가 생기고, 그러면 **크기 예산(§4.2)의 경쟁자가 하나
   늘어난다** — 모델과 데이터셋과 첨부가 같은 파일 안에서 자리를 다툰다. 본문에서
   그림을 어떻게 가리킬지(마크다운 경로? id?), 무엇을 받을지, 하나에 얼마까지인지가
   전부 열려 있다. **#4(이미지 데이터의 `.mlpx` 포함 방식)와 같은 자리를 건드리지만
   다른 물건이다** — 저쪽은 훈련 데이터이고 이쪽은 학생이 쓴 글의 삽화다.
2. **교사가 자기 질문지를 만들어 나눠 준다.** 파일 안의 커스텀 문항(§8의
   `template.sections`)은 이미 포맷이 견디는데, **그 템플릿이 어디서 오는가**가 없다.
   프런트엔드에 내장할 수 없다 — 교사마다 다르고, 우리는 그것을 배포하지 않는다
   (CLAUDE.md §1.1). 후보는 "교사가 빈 프로젝트를 만들어 `.mlpx`로 나눠 준다"이고
   그러면 새 형식이 안 늘지만, **파생 표시(§7.3의 `derivedFrom`)가 교사 배포본에도
   걸린다**는 문제가 따라온다 — 학생 전원이 "남의 파일에서 시작함"으로 표시된다.

기본 템플릿과 기본 문항은 지금 것을 쓴다. 바뀌는 것은 **그 위에 무엇을 얹을 수
있는가**다.

### 22. 행 랜덤 샘플링 — 필요 시점: 곧 (전처리 화면에 붙는다)

**어떤 모델은 행이 많으면 교실에서 못 쓴다.** 랜덤포레스트 100그루는 1600행에서 39초,
5000행에서 약 7분이다(#19). 학생이 **일부만 뽑아 빠르게 돌려 보고** 감을 잡을 수 있어야
한다. 그리고 **뽑히지 않은 행은 나중에 예측 화면에서 쓴다** — 모델이 한 번도 못 본 줄로
시험해 보는 것은 이 도구가 줄 수 있는 좋은 장면이다.

**정형 데이터에만 있다.** 이미지·음성의 전처리는 성질이 달라서 따로 만든다.

이미 정해진 것에서 따라 나오는 제약들:

- **거는 자리는 `usableRows` 다음, `holdoutSplit` 앞이다.** 뽑힌 행만 분할되고,
  그래야 `trainIndices`/`testIndices`가 지금 뜻 그대로 유지된다.
- **빠진 행 목록을 파일에 새로 적지 않는다.** `trainIndices ∪ testIndices`의 여집합이
  곧 그것이다. 같은 값을 두 곳에 두면 어긋났을 때 판정할 근거가 없다
  (`mlpx-spec.md` §3의 `randomState`와 같은 규칙).
- **씨앗도 새로 만들지 않는다.** `split.randomState` 하나를 쓴다. 씨앗이 둘이 되면
  재현 대조가 무엇을 믿어야 하는지 모르게 된다.
- **`settings`에 필드가 하나 는다.** 선택 항목이므로 읽기 호환이고 `formatVersion`은
  안 오른다. 실험 스냅샷에도 들어가야 재현이 성립한다.
- **화면이 데이터 종류마다 갈라져야 한다.** 지금 전처리 화면은 `data/kinds.ts` 등록부를
  안 지나고 표를 곧장 그린다. `if (dataType === 'tabular')`를 만들지 않으려면 데이터
  화면처럼 종류별 판으로 나눠야 하고, **이 항목의 진짜 구조 비용이 거기 있다.**

정해야 할 것 셋.

1. **크기를 비율로 줄 것인가 행 수로 줄 것인가.** 비율은 데이터가 바뀌어도 뜻이 유지되고,
   행 수는 "몇 초 걸릴까"와 직접 이어진다(#13의 예상 시간과 같은 축이다).
2. **샘플링도 층화할 것인가.** 안 하면 희소한 클래스가 통째로 빠져 `SPLIT_STRATIFY_IMPOSSIBLE`이
   그다음 단계에서 터진다. 층화 설정이 이미 분할에 있으므로 **그 값을 따라가는 것**이
   후보다 — 손잡이를 둘로 늘리지 않는다.
3. **예측 화면이 그 행들을 어떻게 쓰는가.** "학습에 안 쓰인 줄"에는 샘플링에서 빠진 것과
   결측 때문에 빠진 것이 섞인다. 둘을 갈라 보여줄지, 그냥 "모델이 못 본 줄"로 묶을지.

**V4 전체가 이 하나에 걸려 있다.** 안 정하면 데이터 화면·전처리·지표·모델 형식이

**지금 상태.** 프런트엔드 의존성에 딥러닝 라이브러리가 하나도 없다 — `ml-cart`,
`ml-logistic-regression`, `ml-random-forest`, `ml-regression-multivariate-linear`,
그리고 벤더링한 SMO가 전부다. 표 데이터용 고전 알고리즘뿐이다.

**무엇이 걸리는가.**

- **CLAUDE.md §1.1** — 무거운 것을 넣을지 판단하는 기준은 **저사양 학교 PC와 휴대폰**이다.

**답해야 할 것.** 전이학습(고정된 특징 추출기 + 마지막 층만 학습)으로 갈 것인가,
아니면 아주 작은 모델을 처음부터 학습시킬 것인가. 전자면 특징 추출기를 무엇으로 하고
그 가중치를 언제 내려받게 할 것인가(§3.3의 "로딩 시점을 상태 점검이 쥔다"와 같은 문제다).

**실측 없이 정하지 마라.** 교실 PC와 휴대폰에서 재는 것이 이 결정의 유일한 근거다

따로 재서 나란히 준다).

### 7. IndexedDB 할당량 정책 — 필요 시점: 저장 화면
**`estimate()` 사전 검사는 결정됨(아래).** 남은 것은 둘이다.

- `persist()`를 언제 부를 것인가. 파이어폭스는 사용자에게 권한 팝업을 띄운다.
  앱을 켜자마자 뜨면 수업 시작을 거기서 까먹는다. 부른다면 "저장"을 처음 누른 순간이어야 한다.
- 프로젝트 수 상한을 둘 것인가. 현재 방향은 상한 없이 목록에 프로젝트별 용량을 보여주고
  학생이 지우게 하는 것 — 상한에 걸려 저장이 실패하는 것보다 낫다.
- **iOS Safari는 저장소를 지운다.** `persist()` 없이 둔 IndexedDB는 일정 기간 방문이
  없으면 통째로 삭제될 수 있다. 모바일에서도 도는 이상(아래 "모바일에서도 동작한다")
  이건 가정이 아니라 실제 경로다. **§1.2 "브라우저가 저장소다"가 여기서 가장 약하다** —
  수행평가 제출물이 조용히 사라지는 것은 이 프로젝트가 낼 수 있는 최악의 실패에 가깝다.
  `persist()` 타이밍 결정이 이것 때문에 더 무거워졌고, ".mlpx로 내보내라"는 안내를
  어디에 둘지도 같이 정해야 한다.
- **같은 프로젝트를 두 탭에서 여는 것은 막기로 했다** → 아래 "프로젝트는 한 번에 하나만
  연다". 남은 것은 구현 수단(`Web Locks` / `BroadcastChannel`)을 고르는 것뿐이고,
  화면 동작은 정해졌다.

### 9. 세션 상한값 — 필요 시점: 백엔드 구현(4단계)
세션이 WebSocket 연결 수명만큼 살게 되면서 디스크 점유가 "작업 중"에서 "접속 중"으로 늘었다.
30명 학급 × 50MB = 1.5GB가 상주한다. 아래 값을 정해야 한다 (전부 환경 변수).

| 항목 | 제안 기본값 | 환경 변수(안) |
|---|---|---|
| 세션 유휴 타임아웃 | 15분 | `SESSION_IDLE_TIMEOUT_SECONDS` |
| heartbeat 간격 / 무응답 허용 | 30초 / 3회 | `WS_PING_INTERVAL_SECONDS`, `WS_PING_MAX_MISSED` |
| 동시 세션 수 상한 | 미정 (디스크에서 역산) | `MAX_CONCURRENT_SESSIONS` |
| 세션당 디스크 상한 | 업로드 상한과 동일 | `MAX_SESSION_DISK_MB` |
| 고아 디렉터리 정리 기준 | 마지막 접근 후 30분 | `ORPHAN_SWEEP_AFTER_SECONDS` |

상한에 걸리면 새 세션을 `SERVER_BUSY`로 거절한다. 접속 중인 세션을 죽이지 마라.

### 10. 배포 패키징 — 남은 부분 (2경로는 결정됨)
**두 경로로 나간다는 것은 정해졌다**(아래 결정됨). 남은 것은 도커 쪽 구성이다.

확정할 것: 프런트와 백엔드를 **한 컨테이너의 같은 오리진**에서 서빙하는 방법(FastAPI가
정적 파일도 서빙할지, nginx를 앞에 둘지), WebSocket 프록시 타임아웃,
작업 디렉터리를 tmpfs로 올릴지.

`SIGNING_SECRET`은 항목에서 빠졌다 — 서명을 만들지 않는다.

#### 10-1. 배포 파이프라인의 모양 — **프런트엔드는 확정됐다 (2026-08-06)**

방향은 2026-08-05에 정해 뒀고, 아래 "걸릴 것 둘"을 2026-08-06에 답했다.
**백엔드(도커) 쪽은 여전히 미결이다** — 릴리스 주기가 다르므로 여기서 함께 정하지 않는다.

| | 무엇을 | 어디로 |
|---|---|---|
| 랜딩 소개 | 별도 저장소(`teacher-utility-kit`) | `luminousky.com/teacher-utility-kit/ml-playgrounds` |
| **앱 본체** | 이 저장소의 `frontend/dist` | `luminousky.com/ml-playgrounds` |
| 백엔드 | 멀티 플랫폼 도커 이미지(arm 포함) | 도커 허브 |

- **빌드 산출물을 다른 저장소로 옮기지 않는다.** 랜딩과 앱을 한 저장소에 몰면 배포마다
  저장소를 넘나들어야 해서 사실상 굴러가지 않는다. 랜딩은 소개 문서로 두고 앱은
  이 저장소의 Pages로 따로 나간다.
- `main`은 작업 소스 전용이고, **저장소에 빌드 산출물이 들어가지 않는다.** 처음에는
  `gh-page` 브랜치에 올리는 것으로 적었으나 2026-08-06에 뒤집었다 — 아래 2번을 보라.
- **두 파이프라인은 별개다.** 프런트(정적)와 백엔드(도커)는 릴리스 주기가 다르다.
- **둘 다 `workflow_dispatch` 수동 실행이다.** `main`에 푸시할 때마다 나가지 않는다 —
  수업 중에 원치 않는 배포가 나가는 것이 이 프로젝트에서는 실제 사고다.

##### 1. `base`는 **`'./'`(상대 경로)**다 — 두 경로의 충돌이 사라진다

문제는 이렇게 적혀 있었다: 프로젝트 페이지는 하위 경로에서 서빙되는데 도커 자가호스팅은
루트에서 서빙하므로 **두 경로의 base가 다르고**, 그것이 "빌드 산출물은 하나다"(CLAUDE.md
§2)와 부딪히는 유일한 지점이라고.

**상대 base면 부딪히지 않는다.** 같은 `dist/`가 어느 하위 경로에서도, 루트에서도 그대로
돈다. `/ml-playgrounds/`를 박아 넣는 것과 달리 **주소가 바뀌어도 다시 빌드하지 않는다.**

이게 되는 이유는 이미 갖춰져 있었다.

- **라우터가 해시 모드다**(`router/index.ts`). Pages SPA 배포에서 제일 흔한 함정인
  `404.html` 폴백이 **필요 없다.** history 모드였으면 base와 재작성 규칙이 함께 얽혔다.
- 워커가 `new URL('…', import.meta.url)`로 잡히므로 모듈 위치 기준으로 따라온다.
- 소스 어디에서도 `import.meta.env.BASE_URL`을 읽지 않는다.

**실측으로 확인했다** (2026-08-06, `vite build --base=./`): `index.html`의 자산 참조와
CSS의 글꼴 참조가 전부 `./`로 나오고, 빌드 산출물 전체에 절대 경로 `/assets/`가 하나도
남지 않는다.

주소는 `luminousky.com/ml-playgrounds/`다. 커스텀 도메인이 **사용자 사이트 저장소**
(`itmir913.github.io`)에 걸려 있어서 이 저장소는 그 하위 경로로 나간다.

##### 2. **브랜치를 쓰지 않는다** — Actions 아티팩트 배포(`actions/deploy-pages`)

`gh-page` 브랜치 force push를 버린다. 이유는 셋이다.

- **아무도 쓰지 않는 브랜치가 남는다.** 그 자체로 저장소를 읽는 사람을 헷갈리게 한다.
- **force push 이력이 저장소에 쌓인다.** 빌드 산출물의 세대가 전부 객체로 남는다.
- **워크플로에 `contents: write`를 줘야 한다.** 배포하겠다고 소스를 고칠 수 있는 토큰을
  발급하는 셈이다. 아티팩트 배포는 `contents: read`면 된다.

`upload-pages-artifact` → `deploy-pages`로 간다. Jekyll을 아예 안 태우므로 `.nojekyll`도
필요 없다. **저장소 설정에서 Pages Source를 `GitHub Actions`로 한 번 바꿔야 한다** —
예전에 브랜치 배포를 쓴 저장소는 `Deploy from a branch`로 잡혀 있다.

##### 3. 취소는 **빌드만** 한다 — 배포는 끝까지 둔다

같은 워크플로에 취소 규칙 하나를 걸면 안 된다. Pages 배포가 중간에 끊기면 사이트가 깨진
상태로 남을 수 있다. 잡마다 다르게 건다.

| 잡 | 그룹 | `cancel-in-progress` |
|---|---|---|
| build | ref별 | **true** — 나중 실행이 이긴다 |
| deploy | 저장소 하나 | **false** — 끝날 때까지 둔다 |

##### 4. 배포 잡이 **`npm run ci` 전체를 다시 돌린다**

lint·prettier·typecheck·vitest·build를 다 거친 뒤에만 나간다. `ci.yml`이 같은 커밋을 이미
검사하지만 **그 성공을 배포의 전제로 걸지 않는다** — 두 워크플로를 엮으면 수동 실행
경로에서 조건이 흐려지고, 그 복잡도가 아끼는 2분보다 비싸다. **배포 워크플로 하나만
읽어도 무엇을 통과해야 나가는지 알 수 있어야 한다.**

**"그 커밋의 CI가 통과했는지 조회하면 되지 않나"는 기각했다** (2026-08-06). 조회 자체는
된다 — `gh api repos/{repo}/actions/workflows/ci.yml/runs?head_sha=$SHA`에 `actions: read`
권한이면 충분하다. 그런데 아끼는 것이 거의 없고 새 실패가 하나 생긴다.

- **`dist/`는 어차피 배포 잡이 빌드해야 한다.** `ci.yml`이 산출물을 아티팩트로 올리지
  않으므로, CI가 통과했든 아니든 `npm ci`와 `vite build`는 그대로 낸다. 줄여서 아끼는
  것은 eslint·prettier·vitest뿐이고 **1분 남짓**이다(실측: vitest 38초, eslint 10초).
- **푸시하고 바로 디스패치하면 CI가 `in_progress`라 거부된다.** "깨져서"가 아니라 "아직
  안 끝나서"인데 배포 로그만 보면 구분이 안 간다. `main`이 아닌 ref에서 디스패치하면
  CI 실행 자체가 없어 항상 거부된다(`ci.yml`은 `push: branches: [main]`이다).

**대가는 알고 간다** — `ci.yml`은 `scripts/check_locales.py`(로케일 ↔ 백엔드 에러 코드
계약)와 백엔드 잡도 돌리는데 그 둘이 배포 게이트에서 빠진다. 공식 배포에는 서버가 없어
영향이 작지만(CLAUDE.md §1.1) 자가호스팅 경로에서는 실재한다. 걸리면 CI 조회를 붙이는
것보다 **배포 잡에 그 한 줄을 나란히 넣는 편이 단순하다.**

##### 5. 트리거는 `workflow_dispatch` **전용을 유지한다**

위에 적어 둔 근거가 그대로 산다 — 수업 중에 원치 않는 배포가 나가는 것이 이 프로젝트에서는
실제 사고다. `main` 푸시로는 배포되지 않는다. 푸시가 깨진 것을 잡는 일은 `ci.yml`이 한다.

##### 6. **이 배포는 아직 실기 점검용이다** (2026-08-06)

주소는 살아 있지만 아무에게도 알리지 않는다. 그래서 **"밖에 학생 파일이 하나도 없다"는
전제가 아직 유효하고**, 그 전제에 기대어 미뤄 둔 것들도 그대로다 — `formatVersion`을 안
올리는 것, 마이그레이션을 안 만드는 것(위 "전처리도 분할도 끌 수 있다", "학습용과 평가용
파일이 따로일 수 있다").

**공개하는 순간 그 전제가 죽는다.** 그때 되돌려야 하는 것은 이 문서 여러 곳의 "배포
전이라" 근거 전부다. 공개는 별도의 결정으로 다룬다.

##### 남은 것 — 실기 확인 목록

배포본이 서면 브라우저에서 직접 볼 것들이다. 정적 분석으로는 못 답한다.

- 엑셀 지연 로딩(ExcelJS/SheetJS)이 하위 경로에서 내려오는가
- 워커 학습이 도는가
- **Pyodide(scikit-learn 런타임)가 Pages에서 뜨는가.** Pages는 응답 헤더를 못 정한다.
- **모바일 Safari ↔ 윈도우 Chrome**에서 같은 데이터의 지표가 갈리는지(#12의 실측)

### 12. 재실행 대조의 허용 오차 — 필요 시점: 교사용 화면
**엔진을 넘지 않는다는 규칙은 결정됐다**(아래). 남은 것은 같은 엔진 안에서의 오차다.
같은 엔진·같은 `randomState`라도 CPU와 스레드 수에 따라 마지막 자리가 갈릴 수 있다.

확정할 것: 지표별 허용 오차, 학급 단위 일괄 대조 여부.

**대조 자체는 섰다 (2026-08-06).** `ml/reproduce.ts`가 파일의 설정과 분할로 다시 돌려
**지표마다의 차이**를 내놓는다. 거기서 하지 않는 것이 정확히 이 항목이다 — 지금은 차이가
0인지만 보고, 얼마까지 봐 줄지는 화면과 함께 정한다. **임의의 숫자를 코드에 먼저 박으면
그 숫자가 곧 규칙이 되고 실측으로 정할 자리가 사라진다.**
→ `architecture.md` §3.2, §7.5

**같은 `kind`·`version` 안에서도 브라우저가 다르면 지표가 이산 점프할 수 있다 (가설).**
ECMAScript는 `Math.exp`/`Math.log`의 정확한 반올림을 요구하지 않아 JS 엔진마다 마지막
자리가 다를 수 있고, 그 차이를 **누적하는** 알고리즘이 둘 있다 — 로지스틱 회귀와
가우시안 나이브 베이즈(pdf의 exp/log). 트리·KNN·랜덤포레스트는 비교 연산과 시드 RNG라
해당 없다.

**로지스틱 쪽은 1단계-B에서 위험이 줄었다 (2026-08-11에 고쳐 적는다).** 원래 이 자리에는
"경사하강 1000스텝의 시그모이드"라고 적혀 있었는데 그 구현은 사라졌다. 지금은 L2 규제로
**최적점이 유일하고** 기울기가 `tol` 아래로 내려가면 멈추므로, 고정 스텝을 끝까지 걷던
옛 구현보다 도착점이 ULP 잡음에 훨씬 둔하다. 다만 **없어진 것은 아니다** — ULP 차이가
선탐색과 반복 수를 바꿀 수 있고, **`maxIter`에 걸리는 자리에서는 애초에 도착점이 경로에
달려 있다**(상한 근처가 그렇다, #13). 그래서 실측 대상에서 빼지 않는다. 예측 라벨이 하나 뒤집히면 정확도는 1/n만큼 **점프**하므로
"마지막 자리 오차"라는 위 가정으로는 못 덮는다.

**아직 실측이 없다. 그래서 가설이다.** ULP 차이가 결정 경계를 실제로 넘는지는 데이터의
마진 분포에 달렸고, 아무도 재지 않았다. 이 저장소는 엔진 간 차이를 붓꽃 실측 표로 확정하고
나서야 결정한 전례가 있다(아래 "브라우저 학습 엔진은 둘 다 간다"). 같은 기준을 적용한다.

**실측 방법을 미리 정해 둔다** — 배포 단계의 실기 확인에 얹는다(#10-1, "모바일에서도
동작한다").

- 지표 차이가 아니라 **어느 행이 뒤집혔는지**를 본다. 지표만 보면 상쇄로 가려진다.
- 조합은 실제 교실 짝이어야 한다: **모바일 Safari ↔ 윈도우 Chrome.**
- 대상은 LR·NB. 나머지는 볼 필요가 없다.

**뒤집힘이 실재로 확인됐을 때의 선택지 둘. 지금 고르지 않는다.**

1. **허용 오차를 "뒤집힌 예측 수"로 정의한다.** 정면으로 다루는 방법이지만 **작은 n에서
   변조 탐지를 깎는다** — 예측 1개를 허용하면 붓꽃 30행에서 0.9000 → 0.9333이 정확히 그
   1개다(위 실측 표에 있는 숫자 쌍이다). 해시 층이 `runs.json` 편집을 먼저 잡지만, 해시를
   재계산한 뒤 지표를 한 칸 올리는 조작은 세 층을 다 통과한다.
2. **LR·NB의 대조 결과에 "참고용" 등급을 표기한다.** 오차를 넓히지 않고 신뢰도를 낮춘다.

**하드 게이트(브라우저가 다르면 대조 불가로 강등)는 하지 않는다.** "폰 사파리 학생 /
학교 크롬 교사"가 가장 흔한 조합이라 LR·NB 대조가 상시 불가가 되고, **주장을 검사하는
유일한 층이 가장 필요한 자리에서 죽는다.** 그리고 `engine`에 런타임 필드를 지금 넣을
이유도 없다 — `engineSchema`는 loose이고 구버전 앱이 새 필드를 무시했을 때의 동작이
지금과 같으므로, 필요해지면 그때 넣어도 `formatVersion`이 안 오른다.


### 13. 브라우저 학습 행 수 상한 — **알고리즘별 값은 정해졌다 (2026-08-07).** 남은 것은 예상 시간 표시
알고리즘마다 값을 쟀고 등록부에 넣었다 — 아래 "쟀다 (2026-08-07)"가 그것이다.
**아직 안 한 것은 "막지 않고 예상 시간을 보여준다"의 구현이다** (2026-08-05 결정, 아래).
서버 상한(`MAX_ROWS`)과는 무관하다.

**엔진마다 다를 수 있다.** 순수 JS와 WASM은 메모리 모형이 다르고, ml.js의
랜덤포레스트는 붓꽃에서도 235ms였다. 상한이 하나로 충분한지부터 확인해야 한다.

**알고리즘마다도 다르다 — 이건 이제 추측이 아니다 (2026-08-05).** #19를 재다가 학교 보급
노트북에서 같이 나온 값이다. 같은 5000행에서 결정트리는 12초, 랜덤포레스트 100그루는
약 7분이다. 행이 두 배가 될 때마다 약 3.5배씩 늘어난다(`ml-cart`의 분할 탐색이 노드마다
O(특성 × 행²)이다). **랜덤포레스트가 45분 수업에서 쓸 만한 구간은 1000행 안쪽이다.**

**막지 않는다. 예상 시간을 보여준다. (2026-08-05 결정)**

느린 것과 못 쓰는 것은 다르다. **학생이 집에서 오래 걸려도 돌려 보겠다면 그건 학생의
선택이고, 45분이라는 제약은 교실의 것이지 도구의 것이 아니다.** 상한으로 막으면 교실
사정을 집에까지 강요하게 된다. 학생 설정을 먼저 좁히지 않는다는 결정이 여기에도 걸린다.

대신 **누르기 전에 얼마나 걸릴지 말해 준다.** 학생이 판단할 근거를 주는 것이 막는 것보다
낫고, 이건 경고이지 차단이 아니다(아래 "학습 실패는 교사가 읽을 수 있게 전달한다"와 같은
성격이다). 추정에 필요한 것은 알고리즘·행 수·특성 수·나무 수이고, 실측 표가 #19에 있다.

**아직 정할 것:** 추정을 어떤 식으로 낼지(실측표 보간 대 첫 나무를 재서 외삽),
얼마나 틀려도 되는지, 어디에 띄울지.

#### 쟀다 (2026-08-07) — 알고리즘별로 나눈다

**전역 5000이 가벼운 알고리즘을 근거 없이 막고 있었다.** 학생이 1만 행짜리 엑셀에서
선형 회귀를 못 돌리는데, 실제로 그 학습은 0.3초다.

측정 기기는 **#19와 같은 학교 보급 노트북**(i5-1135G7 · RAM 7.7GB)이다. 데이터는
8특성 · 3클래스 · 라벨 15% 잡음 합성이고 80/20 분할이다. `fit()`을 직접 불러 쟀다.

| 알고리즘 | 5,000 | 10,000 | 20,000 | 50,000 | 100,000 |
|---|---|---|---|---|---|
| 선형 회귀 | 0.0초 | 0.0초 | 0.1초 | 0.2초 | **0.3초** |
| 나이브 베이즈 | 0.0초 | 0.0초 | 0.0초 | 0.1초 | **0.1초** |
| 로지스틱 회귀 | 4.3초 | 8.1초 | 19.6초 | 71초 | 155초 (heap +368MB) |
| 의사결정트리 | 7.6초 | 11초 | 22초 | 91초 | — |
| KNN — 학습 | 0.0초 | 0.0초 | 0.0초 | 0.0초 | — |
| KNN — **평가 예측**(테스트 20%) | 0.3초 | 1.4초 | 8.7초 | 78초 | — |

랜덤포레스트(5000행 약 7분)와 SVM(수렴하는 5000행 181초)은 #19와 위 SVM 절의 값을
그대로 쓴다. 모델 크기는 어느 줄에서도 문제가 아니다 — 최대가 KNN 50,000행의 0.23MB이고
`MAX_MODEL_BYTES`는 5MB다(#19의 결론과 같다).

**읽어야 할 것 셋.**

- **"가벼운 것"은 둘뿐이다.** 선형 회귀와 나이브 베이즈는 데이터를 한 번 훑는다. 10만
  행에서도 사실상 0초라 브라우저 전용 상한을 둘 이유가 없다 — `MAX_DATASET_ROWS`가
  천장이다.
- ~~**로지스틱 회귀는 가벼운 쪽이 아니다.**~~ **가벼운 쪽이 됐다 (2026-08-10 재실측,
  V2 감사 1단계-B).** 위 표의 로지스틱 줄은 떼어낸 경사하강 구현(`ml-logistic-regression`,
  스텝 1000 고정)의 값이다. L-BFGS로 바꾼 뒤(위 "로지스틱 회귀 솔버를 sklearn과 같은
  구조로 바꾼다") 시간·메모리·실패 모양을 나란히 다시 쟀다 (2026-08-11):
  **수렴하면 2만 행 52ms · 5만 행 134ms · 10만 행 0.2초**이고, 선탐색 꼬리가 길어
  **maxIter(기본 100)에 걸리면 10만 행 최악 9.5초** — 그때는 경고가 뜨고 시간의
  천장은 행이 아니라 maxIter가 쥔다(학생 최대 1000이면 그 10배). **힙은 +2~17MB,
  RSS 최대 +45MB**다(옛 구현 +368MB) — 증강 행렬 복사본이 없다. 실패 모양은 "조용한
  오답"이 아니라 "경고 붙은 done"이다. 상한을 선형 회귀·나이브 베이즈처럼
  `MAX_DATASET_ROWS`로 올린다. 2만 행에서 옛 구현이 수렴 미달(0.78, 최적점 0.92)
  이었던 것도 이 교체로 해소됐다(같은 데이터에서 0.915 = sklearn).
- **KNN의 벽은 학습이 아니라 예측이다.** 학습은 행 번호만 담아 0초인데 평가 예측이
  20,000행에서 8.7초다. 그리고 **이 비용은 한 번이 아니다** — 예측 화면에서 학생이 올리는
  행마다 학습셋 전체와의 거리를 다시 계산한다(`PREDICT_PAGE_SIZE`가 경고하는 자리).
  **학습 시간만 보고 상한을 정하면 안 되는 유일한 알고리즘이다.**

**정한 값. 전부 순수 JS(mljs) 칸이다** — 아래 "상한은 알고리즘이 아니라 (알고리즘 ×
구현)에 걸린다"를 함께 읽어라. 출처는 `frontend/src/limits.ts`이고 여기 적은 것은 근거다.

| 알고리즘 | 상한 | 왜 |
|---|---|---|
| 선형 회귀 | `MAX_DATASET_ROWS` | 0.3초. 브라우저 상한을 둘 이유가 없다 |
| 나이브 베이즈 | `MAX_DATASET_ROWS` | 0.1초. 같음 |
| 로지스틱 회귀 | 20,000 | 20초. 50,000은 71초에 메모리가 붙는다 |
| 의사결정트리 | 20,000 | 22초 |
| KNN | 10,000 | 평가 1.4초. 비용이 예측마다 되풀이되므로 학습 시간만큼 못 올린다 |
| 랜덤 포레스트 | 5,000 | 지금 값 그대로. **다만 등록부에 명시한다**(아래) |
| SVM | 3,000 | 위 SVM 절 그대로 |

**20초대를 상한으로 삼는 근거는 "기다림은 비용이지 실패가 아니다"다.** 45분 수업에서
설정을 바꿔가며 여러 번 돌리는 것이 이 도구의 핵심 활동이므로 분 단위는 그 활동을
깨뜨리지만, 20초는 깨뜨리지 않는다. 여기가 막는 선이고 그 위는 예상 시간이 할 일이다.

#### 그래서 `BROWSER_ROW_LIMIT`의 역할이 뒤집힌다

`ml/backend.ts`에 이렇게 적혀 있었다 — *"전역보다 낮은 값만 오므로 (…) 더 높은 상한을
선언하는 것은 '전역이 틀렸다'는 뜻이고, 그건 알고리즘 등록부가 할 말이 아니다."*

**이번 실측이 바로 그 "전역이 틀렸다"다.** 하나의 값으로 0.3초와 7분을 같이 담으려 한
것이 애초에 틀린 축이었다. 그러므로:

- **상한의 출처는 등록부의 알고리즘별 값이다.** 전역은 상한이 아니라 **"아직 재 보지 않은
  알고리즘의 기본값"**이다. 등록부 값이 전역보다 높아도 정상이다.
- **재 본 알고리즘은 전부 자기 값을 적는다.** 랜덤포레스트를 전역에 얹어 두면 다음에
  전역을 올리는 사람이 7분짜리 학습을 대신 허락하게 된다. 값이 안 바뀌어도 적는 이유가
  이것이고, `EVERYWHERE` 상수를 지운 것과 같은 논리다(`ml/algorithms.ts`).
- **알고리즘마다 상수를 따로 둔다.** 비용이 닮았다고 상수를 공유하면 한 사람이 여러
  알고리즘을 대신 판단하게 된다 — 위 표에서 로지스틱 회귀와 의사결정트리가 같은 20,000이지만
  근거가 다르고, 다음에 갈릴 값이다.
- **서버에는 여전히 안 걸린다.** 여기 있는 것은 브라우저 구현의 성질이다.

**휴대폰은 이 표에 없다.** 아래 "모바일에서도 동작한다"가 남긴 축이고, 특히 로지스틱
회귀의 메모리와 KNN의 예측이 거기서 먼저 아프다.

#### 상한은 알고리즘이 아니라 (알고리즘 × 구현)에 걸린다

**모델 하나에 상수 하나를 주면 안 된다.** 위 표의 숫자는 전부 **순수 JS**를 잰 것이고,
같은 의사결정트리를 sklearn으로 돌리면 다른 숫자가 나온다 — `ml-cart`의 분할 탐색이
O(특성 × 행²)인 것은 `ml-cart`의 성질이지 의사결정트리의 성질이 아니다. 20,000이라는 값을
알고리즘에 붙여 두면 **재 보지도 않은 구현까지 그 값에 묶인다.**

그래서 등록부의 칸은 `runtimes`와 같은 모양이다 — **브라우저 구현마다 한 칸.**
칸이 비면 컴파일이 깨지고, 새 브라우저 엔진이 붙는 날 알고리즘 일곱 줄이 전부
"이건 얼마인가"를 묻는다. `Axis`가 있는 이유와 같다(`ml/axes.ts`, architecture.md §9.3).

**안 재 본 칸은 빈 칸이 아니라 "안 쟀다"라고 적는다.** 지금 `pyodide-sklearn` 칸이 전부
그렇다. 숫자를 지어 넣으면 근거 없는 값이 실측처럼 보이고, 옵셔널로 비워 두면 빠뜨림이
합법이 된다. `false`가 "아직 안 만들었다"를 뜻하지 않는 것과 같은 규칙이다(§9.2.1).
안 쟀다고 적힌 칸은 전역 기본값(`BROWSER_ROW_LIMIT`)을 따른다 — **보수적으로 틀리는 쪽이다.**

#### 서버의 상한은 등록부에 없다 — 협상이 준다

**서버가 1만인지 10만인지 1000만인지 우리는 모른다.** 자가호스팅 서버의 능력은 그 학교가
꽂은 하드웨어에 달렸고, 우리가 숫자를 적어 두면 **GPU 서버를 띄운 학교의 상한을 우리
상수가 깎는다.** 아래 "무엇을 학습할 수 있는지는 서버가 알려준다"가 막으려는 것과 정확히
같은 실수다.

그래서 **행 상한은 능력 협상의 일부다.** 서버가 알려주는 (알고리즘, 구현) 항목마다
하이퍼파라미터 서술과 나란히 행 상한이 온다 — 그 절의 "정해야 할 것" 6번이 이것이다.
코드에서 이 규칙이 서는 자리는 `runtimeOptions`가 **브라우저 위치에서만** 상한을 보는
것이고(`ml/backend.ts`), 그건 이미 그렇게 돼 있다.

**협상이 없는 지금은 서버에 상한이 걸리지 않는다.** 자리표시자 필드를 미리 만들지 않는다 —
무엇이 올지 모르는 채로 만든 필드는 협상이 생기는 날 버려진다.

**기기마다도 다르다.** 모바일에서도 도는 이상(아래 "모바일에서도 동작한다") 축이 하나
더 붙었다. 휴대폰은 메모리가 적고, 무엇보다 **탭이 백그라운드로 가면 브라우저가 통째로
버린다** — 데스크톱에서는 "느리다"로 끝날 것이 여기서는 "학습이 사라졌다"가 된다.

### 16. 백엔드 요청 남용 방어 — **강등됨.** 필요 시점: 자가호스팅 백엔드(8단계)
공개 백엔드를 운영하지 않기로 하면서(CLAUDE.md §1.1) **"익명의 인터넷"이라는 적대 모델이
사라졌다.** 자가호스팅 서버는 학교 네트워크 안에서 한 학급을 상대한다.

남은 것은 방어가 아니라 **폭주 방지** 수준이다.

- 프런트엔드 재연결(WebSocket)의 지수적 백오프. 수업 시작 시각에 30명이 동시에 접속하고
  동시에 재시도하면 학교 서버도 무너진다. **지터를 반드시 넣는다.**
  이건 서버와 무관하게 프런트엔드 쪽 작업이다.
- 세션 수 상한(#9)에 걸리면 `SERVER_BUSY`. 이미 있는 메커니즘으로 충분하다.

**IP 단위 rate limit은 만들지 마라.** 학교는 한 IP 뒤에 30명이라 정상 수업이 차단된다.

### 17. 한셀 xlsx 폴백의 실제 재현 — 필요 시점: 폴백을 손볼 때
SheetJS 폴백은 과거 프로젝트에서 겪은 실패를 근거로 **선제적으로** 넣었다(아래 결정됨).
실제 한셀 저장 파일로 다음을 확인해야 한다.

- ExcelJS가 정말 실패하는가, 아니면 예외 없이 이상한 값을 주는가.
  후자면 폴백이 발동하지 않는다 — 현재 폴백 조건은 "예외 또는 시트 0개"뿐이다.
- SheetJS는 그 파일을 제대로 읽는가

재현 파일을 얻으면 `frontend/tests/fixtures/`에 넣고 테스트로 고정한다.

### 18. 엑셀 날짜 셀 — 필요 시점: 날짜 데이터를 쓰는 수업이 나올 때
현재는 범위 밖이다. ExcelJS 경로는 ISO 문자열을, SheetJS 폴백 경로는 엑셀 표시
문자열을 준다 — 두 경로가 갈린다. `styles.xml`의 `numFmt` 해석까지 가면 작업이 커져서
미뤘다. 날짜를 쓰는 수업이 실제로 나오면 그때 정한다.

### 19. 모델 크기 예산의 실제 값 — 필요 시점: 모델 직렬화 구현
`MAX_MODEL_BYTES`(모델 하나)와 `MODEL_BUDGET_BYTES`(한 파일 합계)는 잠정값이다
(`frontend/src/limits.ts`). `BROWSER_ROW_LIMIT`과 같은 처지인데 그쪽(#13)만 항목이 있었다.

**상한을 두는 방향 자체는 맞다.** 상한이 하는 일은 모델을 빼앗는 것이 아니라 **실패의
종류를 고르는 것**이다 — 있으면 저장은 성공하고 지표는 남고 예측만 못 한다(`mlpx-spec.md`
§4.2). 없으면 실패가 사라지는 게 아니라 더 나쁜 자리로 옮겨간다: 학교 LMS 업로드 거부,
휴대폰에서 안 열림, 수행평가 제출 직전에 발견. 전부 교사가 뒤집어쓰는 자리다.

#### 쟀다 (2026-08-05) — `mlpx-tree-v1` 기준

측정 기기는 **학교 보급 노트북(Intel Core i5-1135G7, 4코어/8스레드, RAM 7.7GB)**이다.
교실 PC와 성능이 비슷하므로 아래 숫자는 낙관적 상한이 아니라 **교실 실측치에 가깝다.**
휴대폰은 이보다 나쁘다. 데이터는 3분류 합성이고 "잡음"은 라벨 30%를 무작위로 섞은 것이다.

**크기 — 랜덤포레스트 100그루, 우리 형식(들여쓰기 없음).**

| 데이터 | raw | gzip |
|---|---|---|
| 400행 4특성, 깨끗함 | 41.6KB | 7.0KB |
| 400행 4특성, 잡음 | 189.6KB | 38.4KB |
| 800행 4특성, 잡음 | 228.0KB | 46.8KB |
| **1600행 4특성, 잡음** | **272.0KB** | **56.7KB** |
| 800행 10특성, 잡음 | 242.2KB | 51.7KB |
| 3000행 4특성, 잡음 (10그루 ×10 추정) | 312KB | 72KB |
| 5000행 4특성, 잡음 (10그루 ×10 추정) | 246KB | 58KB |
| 결정트리 (5000행까지 전부) | 1~3KB | 1KB 미만 |

**크기 상한은 안 걸린다. 현재 값을 유지한다.** 최댓값이 272KB이고 `MAX_MODEL_BYTES`는
5MB다 — 18배 여유다. `MODEL_BUDGET_BYTES`(20MB)에는 그런 모델이 73개 들어간다.
**낮추지 않는다** — 지금 낮추면 아무도 안 겪던 실패를 새로 만드는 것뿐이고, 상한의 일은
겪을 실패를 고르는 것이지 만드는 것이 아니다.

**크기를 지배하는 것은 행 수가 아니라 잡음이다.** 같은 400행에서 깨끗하면 41.6KB,
라벨이 30% 섞이면 189.6KB로 **4.6배**다. 갈리지 않는 데이터일수록 나무가 깊어진다.
그리고 **행이 늘면 크기는 오히려 평평해진다** — `minNumSamples`와 `gainThreshold`가
분할을 멈추므로 나무 깊이에 천장이 있다. 5000행이 1600행보다 작게 나온 이유다.

#### 그런데 상한이 잘못된 축에 걸려 있었다

**진짜 벽은 크기가 아니라 시간이다.** 같은 측정에서 나온 학습 시간:

| 행 (4특성, 잡음) | 100그루 학습 |
|---|---|
| 100 | 0.3초 |
| 400 | 3.4초 |
| 800 | 11.1초 |
| **1600** | **39초** |
| 3000 (추정) | 약 2분 |
| 5000 (추정) | **약 7분** |

행이 두 배가 될 때마다 약 3.5배씩 늘어난다(`ml-cart`의 분할 탐색이 노드마다
O(특성 × 행²)이다). 특성을 4개에서 10개로 늘리면 여기서 2.4배가 더 붙는다.

**`BROWSER_ROW_LIMIT`(5000)은 랜덤포레스트에 대해 사실이 아니다.** 같은 5000행에서
결정트리는 12초에 끝난다. 상한이 알고리즘과 무관한 값 하나인 것이 문제다 → **#13**.

수업 시간이 45분이고 학생이 설정을 바꿔가며 여러 번 돌리는 것이 이 도구의 핵심 활동인데,
한 번에 7분이면 그 활동 자체가 성립하지 않는다. 워커에서 돌아 화면이 얼지는 않지만
(open-decisions "학습은 언제나 백그라운드다") 얼지 않는 것과 쓸 만한 것은 다르다.

#### 제출 경로의 상한은 확인했다 (2026-08-05, 교사 확인)

측정이 아니라 **현직 교사의 확인**이다. 그래서 숫자보다 경로 구분이 중요하다.

| 제출 경로 | 상한 |
|---|---|
| 구글 클래스룸 | 사실상 없다 |
| 자가호스팅 백엔드로 직접 제출 | 없다 |
| 외부 업체 LMS에 첨부 | **대략 100MB** |

**최악의 경로가 100MB이고 `PROJECT_FILE_WARN_BYTES`는 50MB다.** 경고 문턱이 그 절반에
있다는 뜻이고, 그동안 근거 없이 고른 숫자였던 것이 이제 근거를 얻었다.

**그래서 모델 상한은 이 축과 무관해졌다.** 272KB짜리 모델이 100MB에 닿을 길이 없다.
`MAX_MODEL_BYTES`와 `MODEL_BUDGET_BYTES`가 LMS 때문에 존재할 이유는 없다는 뜻이다.
`.mlpx`의 크기를 지배하는 것은 모델이 아니라 **데이터셋**이고(원본 바이트를 그대로 담는다),
`PROJECT_FILE_WARN_BYTES`가 그쪽을 보는 상한이다.

**남은 축은 브라우저다 — "브라우저 공간이 허용하는 범위가 곧 상한이다."** 실제로 쓰일
두 경로(구글 클래스룸, 자가호스팅)에서 LMS가 안 막으므로, 학생이 먼저 부딪히는 벽은
IndexedDB 할당량과 파일을 여는 시간이다. → **#7**

#### 그래서 아직 미결이다

**바깥에서 오는 비교 대상 셋은 다 닫혔다** — 크기 실측, 저사양 PC 실측, 제출 경로 상한.
그래도 항목을 닫지 않는 이유는 안쪽에 있다.

- **잰 형식이 하나뿐이다.** `mlpx-tree-v1`은 네 형식 중 가장 큰 것이라 상한을 정하는 데
  가장 중요하지만, 참조형(KNN·SVM)은 데이터 행 수에 비례하므로 성질이 다르다.
- **표 데이터만 쟀다.** 이미지가 들어오면 전제가 통째로 바뀐다. 그때 이 항목을 다시 연다.
- **휴대폰에서 파일을 여는 시간은 안 쟀다.** 저장은 브라우저가 하므로 이건 #7과 같이 본다.

상한이 자주 걸리면 고를 것: 상한을 올릴 것인가, 화면이 미리 "나무 100개면 파일이
커집니다"를 말할 것인가. **후자는 학생 설정을 먼저 좁히지 않는다는 결정과 충돌하지
않는다** — 경고는 막는 것이 아니다(아래 "학습 실패는 교사가 읽을 수 있게 전달한다").
다만 위 실측대로면 **경고가 필요한 쪽은 크기가 아니라 시간이다.**

### 20. 포트폴리오 플랫폼으로의 확장 — **방향은 정해졌고 착수는 나중이다** (2026-08-05)

**지금 아무것도 만들지 마라.** V1(ML)이 끝나기 전에는 착수하지 않는다. 여기 적어 두는
것은 그때 이 논의를 처음부터 다시 하지 않기 위해서다.

**발견은 이것이다 — 워크플로가 같다.** 학생이 주제를 정하고, 만들고, 실행하고, 결과를
보고, 고치고, 정리해서 파일 하나로 낸다. 프로그래밍 포트폴리오가 교실에서 진행되는
모양이 ML 포트폴리오와 같은 뼈대다. 그리고 이 저장소가 이미 만든 것 중 절반 이상이
ML과 무관하다 — zip 왕복·마이그레이션·검증·해시 3층·표절 신호·i18n 규약·`JobQueue`와
WS 진행 이벤트·자원 상한 상수화·포트폴리오 템플릿.

`runs.json`이 특히 그렇다. 실험 = 실행 한 번, run = 결과 하나, `status: done|failed` +
`failure.code`, 설정 스냅샷. **코드 실행 이력이 여기 거의 손대지 않고 들어간다.**

#### 정해진 방향

| 축 | 결정 | 왜 |
|---|---|---|
| 앱 | **하나** | 배포 경로와 백엔드가 하나여야 한다 |
| 확장자 | **종류마다 다르다** | 잘못 연 파일이 무엇으로 거부되는가 |
| 저장소 | **하나** | 공통 계층 변경이 두 곳 PR이 되면 안 된다 |
| 분기 지점 | **새 프로젝트를 만들 때** | 열린 프로젝트의 종류가 곧 앱의 모드다 |
| 구현 방식 | **등록부** | `if (kind === 'ml')` 금지 |

**앱이 하나여야 하는 이유가 가장 강하다.** CLAUDE.md §2가 "백엔드 주소를 설정 가능하게
만들지 마라 — 같은 오리진이면 CORS도 mixed content도 교사가 고칠 설정 파일도 생기지
않는다"고 못 박았다. 앱을 쪼개면 학교가 도커를 띄울 때 서버가 둘이 되거나 한 서버에
프런트엔드를 둘 얹어야 하고, 교사가 학생에게 알려줄 주소가 두 개가 된다. 리셋되는
컴퓨터실 PC에서 그건 실패한다.

**백엔드는 애초에 하나다.** "무엇을 학습할 수 있는지는 서버가 알려준다"(아래)가 이미
결정돼 있고, "무엇을 실행할 수 있는지"는 **그 메커니즘 그대로**다. 새 개념이 아니라
같은 응답에 필드가 하나 느는 것이다.

**확장자를 나누는 기준은 거부의 모양이다.** 확장자가 같고 안에 `kind`만 있으면, ML
화면에 프로그래밍 파일을 떨어뜨렸을 때 학생이 보는 것은 zod 검증 실패다 — `path`는
`settings.dataset`. 학생과 교사는 파일이 손상됐다고 결론 낸다. §9가 `formatVersion`
검사를 엔트리 존재 검사보다 앞에 둔 이유가 정확히 이것이었다. 그리고 정보 교과는 ML
단원과 프로그래밍 단원이 같은 학기에 있어서 **수거 폴더에 두 과제가 섞인다** —
확장자가 같으면 아이콘도 같고 파일명만 봐서는 모른다.

#### 브라우저 실행 원칙은 유지된다

"실행은 항상 브라우저"(`mlpx-spec.md` §0.2)가 무너지면 정적 배포본이 제품이 아니게
되므로, 이것이 이식 가능성의 관문이었다. **중·고 정보 교과는 사실상 파이썬이고
Pyodide는 이 저장소가 이미 받아들인 물건이다.** 그래서 브라우저 실행 경로가 성립하고,
Judge0는 "더 강한 것이 필요한 학교"의 자가호스팅 경로가 된다 — 지금 서버 학습이 놓인
자리와 같다.

**순서를 뒤집으면 원칙이 깨진다.** Judge0부터 붙이면 실행이 서버를 전제하게 되고,
그러면 GitHub Pages 배포본은 "편집기 + 저장"뿐이다.

#### `kind`는 `dataType`·`taskType`보다 위의 축이다

같은 층에 두지 마라. `dataType`은 "업로드한 데이터가 무엇인가"이고 `taskType`은
"무엇을 하려는가"인데, 프로그래밍 프로젝트에는 업로드한 데이터가 없고 분류/회귀/군집은
ML 어휘다. `kind`가 정해져야 나머지 둘이 뜻을 갖는다. 같은 층에 두면 성립하지 않는
조합을 걸러내던 표(`mlpx-spec.md` §0.1)에 "프로그래밍 + 회귀" 같은 무의미한 칸이 생긴다.

#### `manifest.kind`는 지금 v1에 넣는다 — 유일하게 지금 하는 일이다

**확장자와 `kind`는 중복이 아니다. 층이 다르다.**

```
확장자   OS와 앱이 무엇으로 열지 고르는 힌트     밖에 있다. 통제 밖이다
kind     파일이 자기가 무엇인지 말하는 사실       안에 있다. 어긋나면 이쪽이 이긴다
```

확장자는 학생이 바꾸고 LMS가 바꾸고 압축을 다시 하면 사라진다. 이 저장소는 §7에서
"학생이 압축을 풀어 고친다"를 전제로 깔았고 §6.3의 표절 판정도 전부 파일 **안**의 값으로
돌아간다 — 파일명이 증거로 쓰인 적은 한 번도 없다(§6.2에서 파일명은 검사 수단이지
데이터가 아니다). 그러므로 `.mlpx`인데 내용이 다른 종류인 파일은 반드시 생기고, 그때
할 말은 "파일이 깨졌습니다"가 아니라 "이건 다른 종류의 프로젝트입니다"다.

"같은 값을 두 곳에 두지 마라"에 걸리지 않는다. 그 규칙이 막은 것은 **둘 다 파일 안**일
때다(`randomState`). 여기는 §7.2.1의 `contentHash` vs 수거 해시와 같은 구조 —
안과 밖, 쓰임이 다른 두 값이다.

**지금 넣는 이유는 배포 전이기 때문이다.** UI가 없고 학생 파일이 세상에 하나도 없다.
지금은 필드 하나 + 테스트 한 줄이고, 나중은 마이그레이션 함수 + 그 테스트 + 옛 파일
픽스처이며 그 시점에는 파일이 이미 돌아다닌다. **포맷 필드는 코드와 달리 파일에 박히는
것이라 미루는 값이 훨씬 비싸다.**

**그런데도 `FORMAT_VERSION`은 오르지 않는다.** `kind`는 §10의 "어휘"가 아니라
**등록부 축**이기 때문이다 — §10이 이미 예외를 명시했다: "`algorithm` 이름과
`model.format`은 등록부에 속하고 등록부 변경은 포맷 변경이 아니다." 종류를 더하는 것은
등록부에 항목을 더하는 것이고, 종류마다 자기 체인을 들고 있으므로 ML 포맷은 안 움직인다.
그래서 `z.enum`이 아니라 `z.string()`이고, 옛 파일 대비는 마이그레이션이 아니라
기본값으로 끝난다 — `runsFileSchema.experiments`가 이미 같은 일을 한다.

**값은 `'machineLearning'`이다.** 두 번째 종류가 `'programming'`인데 `'ml'`과 짝지으면
한쪽만 축약된 비대칭이 되고, 표기는 같은 객체의 이웃과 `schema.ts`의 파일 어휘를 따른다
(`mostFrequent`·`overBudget`·`engineUnsupported`). **값에 제품명을 넣지 마라** —
제품명은 아직 미결이고 파일에 박힌 값은 못 바꾼다. 값이 가리키는 것은 앱이 아니라
활동의 종류다.

착수 시점까지 **만들지 않는 것 둘.** 종류가 하나뿐인 지금은 도달할 경로가 없다.

- **검사 순서에서 `kind`가 `formatVersion`보다 앞이다.** 종류마다 체인이 다르므로 ML의
  v3와 프로그래밍의 v3는 다른 것이다. `kind`로 체인을 고른 뒤 그 체인이 버전을 본다.
  그리고 엔트리 요구보다도 앞이어야 한다 — 아니면 프로그래밍 파일이 "dataset/data.csv가
  없습니다"로 거부되고, 그건 §9가 막으려던 새어나감 그대로다.
- **"이 앱은 이 종류를 모릅니다" 에러 코드.** `MODEL_FORMAT_UNSUPPORTED`와 성격이 같지만
  이쪽은 **파일이 아예 안 열린다**(모델 쪽은 파일이 열리고 그 모델만 못 쓴다). 별도 코드다.

#### ML 쪽에 실제로 닿는 지점 둘 — 나머지는 안 닿는다

1. **프로젝트 목록과 새 프로젝트 화면은 공용이다.** ML 학생이 안 쓰는 기능 때문에
   클릭이 하나 늘면 안 된다 → **등록부에 항목이 하나뿐이면 고르는 화면을 건너뛴다.**
   그러면 두 번째 종류가 실제로 들어오기 전까지 화면이 지금과 같다.
2. **포맷 계층이 일반화 압력을 받는다. 여기가 유일한 진짜 위험이다.** 두 번째 종류는
   엔트리 구성이 다르므로(`dataset/` 자리에 소스와 입력이 온다) §9의 "엔트리 구성은
   v1에서 동결"을 밀어붙인다. → **종류마다 자기 마이그레이션 체인을 들게 하고 공통
   체인을 만들지 않는다.** 그러면 ML 체인은 건드려지지 않는다.

종류별 화면은 **지연 로드**한다. 안 그러면 ML만 쓰는 학생이 프로그래밍 쪽 번들을 받고,
그건 "모바일에서도 동작한다"(아래)의 전제를 깬다.

#### 함께 열려 있는 것 둘 — 착수 시점에 판단한다

- **제출물의 서버 보관과 [제출] 버튼.** 자가호스팅이면 학교가 파일을 보관할 수 있다는
  관찰은 맞다. 다만 개인정보 책임은 망 위치가 아니라 **보관 주체**에서 나오므로
  "간단해진다"가 아니라 "학교가 진다"가 정확하고, 그 학교는 대개 그 교사 본인이다.
  그리고 지금도 파일 제출로 수거는 된다(`mlpx-spec.md` §7.2.1) — 서버 보관이 그 위에

  `privacy.md` 보완이 선행한다.
- **상위 이름과 두 번째 확장자 이름.** 아래에서 **ML 쪽 이름은 확정됐다.** 남은 것은

  **두 번째 종류에 착수하기 전에 반드시 정한다.** 지금 확장자 이름을 임의로 확정하지 않는다.

#### ML 쪽 이름은 확정한다 — **머신러닝 플레이그라운드** (2026-08-05)

### 24. 일괄 예측 표의 색 배정을 등수 기반으로 바꿀 것인가 — 필요 시점: 값 종류 8개 이상인 데이터가 자주 보이면

**지금은 "처음 본 순서"로 색을 준다.** `architecture.md` §8.13.1 "일괄 예측 표의
셀도 값별로 다른 색이다"에 이유가 있다 — 표가 `PREDICT_PAGE_SIZE`행씩 끊겨 있어
화면이 파일 전체의 값 분포를 미리 모르고, 그래서 카드·갈림표처럼 "개수 순 등수"를
못 매긴다. 대신 이미 배정된 값은 안 건드리고 새 값에만 다음 색을 준다.

**받아들인 트레이드오프:** 어떤 값이 일곱 색 안에 드는지가 **페이지를 넘긴 순서에
달려 있다.** 결정적이지 않다 — 같은 파일도 어느 페이지부터 먼저 봤는지에 따라
다른 일곱 개가 색을 받을 수 있다. 값 종류가 대개 2~5개인 교실 데이터(붓꽃 3종,
생존 여부 2종 등)에서는 거의 안 느껴질 문제라 지금은 그대로 둔다.

**정할 것:** 값 종류가 여덟 개를 자주 넘는 데이터가 실제로 보이면, 파일 전체를 한
번 미리 스캔해(값별 개수만 세면 되므로 JS로 어렵지 않다) 카드·갈림표와 같은
"개수 순 등수" 방식으로 바꾸는 것을 고려한다. 이때 정해야 할 것:

1. **사전 스캔을 얼마나 무겁게 허용할 것인가.** 지금 페이지네이션은 "한 페이지분만
   계산한다"는 연산 억제 원칙인데(§8.13.1 "100줄씩 끊고, 계산도 그만큼만 한다"), 색
   배정만을 위해 파일 전체를 훑는 것은 그 원칙과 별개의 예산이 필요하다 - 저사양
   학교 PC 기준으로 몇 행까지 괜찮은지 실측이 없다(#19와 같은 축).
2. **언제 스캔하는가.** 파일을 붙이는 순간(`applyPredictDataset`)에 한 번 세어
   `settings`에 캐시해 둘 것인지, 표를 처음 열 때 셀 것인지.
3. **스캔 중 화면을 어떻게 보여주는가.** 값이 몇만 행이면 세는 동안에도 뭔가는
   보여야 한다 - "계산하는 중" 문구를 재사용할 수 있는지, 아니면 우선 처음 본
   순서로 보여주고 다 세면 색을 다시 칠하는 점진적 갱신이 나은지.

### 27. 다중 타깃(multi-output)을 받을 것인가 — **결정됨: V1~V2 범위에서 안 한다 (V2 감사 3단계, 2026-08-11)**

**타깃은 스키마 처음부터 끝까지 단일 문자열이다** — `settings.target`이
`userString.optional()`(`frontend/src/project/schema.ts`), `targetValues`가 `string[]`
하나(`ml/preprocess.ts`), `evaluate`가 평평한 배열 둘을 받아 지표 하나를 낸다
(`ml/metrics.ts`). 전처리 화면에서 타깃을 라디오 버튼으로 하나만 고르게 한 것은 UI
제한이 아니라 이 데이터 모델의 제한이다.

**안 하기로 한다. 교육적으로 단일 타깃이 옳은 형태이기 때문이지, 아직 못 만들어서가
아니다.**

- **교실에 필요한 것은 이미 된다.** "여러 개 예측"은 다중 클래스(붓꽃 3종 중 **하나**
  고르기)와 다중 타깃(정답 **열**이 여럿)으로 갈리는데, 앞은 완전히 지원한다 — 클래스
  수 제한이 없고 SVM은 one-vs-one, 로지스틱은 multinomial로 푼다. 교실 수업은 전부
  앞이고, 뒤(키·몸무게 동시 예측)는 중·고 성취기준에 없다.
- **다중 타깃은 정신 모델을 흐린다.** 이 도구의 회로는 특성 → 하나의 타깃 → 채점이다.
  타깃이 둘이 되면 독립성·타깃별 지표 읽는 법을 설명해야 하고 그건 핵심을 가린다.
  키·몸무게를 함께 예측하려는 학생은 **실험을 두 번 돌리면 되고, 그게 두 개의 별개
  문제라는 사실을 오히려 또렷이 보여준다** — 우회로가 본 기능보다 교육적으로 낫다.
- **발판 논리도 단일 편이다.** sklearn 입문이 단일 타깃에서 시작하고, sklearn의
  multi-output은 네이티브(트리·랜덤포레스트·KNN)와 래퍼(`MultiOutputClassifier`,
  로지스틱·SVM·나이브베이즈)로 갈리는 고급 코너라 여기서 익히면 **더 약한 발판**이 된다
  (위 "파이썬 표준 관행을 따른다").

**문은 공짜로 열려 있다.** `target`이 단일 옵셔널이라 나중에 배열로 넓히는 것은
`"a"→["a"]`이고 배포 전이라 마이그레이션조차 없다(위 #10-1 "이 배포는 아직 실기
점검용이다"). **미루기 위해 지금 지어야 할 것이 하나도 없다 — 그냥 두는 것이 곧 문을
열어 두는 것이다.** 넓히는 날 실제로 흔들리는 곳은 지표(subset accuracy·출력별 F1)·모델
형식(`classes` 하나 → 타깃별)·결과 화면이고, 그 비용은 지금 열든 나중에 열든 같다.

**한 곳만 재검토로 남긴다 — 다중 라벨 이미지 분류(V4).** 사진 하나에 라벨 여럿(바다+노을)은
표 다중 회귀와 달리 상상 가능한 장면이다. 다만 입문 도구의 목표 경험은 한 사진 한
라벨이고, 이미지 스키마 자체가 #25(브라우저에서 이미지를 무엇으로 돌리나)에 걸려 있어
지금 표 스키마를 건드릴 근거가 아니다. **V4 착수 시 #25·#4와 함께 이 항목을 다시 편다.**

### 29. 군집의 Evaluator 시그니처 — **결정됨 (V3, 2026-08-11)**

분류·회귀의 `Evaluator`는 `(actual, predicted) => Evaluation`이다. 군집은 정답이
없으므로 같은 시그니처를 쓸 수 없다 — `actual`에 빈 배열을 넣는 꼼수를 쓰면
타입이 거짓말을 하게 된다.

**`ClusterEvaluator`를 별도 타입으로 만들고, 등록부를 분리한다.** `EVALUATORS`는
분류·회귀만 갖고, 군집용 등록부가 따로 있다. 컴파일러가 시그니처를 각각 강제한다.

> **구현은 이 문장과 한 군데 다르다** (2026-08-11, V3 감사). 여기 "`evaluate()` 함수가
> `taskType`으로 갈라서 각각의 등록부를 부른다"고 적었는데, 실제로는 `evaluate()`와
> `evaluateCluster()`가 밖으로 둘 다 노출되고 **가르는 것은 부르는 쪽**(`experiment.ts`)
> 이다. 시그니처가 다른 두 함수를 하나의 이름 뒤에 넣으면 반환 타입이 합집합이 되어
> 부르는 쪽이 다시 좁혀야 한다. 결정의 알맹이(등록부를 나눈다)는 그대로다.
> → `architecture.md` §3.7

군집 지표는 **실루엣 계수(Silhouette Coefficient)**와 **이너셔(Inertia)** 둘이다.

- 실루엣: 각 데이터가 자기 군집과 얼마나 잘 맞고 다른 군집과 얼마나 떨어져 있는지.
  −1~1, 높을수록 좋음. sklearn의 대표 군집 지표. `docs/terms.md`에 이미 있다.
- 이너셔: 각 데이터와 자기 군집 중심점까지 거리의 제곱합. K-Means의 목적함수.
  sklearn `KMeans.inertia_`가 이것. 낮을수록 좋지만 k를 올리면 무조건 내려가므로
  단독으로 "좋다"를 말할 수 없다 — 그 사실을 학생이 k를 바꿔 가며 발견하는 것이
  교육적 가치다.

   멈춘다. `tol`의 기본값은 sklearn `SVC`의 1e-3을 따른다 — 지금 우리 1e-4는
   경사 기반 수렴 기준이고 KKT 위반과는 뜻이 다른 값이라 그대로 쓸 수 없다.
2. **우리 구현으로 선언한다.** 로지스틱 회귀가 이미 그 길을 갔다. 정지 조건 변경은
   원본 SMO(`ml-svm`)와 나란히 놓고 볼 수 있는 수준을 넘으므로 벤더링 전제를
   유지할 수 없다. 파일 머리말을 "우리 구현, 원본은 `ml-svm`"으로 고친다.
3. **`maxIterations` 충분성은 변경 뒤 실측한다.** sklearn은 800행 겹침 데이터에
   7,174 반복을 썼으므로 10,000이 부족할 수 있다. 실측 결과에 따라 올린다.

근거: V3에서 sklearn 엔진이 실물로 붙어 교차 검증이 가능해진다. 정지 조건이
다르면 도착점이 다르고, 도착점이 다른 이유에 "휴리스틱이라서"라는 이름밖에
못 붙인다 — 로지스틱을 V2 감사 1단계에서 고친 것과 같은 논리다.

#### 26-1. 정체 종료는 이 솔버의 수렴이다 (V3 감사, 2026-08-11)

**연속 `SMO_DEFAULTS.stallPasses`(10) 패스 동안 α가 하나도 안 바뀌면 멈추고,
그때 `converged: true`를 준다.** 반복 예산(`maxIterations`)을 다 쓴 경우만
`converged: false`다. 감사가 "결정문의 기준(KKT < tol)을 만족하지 않고도 수렴이
되는 두 번째 출구"라고 지적한 자리이고, 그 지적은 사실이다. 그래도 이렇게 둔다.

**실측이 이 판단의 근거다** (개발 PC i5-1135G7, 2026-08-11). 겹침 10~50%의
800·1500·3000행과 멀찍이 떨어진 두 덩어리 20~400행 — **열다섯 벌이 전부 정체로
끝났고, KKT 최댓값이 `tol` 아래로 내려간 것은 한 벌도 없었다.** 갈라치기의 α
변화량 문턱(1e-3)이 `tol`과 같은 규모라 마지막 위반이 그 아래로 잘 안 깎이기
때문이다.

**KKT 출구가 아예 안 열리는 것은 아니다** (감사자의 독립 측정, 2026-08-11).
`stallPasses`를 도달 불가능하게 만들고 예산을 넉넉히 준 뒤 `converged: true`가
나오는지 보는 방법으로, **완전히 갈라지는 데이터 여섯 벌 중 한 벌에서 KKT 출구가
열렸다**(100행 간격 50 · 예산 200에서 152회). 처음 이 자리에 "하나도 없다 ·
이론상의 출구"라고 적었던 것은 **표본 열다섯 벌이 뒷받침하는 것보다 강한 문장**이었고
반례 하나로 깨졌다 — 재지 않은 범위까지 말하지 않는다.

**정리하면 이렇다.** 겹치는 데이터 — 교실 CSV의 대부분 — 에서는 KKT 출구가 한 번도
나오지 않았고, 완전히 분리된 데이터에서만 드물게 나온다(독립 측정 15벌 중 1벌).
**실질적 종료는 정체다.**

그래서 정체를 `converged: false`로 보내면 **교실의 거의 모든 SVM 학습에
`SVM_NOT_CONVERGED`가 붙는다.** 그 경고의 뜻("솔버가 이론적 최적점에 이르지
못했지만 모델은 괜찮을 수 있다")을 중고등학생이 읽어낼 방법은 없고, 학생은
"모델이 잘못됐다"로 읽는다. **덜 다듬어진 것과 더 못 다듬는 것은 다르다** —
단순화 SMO는 WSS3 짝 선택이 없어 무작위 짝으로는 남은 위반을 해소할 수 없고,
그 상태가 이 솔버의 해 공간에서는 끝이다. 모델이 쓸 수 있는 상태라는 근거는
`tests/sklearn-parity.spec.ts`의 대조가 전부 통과한다는 사실이다.

**같은 실측이 3번의 답도 준다.** 반복 수는 38~702회였고(3000행 겹침 30%가 702회로
최대, 24.5초·힙 +47MB) **`maxIterations`(10,000)에 닿은 경우가 없다.** 올리지
않는다. sklearn이 800행에 7,174 반복을 쓴 것과 자릿수가 다른 이유는 그쪽이 이론적
최적점까지 가고 우리는 정체에서 멈추기 때문이다.

**`10`은 이름을 갖는다.** 원본 `ml-svm`의 `maxPasses`를 손잡이에서 뺐는데 같은 값이
함수 본문에 리터럴로 되살아나 있었다 (CLAUDE.md §1.5 위반). `SMO_DEFAULTS.stallPasses`가
출처이고, 손잡이로 되돌린 것은 아니다 — `SmoOptions`에는 없다.

### 28. 군집 결과를 어떻게 보여주는가 (V3, 2026-08-11)

**군집은 그림으로 봐야 뜻이 생기는 유일한 유형이다** (`roadmap.md`). 표로 "이 행은
2번 군집"이라고만 쓰면 학생은 아무것도 못 본다.

**특성이 2개 이하면 바로 그린다.** x/y가 하나씩이므로 축 선택이 필요 없다.
**특성이 3개 이상이면 학생이 x축과 y축을 고른다** (Orange3 방식). PCA·t-SNE 같은
차원 축소를 끼우지 않는다 — 학생이 "어떤 특성끼리 보면 군집이 잘 나뉘는가"를
직접 바꿔 보는 것이 교육적 가치이고, 차원 축소는 이 도구가 설명할 수 없는
변환을 학생 모르게 끼우는 것이다.

#### 28-1. 중심점을 함께 그린다. 색이 아니라 **모양**으로 가른다

데이터는 원, 중심점은 **✕에 흰 테두리**다. 색은 군집 번호에 이미 쓰고 있으므로
중심점을 색으로 가르면 색의 뜻이 둘이 된다.

**함께 그리는 것이 이너셔를 설명한다.** "가장 가까운 중심점으로 배정된다"는 규칙과
"자기 중심점까지의 거리 제곱합"이라는 지표가 그림 위에서 같은 것을 가리킨다. 중심점이
없으면 학생이 보는 것은 색깔 뿌린 점들뿐이고, 옆의 숫자와 이어지지 않는다.

#### 28-2. 축 선택은 산점도 **위 왼쪽**에 드롭다운 둘

x축·y축 순서로 나란히 두고, 좁은 화면에서는 세로로 쌓는다 (§8.10.1 — 넓은 화면에서
세로로 늘리지 않는다). 옆(오른쪽 열)에 두지 않는 이유는 결과 화면이 이미 두 열이라
(§8.13) 그 안에 세 번째 열이 생기면 좁은 화면에서 접히는 순서를 또 정해야 하기 때문이다.

**특성이 2개 이하면 드롭다운을 아예 안 그린다.** 고를 것이 없는데 자리를 두면 학생이
고장으로 읽는다 (§9.2 "없는 것을 이름으로 말하지 않는다").

**축 후보는 수치 열뿐이다.** 원핫으로 늘어난 범주 열은 값이 0/1 둘뿐이라 산점도에서
읽을 것이 없다. 목록에서 빼되 그 사실을 말하지는 않는다 — 학생이 고를 수 있는 것만
보인다.

#### 28-3. 색은 일곱을 돌려 쓰고 여덟부터는 **모양으로 가른다**

지금 `--color-chart-1`~`-7`이 일곱 개다(Okabe-Ito, 색맹 안전). `n_clusters` 상한은
20이므로 색만으로는 모자란다.

**색을 스무 개로 늘리지 않는다.** 늘리는 순간 그 팔레트가 색맹 안전이라는 근거가
깨지고, 옆 화면(예측 답 카드)이 쓰는 색과도 갈린다. 대신 **여덟 번째 군집부터 점의
모양을 바꾼다** — 원 → 삼각형 → 사각형. 7 × 3 = 21이라 상한 20을 덮는다.
임의 상수가 새로 생기지 않는다: 색 수도 상한도 이미 있는 값이다.

k가 커지면 그림이 읽기 어려워지는 것은 사실이고, 그건 **k를 크게 잡은 결과**이지
화면이 숨길 일이 아니다.

#### 28-4. 그림의 재료는 파일에서 되계산한다 (담지 않는다)

**`run`에 군집 배정을 담지 않는다.** 혼동 행렬·클래스별 지표는 담는데(k×k라 작다)
배정은 **행마다 하나**라 10만 행이면 runs.json이 그만큼 커진다 — 데이터가 클수록
커지는 값을 요약 파일에 넣지 않는다.

대신 그릴 때 만든다. 재료가 셋 다 파일 안에 있다: `dataset/` · 전처리기 · 모델
(`mlpx-kmeans-v1`). **되계산이라고 해도 재학습이 아니라 예측이다** — 예측 화면이
이미 같은 길을 쓴다(§1.3의 "재학습 없이"에 걸리지 않는다).

**모델이 파일에 없으면 패널도 없다** (§9.5). `run.model`이 없는 경우(예산에서 밀렸거나
직렬화기가 없는 엔진)가 그것이고, 화면은 그 자리에 아무 말도 안 한다 — 사유는 이미
`run.modelOmitted`가 다른 자리에서 말한다.

**점의 위치는 학습 행렬을 그 열의 스케일로 되돌린 값이다.** 원본 표의 값을 그대로 쓰지
않는 이유는 둘이다. (1) 결측을 채운 행이 원본에는 빈 칸이라 자리가 없다 — 모델이 본
것은 채워진 값이다. (2) 중심점은 전처리된 공간의 좌표라, 점만 원본 좌표로 그리면 둘이
다른 공간에 놓인다. 되돌리면 축 눈금이 원래 단위(cm, 원)로 보이면서 점과 중심점이 같은
공간에 있다. 스케일링을 껐으면 되돌리기는 항등이다.

#### 28-5. 그릴 점의 상한 — **이름을 세우고 값은 실측 뒤에 정한다**

10만 행을 그대로 Chart.js에 넘기면 저사양 학교 PC와 휴대폰에서 무엇이 일어나는지
아무도 재지 않았다. 상한은 `frontend/src/limits.ts`가 갖고(CLAUDE.md §1.5),
넘으면 **시드로 표본을 뽑아 그리고 화면이 그 사실을 말한다** — 조용히 일부만 그리면
학생은 자기 데이터가 다 거기 있다고 믿는다. 표본은 `randomState`에서 나오므로 같은
설정이면 같은 그림이다.

**값은 구현하면서 잰다** (시간·힙·상호작용 반응). 재기 전까지 지어 넣지 않는다.

**쟀다 (2026-08-11).** 개발 PC(i5-1135G7) · Chromium · 캔버스 800×420 · 군집 5개 ·
**`animation: false`**로 잰 값이다. 다른 모양으로 재면 그 숫자는 우리 화면의 숫자가 아니다.

> **처음 여기 "화면과 같은 옵션으로 잰 값"이라고 적은 것은 거짓이었다** (2026-08-11,
> 감사가 잡았다). 하네스에는 `animation: false`가 있었는데 **화면에는 없었다.** Chart.js는
> 기본으로 애니메이션을 켜므로 축을 한 번 바꾸면 71프레임을 다시 그린다 — 감사자 측정으로
> 1만 점에서 799ms, 2만 점에서 4,210ms다. 아래 표는 그 옵션을 켠 화면의 숫자가 아니었다.
> **화면에 `animation: false`를 넣어 표와 화면을 맞췄다.** 애니메이션이 켜진 산점도는
> 점 수천 개가 날아다니는 것이라 어차피 이 화면에서 원하는 것이 아니다.

| 점 | 데이터 만들기 | 첫 그리기 | **다시 그리기** | 히트테스트 | 힙 |
|---|---|---|---|---|---|
| 1,000 | 1ms | 57ms | 32ms | 0.2ms | +1.8MB |
| 2,000 | 2ms | 53ms | 35ms | 0.1ms | +3.2MB |
| 5,000 | 11ms | 57ms | 65ms | 0.3ms | — |
| 10,000 | 12ms | 51ms | **46ms** | 0.2ms | — |
| 20,000 | 22ms | 152ms | 164ms | 0.1ms | +15.3MB |
| 50,000 | 48ms | 342ms | 302ms | 0.2ms | — |
| 100,000 | 146ms | 726ms | 740ms | 0.2ms | +24.8MB |

(힙에 `—`인 칸은 그 사이에 GC가 돌아 음수가 나온 칸이다. 뒤의 세 값이 추세를 말한다.)

**감사자가 독립적으로 다시 쟀다** (2026-08-11): 같은 `animation: false`에서 1만 점 92ms ·
2만 점 155ms · 10만 점 1,058ms. 위 표와 두 배까지 갈리는데 **재는 지점이 다르기 때문**으로
보인다(이쪽은 `update()`가 돌아오는 시점, 저쪽은 프레임까지). **두 측정이 같은 결론을
가리키므로 양쪽을 나란히 남긴다** — `limits.ts`의 K-Means 칸이 같은 종류의 차이를 이미
그렇게 두고 있다. 이 칸을 다시 잴 사람은 숫자보다 **어디를 재는지**를 먼저 맞춰야 한다.

**보는 것은 "다시 그리기"다.** 첫 그리기는 패널을 열 때 한 번이지만 다시 그리기는
**학생이 축을 바꿀 때마다** 도는 비용이고, 이 화면에서 학생이 실제로 하는 일이 그것이다
(#28-2 — 어떤 특성끼리 보면 잘 갈리는지 바꿔 보는 것이 교육적 가치다).

**상호작용 반응은 상한의 근거가 아니다.** 히트테스트가 10만 점에서도 0.2ms다 — Chart.js가
점을 훑지 않고 자리로 찾는다. 걸리는 것은 그리기뿐이다.

**10,000으로 정한다.** 근거 셋이고, 임의로 고른 자리가 아니다.

1. **10,000에서 다시 그리기가 46ms다.** 20,000은 개발 PC에서 이미 164ms다. 기준 기기는
   개발 PC가 아니라 **저사양 학교 PC와 휴대폰**이므로(CLAUDE.md §0) 몇 배 느린 기기에서도
   버틸 여유가 있어야 하는데, 46ms는 그 여유가 있고 164ms는 없다.
2. **힙이 그림 하나에 붙는다.** 20,000에서 +15MB, 100,000에서 +25MB다. 학습 행렬을 이미
   들고 있는 위에 얹히는 값이다.
3. **교실 CSV 대부분이 이 아래라 표본 안내가 안 뜬다.** 안내는 정직해서 필요한 것이지
   자주 보이면 좋은 문장이 아니다.

**점이 많아 못 읽는 문제는 상한이 풀어 주지 않는다.** 800×420 캔버스에 반지름 4짜리 점
10,000개면 잉크가 캔버스 넓이를 넘는다 — 이건 표본을 뽑아도 그대로다. 그 자리에서 학생이
할 일은 축을 바꿔 보는 것이고, 화면은 그 길을 이미 열어 둔다.

#### 28-6. 그림만으로는 답이 안 된다 — 요약과 구성원, 그리고 예측 화면 (2026-08-11)

**지금 군집 결과가 어떻게 이루어졌는지 알 방법이 하나도 없다.** 위 다섯은 "어떻게
그리는가"까지만 닫았는데, 학생이 실제로 묻는 것은 **"2번 군집은 어떤 애들인가"**이고 그
질문은 점에 색이 칠해져 있다고 답해지지 않는다. **어떤 특성을 가진 데이터끼리 모였는가가
곧 군집의 결과물이다.**

**그리고 같은 질문을 예측 화면도 받는다.** 새 데이터를 넣어 `2번 군집`이라는 답을 받은
학생의 다음 말은 **"그래서 이거랑 비슷한 게 뭔데"**다. 군집 번호만 주면 그 답은 학생에게
아무 뜻이 없는 정수 하나다.

**두 질문은 정렬 기준이 다르다.** 결과 화면은 *중심점에 가까운 순*(그 군집에서 가장
전형적인 것)이고, 예측 화면은 *그 입력에 가까운 순*(진짜 이웃)이다. 하나로 뭉치면 예측
화면이 "전형적인 것"을 "너와 비슷한 것"이라고 말하게 된다.

**계산은 하나다 — 전체 행의 군집 배정.** 산점도·요약표·구성원 표가 전부 그 하나를 다르게
보여주는 것뿐이다. #28-4의 "재료는 파일에서 되계산한다"가 그대로 적용되고, `run`에 담을
것도 늘지 않는다.

**요약표의 값은 구성원의 실제 평균이다. 중심점을 그대로 쓰지 않는다.**

> **이 문장은 한 번 틀렸다가 고쳤다** (2026-08-11, 감사). 처음에는 "요약은 새로 계산하지
> 않는다 — 중심점이 곧 그 군집의 평균이다"라고 적었다. **그것은 수렴했을 때만 참이다.**
> `fitKMeans`는 루프를 나온 뒤 **최종 중심점으로 한 번 더 배정하는데**(V3 감사가 배정과
> 중심점의 한 스텝 어긋남을 고치면서 넣은 것이다) 그 중심점은 **직전 배정의 평균**이다.
> 수렴하면 두 배정이 같아 중심점이 정확히 그 평균이지만, `maxIter`에 닿으면 갈린다 —
> 0~100 규모의 열에서 2.7만큼 어긋난 실측이 있다.

그래서 **배정에서 한 번 훑어 실제 평균을 낸다.** 이미 들고 있는 학습 행렬로 O(n·d)이고,
10만 행에서도 수십 ms다. 표가 `평균`이라고 쓰고 그 자리에 평균이 아닌 값을 보이는 것이
이 저장소가 규정한 최악(조용히 틀린 결과)에 가장 가까운 자리다.

**중심점은 그림의 ✕로 남는다.** 그것은 모델이 실제로 쓴 점이고(#28-1이 이너셔를 설명하는
근거로 삼은 것이 그것이다), 요약표가 답하는 것은 "이 군집은 어떤 애들인가"라 **구성원의
평균**이다. 둘이 갈리는 경우는 수렴하지 못한 학습뿐이고, **그 차이 자체가 정보다** —
화면은 이미 `KMEANS_NOT_CONVERGED`로 그 사실을 말하고 있다.

평균은 **되돌린 값의 평균**이다(스케일 되돌리기가 열마다 1차식이라 되돌린 뒤 평균이나
평균 뒤 되돌리기나 같다). 원핫 열이라면 그 값이 **그 범주의 비율**이 된다. 엄밀히는
결측을 채운 뒤의 평균이고, 그 차이는 아래에서 표가 원본 값을 보이는 것으로 드러난다.

**정한 것 넷.**

1. **구성원 표는 원본 표의 열을 전부 보인다. 특성 열만이 아니다.** 이름·번호처럼 학습에서
   뺀 열이 **"누가 그 군집인가"에 답하는 유일한 열**이다. 특성 열만 보이면 표가 숫자
   덩어리이고 학생은 그것이 누구인지 모른다. 넓으면 가로로 스크롤한다.
2. **군집은 요약표의 줄을 눌러 고른다.** 요약표는 군집마다 한 줄(크기 + 특성별 평균)이라
   `n_clusters` 상한 20도 한눈에 들어온다. **결과 화면이 이미 쓰는 문법이다** — 점수 표의
   줄을 누르면 그 아래가 펼쳐진다(`architecture.md` §8.13). 학생이 새로 배울 것이 없다.

   **머리글은 눌러 설명을 연다** (2026-08-11에 더했다). 점수 표의 지표 머리글이 이미
   그렇고(`TermPopover`), 요약표만 아무 설명이 없으면 **한 화면에서 같은 자리가 다르게
   군다.** 다만 여기 제목은 우리 어휘가 아니라 **학생의 열 이름**이라 번역하지 않는다 —
   설명만 우리가 쓴다.

   **설명에 전체 평균과 값의 범위를 함께 준다.** "이 군집의 평균 45"만으로는 그것이 높은
   값인지 낮은 값인지 알 수 없고, **그 판단이 이 표를 보는 이유**다. 예측 화면이 빈 숫자
   칸에 `데이터에 있는 값: {min} ~ {max}`를 주는 것과 같은 종류의 도움이다.
3. **구성원은 중심점에 가까운 순으로 위에서부터 몇 줄만.** 가까운 순인 이유는 **가장
   전형적인 것부터**이기 때문이다. 줄 수 상한은 `frontend/src/limits.ts`가 갖고
   (CLAUDE.md §1.5), **전체 몇 행 중 몇 행인지를 화면이 함께 말한다** — #28-5가 표본을
   말하게 한 것과 같은 이유다. 이 값은 실측 대상이 아니라 **훑어보기 상수(`PREVIEW_ROW_COUNT`)와
   같은 근거**로 정한다: 표를 눈으로 훑어 감을 잡는 데 필요한 줄 수다.
4. **요약표에는 수치 열만 넣는다. 범주 비율은 미룬다.** 원핫 열의 평균에도 뜻이 있지만
   (`성별=남 0.72`) 범주가 많으면 표가 옆으로 터진다. 넣는 날 고칠 자리는 요약표 하나다.

**표는 원본 값, 그림은 되돌린 값이다. 둘이 다를 수 있고 그것이 맞다.** #28-4가 정한 대로
점의 좌표는 학습 행렬을 되돌린 값이라 **결측을 채운 자리에 값이 있다.** 표는 원본 행
그대로이므로 그 칸이 빈 칸이다. 표를 채워진 값으로 보이면 **학생의 데이터에 없는 숫자를
우리가 지어내 보여주는 것**이 되고, 빈 칸으로 두면 오히려 "결측을 채워서 학습했다"는
사실이 눈에 남는다.

**전처리 공간으로 그리지 않는다** (2026-08-11에 한 번 더 물었고 같은 답이 나왔다).
스케일링이 열마다 1차식이고 차트가 각 축을 데이터 범위에 맞춰 늘리므로, **되돌리든 안
되돌리든 점의 배치는 같다 — 달라지는 것은 축에 적히는 숫자뿐이다**(눈금 정리 때문에
가장자리 여백만 미세하게 다르다). 그러면 `-0.4`와 `170` 중 무엇이 학생에게 읽히는가만
남고, **그림 아래에 원본 값 표가 붙는 이상 축은 `170`이어야 한다.** 축이 `-0.4`인데
표에 `170`이 있으면 학생이 둘을 이을 방법이 없다.

**배정은 전체 행에 하고, 표본은 그리는 점에만 건다.** #28-5의 상한을 여기서 한 겹 좁힌다 —
구성원 표는 "그 군집의 구성원"이라고 말하므로 표본 안에서 고르면 거짓말이 되고, 군집
크기도 마찬가지다. 상한이 걸리는 것은 **산점도에 찍는 점**이고, 배정·크기·구성원은 전체
행에서 나온다.

**예측 화면 — 군집 번호 옆에 그 군집의 요약과 가까운 행 몇 개가 선다.**

- **정렬은 입력과의 거리다.** 전처리기로 만든 입력 벡터와 학습 행렬 사이의 거리이고,
  중심점까지의 거리가 아니다.
- **데이터가 없으면 답은 나오고 표만 없다** (`architecture.md` §9.5). `mlpx-kmeans-v1`은
  `needsTrainingRows: false`라 중심점만으로 군집 번호를 답한다 — 여기서 모델을 통째로
  끄면 **지금 되던 것이 안 되게 된다.**
- **비용은 참조형과 다르다.** KNN이 무거운 것은 *예측 행마다* 학습셋 전체와 거리를 재기
  때문인데(`MLJS_KNN_ROW_LIMIT`의 근거), 여기는 **입력 한 줄 대 학습 행 전체**라 한
  번이다. 실제 비용은 학습 행렬을 만드는 쪽이고 그건 화면이 한 번 만들어 들고 있는다.

#### 28-7. 예측 화면에도 그림이 선다 — 새 점은 색이 아니라 모양으로 가른다 (2026-08-11)

**"내가 넣은 데이터는 저기 어디쯤 있나"가 이 그림의 유일한 이유다.** #28-6이 답 옆에
이웃 표를 세웠는데, **그 다섯 줄이 왜 비슷한지는 숫자를 눈으로 견줘야** 안다. 점 하나가
찍히면 그게 한눈에 끝난다.

**새 점을 빨간색으로 그리지 않는다.** 색은 이미 군집 번호에 쓰이고 있고(#28-3), 빨강은
이 저장소에서 `danger`(실패·경고)의 자리라 **학생이 "내 데이터가 잘못됐다"로 읽는다.**
중심점을 색이 아니라 모양(✕)으로 가른 것과 같은 방식을 쓴다.

> **입력한 데이터는 흰 테두리를 두른 마름모이고, 색은 답으로 나온 군집의 색이다.**

그러면 **"너는 2번 군집이다"가 색으로, "이건 네가 방금 넣은 것이다"가 모양으로** 읽힌다.
마름모(`rectRot`)를 고른 이유는 군집이 쓰는 세 모양(원·삼각형·사각형, #28-3)과 겹치지
않는 채워진 도형이기 때문이다 — 중심점의 ✕처럼 선으로만 그려지는 모양은 점이 몰린
자리에서 묻힌다.

**그림은 두 화면이 같은 부품을 쓴다** (`components/ClusterScatter.vue`). 축 선택·표본
안내·배색 토큰 읽기가 전부 그 안에 있고, 결과 화면과 예측 화면은 **재료와 새 점만**
넘긴다. 같은 그림을 두 벌로 두면 축 규칙이나 색 규칙이 한쪽에서만 고쳐질 자리가 생긴다.

**자리는 이웃 표 위, 군집 요약 배지 아래다.** 답 카드는 3분의 1 폭이라 그림이 안
들어가므로 `이 답과 비슷한 데이터` 덩어리 안에 놓는다. 모델이 여럿이면 덩어리마다
하나씩이다.

### 군집화(K-Means)의 핵심 결정 넷 (V3, 2026-08-11)

**1) K-Means 엔진은 직접 구현한다.** 의존성(`ml-kmeans`)을 쓰지 않는다. K-Means
알고리즘은 단순하다 — 초기화(K-Means++) + Lloyd 반복이 핵심이고 50줄 이내다.
SVM을 벤더링한 기준이 세워 둔 잣대가 있다: "라이브러리가 해 주는 일이 직접 짜는
것보다 충분히 많은가." K-Means는 아니다.

**2) 군집에 훈련/테스트 분할을 하지 않는다.** 비지도학습에는 정답이 없으므로
"보지 않은 데이터에서 성능을 확인한다"는 전제가 성립하지 않는다. sklearn도
`fit(X)` → `score(X)`이지 `fit(X_train)` → `score(X_test)`가 표준 용법이 아니다.
전체 데이터로 학습하고 전체 데이터에 대해 지표를 낸다.

**3) 군집 지표는 실루엣 계수와 이너셔 둘이다** (위 #29).

**4) 산점도는 V3의 맨 마지막에 한다** (위 #28). 특성 3개 이상이면 학생이 x/y축을
고르는 방식이다 (Orange3 방식).

### sklearn 대조 픽스처가 CI 관문에 들어간다 (2026-08-10)

**"저장했다 읽으면 같은 예측"만으로는 찍기보다 못한 모델도 충실하게 왕복한다.** 순수 JS
엔진의 결함이 세 번 다 지표 대조가 아니라 sklearn 대조에서 잡혔는데
(`ml-naivebayes`의 특성 2개, 로지스틱 원좌표 발산, `ml-svm`의 H 수식) 그 대조가 일회성
프로브라 다음 결함이 들어와도 CI는 조용했다. V2 감사 1단계-A가 상시 장치로 바꿨다.

**장치는 하이브리드다.** 근거는 CI의 제약 둘 — `frontend/npm run ci` 한 줄이 프런트엔드의
완전한 관문이어야 하고(deploy.yml이 배포를 거기 걸었다), 기대값이 저장소 안 숫자로
있어야 엔진 변경이 diff에서 보인다.

1. **기본 관문**: sklearn으로 한 번 생성한 기대값을 JSON 픽스처로 커밋하고
   (`frontend/tests/fixtures/sklearn/`), vitest가 우리 엔진을 그 픽스처와 대조한다
   (`tests/sklearn-parity.spec.ts`). 파이썬 없이 돈다.
2. **낡음 방지**: CI에 잡을 하나 더 둬서 sklearn(backend uv.lock이 1.9.0을 못박는다)으로
   픽스처를 재생성해 커밋된 것과 다르면 실패시킨다
   (`scripts/generate_sklearn_fixtures.py --check`). 픽스처가 조용히 낡는 것을 막는다.

**데이터셋은 감사가 결함을 실제로 잡은 아홉 모양이다** — 붓꽃 하나로는 세 결함 전부가
통과했었다. 원점 경계·합격선·스케일 제각각·겹침·다중 클래스·붓꽃 150행·회귀·범주
혼합·결측. 각 픽스처에 **다수 클래스 기준선이 함께 들어 있다** — "모델이 찍기보다
못하다"가 자동으로 걸린다.

**판정 문턱은 실측에서 나왔다** (2026-08-10 감사 대조표). 임의 상수가 아니다.

|---|---|---|
| 나이브베이즈 | 예측 라벨 완전 일치 + 파라미터 상대차 ≤ 1e-9 | 닫힌 식. 실측 비트 일치 |

| 로지스틱 (양쪽 수렴) | 예측 라벨 완전 일치 (경계 행은 판정 제외) | L2의 유일 최적점 — 일치가 구조다. 11벌 실측 라벨 일치·계수 3.3e-3 |
| 로지스틱 (한쪽이라도 미수렴) | 기준선 초과 + sklearn − 0.1 이상 + 라벨 일치율 ≥ 0.9 | 둘 다 경로 중간에 멈춘 자리 — 트리 계열과 같은 갈래 (2)이므로 같은 여유(0.1)를 쓴다. 일치가 우연이라 완전 일치를 요구하면 아무 문제 없이도 빨개진다 |
| **로지스틱 경고 발화** | **우리 `run.warning` 유무 = sklearn의 수렴 실패 여부** | 1단계-B·C의 가장 값진 실측 — 11벌 중 10벌 + Opus 독립 2벌에서 같은 자리에 떴다. 관찰로 두면 다음 변경에서 조용히 사라진다. **iris 한 벌은 예외로 기록한다**(sklearn은 83회에 아슬아슬 수렴, 우리 선탐색은 꼬리가 길어 100회 초과 — 보수적인 쪽. 문턱을 조정해 침묵시키면 근거 없는 임계값이 된다) |

이를 위해 픽스처가 **sklearn의 `n_iter_`와 수렴 여부를 함께 담는다** (2026-08-11,
1단계-C) — 관문이 빨개졌을 때 "진짜 결함인가, 경로가 조금 움직인 것인가"를 가를
근거가 파일 안에 있어야 한다.

### 로지스틱 회귀 솔버를 sklearn과 같은 구조로 바꾼다 (2026-08-10, 1단계-B)

**아래 "내부 표준화" 결정을 대체한다.** 그 수정으로 정확도는 sklearn 수준이 됐지만
검토(1단계-B)에서 남은 문제 셋이 **하나의 원인**으로 판정됐다 — 규제가 없으면 분리
가능한 데이터에서 로그손실의 최적점이 **무한대**라, ① 확률이 포화하고(우리 48~62%
vs sklearn 0%), ② 수렴 경고의 문턱을 어떤 값으로도 근거 있게 그을 수 없고("좋은
모델"과 "덜 배운 모델"을 기울기가 못 가른다), ③ 큰 행에서 고정 스텝이 수렴을 못 한다
(2만 행 0.78 vs 최적점 0.92). 코드 소유자가 이 항목에 한해 의존성 교체 제한을 풀었다.

**sklearn `LogisticRegression` 기본값의 목적함수를 그대로 푼다** — L2(`C=1.0`),
절편(규제 제외), `tol=1e-4`, `max_iter=100`. 손잡이도 sklearn 이름이다(`C`·`maxIter`·
`tol`). L2가 최적점을 유한하고 **유일하게** 만들므로, 어떤 올바른 솔버든 sklearn과
같은 자리에 도착한다 — 대조가 "경로"가 아니라 "도착점"의 문제가 되고, 그 도착점은
CI의 sklearn 픽스처가 지킨다.

**다중 클래스는 multinomial(softmax)이다** — sklearn 1.9의 lbfgs 기본값과 같다.
one-vs-rest로 남기면 다중 클래스에서 두 엔진이 구조적으로 일치할 수 없다.
**이진은 sklearn과 같이 binomial(시그모이드) 목적함수로 풀되**, 저장은 가중치를
±절반으로 나눈 두 줄로 한다 — `softmax([−s/2, +s/2]) = sigmoid(s)`가 정확히 성립해
해석기가 softmax 하나로 통일되고, sklearn의 이진 규제 세기와도 정확히 같다.
(이진을 softmax로 직접 풀면 규제가 사실상 절반이 되어 sklearn과 계수가 갈린다.)

**솔버는 L-BFGS를 우리가 짠다** (`ml/engines/logistic.ts`). 의존성·벤더링을 먼저
검토했다:

- mljs 생태계에는 lbfgs도, 규제 있는 로지스틱도 없다. 떼어낸
  `ml-logistic-regression`이 그 생태계의 답이었고 그 답이 이번 감사의 발견이다.
- 범용 최적화 JS 패키지(fmin 등)는 8년 이상 방치됐고 sklearn과 대조된 적이 없다.
- **벤더링해도 검증 비용은 같다** — SMO를 벤더링했더니 원본에 수식 오류가 있었다
  (H 경계, 1단계-A). 이 종류의 코드는 어차피 sklearn 오라클로 전수 대조해야 하고,
  그 오라클(CI 픽스처)이 이제 상시로 있다. 위 유일-최적점 성질 때문에 이 대조는
  SMO 때보다 강하다 — 계수 자체가 sklearn과 맞아야 한다.

수렴 판정은 sklearn과 같다 — 목적함수 기울기의 최대 성분이 `tol` 아래로 내려가면
수렴, `maxIter`에 닿으면 `LOGISTIC_NOT_CONVERGED`(sklearn의 `ConvergenceWarning`
자리). 최적점이 유한해졌으므로 이 경고는 이제 정말로 "덜 배운 모델"에서만 뜬다.

**정확한 서술은 조건부다 (2026-08-11, 1단계-C):**

> **로지스틱은 수렴하면 갈래 (1)이고, `maxIter`가 물리면 갈래 (2)다.** 갈래 (2)일 때
> 원인의 이름은 "둘 다 반복 예산에서 멈춘 서로 다른 지점"이고, 교실에서 설명되며,
> **경고가 그 사실을 말해 준다.** Opus의 독립 대조(픽스처 밖 데이터 두 벌)에서 수렴한
> 벌은 계수 상대차 1e-3·라벨 완전 일치였고, 양쪽 다 maxIter에 걸린 벌은 계수가 3배까지
> 갈리면서도 정확도는 동일했다 — 그리고 그 자리에서 양쪽 경고가 같이 떴다.

우리 선탐색(Armijo 역추적)은 scipy(강한 Wolfe)보다 **tol 도달의 꼬리가 길다** —
행이 많을수록 같은 tol이 더 높은 상대 정밀도를 뜻하기 때문에(기울기가 합 규모라 n에
비례해 자란다) 큰 데이터에서 sklearn은 수렴하는데 우리는 maxIter에 걸리는 쪽으로
갈릴 수 있다(실측: 같은 분포에서 5만 행 24회 수렴 / 10만 행 100회 도달). 보수적인
쪽(경고를 내는 쪽)으로 갈리고, 학생 대응(maxIter ↑)은 sklearn과 같다.

`numSteps`·`learningRate`는 lbfgs에서 뜻이 없어 손잡이 표에서 빠진다. 옛 파일에
남은 값은 `resolveWith`가 모르는 키로 그대로 통과시키고 엔진이 무시한다.

### ~~로지스틱 회귀는 엔진 안에서 표준화하고 절편을 학습한다~~ (2026-08-10, 위 결정으로 대체됨)

**원좌표 경사하강은 교실 데이터에서 기준선 이하였다.** `ml-logistic-regression`은
규제도 절편도 없는 고정 학습률 경사하강이고, 이 조합은 **값의 높낮이로 갈리는 데이터**
(합격선·기준 점수 — 교실 데이터의 대부분)에서 다수 클래스로 전부 찍는 것보다 못했다.
2026-08-07의 사용자 실측(합격선 데이터에서 35%, 기준선 65%)을 V2 감사 1단계-A가
독립 데이터 8벌로 재현·확장했다.

**실측 (2026-08-10, 감사 대조 장치 · 시드 42 · sklearn 1.9.0).** 값은 정확도이고
sklearn 열은 같은 행렬 위의 `LogisticRegression()` 기본값이다.

| 데이터 모양 | 기준선 | 고치기 전 | 내부 표준화+절편 | sklearn |
|---|---|---|---|---|
| 원점 지나는 경계 (`국어>수학`) | 0.500 | 1.000 | 0.950 | 0.975 |
| 합격선 (`국어+수학≥120`) | 0.700 | 0.700 | **1.000** | 1.000 |
| 합격선 + 절편만 (표준화 없이) | 0.700 | **0.367** | — | — |
| 스케일 제각각 (키/몸무게/나이) | 0.500 | **0.500** | **1.000** | 1.000 |
| 겹치는 두 클래스 | 0.500 | **0.500** | 0.717 | 0.717 |
| 3클래스 | 0.433 | 0.650 | 0.867 | 0.850 |
| 붓꽃 150행 | 0.333 | 0.933 | 0.967 | 0.967 |
| 범주 혼합(원핫) | 0.604 | 0.750 | 0.750 | 0.750 |
| 결측 있는 데이터 | 0.512 | 0.707 | 0.829 | 0.829 |

- **표준화와 절편은 한 몸이다.** 절편만 더하면 오히려 기준선 아래로 떨어지고(0.367),
  표준화만 하면 붓꽃에서 0.933→0.767로 되레 나빠진다. 둘을 함께 넣어야 여덟 벌 전부에서
  sklearn 기본값과 같은 수준이 된다.
- **스텝을 늘리는 것은 답이 아니다.** 원좌표에서 10000스텝은 3클래스 데이터를
  0.650→0.383(기준선 이하)으로 떨어뜨렸다 — 조건수가 나쁜 좌표계에서 고정 학습률은
  더 걸을수록 발산한다.

**그래서 솔버를 바꾸지 않고 좌표계를 바꾼다.** 최적화 직전에 엔진이 내부 표준화를 하고
값이 늘 1인 열로 절편을 학습한 뒤, 가중치를 원래 좌표계로 접어 저장한다
(`mlpx-spec.md` §5.4.1). 학생의 스케일링 설정과 무관하다 — "표준화를 켜야 제대로 도는
모델"은 화면이 말해 주지 않는 함정이고, SMO가 min-max를 접어 돌려주는 것과 같은 자리다.
절편이 생기므로 모델 형식이 `mlpx-linear-v2`가 된다 (§5.4 규칙 3이 예고한 그대로다).

**확률 보정(온도)은 넣지 않는다 — 지금은.** 규제가 없으므로 분리 가능한 데이터에서는
가중치가 자라 확률이 포화하는 것이 남는데, 실측에서 **포화는 정확도 100% 근방에서만
남았다**(합격선 48%·스케일 62.5%가 포화, 겹치는 데이터와 3클래스는 0%). 문제였던
"정확도 60%짜리가 100%라고 말하는" 조합은 원좌표 발산의 증상이었고 좌표계를 고치니
사라졌다. 온도는 평가셋으로 맞춰야 해서(학습셋으로 맞추면 분리 가능한 데이터에서 더
확신하는 쪽으로 간다) 설계가 한 덩어리 더 필요하다 — 필요해지면 그때 연다.

**sklearn과 같은 구조(L2 + lbfgs)로 가는 것은 의존성 교체라 이 감사의 범위 밖이다**
(1단계-A C등급). 위 표가 보여주듯 좌표계만 고쳐도 여덟 벌 전부에서 sklearn 기본값과
같은 수준이므로, 솔버 교체는 그 수준이 모자라는 데이터가 실제로 나타날 때 연다.

### 파이썬 표준 관행을 따른다 — 열 순서까지 (2026-08-07)

**이 도구는 종착지가 아니라 발판이다.** 여기서 배운 학생이 다음에 만나는 것은
scikit-learn이고, 그때 **화면에서 익힌 모양이 그대로 통해야** 이 도구가 한 일이 남는다.
낯선 배열을 우리가 지어내면 학생은 두 번 배우고, 둘 중 하나는 여기서만 통하는 지식이다.

> **이름·순서·기본값에서 고를 것이 있으면 파이썬 생태계의 관행을 고른다.**

**범주별 점수표의 열 순서가 그 첫 적용이다.** `정밀도 · 재현율 · 특이도 · F1 점수 ·
실제 데이터 수` — sklearn `classification_report`의 `precision, recall, f1-score, support`가
**상대 순서 그대로** 들어 있고, 그 표에 없는 특이도만 사이에 끼워 넣었다. 끼워도 넷의
앞뒤가 안 바뀌므로 관행은 지켜진다.

**수업 교재의 소개 순서를 근거로 삼지 않는다** (2026-08-07에 뒤집었다). 한때 "교재가
정확도 → 정밀도 → 재현율 → 특이도로 소개하니 그 순서"라고 적었는데, **순서·이름·기본값은
다음에 만날 도구가 정한 약속**이라 표준 라이브러리를 따르는 것이 맞다.

**낱말 쪽도 2026-08-11에 한 번 더 정리됐다** — 한때 "낱말은 교재를 따른다"였는데
지금은 **학계에서 굳어진 말**이 기준이다(`CLAUDE.md` 2, `terms.md`). 학생이 다음에 갈
곳에서 통하는 말이어야 여기서 배운 것이 남기 때문이고, 그래서 낱말과 구조가 이제 같은
곳을 가리킨다.

같은 규칙이 걸리는 자리들 — 지표 이름(`f1Macro`는 sklearn의 `f1_score(average='macro')`),
0으로 나누는 자리의 처리(sklearn `zero_division=0`, `ml/metrics.ts`), 혼동 행렬의 축
(행이 실제, 열이 예측 — `mlpx-spec.md` §4). 새 표나 새 지표를 더하는 사람은 **sklearn이
그걸 어떻게 부르고 어느 순서로 두는지 먼저 확인한다.**

### 데이터 종류는 프로젝트를 만들 때 고르고, 그 뒤로 안 바뀐다 (2026-08-06)

**업로드한 파일로 추론하지 않는다.** 새 프로젝트를 만드는 자리에서 "표로 배우기 /
사진으로 배우기"를 고르고, `manifest.dataType`이 거기서 정해져 **프로젝트가 끝날 때까지
그대로다.** 바꾸고 싶으면 새 프로젝트를 만든다 — "하나의 프로젝트 = 하나의 파일"과
어긋나지 않는다.

V1은 표뿐이라 선택지가 하나다. **선택지가 하나면 묻지 않는다.** 이 결정이 화면에
나타나는 것은 이미지가 들어올 때부터다.

**왜 추론이 아니라 선택인가.**

- **§9의 dataType 축이 프로젝트 수명 내내 고정된다.** 등록부 넷(알고리즘·지표 패널·
  전처리 단계·데이터 판)이 전부 이 축을 본다. 도중에 값이 바뀌면 이미 고른 모델·전처리·
  타깃이 새 조합에서 성립하는지 매번 다시 판정해야 하고, **성립하지 않을 때 무엇을
  버릴지가 전부 새 결정이 된다.** 고정이면 그 문제가 통째로 없다.
- **추론은 실패 상태를 만든다.** "이미지 수업인 줄 알고 CSV를 올렸다"에 화면이 답해야
  하는데, 그건 학생이 무엇을 잘못했는지 모르는 자리다. 생성 시 정하면 업로드 버튼이
  애초에 그 종류만 받는다 (`data/kinds.ts`의 `accept`).
- **데이터 화면이 하나로 정해진다.** "이미지 올리기 / 표 올리기"를 고르는 버튼이 없다.
  판 하나가 화면 전체를 쓴다.
- **교실 흐름과 같다.** 교사가 "오늘은 사진으로 합니다"라고 말하고 수업이 시작된다.
  파일을 올려 봐야 무엇을 하는 수업인지 정해지는 것은 거꾸로다.
- Teachable Machine도 프로젝트를 만들기 전에 Image/Audio/Pose를 묻는다. 훨씬 단순한
  도구인데도 그렇게 한 것은 **종류가 정해져야 그 뒤 화면이 하나로 정해지기** 때문이다.

**대가는 하나다 — 아무것도 보기 전에 질문을 하나 받는다.** 문구로 감당한다. `image` /
`tabular` 같은 말이 아니라 학생의 말로 쓴다. 실제 문구는 그때 `docs/copy.md` 규칙대로
짓는다 — **지금 미리 쓰지 마라.** 쓸 대상이 없는 문장은 아무도 화면에서 못 보고
검사도 못 잡는다.

**값의 이름은 `tabular`다. 바꾸지 마라.** `csv`면 xlsx가 거짓말이 되고, `numeric`이면
문자 열이 든 표가 거짓말이 된다(범주형 인코딩이 있는 이유다). `tabular`는 표 형태만
말하고 안의 자료형은 말하지 않는다. 그리고 이 값은 `.mlpx`에 그대로 들어가므로
바꾸는 것은 포맷 변경이다.

**`DATA_TYPES`에는 지금 되는 것만 넣는다 (2026-08-06).** 한동안 `['tabular', 'image',
'audio', 'text']` 넷이 다 들어 있었다. 빼기로 했다 — 안 되는 값을 어휘에 미리 넣으면
**등록부가 거짓말을 하고, 강제 장치가 죽는다.**

- 혼동 행렬 항목이 `image: false`라고 선언하는데, `false`의 뜻은 "이 조합에서 성립하지
  않는다"다 (§9.2.1). **혼동 행렬은 이미지 분류에 당연히 성립한다.** 안 만들었을 뿐인데
  파일에는 "안 된다"라고 적혀 있다.
- 그리고 V5에 이미지를 구현해도 **아무것도 안 깨진다.** 칸이 이미 `false`로 채워져
  있으므로 사람이 다시 볼 일이 없고, 일곱 줄이 전부 "이미지에서는 안 됩니다"라고 말한
  채로 넘어간다. 축을 미리 채워 두는 것은 **§9.3.1이 금지한 일괄 치환을 미리 해 두는
  것**과 같다.

그러므로 **어휘에 값을 더하는 것은 그 종류를 구현하는 커밋이 한다.** 그때 등록부가
전부 빨개지고, 넣는 사람이 항목마다 판단한다. 그것이 §9의 장치가 일하는 순간이다.

무엇을 만들 예정인지는 `roadmap.md`가 갖는다(V5 이미지 → V6 음성 → V7 텍스트).
**어휘는 지금 참인 것만 담는다** — 등록부에 'planned'를 안 두는 것과 같은 규칙이다.

### 순수 JS 서포트 벡터 머신을 넣는다 (2026-08-06)

**브라우저에서 SVM이 돈다.** 지금은 sklearn 전용이라 서버나 pyodide가 없으면 카드가
꺼져 있는데, 그 상태가 공식 배포(GitHub Pages)의 기본값이라 **대부분의 학생에게 SVM은
없는 물건이었다.**

**솔버는 직접 짜지 않는다. `ml-svm`(mljs, SMO, MIT)을 쓴다.** 직접 구현을 검토했고
그러지 않기로 했다 — 짜야 하는 것은 껍데기가 아니라 SMO(KKT 조건·작업집합 선택·수렴
허용오차·커널 캐시)이고, **이 종류의 코드는 틀렸을 때 예외를 던지지 않고 그럴듯한 숫자를
낸다.** 그런데 브라우저 안에는 대조할 상대가 없다. 유일한 오라클이 sklearn 대조
프로브인데 **그건 라이브러리를 쓰든 직접 짜든 어차피 해야 하는 일이라**, 직접 구현은
비용만 훨씬 크고 검증 수단은 똑같다.

`ml-naivebayes`를 뺐던 종류의 결함은 실측으로 배제됐다(아래 표). 남은 위험은 마지막
배포가 10년 전이라는 것인데 **그건 코드가 안 바뀐다는 뜻이기도 하고**, MIT라 최악의
경우 벤더링한다.

**실측 (2026-08-05, 합성 데이터·결정적 난수).** 다시 재지 마라.

| 확인한 것 | 결과 |
|---|---|
| 특성 4·10·20개, **신호를 뒤쪽 특성에만** | 전부 정확도 1.0000 |
| 3클래스 라벨을 그대로 넘기면 | **던지지 않고 전부 `1`** — 조용히 틀린다 |
| one-vs-rest로 감싸면 (3클래스·특성 8개) | 1.0000 |
| 선형 커널 직렬화 | `{options, b, minMax, W}` — **747바이트, 왕복 동일** |
| 속도 (이진 1개) | 200행 66ms · 500행 311ms · 1000행 1.8초 · **2000행 10.4초** |

**다중 클래스는 one-vs-one으로 우리가 감싼다.** 라벨을 그대로 넘기면 조용히 틀리므로
감싸는 것 자체가 필수고, 방식을 `SVC`와 맞춘다 — 우리 화면에서 순수 JS SVM은
`scikit-learn · 내 컴퓨터`와 **나란히 서므로**, 방식이 다르면 학생이 그 차이를 "엔진
차이"로 읽는다. 각 분류기가 두 클래스만 보므로 위 표의 제곱 곡선에서도 이득이다
(3클래스 총 연산이 같은 크기 이진 한 번의 1.3배쯤이다).

**껍데기는 40줄이고 루프와 투표뿐이라 테스트로 전수 확인된다.** 위험한 곳은 솔버이고
그건 우리가 안 건드린다.

**함께 들어가야 하는 것 둘.** 없이 넣으면 안 된다.

- **sklearn 대조 프로브.** 가우시안 나이브 베이즈 때와 같은 방식. 여기서 어긋나면
  그때 직접 구현을 다시 본다.
- **알고리즘별 행 상한.** 지금 `BROWSER_ROW_LIMIT` 하나가 전역인데, 의사결정트리가 즉시
  끝나는 데이터에서 SVM만 몇 분이다. 등록부에 값 하나가 느는 일이고, 화면은 이미
  사유와 함께 카드를 끄는 법을 안다.

**착수 시점은 나머지 모델 형식 작업과 한 덩어리다** — 예측 화면 뒤이고(#21), 직렬화
형식이 그때 함께 정해진다 (`roadmap.md` 구현 순서 6의 "모델 직렬화").

**구현하면서 정할 것 셋** — **전부 정해졌다 (2026-08-06). 아래 "다시 쟀더니"를 보라.**

1. **동점 처리.** sklearn `SVC`는 결정함수 값의 합으로 가른다. `ml-svm`이 마진을
   내주면 같게 맞추고, 안 주면 **클래스 이름 순으로 가르고 그 사실을 적는다.** 3파전
   동점은 드물지만 일어나고, 그때 sklearn과 한 줄 다를 수 있다.
2. **하이퍼파라미터(`C`·커널)를 화면에 열 것인가.**
3. **`mlpx-spec.md` §5의 분류를 고쳐야 한다.** 표는 SVM을 참조형
   (`mlpx-reference-v1`, `dataset/`이 필요)으로 적어 두었는데 **선형 SVM은 가중치뿐이라
   자체 완결이다.** RBF는 안 재 봤다 — 서포트 벡터를 담을 테니 커지겠지만 그때도
   `dataset/`은 필요 없을 가능성이 높다.

#### 다시 쟀더니 위 표가 다른 축을 재고 있었다 (2026-08-06)

**"다시 재지 마라"고 못 박아 둔 표가 틀렸다.** 재 보라는 뜻이 아니라, **그 표가 재고
있던 것이 행 수가 아니었다**는 뜻이다. 위 속도 줄은 전부 **완전히 분리되는 합성
데이터**에서 나왔고(정확도 1.0000이 그 증거다), 갈리는 축은 행 수가 아니라 **두 클래스가
경계에서 겹치는가**다.

같은 조건(특성 8개·이진 1개·시드 고정)에서 데이터 모양만 바꿔 다시 쟀다.

| 데이터 | 1000행 | 2000행 | 5000행 |
|---|---|---|---|
| 여백을 두고 분리 | 2.0초 · 748바이트 | 25.7초 | 181초 |
| 경계에 닿게 분리 | 19.6초 **던짐** | — | — |
| 경계가 겹침 (교실 CSV) | 24초 **던짐** | 158초 **던짐** | — |

**`ml-svm`은 수렴하지 못하면 던진다** — `svm.js:139`의 `throw new Error('max iterations
reached')`. 500행에서도 던진다. **상한을 낮춰도 이 실패는 안 없어진다.** `tol`을 1e-2로
풀고 `maxPasses`를 3으로 낮추면 겹치는 1000행이 5.1초에 정확도 0.969로 수렴하지만,
1e-3·5로는 여전히 던졌다 — **수렴이 데이터 모양에 아슬아슬하게 걸려 있고, 그 손잡이를
감으로 돌리는 만큼 sklearn의 답에서 멀어진다.**

그리고 `defaultOptions.random`이 `Math.random`이다. SMO가 짝을 무작위로 고르므로
**시드를 안 꽂으면 같은 설정으로 두 번 돌려도 결과가 다르다.** `randomState`는 항상
저장하고 항상 쓴다(CLAUDE.md §2)가 그대로 깨진다.

##### 그래서 벤더링한다

MIT이고 원래 "최악의 경우"로 열어 둔 길이다. 바꾸는 것은 셋뿐이다.

- **반복을 다 써도 던지지 않는다.** 그때까지의 계수로 모델을 만들고 **수렴하지 못했다는
  사실을 함께 낸다** (`mlpx-spec.md`의 `run.warning`). sklearn도 같은 자리에서 경고만
  내고 모델을 준다. **조용히 틀리는 것이 아니다 — 화면이 그 사실을 말한다.**
- **난수를 주입한다.** `randomState`가 들어가면 재실행 대조가 성립한다.
- **선형 커널만 남긴다.** 커널 추상이 빠지면 학습 루프가 짧아지고 빨라진다.

위험한 곳이 솔버라는 판단은 그대로다. 그래서 **바꾸는 세 줄 말고는 손대지 않고**,
sklearn 대조 프로브로 확인한다.

##### 정해진 셋

1. **동점은 sklearn `SVC`와 같게 결정함수 값의 합으로 가른다.** 마진을 낼 수 있으므로
   추측할 이유가 없다. 그래도 남는 동점은 클래스 이름 순이다 — 결정적이어야 한다.
2. **`C` 하나만 화면에 연다.** 커널은 선형뿐이라 손잡이가 아니고, 수렴 허용오차·반복
   횟수는 수업 내용이 아니라 수업 시간을 말아먹는 값이다.
3. **선형 SVM은 자체 완결이라 참조형이 아니다.** 새 형식 `mlpx-svm-v1`이고
   `needsTrainingRows`는 `false`다. `mlpx-spec.md` §5 표와 §5.8이 그것이다.

##### sklearn 대조 프로브 (2026-08-06)

**함께 들어가야 한다고 적어 둔 둘 중 하나다.** scikit-learn 1.9.0의 `SVC(kernel='linear',
C=1)`와 같은 데이터에서 붙였다. 우리 솔버는 학습 전에 열마다 min-max로 펴므로 sklearn도
**같은 조건으로 한 번 더** 잰다 — 안 그러면 솔버 차이와 정규화 차이가 한 숫자에 섞인다.

| 데이터 | 우리 | sklearn | sklearn(정규화) | 행 일치율 |
|---|---|---|---|---|
| 붓꽃 축소판 (3클래스·4특성·30행) | 0.9667 | 1.0000 | 0.9333 | 0.9667 |
| 이진·잘 갈림 (2클래스·5특성·200행) | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| 3클래스·잘 갈림 (5특성·300행) | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| 3클래스·겹침 (5특성·300행) | 0.7500 | 0.7800 | 0.7500 | 0.9900 |
| 4클래스·겹침 (6특성·400행) | 0.8550 | 0.8750 | 0.8550 | 1.0000 |

**가를 수 있는 데이터에서는 한 행도 안 갈린다.** 겹치는 데이터에서는 정확도가 같은
조건의 sklearn과 소수점 넷째 자리까지 같고 행 일치율이 0.99~1.00이다. **남는 차이는
솔버가 아니라 정규화다** — 원본 좌표계의 sklearn과 벌어지는 폭(0.78 대 0.75)이 정규화한
sklearn과 벌어지는 폭(0.75 대 0.75)보다 크다는 것이 그 증거다.

**"조용히 틀린 숫자"의 징후는 없다.** 그게 이 프로브가 확인하려던 전부다 — 비트 일치가
목적이면 애초에 같은 솔버를 써야 한다.

##### 행 상한은 3000이고, **알고리즘마다 따로 둔다**

수렴하는 데이터에서 2000행 26초·5000행 181초 사이의 타협이다. 5000행은 rss 202MB라
저사양 학교 PC와 휴대폰에서 위험하기도 하다(`svm.js:76`이 학습 시작에 N×N 커널 행렬을
통째로 만든다 — 1만 행이면 1억 칸이라 시간 이전에 메모리에서 끝난다).

**전역 `BROWSER_ROW_LIMIT` 하나로는 못 담는다.** 의사결정트리가 즉시 끝나는 데이터에서
SVM만 몇 분이다. 등록부가 알고리즘마다 상한을 들고, 없으면 전역을 따른다.

##### 열어 두는 것 — 상한을 넘으면 잘라서 쓰기

**상한을 넘는 데이터에서 그 모델을 그냥 끄는 것 말고 할 일이 있다.** 전처리 단계에서
상한만큼 표본을 뽑아 학습하고 **남은 행을 평가로 돌리면** 학생은 큰 데이터에서도 그
모델을 본다. 지금 넣지 않는 이유는 이것이 분할 규칙을 건드리기 때문이다 — `trainIndices`와
`testIndices`가 지금은 학생이 고른 분할에서만 나오는데, 여기서는 상한이 그 둘을 다시
정하게 된다. **예측 화면이 선 뒤에 분할과 함께 본다.**

**새 실행 방법이 아니다.** 순수 JS라 기존 mljs 엔진에 알고리즘 한 줄을 더하는 일이고,
`engine.kind`는 우리 엔진을 가리키는 이름이지 라이브러리마다 붙는 것이 아니다
(이미 `ml-cart`·`ml-knn`이 한 kind 안에 있다). libsvm-js(WASM)와 갈리는 지점이 여기다 —
그쪽은 준비 단계와 새 카드와 대조 축이 함께 는다.

### 학습용과 평가용 파일이 따로일 수 있다 (2026-08-06)

**교실에 실제로 있는 상황이다.** 학생이 받아 오는 데이터가 `train.csv`와 `test.csv`로
갈려 있는 경우가 흔한데, 지금은 정본이 하나뿐이라 둘째 파일을 넣을 자리가 없다. 그래서
분할을 끄고(`none`) 쓰게 되는데 그러면 **평가셋이 있는데도 "점수가 부풀려져 나옵니다"
경고를 보는** 이상한 상태가 된다.

#### 먼저 규칙 하나를 바로잡는다 — "예측 결과"는 **산출물**이지 데이터가 아니다

`mlpx-spec.md` §0의 **"예측 결과는 파일에 기록하지 않는다"를 "학생이 올린 데이터도 안
남긴다"로 읽으면 안 된다.** 그 규칙이 막는 것은 **예측의 산출물** — 어느 모델이 무엇이라
답했는지 — 이고, 그건 플레이그라운드의 부산물이라 남길 이유가 없다는 뜻이다.

**학생이 올린 데이터는 프로젝트 파일 안에 있다.** 학습에 쓴 것이든 시험에 쓴 것이든
마찬가지다. 이 원칙은 정형 데이터에서 끝나지 않는다 — **이미지 단계에서도 학습에 쓴
이미지와 시험에 쓴 이미지가 함께 담긴다**(#4가 다룰 자리다). 그래야 파일 하나로
재현·확인·제출이 성립한다(§1.3).

#### 그러므로 정본이 둘이다 — 이어 붙이지 않는다

| 자리 | 무엇 |
|---|---|
| `dataset/data.csv` | 학습용 정본. 지금 그대로다 |
| `dataset/test.csv` | **평가용 정본.** 새로 생기고, 없는 것이 정상이다 |
| `dataset/predict.csv` | **예측용 정본.** 예측 화면에서 올린다 |
| `settings.testDataset` · `settings.predictDataset` | 위를 가리키는 참조. `DatasetRef`를 그대로 다시 쓴다 |
| `split.method` | 어휘 `provided` 하나 — 평가셋이 파일에서 왔다는 표시 |

**이어 붙이는 안은 버렸다.** 한 파일로 합치면 학생이 올린 파일이 원형을 잃고, 이미지로
확장될 때 같은 일을 또 다르게 해야 한다. 파일을 따로 두면 **올린 그대로 남는다.**

**셋 다 `데이터` 업로드와 같은 길을 지난다** — 엑셀이든 CP949든 UTF-8 CSV(BOM 포함)
정본으로 정규화되고 `hashes.json`에 각자 항목을 갖는다(`mlpx-spec.md` §1.1).

**`testIndices`의 뜻이 한 줄로 정리된다** — **테스트 데이터셋의 행 번호.** `holdout`에서는
그 데이터셋이 `data.csv`이고 `provided`에서는 `test.csv`다. `trainIndices`는 언제나
`data.csv`다. 참조형 모델이 보는 것은 `trainIndices`뿐이라(`mlpx-spec.md` §5.1) 그쪽은
흔들리지 않는다.

**`formatVersion`은 안 오른다.** 배포 전이라는 같은 근거다(위 "전처리도 분할도 끌 수 있다").

#### 받을 때 한 번만 검사한다 — **정본의 열 전체와 대조한다**

> **`test.csv`는 정본의 모든 열을 가져야 한다. 타깃 열만 없어도 된다.**

"학습에 쓴 특성 열과 대조"가 아니다. **특성은 학생이 계속 바꾸는 값**이라, 특성이
`{A,B}`일 때 받아 둔 파일이 나중에 `C`를 추가하는 순간 무효가 된다 — 그 실패가 [학습]을
누른 뒤에 터진다. 정본 열 전체와 대조하면 `특성 ⊆ 정본 열 ⊆ test 열`이 **항상** 참이라
**늦은 실패가 구조적으로 불가능해진다.**

- **열 순서가 달라도 이름으로 다시 세운다.** 이건 매핑이 아니라 모호함이 없는 재배열이다.
  이름이 다른 열을 우리가 짝지어 주지는 않는다 — 그건 학생의 데이터 품질 문제다.
- **하나라도 없으면 거부하고 어느 열이 없는지 말한다.** 이상한 파일은 여기서 걸린다.

#### 화면이 의도를 말한다 — 파일 내용으로 추측하지 않는다

처음엔 "타깃 열이 있는지 보고 평가용인지 예측용인지 가른다"로 잡았는데, **그럴
필요가 없다.** `test.csv`라는 한 이름이 서로 다른 두 물건을 가리키고 있었고,
**화면이 이미 그 둘을 가르고 있다.**

| | 전처리에서 받는 파일 | 예측에서 받는 파일 |
|---|---|---|
| 무엇인가 | **테스트 데이터** | **새로 예측할 데이터** |
| 타깃 열 | **반드시 있다.** 없으면 거부 | **없는 게 정상.** 있어도 안 본다 |
| 왜 그런가 | 정답이 없으면 채점을 못 한다 | 답을 모르니까 물어보는 것이다 |
| 검사 | 정본의 **모든 열 + 타깃** | 지금 보이는 모델들의 **특성 열** |
| 저장 | 정본 순서로 **다시 세워서** | **올린 열 전부** (아래 2026-08-07) |
| 경로 | `dataset/test.csv` | `dataset/predict.csv` |
| 점수 | **실험의 점수.** `runs.json`에 들어간다 | 없다 |

**추측이 사라지면서 에러 메시지가 정확해진다.** 전처리에 타깃 없는 파일을 올리면
"정답 열이 없습니다"라고 딱 집어 말하면 된다 — 조용히 다른 물건으로 취급하지 않는다.

#### `분할 안 함`을 없앱니다 — 그 자리가 양자택일이 된다

**경고가 잘못된 것이 아니라 그 상태가 잘못됐다.** `점수가 부풀려집니다`는
**틀린 것을 허용해 놓고 미안해하는 문장**이다. 학습에 쓴 데이터로 정답률을 재는 것은
"덜 정확한 측정"이 아니라 **측정이 아니다.** 그런데 화면은 그걸 `정확도` 열에 같은
모양으로 넣고 옆에 주의 문구만 붙였다. **중학생은 숫자를 읽고 문장은 안 읽는다.**

> **정확도를 내려면 테스트 데이터가 있어야 한다. 길은 둘뿐이다 —
> 훈련 데이터를 나누거나, 평가용 파일을 받거나.**

그래서 전처리의 그 자리가 **양자택일**이 된다. 세 번째 상태가 없으므로 학습
데이터로 채점하는 길이 **구조적으로 막힌다.**

| 섹션 | `테스트 데이터(Test Data)` |

> **국문이 2026-08-11에 `평가 데이터`에서 `테스트 데이터`로 바뀌었다** (V2 감사 4단계).
> 병기하던 영문은 처음부터 `Test Data`였고, `평가`(evaluation)가 `테스트`보다 넓은 말이라
> 수단 하나에 상위 개념의 이름을 붙이는 꼴이었다. `훈련/테스트`가 sklearn
> `train_test_split`의 한 쌍이기도 하다. 용어는 `terms.md`가 갖는다.
|---|---|
| ① | `훈련 데이터에서 일부를 떼어 씁니다` → `holdout` |
| ② | `평가용 파일을 따로 올립니다` → `provided` |

**섹션 이름을 `학습용과 평가용 나누기`에서 바꾸는 이유**는 `나누기`가 ①에만
해당하기 때문이다. 이 자리가 정하는 것은 "무엇으로 점수를 매길까"이다. 오렌지3도
[테스트 및 점수]에 **"별도의 테스트 데이터로 검증"**을 두고 있고, 수업에서 쓰는 말은
**훈련 데이터 / 시험(평가) 데이터**다. 원어 병기는 `copy.md` §2 규칙을 따른다.

**과적합을 가르치는 올바른 방법은 분할을 끄는 것이 아니다.** 정상적으로 나눈 뒤
**학습셋 점수와 평가셋 점수를 나란히 보이는 것**이다. "학습셋 100% / 평가셋 71%"가
한 줄에 있으면 과적합이 눈에 보인다. 분할을 꺼서 100% 하나만 보이는 것은 같은
교훈을 **못 주면서** 틀린 숫자만 남긴다. 그 기능은 나중에 따로 만든다.

**마이그레이션은 만들지 않는다** (2026-08-06). `none`을 어휘에서 빼면 그 값을 가진
기존 파일이 거부되는데, **지금 있는 프로젝트는 전부 지울 예정이므로 올려 줄 상대가
없다.** 배포 전이라 밖에 파일이 하나도 없다는 같은 근거다(위 "전처리도 분할도 끌 수
있다"). 마이그레이션 함수를 만들면 **되살릴 일이 없는 코드가 영구히 남는다.**

#### 따라오는 것 넷

- **타깃이 정해진 뒤에만 받을 수 있다.** 그전에는 타깃 열이 있는지 볼 수가 없다.
- **붙이거나 떼면 지금까지의 실험이 지워진다.** 평가셋이 바뀌면 그 위의 점수가 전부
  다른 것을 잰 값이 된다 — `applyDataset`과 같은 사유이고(`mlpx-spec.md` §4.3)
  같은 경고를 거친다.
- **크기 예산에 경쟁자가 는다.** `test.csv`와 `predict.csv`가 모델·데이터와 같은
  파일 안에서 자리를 다툰다(§4.2). #23의 첨부와 같은 자리다.
- **테스트 데이터에도 전처리 옵션이 그대로 걸린다.** 결측 처리·스케일링·인코딩이 학습
  데이터와 **같은 설정**으로 적용된다 — 다르게 적용하면 두 데이터가 다른 좌표계에 서고
  점수가 뜻을 잃는다. 스케일링·인코딩의 **파라미터는 학습셋에서 fit한 것을 그대로
  쓴다**(평가셋으로 다시 fit하면 정보가 새어 나간다). 결측 규칙도 같이 적용되므로
  결측이 있는 평가 행은 빠지고 **평가셋이 줄어든다.**

#### 몇 행으로 학습하고 몇 행으로 채점하는지 말한다

**지금 훈련 데이터 쪽에도 이 안내가 없다** (2026-08-06). 학생은 200행짜리 CSV를 올려
놓고 결측 때문에 30행이 빠진 줄 모른 채 170행으로 학습한다. 그러면 점수가 무엇을 잰
것인지 본인도 모른다.

> **올린 n행 중 k행이 전처리에서 빠져 최종 m행을 씁니다.**

**훈련 데이터와 테스트 데이터 양쪽에 똑같이 붙인다.** 빠진 행이 0이면 그 말은 안 한다 —
할 말이 없을 때 굳이 하지 않는다. 세는 자리는 `usableRows` 하나이므로 두 화면이 같은
함수를 본다(따로 세면 반드시 어긋난다).

### 일괄 예측은 `행 × 모델` 매트릭스다 (2026-08-06)

`dataset/predict.csv`를 받는 자리는 위에서 이미 정해졌다(예측 화면, 검사는 **보이는
모델들의 특성 열**, 타깃은 없는 것이 정상). 여기서 정하는 것은 **그 결과를 어떻게
보여주고 무엇을 남기는가**다.

#### 한 줄 입력과 같은 자리에서 갈라진다

**왼쪽 입력 영역이 양자택일이 된다** — 전처리의 `테스트 데이터(Test Data)`와 **똑같은
라디오 분기**다(위 "`분할 안 함`을 없앱니다").

| | 왼쪽 입력 영역 |
|---|---|
| ① | `값을 직접 넣습니다` → 지금의 칸 한 줄 |
| ② | `파일로 여러 줄을 한 번에 예측합니다` → `predict.csv` |

새 탭이나 새 화면을 만들지 않는다. **묻는 것이 같기 때문이다** — "이 모델들에 무엇을
넣을까".

**②를 고르면 오른쪽 답 목록이 표에 자리를 내준다** (2026-08-06에 구현하며 정했다).
처음엔 "오른쪽은 그대로 두고 입력의 모양만 갈린다"로 적었는데 **그 둘이 같은 것을
가리키고 있었다** — 파일 쪽의 답은 카드 목록이 아니라 `행 × 모델` 표 자체이고, 그것을
한 줄 입력용의 좁은 칸(`max-w-lg`) 옆에 밀어 넣으면 정작 비교할 모델 열이 가로 스크롤
안으로 사라진다. 그래서 ②에서는 표가 폭을 전부 갖는다. 갈리는 자리가 하나(라디오)라는
것은 그대로다.

#### 결과는 `행 × 모델` 표다

**1열이 행 번호이고 2열부터 모델이다.** 세로로 읽으면 한 모델이 전체에 어떻게
답했는지가, 가로로 읽으면 **같은 줄에 모델들이 서로 다르게 답한 자리**가 보인다.
후자가 이 도구가 주려는 장면이고(§8.13의 세로줄 읽기와 짝이다) 한 줄 입력에서
"같은 값인데 모델마다 답이 다르다"를 보여주던 것의 여러 줄 판이다.

**특성 값은 기본으로 숨기고 펼쳐서 본다.** 특성이 스물이면 표가 옆으로 밀려 정작
비교할 모델 열이 화면 밖으로 나간다. 그러나 답이 갈린 줄을 보면 **"3번이 뭐였더라"가
반드시 따라오므로** 없애지는 않는다.

#### 100줄씩 끊어 보여주고 계산도 그만큼만 한다

**페이지네이션은 화면을 위한 것이 아니라 계산을 위한 것이다.** 5천 줄 × 모델 5개면
2만 5천 번이고 참조형이면 그 한 번마다 학습셋 전체와의 거리 계산이다 — 저사양 학교
PC가 기준이다(CLAUDE.md §0).

**한 번 계산한 페이지는 다시 계산하지 않는다.** 캐시는 (파일, 모델 선택, 전처리 설정)이
하나라도 바뀌면 통째로 버린다 — 그 셋이 바뀌면 이전 페이지의 답은 다른 것을 잰 값이다.

**연산 상한을 따로 두지 않는다** (2026-08-06에 실측도 하지 않기로 했다). `predict.csv`도
같은 가져오기 경로를 지나므로 `MAX_DATASET_ROWS`가 이미 걸리고, **화면에서 도는 것은
언제나 한 페이지뿐**이라 상한이 막아 줄 자리가 이미 페이지네이션으로 닫혀 있다.
숫자를 하나 더 만들면 상한이 둘이 되고 둘은 반드시 어긋난다.

**한 곳만 예외다 — 내려받기는 전체 행을 계산한다.** 페이지를 넘겨 본 적 없는 파일을
바로 내려받으면 그 순간 전부 돈다. 그래도 상한을 두지 않는 이유는 그것이 **학생이
일부러 누른 일**이고 기다림은 비용이지 실패가 아니기 때문이다(위 같은 이름의 절).
막을 것이 아니라 진행을 보여줄 자리다 — 지금은 "계산하는 중입니다"만 띄운다.

#### 빈 칸이 있는 행은 **그 행만** 빈 답이다

한 줄 입력의 규칙(`PREDICTION_INPUT_INCOMPLETE` — 전처리기의 대체값으로 조용히 채우지
않는다)을 **행마다 그대로 적용한다.** 파일 전체를 거부하면 500행 중 한 칸이 비었다고
멀쩡한 499행을 못 본다. 나머지 행은 그대로 예측하고 그 행만 "예측할 수 없음"으로 둔다.

#### 검사는 특성 열, 저장은 **올린 열 전부** (2026-08-07)

처음엔 "요구한 특성 열만 남겨 재배열해 저장한다"로 잡았다 — `test.csv`가 정본 순서로
다시 세워 저장하는 것을 그대로 따른 것이다. **그 둘은 같은 물건이 아니다.**

`test.csv`가 정본 열과 짝을 맞추는 것은 **채점하려면 정본과 같은 좌표계에 서야 하기
때문**이고, 그 좌표계는 데이터가 바뀌면 실험이 통째로 지워지므로(mlpx-spec.md §4.3)
어긋날 자리가 없다. `predict.csv`가 맞춰야 하는 것은 **지금 보이는 모델들의 특성 열**인데,
**그 목록은 학생이 언제든 바꾸는 값이다.** 특성을 `{키, 몸무게}`로 학습하고 파일을 붙인
뒤 `나이`를 특성에 넣어 재학습하면, 저장된 파일에 `나이` 열이 없어서 **학생이 올린
파일에는 있었는데도** 그 모델의 모든 칸이 실패한다. 그것도 "빈 칸입니다"라는 틀린
사유로 — 값이 빈 것이 아니라 열이 없는 것이다.

> **검사와 저장을 가른다. 받을 때 특성 열이 다 있는지 보고, 저장은 올린 열을 전부 한다.**

거부 조건은 그대로다(`PREDICT_DATASET_COLUMN_MISSING`, 어느 열이 없는지 함께). 바뀌는
것은 통과한 뒤다 — 열을 버리지 않으므로 학생이 특성·타깃을 바꿔 재학습해도 이미 붙인
파일이 그대로 산다. 여분의 열은 `inputVector`가 전처리기의 열만 보므로 예측에 안 섞이고,
크기도 학생이 올린 그 파일 이상으로는 안 는다.

**표와 내려받기가 보여주는 것은 그대로 특성 열이다.** 파일에 다른 열이 함께 담기는 것은
보관이고, 표가 보여줄 것은 "모델이 보는 열"이다.

#### 붙일 때 본 것을 **예측 직전에 다시 본다** (2026-08-07)

위 검사는 **붙이는 순간의 사실**이고, 그 사실은 학생이 특성을 바꾸면 낡는다. 그러니
**모델에 넣기 직전에 한 번 더 본다** — 이미 통과한 파일이라는 것은 지금도 맞다는 뜻이
아니다.

`inputVector`가 **열이 없는 것(`undefined`)과 값이 빈 것(`''`)을 가른다.** 앞은
`PREDICT_DATASET_COLUMN_MISSING`, 뒤는 지금처럼 `PREDICTION_INPUT_INCOMPLETE`다. 두
경우에 학생이 할 일이 다르다 — 앞은 파일을 다시 올려야 하고 뒤는 그 칸을 채워야 한다.
가르지 않으면 **없는 열이 빈 칸으로 읽혀 화면이 틀린 사유를 말한다.**

**(행, 모델) 단위로 잡는 것은 그대로다**(위 "빈 칸이 있는 행은 그 행만 빈 답이다"). 열을
더 쓰는 실험의 모델만 그 칸이 비고, 나머지 모델은 멀쩡히 답한다.

#### 올린 파일은 남기고 예측값은 안 남긴다

**`predict.csv`는 `.mlpx`에 들어간다.** 학생이 올린 데이터이기 때문이다(§0의 못 박은
구분 그대로 — 막는 것은 **산출물**이다).

**예측값은 안 들어간다.** 진리의 원천(데이터·설정·모델)이 이미 파일 안에 있으므로
**교사가 버튼 한 번만 누르면 재현된다.** 연산 결과를 함께 담는 것은 같은 것을 두 번
적는 일이고, 그러면 둘이 어긋날 자리가 생긴다.

**그래도 학생은 CSV로 내려받을 수 있다.** `.mlpx`에 안 담는 것과 학생이 결과물을 받아
가는 것은 다른 질문이다 — 받은 파일은 우리가 다시 읽지 않는다.

> **열 이름은 번역된 모델 이름이다.** `data/columns.ts`가 "여기서 만든 이름은 UI
> 문자열이 아니라 데이터다"라고 못 박은 것의 **예외이고, 예외인 이유가 있다** — 그
> 규칙이 지키는 것은 *다시 읽힐 파일*의 열 이름이 언어마다 달라지지 않는 것인데,
> 이 파일은 우리가 다시 읽지 않는다. 학생이 엑셀에서 열었을 때 `decision_tree`가
> 아니라 `의사결정트리`가 보여야 한다. 같은 알고리즘이 실행 방법만 다르게 두 번 있으면
> 뒤에 실행 방법을 괄호로 붙인다(`copy.md` §2의 규칙 그대로다).

#### 따라오는 것 하나 — `sampleRow`가 지금 틀려 있다

`[데이터에서 한 줄 가져오기]`는 `testIndices`로 `data.csv`를 찾는데, `provided`에서
그 번호는 **`test.csv`의 행 번호다**(위 "정본이 둘이다"). 조용히 다른 줄을 채우고,
테스트 데이터가 더 길면 아무것도 안 채운 것처럼 보인다. **테스트 데이터가 온 실험에서는
테스트 데이터에서 뽑는다** — 그 버튼이 주려던 것이 애초에 "모델이 학습 때 못 본 행"이다.

### 예측을 **설명**한다 — "시각화 가능" 플래그는 안 만든다 (2026-08-06)

**방향은 정해졌고 착수 시점은 아직이다.**

처음 나온 안은 "모델 직렬화에 시각화 가능 여부 플래그(`canVisualize`)를 두고, KNN처럼
그릴 수 있는 것은 2D 산점도와 결정 경계를 보여준다"였다. **플래그는 기각한다.**

**질문이 잘못 걸려 있다.** 2D 결정 경계를 그릴 수 있느냐는 *모델 형식*이 아니라 **그
실험의 특성 개수**에 달렸다. 같은 `mlpx-tree-v1`이라도 특성이 둘이면 그려지고 스물이면
못 그린다. 형식에 박은 불리언은 답할 수 없는 질문에 답하는 셈이다. 게다가 **원-핫이
차원을 부풀린다** — `키 + 지역(3종류)`이면 이미 4차원이라, 그릴 수 있는 경우는 "수치
정확히 둘, 범주 없음"뿐이고 교실 데이터에서 그건 드물다. 비용도 있다: 결정 경계는
격자(100×100이면 1만 점)를 전부 예측해야 하고, 참조형이면 그 1만 번이 전부 거리
계산이다(저사양 학교 PC가 기준이다).

**대신 "이 예측을 어떻게 설명하는가"를 등록부로 둔다.** 차원과 무관하고, 학생이 실제로
궁금해하는 것에 답한다.

| 형식 | 설명 | 왜 이게 더 나은가 |
|---|---|---|
| `mlpx-tree-v1` | 판단에 쓰인 가지를 따라간 **나무 그림** | 구조가 이미 통째로 직렬화돼 있고 그리는 비용이 없다. 트리에서 학생이 보고 싶은 것이 정확히 이것이다 |
| `mlpx-reference-v1` | **투표한 이웃 k개**를 라벨·거리와 함께 | 그 예측을 정확히 설명한다. 2D 산점도보다 오히려 정직하다 |
| `linear-v1`·`linear-regression-v1`·`svm-v1` | **특성별 계수** | 스키마의 `featureImportance` 자리가 여기서 처음 채워진다 |

**키는 형식이다. 알고리즘이 아니다** — `interpreterFor`와 같은 이유이고 같은 모양이다
(`ml/models/index.ts`). 그래서 **의사결정트리와 랜덤 포레스트가 설명기를 공유한다**:
`TreeModel.trees`가 배열이라 한 그루짜리와 여러 그루짜리를 같은 설명기가 받는다. 여러
그루일 때 무엇을 보일지(대표 한 그루? 그루별 표?)는 **그때 실물을 보고 정한다.**

**2D 결정 경계를 영영 안 만든다는 뜻은 아니다.** 이 등록부가 서면 그건 "전처리 뒤
특성이 정확히 둘일 때만"이라는 조건을 달아 **줄 하나 더 넣는 일**이 된다. 지금 플래그를
박으면 그 조건을 걸 자리가 없어진다.

**착수는 포트폴리오(#23) 뒤다.** 이건 있으면 좋은 것이고, 포트폴리오는 없으면 V1이
성립하지 않는다.

### 난수 씨앗은 고정이 기본이고, 다시 뽑는 것은 경고 뒤에 준다 (2026-08-06)

**왜 고정인지를 화면이 말해야 한다.** 지금 문구가 "프로젝트를 만들 때 정해집니다. 같은
씨앗이면 언제 돌려도 같게 나뉩니다"뿐인데, 이건 **무슨 일이 일어나는지만 말하고 왜
그런지는 말하지 않는다.** 학생에게 필요한 것은 뒤쪽이다.

**고정하는 이유는 이 도구의 목적 자체다.** 설정을 바꿔가며 반복 학습하는 것이 핵심
활동이고(CLAUDE.md §1.1), 결과 화면이 답하려는 질문은 **"무엇을 바꿨더니 무엇이
달라졌는가"**(§8.13)다. 씨앗이 매번 달라지면 학습셋과 평가셋이 같이 달라져서, 정확도가
오른 것이 **내가 바꾼 설정 때문인지 이번 분할이 쉬웠기 때문인지 가릴 수 없다.** 비교의
바닥이 흔들리면 그 위의 모든 숫자가 뜻을 잃는다.

**그런데 다시 뽑을 길은 있어야 한다.** 씨앗을 영영 못 바꾸면 **"이 점수가 이 분할에서만
잘 나온 것은 아닐까"**를 확인할 방법이 없는데, 그 질문은 수업에서 다뤄야 할 좋은
질문이다. 분할 운이 지표를 얼마나 흔드는지 직접 보는 것은 과적합만큼 중요한 경험이다.

- **누르자마자 바뀌지 않는다.** 대화상자로 한 번 막고, **지금까지의 실험과 점수를 나란히
  비교할 수 없게 된다**는 것을 이유로 말한다. 되돌릴 수 없는 조작이므로 §8.2의 규칙이
  그대로 걸린다.
- **지난 실험을 지우지 않는다.** 실험마다 자기 `randomState`·`trainIndices`·`testIndices`
  스냅샷을 들고 있으므로(`mlpx-spec.md` §4) 그 기록도 재실행 대조도 그대로 성립한다.
  바뀌는 것은 **앞으로의 분할**뿐이다. 결과 화면의 변경 이력이 `난수 씨앗: 42 → 12345`로
  그 사실을 정직하게 보여준다 — `ml/changes.ts`에 이미 등록돼 있다.
- **새 값은 프로젝트를 만들 때와 같은 곳에서 나온다** (`crypto.getRandomValues`).
  손으로 숫자를 입력받지 않는다 — 씨앗의 값 자체는 아무 뜻이 없고, 고를 것을 주면
  학생이 "좋은 씨앗"을 찾는 데 시간을 쓴다.
- **분할을 껐으면 이 버튼도 뜻이 없다.** 나누지 않으면 씨앗이 하는 일이 없으므로 그때는
  씨앗 칸과 함께 감춘다.

### 전처리도 분할도 끌 수 있다 (2026-08-05)

**어휘 둘을 늘린다.**

| 어휘 | 새 값 | 뜻 |
|---|---|---|
| `preprocessing.missing` | `none` | 빈 칸을 그대로 둔다 |
| `split.method` | `none` | 학습용과 평가용으로 안 나눈다 |

#### `formatVersion`은 안 오른다 — 아직 배포 전이기 때문이다

§10이 "어휘가 늘어나는 변경은 `formatVersion` 증가를 요구한다"고 적어 두었지만, **그
규칙이 지키는 것은 호환성이고 호환시킬 상대가 아직 없다.** 버전이 하는 일은 신버전이
만든 파일을 구버전 앱이 조용히 깨진 채로 여는 것을 막는 일인데, 밖에 v1 파일도 v1 앱도
하나도 없다. `batches`를 `experiments`로 바꾸면서 안 올린 것과 같은 근거다(`mlpx-spec.md` §4).

**첫 배포 뒤에는 규칙이 뒤집힌다.** 그때부터는 어휘가 하나 늘 때마다 반드시 오른다.
같은 판단이 엔진 버전(`MLJS_ENGINE.version`)에도 그대로 걸린다 — 일반 규칙은
`mlpx-spec.md` §9에 적었다.

#### 결측치 `none`은 **시끄럽게 거부한다**

"아무것도 안 한다"를 정직하게 구현할 방법이 하나뿐이다. **빈 칸을 그대로 모델에 넣을
수는 없기 때문이다** — 수치 열의 빈 칸은 어떤 경로로든 결국 숫자가 되고, 지금 코드에서는
0이 된다. 그러면 "아무것도 안 함"이라는 이름으로 **0으로 채우기를 하는 셈**이고, 학생은
자기 데이터가 그대로 들어갔다고 믿는다. 이 저장소가 규정한 최악이 정확히 그것이다.

그래서 뜻을 이렇게 정한다 — **고른 열에 빈 칸이 하나라도 있으면 학습이 거부한다.**
`FEATURE_HAS_MISSING`이고, 전처리 화면이 [학습] 전에 어느 열인지 먼저 말해 준다.
쓸모는 "내 데이터는 깨끗하다"를 선언하는 것이다. 깨끗하면 정말로 아무 일도 안 일어난다.

**전체 데이터를 본다.** 학습셋만 검사하면 평가셋의 빈 칸이 조용히 0이 되어 지나간다.

#### 분할 `none`은 **학습에 쓴 데이터로 점수를 매긴다**

오렌지3의 "Test on train data"와 같다. `testIndices`에 학습 행을 그대로 적는다 —
거짓말이 아니라 사실이고, 재실행 대조도 그대로 성립한다. 지표를 아예 안 내는 쪽은
안 고른다. `run.metrics`가 필수라 스키마가 흔들리고, 결과 화면에 보여줄 것이 없어진다.

**기본값은 여전히 켜짐이다.** 끄면 숫자가 거의 언제나 부풀고(결정트리는 100%가 흔하다)
결과 화면이 하려는 일이 "무엇을 바꿨더니 무엇이 달라졌는가"인데 그 비교가 통째로 잡음이
된다. 오렌지도 교차검증이 기본이고 "Test on train data"는 골라야 되는 선택지다.
**끈 실험에는 화면이 그 사실을 지표 옆에 붙인다.**

`testSize`와 `stratify`는 그때 뜻을 잃지만 파일에는 남긴다. 지우면 다시 켤 때 학생이
맞춰 둔 값이 사라진다.

#### 분할과 랜덤 샘플링은 다른 것이다

헷갈리기 쉬워서 적어 둔다. **분할은 가진 데이터를 갈라 한쪽으로 점수를 매기는 것**이고,
**샘플링(#22)은 애초에 일부만 학습에 쓰는 것**이다. "전부 학습에 쓰고 싶다"에 답하는 것은
분할 쪽이고, "너무 느리다"에 답하는 것은 샘플링 쪽이다.

### 층화는 갈리는 값에서만 뜻이 있다 (2026-08-07)

**버그가 아니라 실행 불가능한 조언이었다.** 회귀 데이터에서 [학습]을 누르면 이렇게 나왔다.

> `'1.1334305711878574'` 값이 1개뿐이라 비율을 맞춰 나눌 수 없습니다.
> 비율 맞추기를 끄거나 이 값의 데이터를 2개 이상 모아 주세요.

문장은 참인데 **뒤쪽 조언이 영원히 불가능하다** — 그 소수가 두 번 나오는 데이터는 없다.
`stratify`의 기본값이 `true`이고(`project/create.ts`) 체크박스에 게이트가 없어서,
**회귀 프로젝트는 사실상 전부 이 벽에 부딪힌다.**

#### 알 수 있는 것을 [학습]까지 미루지 않는다

층화가 성립하는지는 **전처리 화면이 이미 아는 사실**이다 — 타깃 열의 값 분포가 손에 있다
(`data/columns.ts`). 그런데 판정은 `ml/split.ts`가 학습 도중에 하고 있었다. 그래서 게이트를
`ml/selection.ts`로 옮긴다 — 이 파일의 issue/caution이 이미 그 물건이고, 새 개념을 만들지
않는다(architecture.md §10.2).

**게이트는 학습이 보는 것과 같은 행을 센다** (`usableRows`). 결측 처리에서 빠질 행을 세면
"화면은 멀쩡한데 학습이 거부한다"가 생긴다.

#### 문구를 두 갈래로 가른다 — 임계값은 만들지 않는다

| 상황 | 무엇을 말하나 |
|---|---|
| 1개뿐인 값이 **하나** | 현행 문구 그대로. "그 값의 데이터를 더 모아라"가 실행 가능한 조언이다 |
| 1개뿐인 값이 **여럿** | 타깃이 사실상 연속이다. "값이 거의 다 달라 비율을 맞출 수 없다"고 말하고 **끄기를 권한다** |

**"고유값이 행 수의 몇 % 이상이면 연속"이라는 상수를 두지 않는다.** 근거 없는 선이 하나
생기고, 그 선은 아무도 다시 못 정한다. 이미 세고 있는 "1개뿐인 값의 개수"만으로 두 상황이
갈린다 — 세는 것은 사실이고 임계값은 판단이다.

#### 회귀를 고르면 값을 내린다. 다만 **잠금은 조건이 다르다**

유형을 회귀로 바꾸는 순간 `stratify`를 `false`로 내리고 알린다. **뜻을 잃은 모델 선택을
지우고 토스트를 띄우는 것과 같은 처리다**(`algorithmsLosingMeaning`, `TrainView`의
`pickTaskType`) — 유형 변경이 방아쇠라는 점까지 같다.

**"분할을 끄면 `stratify`를 파일에 남긴다"(위 "전처리도 분할도 끌 수 있다")와 어긋나 보이는데,
방아쇠가 다르다.** 분할 끄기는 학생이 방금 누른 것이라 다시 켤 일이 바로 있고, 유형 변경은
프로젝트의 성격이 바뀐 것이다. **대가는 적어 둔다** — 회귀로 갔다 분류로 돌아오면 켜 두었던
층화가 안 돌아온다.

**그리고 잠그는 조건은 "회귀"가 아니라 "꺼져 있다"다.** 회귀인데 켜져 있는 상태가 실재하기
때문이다 — 지금 기본값이 `true`이므로 이미 만들어진 프로젝트가 전부 그렇다. 그 상태에서
체크박스를 잠그면 **학생은 이유를 읽고도 끌 수 없고, 학습은 계속 거부한다.** 함정이다.

| 상태 | 체크박스 |
|---|---|
| 뜻이 없고 꺼져 있다 | **잠근다.** 이유를 붙인다 — 켤 수 없는 것을 켜게 두지 않는다 |
| 뜻이 없는데 켜져 있다 | **잠그지 않는다.** 이유를 붙여 학생이 끈다 |

#### 학습 시점의 거부는 그대로 둔다

`SPLIT_STRATIFY_IMPOSSIBLE`을 없애지 않는다. **마지막 방어선이고, 남의 `.mlpx`를 열어 다시
돌리는 경로에는 우리 화면이 없다.** 새 사유 하나가 늘 뿐이다 — 연속형일 때의 문구는
학습 실패 run에도 그 모양으로 남아야 교사가 읽을 수 있다.

### 기계학습 유형은 모델을 고르는 자리에서 고른다 (2026-08-05)

**전처리 화면에는 데이터 얘기만 둔다.** 기계학습 유형·실행 방법·모델 선정은 학습 화면으로
간다. 화면 둘의 경계는 이렇게 갈린다.

| 화면 | 무엇을 정하나 | 무엇의 성질인가 |
|---|---|---|
| 전처리 | 타깃, 특성, 결측치·스케일링·인코딩, 학습용/평가용 나누기 | **데이터** |
| 학습 | 기계학습 유형, 모델, 실행 방법, [학습] | **모델** |

**타깃과 특성은 데이터의 성질이지 모델의 성질이 아니다.** CSV를 올렸으면 어느 열을
예측하고 어느 열로 예측할지는 분류인지 회귀인지와 무관하게 정할 수 있다. Orange3도
변수 역할을 먼저 정하고 모델을 잇는다. **모델을 골라야 열을 고를 수 있다는 것은
모순이다** — 그러면 워크플로가 거꾸로 선다.

**두 축은 그냥 독립이다.** §0.1이 "데이터가 과제 유형을 알려주지 않는다"고 못 박은 것은
맞다 — 같은 이미지셋으로 분류를 할 수도 군집화를 할 수도 있다. 그러나 그 사실이
"유형이 정해져야 열을 고를 수 있다"는 뜻은 아니다. 유형이 좁히는 것은 **모델 목록**이지
열 목록이 아니다.

**그리고 이 화면의 이름이 전처리다.** 전처리는 데이터를 학습에 넣을 수 있는 모양으로
만드는 일이고, 모델을 고르는 일은 거기 들어가지 않는다. 이름이 이미 경계를 말하고 있었다.

> 이 항목은 한 번 반대로 갔다. `architecture.md` §8.2가 전처리를 "전처리·모델 설정"이라고
> 적어 두었고 첫 구현이 그대로 따랐는데, **화면에 실물이 서고 보니 그 문서가 틀렸다.**
> 한 화면이 데이터와 모델을 둘 다 다루면서 학습 화면에는 버튼 하나만 남는 모양이었다.

**기본값을 두지 않는다.** 지금까지 새 프로젝트가 `taskType: 'classification'`으로
시작했는데, 그러면 **학생이 고른 분류와 아무도 안 고른 분류가 파일에서 구분되지 않는다.**
"자동으로 판정하지 않는다, 학생이 고른다"(`mlpx-spec.md` §0.1)를 지킨다고 해 놓고 몰래
하나를 골라 둔 셈이었다. `manifest.taskType`을 **선택 항목으로 내린다.**

**`formatVersion`은 안 오른다.** 필수 → 선택은 읽기 호환이라 옛 파일이 그대로 열리고,
`settings.dataset`을 선택으로 내렸을 때와 같은 모양이다(아래 "데이터 없는 프로젝트는
정상 상태다"). 실험 스냅샷의 `settings.taskType`은 **여전히 필수다** — 학습이 돈 이상
유형은 반드시 정해져 있었다.

**성립하지 않는 조합은 나중에 고른 쪽 옆에서 말한다.** 회귀 + 문자 타깃은 이제 학습
화면에서 드러난다. 유형이 마지막에 정해지므로 그 자리가 학생이 방금 한 선택의 자리다.
거부 자체는 그대로다 — 선택을 바꾸지 않고 그 조합으로는 답이 나오지 않는다고만 말한다.

**진입 조건이 일반화된다.** 전에는 `train`이 `targetChosen`을 요구하지 않았다. 군집화에
타깃이 없어서였는데, 그건 요구 목록에 예외를 손으로 파 둔 것이었다. 이제 **잠금 조건도
할 일 목록과 같은 필터를 지난다**(`factAppliesTo`) — 과제 유형에 해당하지 않는 사실은
요구에서도 빠진다. 그래서 "타깃과 특성이 정해지면 학습이 열린다"를 그대로 적을 수 있고,
군집 알고리즘이 들어오는 V3에서도 손댈 곳이 없다.

### 하이퍼파라미터는 눈금을 주되 막지 않는다 (2026-08-05) — #21의 마지막 줄 마무리

**손잡이에는 범위가 있고, 숫자는 그 밖도 칠 수 있다.** 스테퍼의 `min`/`max`는 "보통
여기서 고른다"는 눈금이지 상한이 아니다. 범위 밖 값은 그대로 저장되고 화면이 그 자리에서
말하며, 학습하면 **그 모델의 run 하나가** `HYPERPARAM_OUT_OF_RANGE`로 실패한다. 실험이
통째로 죽지 않는다 — 나머지 모델의 결과는 나온다(`mlpx-spec.md` §4.1).

**두 규칙이 여기서 만난다.** "학생 설정을 먼저 좁히지 않는다"(아래 "학습 실패는 교사가
읽을 수 있게 전달한다")와 "조용히 틀린 숫자보다 시끄러운 실패가 낫다"이다. 입력을 범위
안에 묶으면 앞엣것을 어기고 — 집에서 오래 걸려도 돌려 보겠다는 학생의 선택을 교실 사정으로
막는 것과 같은 모양이다(#13) — 아무거나 받아 남의 라이브러리 원문을 보여주면 학생은
어디서부터 시작할지 모른다.

**정수 자리는 소수를 반올림해 확정한다.** `nEstimators: 2.5`가 `RangeError`로 가던
구멍(#21의 "사소한 것")이 여기서 닫힌다. 이건 좁히는 것이 아니라 어휘다 — 나무 2.5그루는
범위 밖 값이 아니라 **값이 아니다.** `resolve`가 이미 하는 일(못 쓰는 값 → 기본값)과 같은
종류이고 멱등이라 계약도 안 깨진다. **확정이 곧 기록이므로**(`mlpx-spec.md` §3) 파일에는
반올림된 값이 남는다.

**서술의 출처는 엔진 하나다.** 이름·타입·범위·기본값이 한 곳에 있고 기본값 표가 거기서
파생된다 — 같은 값을 두 군데 두지 않는다는 규칙이 기본값에서 범위로 넓어진 것뿐이다.
그래서 **화면과 학습이 같은 서술을 본다.** 두 곳이 각자 판정하면 화면은 멀쩡한데 학습이
거부하는 상태가 생기고, 학생은 고칠 자리를 못 찾는다.

자가호스팅 서버가 붙으면 같은 모양을 프로토콜로 받는다(아래 "무엇을 학습할 수 있는지는
서버가 알려준다" 1번). 새 개념이 아니라 이미 정해 둔 것의 브라우저 쪽 구현이다.

**범위 값 자체는 여기 적지 않는다. 코드가 출처다** (`frontend/src/ml/hyperparams.ts`).

### 데이터 없는 프로젝트는 정상 상태다 (2026-08-05) — #22 마무리

**`settings.dataset`을 선택 항목으로 내린다.** 표를 아직 올리지 않은 프로젝트가 정상
상태이고, 그대로 IndexedDB에 자동 저장되고 `.mlpx`로도 저장된다.

**왜 이쪽인가.** 워크플로의 첫 화면이 데이터다(`architecture.md` §8.2). 학생이 프로젝트를
만들어 이름을 짓는 순간과 표를 올리는 순간 사이에 그 상태가 **반드시** 생긴다. 화면 구조가
이미 그것을 전제하고 있는데 파일 형식만 부정하면, 그 틈을 메우려고 어딘가에 거짓말이
생긴다 — 빈 경로든, 초안이라는 두 번째 상태든.

**지금이 가장 싸다.** 필수 → 선택은 읽기 호환이라 옛 파일이 그대로 열리고, 애초에 실물
학생 파일이 아직 세상에 없다. 학생 파일이 생긴 뒤에는 못 바꾼다.

**규칙은 하나다 — `settings.dataset`과 `dataset/`의 본체는 함께 있고 함께 없다.**
한쪽만 있는 파일은 거부한다(`mlpx-spec.md` §1). 코드에서도 둘을 한 객체로 묶어
쪼개질 수 없게 한다 — 바이트와 해시가 갈라지면 무결성 대조가 조용히 무의미해진다.

**저장·제출은 막지 않는다.** 한 차시가 끝나 나가야 하는데 아직 자료를 못 정한 학생이 있고,
그때 나가는 파일이 있어야 다음 차시에 이어서 한다(`open-decisions.md` "컴퓨터실 PC는
리셋을 전제한다"). 교사가 데이터 없는 파일을 받으면 그건 안 한 것이지 도구가 막을 일이
아니다.

**"데이터를 올려야만 프로젝트가 된다"(C안)를 안 고른 이유**는 같은 문제가 **교체**에서
다시 나오기 때문이다. 데이터를 바꾸는 순간에도 옛 데이터와 새 데이터 사이의 틈은 있다.

### 가우시안 나이브 베이즈는 의존성을 빼고 우리가 구현한다 (2026-08-05)

**`ml-naivebayes`를 `package.json`에서 지우고 `engines/mljs.ts` 안에서 직접 계산한다.**
이 저장소가 "라이브러리에 맡긴다"를 기본으로 삼아 온 것에 대한 예외이므로 근거를 남긴다.

**뺀 이유는 성능도 취향도 아니고 결함이다.** `ml-naivebayes@4.0.0`의 `GaussianNB`는
**예측할 때 특성을 앞의 2개만 읽는다.** 예측 루프의 상한이
`for (j = 1; j < classes[0][1].length + 1; ++j)`인데 `classes[0][1]`은 특성 하나의
파라미터 쌍 `[C1, C2]`(길이 2)다. 특성 개수와 무관하게 j는 언제나 1, 2다. 학습은 네
특성을 다 받아 평균·분산을 계산하는데 예측이 그중 둘만 읽는다.

실측(붓꽃 픽스처 30행, 같은 분할):

| 넣은 특성 | 예측 배열 | 정확도 |
|---|---|---|
| 4개 전체 | `setosa, setosa, setosa, virginica, virginica, setosa, setosa, versicolor, versicolor` | 3/9 |
| 앞 2개(꽃받침)만 | **위와 완전히 동일** | 3/9 |
| 뒤 2개(꽃잎)만 | `setosa, setosa, setosa, versicolor, versicolor, versicolor, versicolor, virginica, virginica` | 8/9 |

특성을 **1개만** 고르면 `classes[i][2]`가 `undefined`라 `predict`가 TypeError로 즉사한다.

**이것은 "구현 차이"가 아니다.** 아래 "성능이 낮다는 이유로 알고리즘을 빼지 않는다"의
논거 — 어디까지가 구현 차이이고 어디부터가 빼야 할 것인지 그을 선이 없다 — 는 그대로
옳다. 그러나 **알고리즘이 입력을 안 읽는 것에는 선이 그어진다.** 그 결정은 유지하고,
근거 표의 나이브 베이즈 행만 재실측한다. 화면에 뜨는 숫자가 "CSV의 처음 두 열만 쓴
모델"의 것이면, 학생이 특성 순서만 바꿔도 나이브 베이즈만 움직이는 이유를 교사가 설명할
방법이 없다.

**업스트림을 기다리지 않는다.** 4.0.0이 최신이고 사실상 방치돼 있다. 포크를 물리면
그때부터 우리가 남의 코드를 유지보수하면서 출처는 남으로 남는다.

**대신 우리가 쓸 수 있는 이유.** 가우시안 NB는 학습이 클래스별 평균·분산이고 예측이
로그 확률의 합인, 40줄짜리 순수 계산이다. 이 저장소가 이미 직접 쓴 것들(분할, 전처리,
지표)과 같은 수준이고, 테스트로 전부 덮인다. 트리·랜덤포레스트처럼 자료구조와
최적화가 들어가는 것은 계속 라이브러리에 맡긴다 — **선은 "우리가 검증할 수 있는가"에
있지 "직접 쓸 수 있는가"에 있지 않다.** (KNN은 이 문장을 쓴 다음 날 우리 구현으로
바뀌었다 — 재현이 자료구조가 아니라 구조로 보장되게, `mlpx-spec.md` §5.6.)

**로그 공간에서 비교한다.** 라이브러리는 `Math.log(C1 * Math.exp(v²/C2))`로 지수를 한 번
왕복하는데, 지수 합이 대략 −745 아래로 내려가면 `exp`가 0으로 언더플로해서 모든 클래스의
확률이 0이 되고 "예측 없음"(`-1`)이 나온다. 로그 공간에서 그대로 비교하면 그 경로가
아예 없어진다(아래 "범위 밖 클래스 번호는 던진다"의 최대 발생원이 여기다).

**지금이 가장 싼 시점이다.** 숫자가 바뀌는 변경이라 `MLJS_ENGINE.version`이 오르고,
고정 테스트·`mljs.ts` 머리말 표·아래 근거 표를 같은 커밋에서 재실측 값으로 갱신해야 한다.
첫 `.mlpx`가 나간 뒤라면 옛 파일이 전부 "재현되지 않음"으로 뒤집힌다(위 "재실행 대조는
엔진을 넘지 않는다"). 모델 직렬화는 아직 코드가 하나도 없다.

### 범위 밖 클래스 번호는 던진다 (2026-08-05)

라벨 부호기의 `decode`가 범위 밖 번호를 **정렬상 첫 라벨로 조용히 바꾸고 있었다.**
주석은 "예측 한 번을 통째로 실패시키지 않는다"였다. **뒤집는다.**

실측(붓꽃 픽스처로 학습한 `GaussianNB`의 원시 출력, 라벨은 `[setosa, versicolor, virginica]`):

```
[5.1, 3.5, 1.4, 0.2]   ->  0      정상
[50, 35, 14, 2]        -> -1      cm 대신 mm로 넣은 학생
[100, 100, 100, 100]   -> -1
[0, 0, 0, 0]           ->  1
```

`-1`은 둘 다 화면에 **"setosa"**로 나온다. 확신에 찬 오답이고, 아무 에러가 없다.

**그 자리가 §0의 ⑧ 예측 시험이다.** 학생이 값을 직접 넣는 곳이고, 학습 범위 밖의 값이
들어오는 것이 비정상이 아니라 **그 화면의 용도**다. 여기서 조용한 폴백은 도구가 가장
많이 거짓말하는 자리를 고른 셈이 된다.

**이 저장소가 규정한 최악은 실패가 아니라 조용히 틀린 숫자다.** 범위 밖 행 번호를
시끄럽게 실패시킨 것과 같은 논리다(`preprocess.ts`의 `SPLIT_INDEX_OUT_OF_RANGE`).

자체 구현 NB는 `-1`을 내지 않으므로 이 경로는 곧 도달 불가가 되지만 **방어선은 남긴다** —
앞으로 들어올 엔진(pyodide·서버)의 출력도 같은 `decode`를 지난다.

**새 에러 코드를 만들지 않고 `JOB_FAILED`로 던진다.** 학생이 할 수 있는 일이 하나도 없는
도구의 고장이고, `metrics.ts`가 모르는 과제 유형에 이미 같은 코드를 쓴다. 무엇이 범위
밖이었는지는 `params`로 파일에 남아 개발자가 읽는다 — 학생에게는 "학습에 실패했습니다"다.

**정답·예측의 길이 불일치도 같이 던진다.** 지금 등록된 엔진은 전부 입력 행 수만큼 예측을
돌려주므로 도달하지 않는다(확인함). 그러나 이 함수는 곧 서버 학습과 pyodide의 결과도
받고, 비동기 경계를 넘어온 잘린 응답이 들어오면 **에러 없이 그럴듯한 지표**가 나온다 —
분류는 그 행을 혼동 행렬에서 빠뜨린 채 정확도 분모에는 넣고, 회귀는 없는 예측을 0으로
간주해 오차를 잰다. 두 번째 엔진이 들어오기 전이 적기다.

### 컴퓨터실 PC는 리셋을 전제한다 (2026-08-05)
**학교 컴퓨터실은 전원을 끄면 디스크가 되돌아간다.** 복원 솔루션이 걸려 있는 것이 보통이고,
그러면 IndexedDB에 남긴 것은 **전원이 켜져 있는 동안만 산다.** `persist()`를 부르든 무엇을
하든 소용없다 — 브라우저가 지우는 것이 아니라 디스크가 통째로 되돌아가기 때문이다.

**§1.2 "브라우저가 저장소다"를 부정하지 않는다. 환경마다 역할이 다를 뿐이다.**

| 환경 | IndexedDB가 하는 일 |
|---|---|
| 가정 PC·휴대폰 | 프로젝트 보관. 문서가 말하는 그대로다 |
| 학교 컴퓨터실 | **한 차시 안의 새로고침·크래시 복구까지.** 그 이상은 없다 |

**그래서 `.mlpx` 내보내기는 제출 기능이기 이전에 차시를 건너는 수단이다.** 이 도구의 수업은
한 차시로 끝나지 않고 여러 차시에 걸친다 — 다음 시간에 이어서 하려면 파일이 있어야 한다.

**막으려 들지 않는다.** 학생들은 컴퓨터실이 리셋된다는 것을 이미 알고 클라우드나 메일로
알아서 백업한다. 그러므로 요구사항은 "잃지 않게 막는다"가 아니라 **"수업 끝에 내보내는 것이
자연스러운 동작이 된다"**이다. 경고창의 문제가 아니라 화면 설계의 문제이고, 그쪽이 훨씬 쉽다.

교사에게도 걸리는 것이 하나 있다 — **다음 차시 시작은 "새 프로젝트"가 아니라 "파일 열기"다.**
첫 화면이 그 동선을 전제해야 한다.

### 프로젝트는 한 번에 하나만 연다 (2026-08-05)
**편집 중인 프로젝트는 언제나 하나다.** 같은 `projectId`가 두 탭에서 열리면 두 번째 탭에는
"이미 다른 탭에서 열려 있습니다"를 보여주고 편집을 열지 않는다.

이유는 조용한 데이터 소실이다. `saveProject`는 충돌을 감지하지 않고 덮어쓰므로, 탭 A에서
학습을 세 번 돌리고 잊고 있던 탭 B에서 포트폴리오 한 줄을 고쳐 저장하면 **A의 실험 세 개가
흔적 없이 사라진다.**

**한 탭 안의 상태로는 못 막는다.** 브라우저 탭은 서로를 모른다. 앱이 "지금 프로젝트는
하나"를 아무리 지켜도 학생이 주소창에 앱을 다시 열거나 Ctrl+N을 누르면 그 규칙 밖에서
두 번째 탭이 생긴다. 그래서 `Web Locks`나 `BroadcastChannel`처럼 **탭을 가로지르는 수단**이
필요하다. 둘 중 무엇을 쓸지는 구현 세부다.

**낙관적 잠금 대신 이쪽을 고른 이유**는 교실에서 설명할 수 있어서다. 나중에 충돌을 알리고
"어느 쪽을 살릴까요"를 묻는 것은 중학생에게 답할 수 없는 질문이고, 애초에 두 번째 탭을
열지 않으면 그 질문이 생기지 않는다.

**비교 화면은 이 규칙에 걸리지 않는다.** 여러 `.mlpx`를 나란히 보는 것은 **읽기 전용으로
곁들이는 것**이지 편집 중인 프로젝트가 둘이 되는 것이 아니다. 축이 다르다.

### 무엇을 학습할 수 있는지는 서버가 알려준다 (2026-08-05)
**프런트엔드가 서버의 능력을 미리 적어 두지 않는다.** 지금 `ml/algorithms.ts`의 등록부는
알고리즘마다 `runtimes: ['mljs', 'pyodide-sklearn', 'server-sklearn']`처럼 **서버가 뭘 할 수
있는지를 우리가 선언**하고 있다. 자가호스팅 전제와 맞지 않는다 — 학교가 GPU 서버를 띄웠는데
우리 배열이 목록을 좁히는 꼴이다.

**우리가 정의하는 것은 프로토콜이고, 목록은 서버가 준다.** 같은 오리진 헬스 엔드포인트
(`architecture.md` §7.3)의 응답에 능력 목록을 함께 싣는다. 브라우저 엔진은 번들에 있으므로
그대로 하드코딩이고, 화면이 보는 것은 **둘의 합집합**이다.

**프로토콜 버전도 함께 협상한다.** Pages 프런트는 항상 최신인데 도커 설치본은 설치 시점에
고정된다 — 버전이 **구조적으로** 어긋난다. 서버가 지원 버전 배열을 주고 프런트가 자기가
이해하는 것을 고른다.

**포맷 쪽 준비는 이미 끝나 있다.** `schema.ts`가 `algorithm`과 `model.format`을 검증하지
않는 이유가 정확히 이것이고(§5.2, §10), 재실행 대조에는 `ENGINE_UNAVAILABLE`이라는
"불일치가 아니라 대조 불가" 상태가 이미 있다. 학교 서버가 `gradient_boosting`으로 학습한
`.mlpx`를 Pages 빌드에서 열면 **파일은 정상이고 지표도 다 보이며 그 모델로 예측만 못 한다.**

**그래서 화면의 서버 항목에 엔진 이름을 적지 않는다** (2026-08-05). 한동안
`scikit-learn · 학교 서버`라고 적혀 있었는데 그건 **우리가 서버의 능력을 선언한 것**이고
이 절이 막으려던 바로 그것이다. 지금 라벨은 `자체 서버`뿐이고, 무엇으로 학습하는지는
서버가 알려주면 그때 붙는다. `RUNTIMES`에 `server-sklearn` 항목 하나가 남아 있는 것은
**협상이 생기기 전까지의 자리표시자**다 — 목록이 서버에서 오는 순간 사라진다.

"학교 서버"가 아니라 "자체 서버"인 이유도 같다. 띄우는 주체가 학교일 수도 교사 개인일
수도 있고, 우리는 그걸 모른다.

정해야 할 것 여섯. 구현은 로드맵 8번이다.

1. **서버는 이름만이 아니라 하이퍼파라미터를 서술해야 한다.** 이름·타입·범위·기본값이
   와야 UI가 손잡이를 그린다. 안 그러면 학생은 기본값밖에 못 쓴다.
   → 그래서 `settings.hyperparameters`가 **(알고리즘, 실행 방법)** 2단이어야 한다.
   서버마다 파라미터 어휘가 다른데 알고리즘 하나로 키를 잡으면 섞인다.
2. **모르는 알고리즘의 이름은 코드를 그대로 보여준다.** §1.4 때문에 서버는 사람이 읽는
   문장을 못 주고, 우리 로케일에는 우리가 담은 것만 있다. 남의 `.mlpx`에서 모르는
   알고리즘을 만났을 때 이미 그렇게 하기로 돼 있으므로(§5.2) 규칙을 두 개 만들지 않는다.
3. **버전이 안 맞을 때의 동작** — 서버를 통째로 "없음"으로 볼지, 겹치는 기능만 쓸지.
4. **서버가 알려주는 실행 방법은 `engine.kind`가 서로 달라야 한다.** 학교가 구현 셋을
   올렸는데 둘이 같은 kind면, **재실행 대조가 서로 다른 구현으로 만든 결과를 같은
   엔진으로 보고 "재현되지 않음"이라고 판정한다**(§3.2). 무고한 학생이 위조를 의심받는
   그 시나리오다. 스키마는 안 바꿔도 된다(`kind`가 자유 문자열이다) — 프로토콜 규약이다.
5. **서버는 학습 응답에 확정 하이퍼파라미터를 되돌려준다. 성공이든 실패든.**
   1번의 기본값 서술로 프런트가 값을 채울 수는 있지만 그건 **미리보기와 폴백**이지
   기록의 권위가 아니다. 서술이 빠뜨린 파라미터를 서버가 자기 기본값으로 조용히 채우면
   **파일은 `{C: 1.0}`이라 적고 서버는 `max_iter=100`도 썼는데 아무도 모른다.**
   응답이 아예 없는 실패(타임아웃·연결 끊김)에만 프런트가 채운 값을 기록한다.
   구조화된 값이라 §1.4와 충돌하지 않는다. 브라우저 엔진의 "확정은 학습보다 앞"
   (`mlpx-spec.md` §3)이 서버에서도 그대로 성립하므로 구조가 갈라지지 않는다.
6. **능력 항목마다 행 상한이 함께 온다** (#13). 1만인지 10만인지 1000만인지는 그 서버의
   하드웨어가 정하고 우리는 모른다. **상한도 (알고리즘, 구현)마다다** — 같은 서버가
   의사결정트리는 100만 행을 받고 SVM은 5만 행에서 끊는 것이 정상이다.
   상한이 없다고 알려오는 것도 정상이고, 그때는 데이터셋 상한(`MAX_DATASET_ROWS`)이
   유일한 천장이다. 브라우저 쪽 숫자는 이 협상에 넣지 않는다 — 그건 번들에 든 우리
   구현의 성질이라 등록부가 출처다.

**이름은 두 벌이 필요하고 서로 독립이다.** `decision_tree`("의사결정트리")와
`server:xgboost`("XGBoost (학교 서버)")는 축이 달라서, 화면의 "의사결정트리 / XGBoost"는
합친 이름이 아니라 **두 번 조회해 조립한 것**이다. (알고리즘 × 실행 방법)마다 이름을 두면
서버가 알고리즘 20개 × 구현 4개를 알려줄 때 이름표가 80개가 된다.

**교사가 모델을 설치해 넓히는 길이 여기서 열린다.** 백엔드에 알고리즘을 플러그인으로 얹고
관리자 화면에서 켜고 끄는 구성이 자연스럽게 따라온다.

**플러그인이 줘도 되는 것과 안 되는 것의 선은 셋으로 나뉜다.**

| | 예 | 줘도 되나 |
|---|---|---|
| 식별자 | `decision_tree`, `xgboost` | **된다.** 값이다 (docs/i18n.md 백엔드 3) |
| 고유명사 | "XGBoost", "LightGBM" | **된다.** 어느 언어에서도 같다 |
| 문장 | "큰 데이터에 적합합니다", "나무를 늘려보세요" | **안 된다.** ja가 붙으면 그 자리만 한국어다 |

§1.4가 막으려는 것은 세 번째다. 식별자는 애초에 대상이 아니었고 — `schema.ts`가
`algorithm`을 `userString`으로 분류하며 주석에 "알고리즘 id"라고 적어 둔 그대로다.

서버 보안은 우리 위협 모델이 아니다. 그 서버는 학교가 설치하고 학교가 소유한다(§1.1).

### 학습 실패는 교사가 읽을 수 있게 전달한다 (2026-08-05)
**라이브러리 결함마다 에러 코드를 새로 만들지 않는다.** 그러면 어휘가 결함 수만큼 늘고
로케일 파일 둘과 `errors.py`가 그 수만큼 끌려다닌다. 코드는 `JOB_FAILED` 하나로 두고
**원문을 `failure.params.detail`에 실어 보낸다**(`errors.ts`의 `failureDetail`).

§1.4를 어기지 않는다. **주 메시지는 여전히 코드에서 만든 문장**이고, 원문은 번역하지 않는
기술 정보로 그 아래에 붙는다. 코드로 사람이 읽는 문장을 대신하는 것이 아니라, 코드로는
담을 수 없는 것을 버리지 않는 것이다. 스택은 담지 않는다 — 학생 파일에 우리 코드 구조를
흘릴 이유가 없다. 길이 상한은 `limits.ts`에 있다.

**중학생이 영어 원문을 읽고 할 수 있는 일은 없다. 그래도 값이 있다 —** 이건 혼자 보는
화면이 아니라 **교사가 옆에 있는 화면**이다. 도달만 하면 대처할 사람이 있다. 그리고
`failure.params`는 `runs.json`에 그대로 들어가므로 **수업이 끝난 뒤 `.mlpx`를 여는
교사에게까지 따라간다** — "이 모델은 왜 결과가 없나"에 답이 남는다.

그래서 화면에 요구되는 것이 있다. **"학습 실패" 한 줄로 끝내지 마라.** 교사가 무엇을
해볼지 정할 수 있을 만큼은 보여야 하고, 동시에 학생이 겁먹을 만큼 앞에 나오면 안 된다.
접어 두고 펼치는 형태가 기본안이다.

실제로 걸린 사례가 하나 있었다. `ml-random-forest`는 **나무가 적으면 터졌다** — 붓꽃 30행에서
`nEstimators` 5 이하는 시드를 바꿔도 전부 실패했고 15부터 안정적이며, **데이터가 클수록 더
잘 터졌다.** "나무 개수"는 학생이 가장 먼저 줄여 볼 손잡이라 교실에서 실제로 일어나는
실패였다.

**지금은 안 터진다 (2026-08-05).** 원인은 out-of-bag 예측이었다 — 어떤 학습 행이 모든 나무의
표본에 들어가면 그 행의 표가 비는데 라이브러리가 그 경우를 검사하지 않는다. 한 행이 그럴
확률이 나무 하나당 약 0.632이므로 **나무가 적을수록, 행이 많을수록 반드시 터진다.**
기본값 100그루에서는 확률이 0에 수렴해서 안 보였다.

**우리는 OOB 결과를 쓰지 않는다.** 꺼서 막았다(`ml/engines/mljs.ts`의 `noOOB`). 쓰지도 않는
값을 계산하다 죽고 있었던 것이고, 그 블록은 난수를 소모하지 않으므로 **학습된 모델은 한 비트도
달라지지 않는다** — `tests/mljs.spec.ts`의 고정된 정확도가 그것을 지킨다. 덤으로 빨라졌다.

**그래도 위의 결론은 그대로다.** 남의 라이브러리는 우리 어휘로 실패하지 않고, 우리가 하나를
막았다고 그 사실이 바뀌지 않는다. 학생의 설정을 먼저 좁히지 않는 것도 그대로다 — 입력 범위를
어떻게 할지는 **하이퍼파라미터 화면을 만들 때** 다시 본다.

### 모바일에서도 동작한다 (2026-08-04)
**학생이 쓰는 기기는 학교 PC만이 아니다.** 같은 정적 페이지가 휴대폰에서도 돌아야 한다.

이 제약은 새로 추가된 것이 아니라 **여러 결정의 이유를 사후에 설명해 준다.**
서버가 없다는 것(§1.1)과 실행이 항상 순수 JS라는 것(`mlpx-spec.md` §0.2)이
모바일에서 특히 값을 한다 — 설치도, 로그인도, 회선도 필요 없다.

대신 **무거운 것에 대한 판단 기준이 데스크톱보다 엄격해진다.**

- **자체 JSON 대 ONNX의 저울이 기울었다.** onnxruntime-web은 수 MB WASM이고 모바일에서는
  그게 곧 회선과 메모리다. → 아래 "모델 직렬화" 항목
- **scikit-learn(Pyodide)의 26.3MB / 시동 15.4초는 모바일에서 더 나쁘다.** 엔진 선택이
  바뀌지는 않는다 — 어차피 학생이 명시적으로 켜는 선택지이고, 못 켜면 순수 JS로 돈다.
  다만 **상태 패널이 "이 기기에서는 권하지 않는다"를 말할 수 있어야 한다.** → #3-1
- **행 수 상한이 기기마다 다르다.** `BROWSER_ROW_LIMIT` 하나로 충분한지의 질문에
  "모바일"이라는 축이 하나 더 붙었다. → #13
- **iOS Safari의 저장소는 지워질 수 있다.** → #7

화면은 아직 없다. **UI를 만들기 전에 이 제약을 알게 된 것이 이 항목의 값이다.**

**다만 지금 할 일은 없다.** 소스를 훑어 모바일을 막는 API가 하나도 없다는 것까지는
확인했다 — WASM도 `crypto.subtle`도 `SharedArrayBuffer`도 안 쓴다. 실제 바닥선은 학습
코드가 아니라 **Tailwind v4**(Safari 16.4+ / Chrome 111+, 대략 iPhone 8 이후)가 정한다.
**실기 확인은 배포 단계에서 한다** — 그전에는 열어 볼 페이지 자체가 없다(#10-1).
제일 먼저 볼 것은 `TextDecoder('euc-kr')`다. CP949 CSV를 읽는 유일한 경로다.

### 모델 직렬화는 자체 JSON, ONNX는 이미지 단계부터 (2026-08-04) — #2 마무리
**이미 `mlpx-spec.md` §5에 표로 정해져 있었다.** 이 항목이 "미결정"에 남아 있어서 문서 둘이
어긋나 있었을 뿐이다. 여기 옮겨 적지 않는다 — 형식 목록의 출처는 그 표 하나다.

**고를 여지가 실은 없었다.** `mlpx-spec.md` §0.2가 "학습은 브라우저가 기본, **실행은 항상
브라우저(순수 JS)**"라고 못 박는다. 서버에서 학습한 모델이라도 예측은 브라우저에서 돌므로,
모델 형식은 **어느 엔진이 만들었든 순수 JS가 읽을 수 있어야 한다.**

- **pickle** — JS에서 읽을 방법이 없다. "서버 역직렬화 금지" 이전에 이미 탈락이다.
- **ONNX** — 읽으려면 `onnxruntime-web`(수 MB WASM)이 필요하다. "가볍다, 서버 불필요"와
  어긋나고 모바일에서는 더 그렇다. **자체 JSON으로 표현할 수 없을 때만** 그 비용을 낸다 → 딥러닝이 들어온 뒤.
- **자체 JSON** — 트리 구조와 계수는 JSON으로 그대로 표현된다. 학생이 압축을 풀어
  열어볼 수 있는 것은 덤이 아니라 교육적 이득이다.

**구현에 걸리는 결과가 하나 있다 — ml.js의 `toJSON()`을 그대로 담지 마라.** 그러면 모델이
ml.js 내부 구조에 묶여서, 같은 결정트리를 sklearn으로 학습하면 다른 모양이 나오고
"형식 하나에 예측기 하나"가 깨진다. 우리 어휘로 된 중립 JSON을 정의하고 엔진마다
그리로 옮기는 직렬화기를 둔다.

남은 것은 결정이 아니라 구현 세부다. 예를 들어 `mlpx-linear-v1`이 로지스틱 회귀와
나이브 베이즈를 함께 묶고 있는데 둘은 파라미터 모양이 다르다 - 만들면서 정한다.

### 브라우저 학습 엔진은 둘 다 간다 (2026-08-04) — #3 마무리
**순수 JS(ml.js 계열)가 기본이고, scikit-learn(Pyodide)은 학생이 명시적으로 켜는 선택지다.**
하나를 고르는 문제가 아니었다 — 둘은 서로 다른 것을 준다.

실측(개발 PC, 붓꽃, 같은 분할):

| | 순수 JS | Pyodide + scikit-learn |
|---|---|---|
| 전송량(gzip) | **25 KB** | **26.3 MB** (scipy 혼자 13.2 MB) |
| 시동 시간 | 없음 | **15.4초** — 코어 2.9 + 휠 3.9 + 첫 `import sklearn` 8.6 |
| 붓꽃 학습 | 5~235 ms | 8~117 ms |

**시동 15.4초는 다운로드를 뺀 CPU 시간이고, 페이지를 열 때마다 다시 든다.** 서비스 워커는
다운로드를 캐시하지 WASM 시동과 `import sklearn`을 캐시하지 않는다. 그래서 이 비용은
"첫 방문"이 아니라 **"매 수업"**이다. 문서에 있던 "최초 10~25MB"는 낙관적이었다.

지표 차이 — **`run.engine`을 남기는 규칙이 장식이 아니다.**

| 알고리즘 | scikit-learn | ml.js | |
|---|---|---|---|
| 결정트리 | 0.9333 | 0.9333 | 결정론적이라 정확히 일치 |
| KNN | 1.0000 | 1.0000 | 정확히 일치 |
| 로지스틱 회귀 | 0.9667 | 0.8667 | ml.js는 정규화 없는 경사하강 |
| 랜덤포레스트 | 0.9000 | 0.9667 | 배깅 난수가 다르다 |

### 성능이 낮다는 이유로 알고리즘을 빼지 않는다 (2026-08-04)
순수 JS 구현이 sklearn보다 낮게 나오는 알고리즘이 있다. **그래도 등록부에서 빼지 않는다.**

붓꽃 전체를 같은 분할로 돌린 실측:

| 알고리즘 | scikit-learn | 순수 JS |
|---|---|---|
| 결정트리 | 0.9333 | 0.9333 |
| KNN | 1.0000 | 1.0000 |
| 랜덤포레스트 | 0.9000 | 0.9667 | ← **분할이 다르다 — 아래를 보라** |
| 로지스틱 회귀 | 0.9667 | ~~0.8667~~ **낡음 — 아래를 보라** |
| 나이브 베이즈 | 0.9667 | ~~0.7000~~ **삭제됨 — 아래를 보라** |

> **랜덤포레스트 행은 다른 분할의 숫자다 (2026-08-11).** 저장소가 지금 지키는 붓꽃
> 실측은 `frontend/tests/fixtures/sklearn/`(150행·120/30·시드 42)이고 거기서는
> **sklearn 0.9667 / 우리 0.9333**으로 높낮이가 반대다. 어느 쪽도 틀리지 않았다 —
> 배깅 난수가 다르면 분할 하나로는 방향조차 안 정해진다는 것이 이 행의 원래 논지이고,
> 그래서 **분포로 비교하라**가 결론이다(`architecture.md` §3.3). 둘을 나란히 놓고
> 모순으로 읽지 마라.
>
> **로지스틱 회귀 행은 근거로 쓰지 마라 (2026-08-11).** 0.8667은 규제도 절편도 없는
> 경사하강의 숫자이고, 그 구현은 V2 감사 1단계-B에서 sklearn과 같은 목적함수를 푸는
> L-BFGS로 교체됐다(위 "로지스틱 회귀 솔버를 sklearn과 같은 구조로 바꾼다"). 지금은
> 붓꽃에서 0.9667로 sklearn과 같다. **결정 자체는 그대로 유효하다** — 배깅 난수처럼
> 정당하게 갈리는 자리는 남아 있고, 낮다는 이유로 알고리즘을 빼지 않는다는 판단이
> 이 표 하나에 걸려 있지 않기 때문이다.

> **나이브 베이즈 행은 근거로 쓰지 마라 (2026-08-05).** 0.7000은 구현 차이가 아니라
> `ml-naivebayes`가 특성을 앞 2개만 읽은 결과였다 — 꽃받침 둘만 쓴 나이브 베이즈의
> 숫자다(위 "가우시안 나이브 베이즈는 의존성을 빼고 우리가 구현한다").
>
> 자체 구현으로 교체 완료. **픽스처 30행에서 3/9 → 8/9.** 붓꽃 전체 150행 재측정은
> 아직 안 했으므로 이 칸을 새 숫자로 채우지 않는다 — 안 잰 값을 적는 것이 애초에 이
> 행을 틀리게 만든 방식이다. 필요해지면 sklearn 대조와 함께 한 번에 잰다(#3-1).
>
> **결정 자체는 이 행 없이도 선다** — 아래 논거는 로지스틱 회귀와 랜덤포레스트만으로
> 성립한다.

**어디까지가 "구현 차이"이고 어디부터가 "빼야 할 것"인지 그을 선이 없다.** 로지스틱
회귀를 10%p 차이로 빼기 시작하면 그 선은 결국 그때그때의 인상이 된다. 랜덤포레스트는
순수 JS가 **더 높다** — 방향조차 일정하지 않다.

**다만 이번 일이 그 선의 한쪽 끝을 알려줬다.** "알고리즘이 입력을 안 읽는다"는 구현
차이가 아니라 결함이고, 거기에는 선이 그어진다. 낮은 숫자를 보면 **먼저 그것부터
의심한다** — 성능 차이로 접고 넘어가면 결함이 실측 표에 근거로 눌러앉는다.
실제로 그렇게 됐던 것이 이 행이다.

그리고 이 설계는 **이미 엔진마다 숫자가 다르다는 것을 전제로 만들어졌다.** `run.engine`을
기록하고 재실행 대조가 엔진을 넘지 않는 이유가 그것이다. 낮은 것을 감추는 대신 무엇으로
만들었는지 남긴다.

**빼는 기준은 성능이 아니라 실행 가능성이다.** `svm`이 순수 JS에 없는 것은 후보가
WASM(libsvm-js)뿐이기 때문이지 정확도 때문이 아니다.

> 이 항목은 한 번 반대로 갔다가 되돌린 것이다. 낮은 숫자를 보고 빼는 판단을 했는데,
> 그건 코드 소유자가 할 결정이었다. 실측 표는 `frontend/src/ml/engines/mljs.ts`에도 있다.

### 무거운 엔진은 상태 점검에서 학생이 켠다 (2026-08-04)
**페이지를 열자마자 자동으로 받지 않는다.** 순수 JS만 쓸 학생까지 회선을 먹고, 무엇보다
**교사가 그 타이밍을 통제할 수 없다.** 화면 최상단의 상태 점검에서 버튼을 눌러야 받는다 —
그래야 교사가 "수업 시작에 다 같이 눌러라"로 부하를 한 번에 몰아서 끝낼 수 있다.

**상태는 4단계다.** 미설치 / 내려받는 중 / **받았지만 시동 전** / 준비됨.
새로고침하거나 새 탭을 열면 "준비됨"이 "받았지만 시동 전"으로 돌아간다 — 다운로드는 남아도
시동은 매번이기 때문이다. 3단계로 줄이면 학생이 "아까 받았는데 왜 또 기다리지"를 겪는다.

같은 패널이 서버 연결(§7.3의 헬스 엔드포인트)과 저장소 여유(`estimate()`)도 함께 본다.
학생이 수업 시작에 한 번 보는 자리다.

### 학습은 언제나 백그라운드다 — 화면이 멈추면 안 된다 (2026-08-04)
**실행 방법이 무엇이든 학생에게 "멈췄다"는 느낌을 주지 않는다.** 순수 JS든 scikit-learn이든
학교 서버든 마찬가지다. 저사양 학교 PC에서 화면이 몇 초 얼면 학생은 고장으로 보고 새로고침을
누르며, 그러면 진행 중이던 작업이 통째로 날아간다.

**기술적 귀결이 하나 있고 이게 설계를 결정한다 — 메인 스레드에서 돌리면 안 된다.**
스피너를 띄우는 것만으로는 부족하다. 메인 스레드가 막히면 진행률 텍스트도 취소 버튼도 같이
죽고, 남는 것은 "응답 없음"뿐이다. 그러므로 **브라우저 학습은 Web Worker에서 돈다.**

같은 규칙이 **엔진 시동에도 적용된다.** scikit-learn의 15.4초는 통째로 CPU 작업이라
메인 스레드에 두면 상태 점검 패널의 진행 표시부터 얼어붙는다.

부수 효과가 둘 있다.

1. **세 실행 방법이 전부 비동기 메시지 인터페이스가 된다.** 워커도 WebSocket도 모양이
   같아지므로 `TrainingBackend`가 하나로 유지되고, 화면은 어디서 도는지 몰라도 된다.
2. **취소가 실제로 가능해진다.** 워커는 terminate가 확실한 취소지만, 메인 스레드에서 도는
   루프는 멈출 방법이 없다. 45분 수업에서 잘못 누른 학습을 못 멈추는 것은 그 자체로 실패다.

진행 표시는 **모델 단위**다 (`mlpx-spec.md` §0.3). 실험 전체 진행률은 클라이언트가 센다.

### 실행 방법은 (위치 × 엔진)이 아니라 하나의 목록이다 (2026-08-04)
백엔드가 붙으면 결정트리 하나에 실행 방법이 셋이 된다 — 순수 JS(`browser`/`mljs`),
scikit-learn(`browser`/`pyodide-sklearn`), 학교 서버(`server`/`sklearn`).
**드롭다운 두 개("어디서" + "무엇으로")를 두지 마라.** 하나의 목록으로 합친다.

- `computedBy`와 `engine.kind`는 파일에 이미 있는 필드다. 화면용으로 묶을 뿐이라
  **`formatVersion`은 올라가지 않는다.**
- **실험 기본을 두고 모델마다 덮어쓸 수 있다** (2026-08-05 개정). 화면 위에서 한 번
  고르면 전부 그걸 따르고, 바꾸고 싶은 모델만 개별로 바꾼다.
- **자동 이동은 학생이 안 고른 칸만 채운다.** 실험 기본을 물려받은 모델은 못 돌면 되는
  곳으로 넘어가지만(§0.1), **모델별로 콕 집어 고른 것은 옮기지 않는다.** 고른 것과 다른
  데서 돌리는 것은 조용히 다른 일을 하는 것이고, 못 돌면 사유를 주는 편이 낫다.
- **같은 알고리즘을 여러 실행 방법으로 나란히 고를 수 있다.** "같은 SVM인데 엔진이
  다르면 왜 숫자가 다른가"를 한 실험 안에서 본다. **이게 위 규칙이 필요한 이유이기도
  하다** — 자동 이동이 걸리면 셋이 같은 곳으로 몰려 똑같은 줄 세 개가 나오고,
  비교하려던 것이 사라진다.
- 실험에 엔진이 섞였으면 **비교표에 표시한다** — 숨기면 조용히 틀린 비교가 된다.

> **개정 이유 (2026-08-05).** 원래는 "선택은 실험 단위다. [학습] 한 번에 실행 방법 하나"였고
> 근거로 "비교표가 성립하는 조건"을 들었다. **그 근거가 틀렸고, 바로 다음 줄과 모순이었다.**
>
> 자동 이동을 허용하는 이상 **엔진은 이미 섞이고 있었다.** 도구가 말없이 섞는 것은 되고
> 학생이 일부러 섞는 것은 안 된다는 선은 방어할 수 없다. 그리고 실험이 실제로 보장하는
> 것은 셋이다 — **같은 데이터, 같은 전처리, 같은 분할.** 엔진은 애초에 그 목록에 없었고,
> 그래서 `run.engine`을 기록하고 재실행 대조가 엔진을 넘지 않는 것이다.
>
> 실제 피해도 있었다. 학생이 순수 JS를 고르고 SVM을 체크하면 실패 run 하나가 남는다 —
> 고를 수 있게 해 놓고 안 돌려준 것이다. 모델별로 열면 SVM은 그게 되는 곳에서 그냥 돈다.
>
> 대가는 **교사의 부하 통제가 약해진다**는 것이다. "이번 학습은 학교 서버로 간다"가 한눈에
> 안 보인다. 자동 이동이 이미 같은 일을 하고 있어서 새로 생기는 위험은 아니지만, 화면이
> **"이 실험 중 2개가 학교 서버로 갑니다"를 요약해 줘야 한다.**
- **목록은 항상 보인다.** 못 쓰는 항목은 비활성화하되 숨기지 않고 이유를 함께 준다
  (§0.1, `architecture.md` §7.3). "고급 설정"에 접어 넣지 않는다 — 보여주는 것과
  고르게 하는 것은 다르고, 기본값이 이미 골라져 있으므로 학생은 안 건드려도 된다.
- 등록부 키는 **(알고리즘, 실행 방법)**이다. ml.js `maxDepth` / sklearn `max_depth`처럼
  하이퍼파라미터 어휘가 다르고, sklearn 둘은 어휘가 같은데 숫자만 갈린다.
- **같은 (알고리즘, 실행 방법)을 두 줄 고르면 하이퍼파라미터는 같다.** 축이 여기까지다 —
  `settings.hyperparameters`가 그 쌍으로 값을 잡으므로 "결정트리 maxDepth 3 vs 10을
  한 실험 안에 나란히"는 표현할 수 없다. **의도한 선이다.**

  **하이퍼파라미터 비교는 실험을 나눠서 한다.** 교차 실험 비교의 공정성은 구조적으로
  보장된다 — 같은 데이터·같은 결측 전략이면 `usableRows`가 같고, 같은 `randomState`면
  분할이 같다. 그리고 `changed`가 `hyperparameters.decision_tree:mljs`를 정확히 짚어
  준다. 실험이 보장한다고 적어 둔 셋(같은 데이터·전처리·분할)이 여기서도 그대로 선다.

  오히려 **"변수 하나를 바꾸고 [학습]을 다시 누른다"가 더 나은 수업 동선**이고,
  45분 수업에서 [학습] 두 번은 비용이 아니다. 배열을 연 근거는 처음부터 **엔진 비교**
  였다(위 개정 이유). 그걸 하이퍼파라미터 축으로 넓히는 것은 그 결정의 연장이 아니라
  별건이다.

  **나중에 열려면 `formatVersion`이 오른다.** `selectedAlgorithms` 항목에 개별
  `hyperparameters`를 붙이면 구버전 앱이 그 필드를 (loose라) 보존은 하되 무시하고 공유
  값으로 학습한다 — 조용히 다른 동작이다. 지금 안 여는 대가가 그것이라는 것까지 적어 둔다.

### 공식 배포에는 서버가 없다 (2026-08-04)
**공개 배포는 GitHub Pages 정적 페이지 하나뿐이다.** 백엔드는 구현하되 우리가 호스팅하지
않는다. 도커 이미지로 배포하고 더 강한 연산이 필요한 학교가 컴퓨터실에 직접 띄운다.

이유는 셋이다.

1. 공개 호스팅은 익명 사용자에게 **개인이 부담하는 연산을 무제한 열어주는 것**이다.
2. 막으려면 계정이 필요한데, 계정을 두면 개인정보를 다루게 되어 §1.1과 충돌한다.
3. **수행평가 도중 서버가 죽으면 그 실패는 교사가 뒤집어쓴다.** 개인이 질 책임이 아니고,
   전국 단위로는 어떤 계산으로도 버틸 수 없다(`architecture.md` §7.1).

**배포 경로는 둘이고 빌드 산출물은 하나다.** 프런트엔드는 시작할 때 **같은 오리진**의
헬스 엔드포인트를 찔러 서버 유무를 판정한다. Pages에서는 404가 나고 브라우저 전용으로 돈다.
**백엔드 주소를 설정 가능하게 만들지 마라** — CORS, mixed content(Pages는 https, 교실
서버는 대개 http), 교사가 고쳐야 할 설정 파일이 한꺼번에 생긴다.

부수 효과로 **브라우저 학습 엔진의 전송량 문제(구 #11)가 사라졌다.** Pyodide를 쓰더라도
Pages가 CDN으로 서빙하므로 우리 부담은 0이다.

### 무결성은 해시와 재실행 대조로 한다 — 서명은 만들지 않는다 (2026-08-04)
**HMAC 서명·전자서명을 넣지 않는다.** 서명하려면 비밀키를 쥔 서버가 필요한데 공식 배포에는
서버가 없고, 자가호스팅 서버는 설치하는 사람이 극소수다. 거의 아무도 못 쓰는 경로를 위해
키 관리·환경 변수·검증 API를 유지할 이유가 없다.

**전제: 브라우저에서 도는 코드로는 위조를 막을 수 없다.** 학생 컴퓨터에서 실행되는 이상
학생이 통제한다. 목표는 "위조 불가능"이 아니라 **"흔적을 남기고 판단은 교사에게"**다.

세 층으로 간다 — 엔트리별+전체 해시(방지턱, 어디가 바뀌었는지) / 수거 시점 해시 기록
(제출 이후의 변조) / **재실행 대조**(지표가 이 데이터·설정에서 실제로 나오는지).
앞의 둘은 바이트를 검사하고 재실행은 주장을 검사한다. → `mlpx-spec.md` §7

**해시는 `@noble/hashes`의 SHA-256을 쓴다. `crypto.subtle`을 쓰지 않는다.**
`crypto.subtle`은 보안 컨텍스트에서만 존재하는데 **자가호스팅은 대부분 http**라 없는 셈이다.
분기와 폴백을 두는 대신 단일 경로로 간다. 실측 — 1MB 16ms, 10MB 55ms, 50MB 265ms.
**데이터셋은 import 시점에 한 번만 해싱한다**(정본은 그 뒤로 불변). 저장할 때마다 도는 것은
JSON 넷뿐이라 사실상 공짜다.

UI에 **"검증됨"이라고 쓰지 않는다.** 도구가 보증할 수 있는 것보다 강한 말이다.

### 해시는 `hashes.json` 별도 엔트리에 둔다 (2026-08-04)
자기 자신을 해싱 대상에서 빼야 하므로 별도 엔트리다. `manifest.json` 안에 넣으면 manifest의
해시를 계산할 때 그 필드만 빼고 계산해야 해서 "바이트를 그대로 해싱한다"는 단순함이 깨진다.

**`contentHash`는 zip 바이트가 아니라 엔트리 해시들에서 계산한다.** 경로로 정렬해
`"경로\n해시\n"`를 이어 붙인 것을 해싱한다. 다시 압축해도 값이 안 변하므로 **두 제출물의
`contentHash`가 같으면 내용이 같다**는 뜻이 되어 표절 신호로도 쓸 수 있다
(`mlpx-spec.md` §6.3). 반대로 "수거 시점 기록"은 `.mlpx` 바이트 자체를 해싱하면 되므로
파일 안에 아무것도 넣지 않는다.

옛 파일에는 없으므로 **선택 항목**이다. 없거나 깨져 있으면 `UNKNOWN`이고 파일은 열린다.
엔트리가 하나 늘어나는 것은 어휘 변경이 아니므로 `formatVersion`은 올리지 않는다.

`ENTRY_HASH_STATUSES`(`entryHash.*`)를 따로 둔다. 파일 전체 상태와 엔트리 하나의 상태는
축이 다르고, 해시가 실제로 값을 하는 자리는 "**어디가** 바뀌었는지"이기 때문이다.

### 재실행 대조는 엔진을 넘지 않는다 (2026-08-04)
각 run에 **엔진 종류와 버전을 기록**하고, 대조는 그 run을 만든 엔진으로만 한다.
다른 엔진밖에 없으면 "대조할 수 없음"이지 "불일치"가 아니다.

이유는 배포 경로가 둘이기 때문이다. 학생이 Pages에서 학습해 제출하고 교사가 도커 설치본에서
대조하면, 엔진이 다를 때 숫자가 갈린다 → **무고한 학생이 위조를 의심받는다.**
수행평가에서 이건 이 프로젝트가 낼 수 있는 최악의 실패다.

부수 효과로 **엔진 선택과 검증 설계가 분리된다.** 나중에 엔진을 바꿔도 옛 파일의 검증
의미가 깨지지 않으므로, 엔진을 완벽하게 고르려고 멈출 필요가 없었다.

### 정본 데이터셋은 언제나 UTF-8 CSV다 (2026-08-04)
**업로드 형식과 인코딩은 import 시점에 딱 한 번 정규화되고, 그 뒤로는 아무도 모른다.**
xlsx로 올렸든 CP949 CSV로 올렸든 `data/table.ts`의 `importTable()`을 지나면 같은
UTF-8 CSV 바이트가 된다. 이 바이트가 IndexedDB에 들어가고, `.mlpx`의 `dataset/data.csv`가
되고, `datasetHash`의 대상이 되고, 서버로 간다.

이유는 셋이다.

1. `mlpx-spec.md` §1.1은 표 데이터를 `dataset/data.csv`로 규정한다. xlsx를 그대로 담으면
   그 규정이 깨지고, 교사가 파일을 풀었을 때 여는 방법이 형식마다 달라진다.
2. **분할 인덱스와 같은 논리다.** 클라이언트가 분할을 계산해 보내기로 한 이유는 양쪽이
   각자 계산하면 갈리기 때문이었다(`mlpx-spec.md` §0.3). 파싱도 똑같다 — 브라우저와
   pandas의 파싱이 한 행이라도 어긋나면 `trainIndices`가 다른 행을 가리키고, 지표는
   멀쩡해 보이는 채로 **조용히 틀린 학습**이 된다. 파서를 하나로 만들어 원천 차단한다.
3. 서버가 xlsx도 cp949도 몰라도 된다. #15의 "pandas와 인코딩 목록 맞추기"가 사라진다.

**§7의 "바이트를 가공하지 않는다"와 충돌하지 않는다.** 정규화는 데이터셋이 정본이 되기
**전에** 일어난다. 정본으로 확정된 뒤에는 누구도 손대지 않는다.

정본 CSV는 UTF-8 **BOM으로 시작한다.** BOM 없는 UTF-8 CSV를 한국 윈도우 엑셀에서 열면
한글이 전부 깨지고, 교사가 `.mlpx`를 풀어 `data.csv`를 열어보는 일은 실제로 일어난다.
대가는 서버가 `utf-8-sig`로 읽어야 한다는 것 하나이며 서버는 우리 것이다.

따라서 `settings.dataset.encoding`은 **항상 `utf-8`**이다. 업로드 파일이 무엇이었는지는
`originalFileName`과 화면 표시용 `sourceEncoding`으로만 남는다.

### 표 파일 파서는 라이브러리에 맡긴다 (2026-08-04)
직접 구현하지 않는다. 셀 타입·공유 문자열·인코딩·생성기별 호환성을 손으로 맞추는 비용이
이 프로젝트가 감당할 시간보다 크다. #14의 "fflate + 자체 파서" 후보는 그래서 탈락했다.

| 형식 | 라이브러리 | 비고 |
|---|---|---|
| CSV | papaparse | 구분자 추정을 **켜 둔다**. 콤마로 고정하면 세미콜론 파일이 조용히 한 컬럼이 된다 |
| xlsx | exceljs → SheetJS | 순서대로 시도. `data/xlsx.ts`의 `PARSERS` 배열에 등록만 하면 늘어난다 |

**SheetJS는 자체 레지스트리에서 설치한다** — `package.json`에 `cdn.sheetjs.com`의 tarball
URL을 적고 `package-lock.json`이 URL과 integrity 해시를 고정한다. npm의 `xlsx@0.18.5`는
CVE 두 개가 미수정이라 쓸 수 없고, 0.20.x는 npm에 올라오지 않는다.
**런타임 CDN이 아니다** — Vite가 로컬에서 번들링한다. 비용은 `npm ci`가 그 호스트에
닿아야 한다는 것뿐이고, 막히면 tarball을 저장소에 넣어 `file:`로 바꾸면 된다.

폴백을 지금 넣은 이유는 **한셀로 저장한 xlsx가 ExcelJS에서 열리지 않는 것을 과거
프로젝트에서 실제로 겪었기 때문**이다. 교실에서 한컴오피스는 드물지 않다. 다만 이
저장소에서 재현한 적은 없다 → #17.

**zip 서명(`PK\x03\x04`)을 먼저 검사한다.** SheetJS는 형식을 스스로 추정해서 아무
바이트나 한 칸짜리 시트로 "성공"시킨다. 이 검사가 없으면 손상된 파일이 실패 대신
엉뚱한 표가 되고 학생은 그걸로 학습을 돌린다.

### 파싱은 두 단계이고 파일은 한 번만 읽는다 (2026-08-04)
`openTable()`이 파일을 한 번 열어 핸들을 주고, 미리보기와 본 파싱이 그 핸들을 공유한다.
단계마다 파일을 다시 읽으면 5만 행 xlsx에서 1.9초가 들었고, 지금은 0.7초다
(미리보기 자체는 980ms → 6ms).

시트가 있느냐 없느냐는 `sheetNames`의 길이로만 드러난다. CSV는 빈 배열이라 화면이
형식별로 갈라지지 않는다.

### 인코딩 판정과 지원 목록 (2026-08-04) — #15 마무리
`SOURCE_ENCODINGS`(`data/encoding.ts`)가 유일한 출처다: `utf-8`, `cp949`,
`utf-16le`, `utf-16be`.

판정 순서는 **BOM → UTF-8 유효성 검사 → CP949**다. BOM이 있으면 그 말을 믿되,
`TextDecoder`가 다루지 못하는 BOM(UTF-32)이면 `DATASET_ENCODING_UNSUPPORTED`로
**시끄럽게 실패한다.** 조용히 깨진 한글을 보여주면 학생이 할 수 있는 일이 없다.
UTF-32 BOM은 UTF-16LE BOM으로 시작하므로 **긴 BOM을 먼저 본다.**

`cp949`는 파일에 기록되는 이름이자 pandas가 그대로 받는 이름이다. 브라우저에는 그 라벨이
없어 `euc-kr` 디코더를 쓰는데, WHATWG 스펙이 그 라벨을 windows-949 매핑으로 정의해 두어
CP949 바이트가 정확히 풀린다.

**"학생이 판정을 뒤집을 수단"은 만들지 않았다.** 정본이 UTF-8로 정규화되므로 되돌릴
대상 자체가 없고, 판정이 틀리면 미리보기에서 바로 보인다. 필요해지면 그때 연다.

### 인코딩은 자동으로 판정한다 (2026-08-04)
**한국 윈도우의 엑셀에서 "CSV로 저장"하면 UTF-8이 아니라 CP949다.** 이걸 UTF-8로 읽으면
한글 컬럼명이 전부 깨진다. 교실에서 반드시 일어나는 일이고, 그 화면에서 학생이 할 수 있는
게 없으면 수업이 거기서 멈춘다.

**파일을 여는 쪽이 알아서 판정한다. 학생에게 인코딩을 먼저 묻지 않는다.**
"UTF-8과 CP949 중 무엇입니까"는 중학생에게 답할 수 없는 질문이고, 물어보는 것 자체가
수업을 멈추는 지점이다. 기본안은 BOM 확인 → UTF-8 유효성 검사 → 실패하면 CP949이며,
구체적인 판정 방식은 구현 시 확정한다. → 위 #15

### 상위 버전 파일은 거부한다 (2026-08-04)
신버전이 만든 `.mlpx`를 구버전 앱이 열지 못하게 막는다. 학교 PC와 집 PC의 앱 버전이
다를 때 조용히 열렸다 깨지는 것보다 낫다. **버전 검사를 스키마 검증보다 앞에 두므로**
검증 단계에 도달하는 파일은 항상 같은 버전이고, 그래서 어휘(enum)를 엄격하게 막아도
호환성 문제가 생기지 않는다. 대가로 **어휘가 늘어나는 변경은 `formatVersion` 증가와
마이그레이션을 요구한다.** → `mlpx-spec.md` §9

### 상한값은 상수 한 곳에서만 (2026-08-04)
프런트엔드의 크기·개수 상한은 `frontend/src/limits.ts`가 유일한 출처다.
백엔드의 `config.py`(환경 변수)와 대칭이다. → CLAUDE.md §1.5

### IndexedDB 여유 공간 사전 검사 (2026-08-04)
데이터셋을 쓰기 전에 `navigator.storage.estimate()`로 확인하고 부족하면
`STORAGE_QUOTA_EXCEEDED`로 거부한다. `estimate()`가 없는 브라우저에서는 검사를 건너뛰고
`QuotaExceededError`를 잡아 같은 코드로 바꾼다. `persist()`와 프로젝트 수 상한은 보류(#7).

### 백엔드 코드의 한국어 (2026-08-04)
**주석과 docstring은 한국어로 써도 된다.** 막으려는 것은 UI로 새어 나가는 문자열이지
개발자용 설명이 아니다. CI 검사는 `ast`로 **문자열 리터럴만** 순회한다(주석은 AST에 없다).

### 예측 기능의 모델 보관 (2026-08-04)
서버가 학습 후 직렬화된 모델을 클라이언트로 내려보내고, 클라이언트가 `.mlpx`에 담는다.
서버는 모델을 보관하지 않는다. §1.1(서버 무상태)과 "재학습 없이 예측"이 양립한다.
→ `mlpx-spec.md` §5 (형식은 위 미결정 2번)

### 문서 언어 (2026-08-04)
`docs/`와 `CLAUDE.md`는 한국어. 백엔드 코드의 식별자는 영어.

### 파일 확장자: `.mlpx` (2026-08-04)
`.docx` / `.pptx` / `.hwpx` 계열로 읽히고 **그 포맷들도 실제로 zip**이라 이름이 구조와 일치한다.
"hwpx처럼 여러 파일을 하나로 묶은 것"이라는 한 문장 설명이 교실에서 그대로 통한다.
`.mlp`는 MeshLab 프로젝트이자 Dolby TrueHD 오디오 확장자라 탈락.
코드에서는 상수 하나로만 관리하므로 변경 비용은 여전히 낮다.

### zip 라이브러리: fflate (2026-08-04)
gzip 기준 약 8KB로 가장 가볍고 빠르다. 비동기·스트리밍을 지원해 큰 CSV에서 화면이 멈추지 않는다.
JSZip은 약 30KB에 유지보수가 활발하지 않아 제외.

### 런타임 검증: zod (2026-08-04)
`.mlpx`는 외부에서 들어오는 파일이다. 스키마 하나로 타입과 검증을 함께 얻고,
"어느 필드가 왜 잘못됐는지"를 위치 정보와 함께 돌려주므로 깨진 파일을 연 학생에게
무엇이 문제인지 알려줄 수 있다.

### Python 하한 3.12 (2026-08-04)
numpy 2.x 스텁이 `type` 문 등 3.12 문법을 쓴다. mypy를 3.11로 고정하면 스텁 파싱에서
막혀 검사 자체가 진행되지 않는다.

### IntegrityStatus를 ErrorCode에서 분리 (2026-08-04)
"검증됨"은 실패가 아니라 상태다. 검증 요청 자체는 성공했고 결과가 그중 하나일 뿐이다.
로케일 네임스페이스도 `errors.*`가 아니라 무결성 상태 전용이다 — 지금은 축마다 갈려
`fileHash.*`·`entryHash.*`·`reproduction.*`로 나뉘어 있다(`error-codes.md`).
