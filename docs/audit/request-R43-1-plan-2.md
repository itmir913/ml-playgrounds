## 코드 소유자가 정한 것 (검토 대상이 아니라 전제다)

- 범주를 지울 때 **실험 기록은 남긴다.** 테스트 사진이 0장이 되어 원래 분할로 되돌릴 때도 남긴다.
- 확인 창 문구: 테스트 사진이 있을 때만 *"사진은 삭제되지 않고 [범주 없음]으로 이동합니다. 이 범주의 테스트용 사진 {count}장은
  삭제되며 되돌릴 수 없습니다. ({name})"*. 없으면 지금 문구 그대로.
- 테스트 장수를 변경 이력(`ml/changes.ts`)의 비교 항목으로 더하는 일(1차 지적 5)은 **이번에 안 한다.**
- 결정 106(학습 입구 대조)은 안전망으로 **남긴다.**

## 고친 계획

**A. `renameCategory(project, from, to, now)` — 테스트 자리도 같은 트랜잭션에서 옮긴다.** (1차 지적 1·4)

1. 훈련 자리와 똑같이 `readImages(project, 'test')`를 돌아 `from` 범주의 사진을 `imageEntryPath('test', hash, to, format)`로 옮긴다.
   `moveImages`는 역할이 `'data'`로 박혀 있어 재사용하지 않는다.
2. **`to`가 테스트 자리에만 있는 이름이면 거절한다** — 남아 있던 `test/<to>/`와 조용히 합쳐져 옛 사진이 새 범주의 정답으로 채점되는
   것을 막는다. 자리: 화면의 이름 판정 `nameTaken`(`locks.ts:640`)이 보는 목록에 테스트 자리의 범주를 더한다(문구는 기존 "이미 있는
   이름"). 함수(`renameCategory`)는 화면을 못 믿으므로 같은 경우 **아무것도 바꾸지 않고 그대로 돌려준다**(던지지 않는다 — 부르는
   쪽 `ImagePanel.vue:603`이 이미 판정을 지났다는 전제이고, 오면 우리 버그다). → **물음: 던지는 것이 맞나, 그대로 돌려주는 것이 맞나.**
3. 훈련 자리에도 `to`가 이미 있으면(두 범주 합치기) 지금처럼 화면이 막는다. 테스트 쪽 합치기는 2가 막는다.

**B. `removeCategory(project, name, now)` — 그 범주의 테스트 사진을 지우고, 0장이 되면 원래 분할로.** (1차 지적 2·3)

1. 훈련 사진은 지금처럼 `_unlabeled`로 옮긴다(라벨만 뗀다).
2. `readImages(project, 'test')` 중 `name` 범주의 사진을 지운다. 그 해시의 임베딩은 다른 자리가 안 쓰면 함께 지운다(`removeImages`의
   "자리를 넘어 지우면 안 된다" 규칙을 그대로 — 가능하면 `removeImages(project, hashes, now, 'test')`를 부른다).
3. **테스트 사진이 0장이 되면** 테스트 참조를 떼고 `split.method`를 `holdout`으로 돌린다. **실험은 지우지 않는다** — 코드 소유자
   결정이고, 분할 방식이 바뀐 것은 다음 실험에서 변경 이력 `split.method`(`changes.ts:224`)가 말한다. `clearTestImages`는 실험을
   지우므로 재사용하지 않는다.
4. 확인 창(`ImagePanel.vue:951-960`)의 장수는 테스트 자리를 범주별로 세는 함수로 낸다(`countByCategory`는 훈련만 센다) — 화면 밖
   순수 함수로 두고 vitest로 덮는다. 로케일 키 하나(ko·en·ja), 사용자 데이터는 문장 끝 괄호.
5. 결정문(106 개정)에 *"범주 삭제에서 '라벨만 뗀다, 되돌릴 수 있다'는 테스트 사진에는 성립하지 않는다 — 되살리려면 테스트 묶음
   전체를 다시 올려야 하고 그러면 실험이 지워진다"*를 적는다.

**C. 그 밖.** 결정 106의 학습 입구 대조는 그대로. 새 범주로 올리기·`moveImages`·`removeImages`는 손대지 않는다(106이 막는다).
**검사:** A-1·A-2·B-2·B-3의 진짜 입구 재현을 각각 검사로 두고, 고치기 전 코드에서 우는 것까지 본다. 문서가 코드보다 먼저다.
