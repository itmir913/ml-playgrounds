## 0. 요약 — 뿌리 하나

> **화면이 무언가를 들고 있는 동안 그 재료가 바뀌는 길이, 화면 안에서 열려 있다.
> 그리고 그 길을 지나가는 스펙이 이 슬라이스에 거의 없다.**

- **확인 판의 묶음이 범주 이름을 들고 있다.** 읽을 때 적은 이름을 굽을 때 그대로 쓰는데,
  그 사이 같은 화면에서 범주 이름을 바꾸거나 범주를 삭제할 수 있다. 굽고 나면 **지운 이름이
  되살아나 사진이 거기 앉는다** — A-1.
- **전처리 화면의 열 표가 학습과 다른 행으로 열 종류를 센다.** 표는 파일 전체로, 학습은
  그 실행이 쓰는 행으로 센다. 두 집합이 갈리는 흔한 입력(타깃이 빈 행)에서 **표는 "학습에서
  빠집니다 · 2개 중 1개"라고 말하고 학습은 그 열을 쓴다** — A-2. 결정문 53이 이 갈림을
  넓혔다.

**두 시점을 재서 조용했던 것이 더 많다** — 히스토그램의 열 바꾸기(결정대로), 산점도의
상한 스위치 왕복, 표 예측의 입력·필터 바꾸기, 재학습 뒤의 예측(구조적으로 닿지 않는다).
**다만 그 조용함을 지키는 검사는 대부분 없다** — 돌연변이 49개 중 **40개가 좁은 목록에서
조용했고, 슬라이스를 싣는 스펙 전부로 넓혀도 39개가 조용했다**(§3). 안 간 줄을 열어 보니 이 슬라이스의 두 시점 자리 — 미리보기,
[적용], 예측 답 루프, 일괄 예측 내려받기, 사진 선택·범주 편집 — 가 **한 번도 실행되지
않는다**(§2).

**등급 — A 2 · B 3 · C 9.**

## 1. 지적

### A-1. 확인 판에 선 사진 묶음이 범주 이름 변경·삭제 뒤에 **옛 이름을 되살린다**

**자리** `frontend/src/views/data/ImagePanel.vue:265`(`pending`에 범주 이름을 담는 자리) ·
`:351`(`bake`가 그 이름으로 `byPath`를 세우는 자리) · `:501`(`commitName`) ·
`:514`(`commitRemoveCategory`). 여는 손잡이는 `ImageGrid.vue:136`·`:143`.

**주장.** 범주 카드의 [사진 추가]로 사진을 고르면 묶음이 **그 범주 이름을 문자열로** 들고
확인 판에 선다(`readImageFiles(files, into)`). 확인 판이 서 있는 동안 **같은 화면의 [이름
변경]·[범주 삭제]가 잠기지 않는다** — `canName`은 `busy`만 보고, 확인 판은 `busy`가 아니다.
그 뒤 [이 사진 사용]을 누르면 `bake()`가 묶음의 옛 이름을 그대로 `addImages`에 넘기고,
`addImages`는 **목록에 없는 범주를 새로 만든다**(`project/images.ts:401–408`).

**재현** (`tests/zz-r38-image-panel.spec.ts`, 지운 임시 스펙). 진짜 단추로 몰았다 — 카드의
`drop` → 카드의 [이름 변경] → 대화상자 입력·확인 → 바의 [이 사진 사용]. 굽기는 저장소의
가짜 워커(`fixtures/image-workers`)다.

| | 범주 목록 | 사진이 앉은 범주 | 알림 |
|---|---|---|---|
| **처음부터** `cat` 칸에 놓고 굽기 | `[cat]` | `cat` | `1장 추가` |
| `고양이` 칸에 놓기 → 이름을 `cat`으로 → 굽기 | **`[cat, 고양이]`** | **`고양이`** | `1장 추가` (경고 없음) |
| `고양이` 칸에 놓기 → 범주 삭제 → 굽기 | **`[고양이]`** | **`고양이`** | `1장 추가` (경고 없음) |

**화면도 그 사이 거짓말을 한다** — 이름을 바꾼 뒤에도 바의 요약은 `고양이 1개`라고 말한다
(없는 범주다).

**틀리면 학생에게.** 사진을 고른 뒤 확정 전에 범주 이름의 오타를 고치는 것은 자연스러운
순서다. 그러면 **새로 올린 사진이 옛 이름의 범주에 따로 앉고**, 학습은 그것을 **다른
클래스**로 배운다. 카드가 하나 더 생기므로 눈에 보이긴 하지만, 알림은 성공 한 줄뿐이고
학생이 방금 지운 이름이 왜 돌아왔는지 말해 주는 것이 없다.

**무는 검사가 있는가.** **없다.** 사진 판의 이름 변경·삭제·선택 줄(`:436–519`)이 **어느
스펙에서도 실행되지 않는다**(§2). **세울 수 있다** — 위 표가 그 검사다(진짜 입구로 몰았다).

**처방 — 넣어 보고 물리는지까지 쟀다.** 이름을 바꾸거나 범주를 없애는 자리에서 **판에 선
묶음도 함께 옮긴다.** 바꾸기는 새 이름으로, 삭제는 `IMAGE_UNLABELED`로 — 이미 앉은 사진에
`removeCategory`가 하는 일과 같다.

```ts
// commitName, save 뒤
if (draft.mode === 'rename' && pending.value) {
  pending.value = pending.value.map((item) =>
    item.category === draft.from ? { ...item, category: name } : item,
  )
}
// commitRemoveCategory, save 뒤
if (pending.value) {
  pending.value = pending.value.map((item) =>
    item.category === name ? { ...item, category: IMAGE_UNLABELED } : item,
  )
}
```

넣으니 위 표의 둘째 줄이 **처음부터와 같아지고**(`[cat]`·`cat`) 셋째 줄은 사진이
`_unlabeled`에 앉았다. 사진 판을 싣는 스펙 다섯 파일(`image-panel-drop`·`image-panel-fail`·
`image-paste`·`image-upload-zip`·`image-grid`)과 임시 스펙을 합쳐 77개가 초록, `vue-tsc` 깨끗.
**다른 길 — 확인 판이 서 있는 동안 이름 변경·삭제를 잠그는 것 — 은 안 쟀다.** 잠그면
§8.2대로 이유를 말해야 하고, 그 문구가 새로 생긴다.

**같은 병의 이웃 — 셋을 셌고 하나뿐이다.** "범주 이름을 들고 기다리는 묶음"은
`ImagePanel.pending`, `ImagePrepPanel.pendingTest`(`:160`), 그리고 굽는 중의 `baking`이다.

- `pendingTest`는 **굽기 직전에 지금 범주로 다시 대조한다**(`ImagePrepPanel.vue:262`의
  `testZipBlockFor(categories.value, …)`) — "넘긴 뒤에도 참인가"를 이 판은 이미 묻는다. 그리고
  전처리 화면에는 범주를 바꾸는 손잡이가 없다.
- `baking`은 `busy`라 그동안 [이름 변경]의 확인 단추와 [범주 삭제]가 잠긴다.

**`anchor`도 범주 이름을 든다**(`:135`) — 이름을 바꾸면 shift+클릭 범위가 보통 클릭으로
떨어진다(`:439`의 `from.category === category`가 거짓). 해는 없고 조용하다(C-7).

### A-2. 전처리 화면이 **학습이 쓰는 열을 "학습에서 빠집니다"라고 말한다**

**자리** `frontend/src/views/preprocess/TabularPrepPanel.vue:84`(`columns` —
`summarizeColumns(dataset)`, 파일 전체) → `:156`(`plan`) → `ml/selection.ts:159`
(`featureNote: 'notEncodable'`, 소유 밖) · `ColumnPicker.vue:249`(종류 칸). 학습 쪽은
`ml/plan.ts`의 `kindIndices`(결정문 53, 소유 밖).

**주장.** 열 표와 특성 요약 줄은 열 종류를 **파일 전체의 행**으로 센다(`data/columns.ts`).
학습은 **그 실행이 쓰는 행** — 타깃이 빈 행을 뺀 뒤, 뽑기를 지난 뒤의 훈련 ∪ 시험 — 으로
센다(결정문 53). 두 집합이 갈리면 **같은 열이 화면에서는 범주, 학습에서는 수치**가 되고,
인코딩이 `none`이면 화면은 그 열이 빠진다고 말하는데 학습은 쓴다. `architecture.md` §9.1.3이
막으려던 모양 그대로다 — *"화면이 말하는 숫자와 모델이 쓰는 숫자가 같은 객체에서 나온다."*
같은 판의 요약 카드(`TabularPrepSummary`, `runPlan`에서 나온다)는 옳게 말하므로 **화면
둘이 반대말을 한다**(되풀이해 잡은 병 6번).

**재현** (`tests/zz-r38-prep.spec.ts`, 지운 임시 스펙). 판을 진짜 입구로 세웠다 — CSV 바이트
→ `openTable` → `importTable` → `applyDataset` → 설정 문 넷. 40행, `키`는 수치인데 한 칸만
`모름`, 인코딩 `none`, 분류, 특성 `키`·`몸무게`.

| 입력 | 학습(`planRun`) | 열 표의 `키` 줄 | 특성 요약 줄 |
|---|---|---|---|
| `모름`이 있는 행이 **실행에 들어감** | `키` 범주 → 빠짐 | 범주형 · 빠집니다 | 2개 중 1개 ✓ |
| `모름`이 있는 행의 **타깃이 빈 칸** (뽑기 없음) | **`키` 수치 · 평균 169.7로 스케일** | **범주형 · 문자 값이 든 열이라 학습에서 빠집니다** + 같은 줄에 `평균 169.7 · 표준편차 11.99` | **2개 중 1개** ✗ |
| `모름`이 0행, `nSamples` 20 (뽑기가 그 행을 뺌) | **`키` 수치 · 평균 169.9** | 위와 같은 모순 | **2개 중 1개** ✗ |

**전·후·처음부터가 셋 다 같다**(`nSamples`를 없음 → 20으로 바꾼 뒤와, 처음부터 20으로 띄운
것). 즉 **갱신 누락이 아니다** — 미리보기와 열 표의 전처리 칸은 `runPlan`을 따라 바뀐다.
**틀린 것은 처음부터 틀린 쪽**, 파일 전체로 센 종류다. 둘째 줄은 **뽑기도 결정문 53도 없이**
난다: 타깃이 빈 행은 원래 실행에서 빠지므로 결정문 53 이전부터 있던 모순이다. 결정문 53은
뽑기 길을 하나 더했다.

**틀리면 학생에게.** 화면이 *"키는 빠집니다"*라고 말하고, 학생은 그 문장을 믿고 포트폴리오에
*"키는 문자가 섞여 제외했다"*고 쓴다. 모델은 키를 썼다. 교사가 `.mlpx`의 실험 스냅샷을 열면
키가 들어 있다. **트리거는 흔하다** — 설문 CSV에서 한 행을 대충 채운 학생은 타깃도 비우기
쉽다.

**무는 검사가 있는가.** **없다.** 이 판에서 계획이 서는 스펙이 하나도 없다 —
`:141`(미리보기)·`:153`(열마다의 전처리 값)이 **한 번도 실행되지 않는다**(§2). 판을 띄우는
유일한 스펙(`tabular-prep-fail.spec.ts`)의 픽스처는 계획이 안 서는 모양이다. **세울 수
있다** — 위 표가 그 검사다.

**처방.** 둘로 가른다 — **화면이 거짓말을 멈추는 것**은 결정 없이 되고(§9.1.3이 이미 정했다),
**어느 행으로 종류를 셀 것인가**는 결정이다(B-1).

- **화면 쪽(소유 경로 안).** `plan`을 지을 때 계획이 섰으면 **학습이 정한 종류로 요약을
  덮는다** — `fittedColumns`(`:150`)가 이미 열마다의 `kind`를 들고 있다. 빠진 열은
  `fittedColumns`에 없으므로 파일 전체의 종류로 남고, 그때는 두 쪽이 같다.
  **넣어 보고 쟀다 — §3.6.**
- **이웃 — 셋을 셌다.** 같은 판에서 파일 전체의 종류를 읽는 자리는
  `selection.ts:159`(`notEncodable`)·`:168`(`targetIssue`)·`ColumnPicker.vue:249`(종류 칸)이다.
  학습 화면에 둘이 더 있다(`TrainView.vue:320`·`TabularTrainContext.vue:33`) — **R39의 몫이라
  안 쟀다.** 데이터 화면(`TabularPanel`·시각화)은 **파일 전체가 맞는 자리**다 — 거기는 파일을
  보여 주는 화면이다.

### B-1. 결정문 53의 **근거와 본문이 다른 축을 말한다**

**자리** `docs/open-decisions.md` 53 · `ml/plan.ts`의 `kindIndices`(소유 밖 — 안 고쳤다).

결정의 근거는 *"pandas는 분할 전에 열 전체로 자료형을 정하고, 우리 데이터 화면의 요약도
이미 그렇게 하고 있었다"*다. 그런데 본문과 코드는 **"그 실행이 쓰는 행 전체"** — 타깃이 빈
행과 뽑기로 빠진 행을 **뺀** 집합 — 를 쓴다. pandas의 `read_csv`는 `sample()` 전에, 결측
타깃을 버리기 전에 자료형을 정한다. **그러므로 근거가 가리키는 축은 "파일 전체"이고, 그
축이면 A-2의 모순이 애초에 없다.**

지금 축의 대가는 A-2의 표가 보여 준다: **`nSamples` 하나로 한 열의 종류가 바뀐다.** 요청서
§4가 *"시험 비율을 바꾸는 것만으로도"*라고 적었는데 **그것은 안 된다** — 홀드아웃에서 훈련
∪ 시험은 비율과 무관하게 뽑힌 행 전부다(0.2와 0.5에서 같은 종류, 실측). 바꾸는 것은
`nSamples`, 타깃 결측, `missing: 'drop'`의 결측 행이다.

**정할 것.** 종류를 (가) 파일 전체로 셀 것인가(pandas와 같고 A-2의 화면 쪽 처방이 필요
없어진다) · (나) 지금처럼 실행의 행으로 세고 화면이 그것을 따라가게 할 것인가(A-2의
처방이 필수이고, 학생은 **뽑기 칸을 바꾸면 열 종류가 바뀌는 화면**을 보게 된다).
**나간 `.mlpx`에 닿는지**는 안 쟀다 — (가)로 뒤집으면 같은 파일의 재실행 대조가 갈릴 수
있다(`mlpx-spec` 재실행 대조). → `open-decisions.md`.

### B-2. 결정문 46이 박스 플롯에 요구한 로그 축이 **없다**

**자리** `docs/open-decisions.md` 46 · `views/data/charts/BoxChart.vue` ·
`data/chart-config.ts:393`(`boxOptions`에 축 인자가 없다).

결정문 46은 *"박스 플롯 쪽은 축 하나를 공유하므로 `boxOptions`의 `y`도 같은 스위치를
받아야 한다 — 두 그림에 스위치를 따로 두면 학생이 같은 질문을 두 번 만난다"*, 그리고
*"이 항목이 열리면 **두 그림의 문제가 함께 풀린다**"*고 적었다. 그 뒤 `나간 뒤` 문단은
히스토그램만 말하고 박스 플롯이 빠진 이유가 없다. **코드에는 히스토그램에만 스위치가

## 5. 못 한 것 · 확인 못 한 것

- **이미지 예측 판에서 상한 스위치를 켜고 끄면** 판 크기가 바뀌어 **쪽 번호는 그대로인데
  쪽에 선 사진이 바뀐다.** 쪽을 넘기면 이어 도는 감시(`ImagePredictPanel.vue:548`)가 `page`만
  보므로 **새로 들어온 사진은 [예측하기]를 다시 눌러야 답이 선다** — 카드는 *"[예측하기]를
  누르면 여기에 답이 나옵니다"*라고 말하므로 거짓은 아니다. **실측 못 했다** — 이 판의 답
  루프가 어떤 하니스에서도 안 돌아서(C-5) 답이 선 상태를 만들 길이 없었다. 코드 읽기뿐이다.
- **A-2의 처방은 소유 경로 안쪽만 쟀다**(§3.6). B-1의 (가) — `plan.ts`가 파일 전체로 종류를
  세는 쪽 — 은 소유 밖이라 심지 않았다. 그쪽이 재실행 대조를 흔드는지도 안 쟀다.
- **학습 화면의 같은 병 둘**(`TrainView.vue:320`·`TabularTrainContext.vue:33`)은 R39의 몫이라
  세기만 했다.
- **브라우저로 아무것도 안 봤다.** A-1의 바가 옛 이름을 말하는 모습, B-2의 박스 플롯은
  코드와 jsdom으로만 봤다.
- **기준선 관문의 `fixtures:check`·`build`는 안 돌았다**(테스트 단계의 부하 실패에서 섰다).
  `vue-tsc`는 따로 돌려 깨끗했다.
- **백엔드 관문은 안 돌렸다** — 범위 밖이다.

## 6. 방법에 대한 기록

**커버리지 판이 조용히 4분의 1을 버렸다.** 지도 때처럼 스위트 전체에 커버리지를 걸었더니
`Test Files 1 failed | 154 passed (155)` — **192가 아니라 155**였다. 로그 맨 위에
*"Failed to start threads worker … Timeout waiting for worker to respond"*가 **37번** 있었고
**종료 코드는 0**이었다. 커버리지가 부하를 키워 워커가 뜨지도 못한 것이고, 그 판의 수치를
그대로 썼으면 `ChartDialog`·`ImagePanel`·`TabularPrepPanel`이 **0%**로 적혔을 것이다.
**슬라이스를 싣는 스펙 44개만 `--maxWorkers=3`로 다시 돌려** 44/44 · 365 통과였고, 그 판이
지도와 줄 단위로 같은 수를 냈다. **절차로 옮긴다: 커버리지 판은 `Test Files`의 분모가 목록
수와 같은지부터 본다.** `audit-round-queue`의 함정 둘(시간 초과·`reportOnFailure`)에 셋째로
붙일 것이다.

**러너가 되돌리기에 실패했다.** `writeFileSync`가 복원 중에 던져(윈도의 파일 잠금으로 보인다)
러너가 죽고 **PP8 돌연변이(`samplingLocked = false`)가 소스에 남았다.** 다음 묶음 전에
`git status --short`를 봐서 잡았고 **그 한 줄만** `Edit`로 되돌렸다(`git checkout --`을 안
썼다). 러너에 재시도를 넣은 뒤로는 안 났다. **돌연변이 묶음 사이에 `git diff --quiet -- src`를
넣어라** — 대조군(C0)은 "러너가 안 돈다"를 잡지만 "되돌리기가 안 됐다"는 못 잡는다.

**요청서의 단정 둘을 고쳐 적는다.** ① *"그 사이 판이 바뀌었다"* — 여섯 판은 `0.22.0` 이후
한 줄도 안 바뀌었다. ② *"`nSamples`나 시험 비율을 바꾸는 것만으로"* — 시험 비율은 못 바꾼다.
둘 다 요청서가 *"확인함"*을 안 붙인 문장이었다.
