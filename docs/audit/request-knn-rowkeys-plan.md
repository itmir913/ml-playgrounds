# 이미지 KNN이 사진을 더해도 예측한다 — 2단계 계획 검토 요청서 (2판)

> 독립 검토다. 공통 규칙은 `docs/workflow.md` §3 "감사 국면은 어떻게 도는가"·"요청서는 무엇을 담는가"·"감사가 되풀이해 잡은 병"과 §10.
> **읽기 전용이다** — 소스를 고치지 마라(돌연변이·임시 스펙은 심고 되돌리는 것까지만).
> 금지: `git commit`·`push`·`tag`·`add` · `npm run lint` · `npm run ci` 전체 · `git stash` · `git checkout .` · 하위 에이전트·클라우드.
> 기준 커밋: `main-6kb5me`의 HEAD(1단계 `fix: 사진이 바뀐 KNN을 "데이터가 없다"로 말하지 않는다`).
> **판정을 맨 위에 적어라: `APPROVE` 또는 `REQUEST CHANGES`.**
> **1판 감사(REQUEST CHANGES, B-1·C-1~C-8)의 처리는 맨 아래 "1판 지적의 처리"에 있다.** 각 처리가 맞는지도 판정하라.

## 문제

이미지 KNN(`mlpx-reference-v1`)은 훈련 사진을 **임베딩 표의 행 번호**(`trainIndices`)로만 기억한다. 표는 예측할 때마다 지금 사진들로
다시 세워지고(`ml/images.ts`의 `imageTrainingSource`, zip 경로 오름차순), 사진을 한 장만 더해도 번호가 밀린다. 그래서 지금은 장수·
`rowsHash`가 어긋나면 행을 안 내주고, 1단계 뒤로는 `MODEL_TRAINING_DATA_CHANGED`("다시 학습하라")로 꺼진다.
**교실 증상:** 학습 → 사진 몇 장 더 올림 → KNN만 예측 불가.

## 코드 소유자가 정한 것

1. **학습 뒤 범주를 옮기거나 지운 사진이 훈련에 쓴 사진이면 예측을 거부한다**(학습 라벨로 되살리지 않는다, 이웃을 빼고 예측하지 않는다).
2. **훈련에 쓰지 않은 사진**(테스트 분할 몫·표본에서 빠진 몫)을 옮기거나 지운 것은 **예측한다** — 모델이 그 사진을 안 쓰므로 답이 같다.
3. **열쇠는 분류 실험에만, 표 전체를 적는다**(훈련 행만 적으려면 분할 뒤 워커 밖에서 기록을 다시 채우는 장치가 필요해 택하지 않았다).
4. **포맷 버전은 되도록 안 올린다.** 과거 `.mlpx`가 열려야 하고, 과거 파일에서도 예측이 되어야 한다. 이 축을 특히 깨 봐라.

## 계획

### 1. 스냅샷에 행마다의 열쇠를 적는다 — `settings.data.rowKeys` (이미지 실험 스냅샷, 선택 항목, 분류에만)

- 열쇠 하나 = `sha256(범주 + "\n" + 사진 해시)`의 **앞 8바이트.** 범주가 열쇠에 들어가므로 **범주를 옮긴 훈련 사진은 다른 열쇠**가
  되어 못 찾는다 → 결정 1이 별도 장치 없이 선다. 훈련 행만 찾으므로 결정 2도 선다(테스트 몫의 열쇠는 아무도 안 찾는다).
- 표의 행 순서대로 이어 붙인 바이트를 **base64 문자열 하나**로 적는다. 배열이 아니다. **이진 문자열은 덩어리 단위로 짓는다** —
  `String.fromCharCode(...bytes)`로 펼치면 32,500장(260,000바이트)에서 `Maximum call stack size exceeded`(1판 감사 실측, Node 22).
- **크기:** 장당 8바이트 → base64로 약 10.7자. 상한을 켰을 때(`MAX_IMAGE_COUNT` 5,000장) 한 실험 약 53KB, 300장이면 약 3KB.
  **상한을 끄면** 천장은 엔트리 수(`MAX_ARCHIVE_ENTRIES` 65,534, 사진·임베딩이 둘씩)라 약 32,000장, 한 실험 약 350KB.
  사진(장당 약 11KB)·임베딩(약 5KB)과 견주면 실험 하나가 파일의 약 0.05%다. `runs.json`은 압축하지 않는다(`json-text.ts`).
- 옛 결정("목록을 통째로 안 담는다", 64자 × 5,000 = 320KB)을 뒤집는 근거: 그 결정의 전제가 *"되세울 때 필요한 것은 같은가뿐"*이었는데,
  **사진이 늘어도 살리려면 "어느 사진인가"가 필요하다.** 크기는 앞 8바이트 + base64로 6분의 1로 줄였다.
- 충돌: 64비트 열쇠 둘이 겹칠 확률은 5,000장에서 약 7×10⁻¹³. **지금 사진에서 열쇠가 겹치면 그 열쇠를 찾는 예측을 거부한다**(조용히 고르지 않는다).
- **짓는 함수는 하나다** — `ml/images.ts`의 `rowKeysOf(entries)`(열쇠 문자열을 낸다)와 짝 `readRowKeys(text)`(풀어 배열을 내고, 못 풀면 `null`).
  부르는 자리는 둘: 학습 어댑터(`ml/training-source.ts`의 이미지 판, 분류일 때만)와 되세우기(`imageTrainingRows`). **`imageTrainingSource`
  안에서 짓지 않는다** — 그 함수는 결과 화면의 군집 패널 두 곳(`ImageClusterPanel.vue`·`ImageClusterEvidence.vue`, computed)도 불러서,
  안에서 지으면 열쇠가 필요 없는 호출이 5,000장에 16–41ms를 치른다(1판 감사 실측).
  - 어댑터가 `source.snapshot`에 `rowKeys`를 얹어 실험 입력으로 넘긴다. `runExperiment`(워커)는 스냅샷을 받은 그대로 적으므로 안 바뀐다.
- 열쇠를 짓는 사진 목록은 **자리를 밝혀** 읽는다(`readImages(project, 'data')`, `pendingEmbeddings`의 "자리는 필수 인자" 교훈).
  분류이므로 라벨 없는 사진은 뺀다 — `imageTrainingSource`의 행과 **같은 거르기**를 써야 행 번호가 맞는다. 그래서 거르기를
  한 함수로 빼서 둘이 같이 부른다(같은 판정을 두 곳에서 계산하지 않는다).
- 인코딩 상수(8바이트·구분자)는 포맷 규격이므로 `limits.ts`가 아니라 `ml/images.ts`에 둔다 — `rowsHash`의 `SEPARATOR`와 같은 자리.
- **`rowsHash`는 계속 적는다.** 옛 앱이 그것으로 판정하고, 변경 이력이 그것으로 순서 변화를 말한다.
- **이름이 겹치는 것을 정리한다**(1판 C-4). `ml/training-source.ts`의 `TrainingSource.rowKeys`(사진 해시 배열)는 `rowHashes`로
  바꾸고, "결과 화면이 그것으로 사진을 되찾는다"는 틀린 주석을 고친다(src에서 읽는 곳이 없다 — `tests/training-source.spec.ts` 하나).

### 2. 되세우기(`imageTrainingRows`) — 열쇠가 있으면 열쇠로, 없으면 지금 그대로

**열쇠가 있는 실험(새 파일):**
1. 백본이 다르면 `null`(1단계 그대로).
2. `readRowKeys`로 푼다. 못 풀면(길이가 8의 배수가 아니거나 base64가 아니면 — `atob`의 `DOMException`을 잡는다) `null`.
   스키마는 `z.string().optional()`로 둔다 — `regex`를 걸면 그 칸 하나로 파일 전체가 `PROJECT_FILE_INVALID`가 된다(1판 C-6).
3. `trainIndices`의 어느 번호라도 열쇠 수 이상이면 `null`.
4. 지금 사진(라벨 붙은 것)마다 열쇠를 지어 `열쇠 → 사진` 표를 만든다. 겹치는 열쇠는 "모호"로 표시.
5. `trainIndices`의 각 번호 `i`에 대해 `rowKeys[i]`로 사진을 찾는다. 없거나 모호하거나 벡터가 없으면 `null`.
6. 찾은 사진들로 작은 표를 지어 `transform`하고, **`indices`는 원래 `trainIndices` 그대로** 돌려준다. 정답은 지금 범주(= 열쇠에 든
   학습 때 범주).
- 장수·`rowsHash`·임베딩 누락(1단계) 대조는 이 경로에서 **안 한다** — 앞의 둘이 사진 추가를 막던 장치이고, 세 번째는 5가 대신한다.
- **결과 동일성:** 같은 해시의 임베딩은 같은 벡터(`embeddings/{backbone}/{hash}`), 전처리기는 파일의 것, 라벨은 열쇠가 보증, 동점을
  가르는 행 번호(`reference.ts`의 `worse`)도 원래 번호 → **학습 때 구운 임베딩이 남아 있는 한** 사진을 더하기 전과 답이 같다.
  (훈련 사진을 지웠다가 같은 바이트를 다시 올리면 임베딩이 다시 구워질 수 있다 — 1판 C-7. 옛 경로도 같은 상태를 받아들이므로 새 퇴행은 아니다.)

**열쇠가 없는 실험(과거 파일, 옛 앱이 학습한 실험, 군집):** 지금 경로(장수·`rowsHash`·임베딩 누락·백본) 그대로. 사진이 안 바뀌었으면
지금처럼 예측된다. 사진을 더하면 지금처럼 `MODEL_TRAINING_DATA_CHANGED` — **다시 학습하면 그때부터 열쇠가 적힌다.**
군집에는 행이 필요한 모델이 없다(`needsTrainingRows`는 `mlpx-reference-v1`뿐, KNN은 `clustering: false`).

### 4. 호환성 — 포맷 버전은 안 오른다

- **선택 속성 추가는 읽기 호환을 깨지 않는다**(`mlpx-spec.md` §9.2 "깨지 않는 것"). `FORMAT_VERSION`(4)·마이그레이션·`v4.released.json`
  안 건드린다. `tests/fixtures/schema/v4.json`만 다시 뜬다.
- **과거 파일 → 새 앱:** 필드가 없으니 2의 옛 경로. 열기·예측 모두 지금과 같다(v1 파일은 마이그레이션 뒤 같은 경로 — `image-format.spec.ts`의 v1 픽스처).
- **새 파일 → 옛 앱(같은 v4):** `imageSnapshotSchema`가 `looseObject`라 `rowKeys`를 살려 다시 쓴다(§10). 1판 감사가 HEAD를 옛 앱 삼아
  `.mlpx` 왕복·IndexedDB 왕복·예측을 임시 스펙으로 실측했다(통과). 옛 앱의 이력에도 `rowKeys`는 안 뜬다(`DATA_COMPARABLE_KEYS`는 앱의 스키마에서 나온다).
- **어휘 변경 없음** — 버전 지문(`schema-version.spec.ts`)이 세는 `z.enum`이 안 는다. 지금까지 버전을 올린 판례(§9.1·9.3·9.4)는 모두
  옛 앱이 새 파일을 **조용히 잘못 읽는** 경우였는데, 여기서는 옛 앱의 판정이 그대로다.

### 5. 변경 이력 — `rowKeys`는 비교에서 뺀다

- `project/schema.ts`의 `SNAPSHOT_NOT_COMPARED`에 `rowKeys`를 넣는다. 사진 한 장만 더해도 값이 바뀌어, 안 빼면 이력에 읽을 수 없는
  긴 문자열 변경이 뜬다.
- **R6 A-1(맞바꾸기 탐지 실종)을 되풀이하지 않는 증명:** 행은 zip 경로순이라 범주마다 붙은 덩어리를 이루고 덩어리 순서는 범주 이름의
  코드 단위 순서다. 그러므로 **사진 해시의 순서(`rowsHash`)·범주 목록·범주별 장수가 모두 같으면 각 자리의 범주가 정해지고 열쇠 목록도
  같다.** 대우: `rowKeys`가 바뀌면 `rowsHash`나 범주·장수 중 하나가 반드시 바뀐다. 새 실험에는 `rowsHash`가 늘 있으므로 탐지는 줄지 않는다.
  (1판 C-8 — 주석과 결정문에 이 증명을 적는다.) 이 목록 주석의 "지금 비어 있다"는 고친다.

### 7. 검사

진짜 입구로 짓는다: **학습 어댑터(`TRAINING_SOURCES.image`) → `runExperiment`(mljs KNN) → 모델 JSON → 사진 편집 →
`loadModel(payload, imageLoadContext(imageTrainingRows(...), format))`**(1판 C-5). 픽스처가 상태를 미리 주지 않게 한다.

1. 라벨 붙은 사진을 더해도 **답이 더하기 전과 같다** — 층화 holdout 판, `nSamples`를 켠 판, 거리 동점이 생기는 판.
2. 결정 1: 훈련 사진 삭제 / 훈련 사진의 범주 옮기기 / 맞바꾸기 / 훈련 사진이 든 범주의 이름 바꾸기 → `MODEL_TRAINING_DATA_CHANGED`.
3. 결정 2: 테스트 몫 사진 삭제 / 테스트 몫 사진의 범주 옮기기 → 답이 같다.
4. 깨진 열쇠(8의 배수 아님·base64 아님)·`trainIndices`가 열쇠 수를 넘음·지금 사진에서 열쇠가 겹침 → `null`(→ 거부). 파일은 열린다.
5. **과거 실험:** `rowKeys`를 실제로 지운 실험이 지금 경로로 돈다(기존 "지문이 없는 옛 실험" 검사의 이웃). 군집 실험에는 `rowKeys`가 없다.
6. **파일 왕복:** `rowKeys`가 든 프로젝트를 `.mlpx`로 쓰고 읽어 값이 그대로이고 예측이 된다. `rowKeys`가 없는 문서도 같은 왕복으로 열린다.
7. 인코딩: 길이 n → base64 길이, 왕복 무손실. 5,000장과 상한을 끈 규모(33,000장)에서 던지지 않고 길이가 맞다.
8. 변경 이력: 사진 한 장 더한 두 실험의 이력에 `rowKeys`가 안 뜨고, 맞바꾸기는 여전히 `rowsHash`로 뜬다.
9. 기존 검사 수정: 스냅샷 필드 트립와이어(`tests/experiment.spec.ts`), `SNAPSHOT_NOT_COMPARED` 실재 검사(`tests/schema.spec.ts`),
   `training-source.spec.ts`(이름 바꾼 `rowHashes`와 스냅샷 기대값) — 깨지는 것을 기대값이 아니라 의도로 고친다.
- 각 가드는 돌연변이로 우는지 확인한다.

## 범위에서 뺀 것

- 표(tabular) 프로젝트 — 데이터를 바꾸면 실험이 지워진다(§4.3).
- 결과 화면의 군집 격자·군집 근거 — 지금 사진으로 표를 다시 짓고 행 번호를 안 쓴다.
- 재실행 대조(`ml/reproduce*.ts`) — 사진이 바뀌면 다른 결과가 나오는 것이 맞다.
- 과거 실험에 열쇠를 소급해 채우는 것 — 학습 때의 범주·순서를 아무도 안 적어 두었다.
- 행 번호를 쓰지만 사진 추가 뒤 새 거짓이 없다고 1판 감사가 확인한 자리(1판 물음 6): `sampleRow`·`confusion-rows`·`permutation-importance`·`regression-fit`·`image-clusters`·`metrics`.

## 아는 약점 (내가 틀리게 알고 있으면 그건 새 항목이다)

- 모델의 `trainIndices`는 실험의 `trainIndices`와 같은 배열이다(1판 감사 확인: `experiment.ts:800`→`:664`, `mljs.ts:801`, `pyodide-serialize.ts:554`).
- 표본 뽑기를 켜도 `trainIndices`는 전체 표의 번호다(1판 감사 확인: `sample.ts:16`, `plan.ts:5`).
- 어댑터가 얹은 `rowKeys`가 워커 왕복(structured clone)과 `applyExperiment`를 지나 파일까지 그대로 간다고 가정한다 — 7의 진짜 입구 검사가 잰다.
- Safari(JSC)·저사양 PC의 인자 상한과 열쇠 짓기 시간은 아무도 안 쟀다. 덩어리 단위로 지으면 인자 상한은 무관해진다.
