# R43-1 후속 3차 계획 재검토 — APPROVE WITH CHANGES

> 독립 재검토자의 회신을 오케스트레이터가 옮겨 적었다. 요청서 `request-R43-1-plan-3.md`.
> 임시 스펙 하나로 `ImagePanel`의 `commitName`을 진짜 입구로 불렀고(쿼터 거절은 `image-panel-fail.spec.ts`와 같은 방식) 지웠다.
> 결과 `{"cats":["C"],"dangers":1,"naming":null}` — 저장이 실패해 알림이 떴는데 파일은 이미 `A→C`였다.

**요지.** 2차 지적 1·3·4는 닫힌다. 2차 지적 2는 반만 닫히고 A-4가 새 구멍 둘을 연다. 1·2는 막혀야 하고 3·4는 작다. B·C·D는 그대로 진행.

## 고칠 점

1. **[막힘] A-4가 "저장 실패"와 "적용 안 됨"을 뭉갠다.** 스토어 `save`는 쓰기 전에 `file.value`를 바꾼다(`stores/project.ts:395-420`,
   *"던져도 화면은 새 값을 들고 있는다"*, `autosave.spec.ts`가 지킨다). 쿼터 거절이면 `save`는 false인데 이름 바꾸기는 이미 적용됐다 — A-4대로면
   `retagPending`을 건너뛰어 판의 묶음이 옛 이름 `A`로 남고, 구우면 `addImages`가 `A`를 되살린다(R38 A-1 재발). 함수가 던질 때만 "적용 안 됨"이다
   (`resolve` 안에서 던져 대입 전에 끝난다, `:382-386,410-419`). 처방: 뒤처리를 **적용 여부**로 가른다 — `bake`의 `seated`(`ImagePanel.vue:365,449,473`)
   처럼 revision 안에서 `renameCategory`가 돌아온 뒤 표지를 세운다. `commitRemoveCategory`(`:629-637`)가 늘 retag하는 것은 그래서 맞다.
2. **[막힘] 이름 창을 열어 두는 것은 결정 65의 덫이다.** 실패는 `toasts.pushError`로만 말하고(`:480-491`) 알림은 모달 뒤에 덮인다. 창 안에 실패 문장
   자리가 없다(`:915-931`). 쿼터 거절이면 파일이 이미 `C`라 창 안에 거짓 `nameTaken`이 서고 다시 눌러도 조용하다. 처방: (가) 창은 지금처럼 닫고 1의
   적용 여부로 retag·기준점만 가른다(최소) 또는 (나) 창 안에 실패 문장.
3. **[작음] 고아 이름으로 바꾸기를 `nameTaken`으로 거절하면 거짓이 선다** — 고아 `test/C`는 화면에 안 보이는데 "같은 이름의 범주가 이미 있습니다"가 뜨고,
   같은 C 만들기는 통과한다. 이유 코드를 따로 두고 문구도 그것을 말하게 한다.
4. **[작음] 판정을 두 벌 두지 마라.** gate(A-2)와 던지는 조건(A-3)을 술어 하나로 모델 층에 두고 `categoryNameReasons`와 `renameCategory`가 함께 부른다
   (`sectionTopBlockers`/`withSectionMoved` 선례, `locks.ts:621-626`). 모드는 `from === ''`로 추론하지 말고 화면이 든 `mode`를 `CategoryNameInput`에 넘긴다.

## 물음에 대한 답

1. 지적 1 닫힘(문구 거짓은 3), 지적 2 "던진다"는 닫히나 "실패면 뒤처리 안 함"이 1·2를 연다, 지적 3은 C로 닫힘(`RELIED_ON`은 B-3 뒤 참조가 떨어져
   열 때 안 걸림 — 주석만), 지적 4 닫힘(`t(key, {count, name}, count)`의 선례 `TrainView.vue:175`).
2. `useGate`·`refusalFor`는 제네릭이라 그대로. `tests/locks.spec.ts:247-250`의 `CASES.categoryName` 표본에 새 필드를 넣어야 타입 검사가 안 운다.
   바꾸기 거절·만들기 통과는 따로 검사로 문다.
3. 겹친다 — 2.
