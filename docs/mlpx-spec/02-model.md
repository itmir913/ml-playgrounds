# `.mlpx` — 모델 (§5)

> `mlpx-spec.md`에서 갈라져 나온 절이다. **절 번호는 안 바뀌었다** —
> 저장소가 `mlpx-spec.md §5.9`처럼 번호로 가리키므로 여기서도 원래 번호를 쓴다.
>
> 전체 차례는 허브(`../mlpx-spec.md`)에 있다.

## 5. `model/` — 형식은 가변이다

포맷 계층은 모델 안을 들여다보지 않는다. **어떻게 해석할지만 적어 둔다.**

| `format` | 대상 | 전처리 | 예측에 필요한 것 |
|---|---|---|---|
| `mlpx-tree-v1` | Decision Tree, Random Forest | 밖 | 모델 + preprocessor |
| `mlpx-linear-v2` | Logistic Regression (§5.4.1) | 밖 | 모델 + preprocessor |
| `mlpx-naive-bayes-v1` | Naive Bayes | 밖 | 모델 + preprocessor |
| `mlpx-reference-v1` | **KNN** | 밖 | 모델 + preprocessor + **`dataset/`** |
| `mlpx-svm-v1` | **선형 SVM** | 밖 | 모델 + preprocessor |
| `mlpx-linear-regression-v1` | 선형 회귀 (§5.7) | 밖 | 모델 + preprocessor |
| `mlpx-kmeans-v1` | **K-평균** (§5.10) | 밖 | 모델 + preprocessor |
| `onnx-v1` | 딥러닝이 들어온 뒤 | **그래프에 포함** | 모델 하나 |

> **SVM은 이 표에서 KNN과 같은 칸에 있었고, 그게 틀렸다** (2026-08-06). 훈련 행을 들고
> 다녀야 하는 KNN과 달리 **선형 SVM은 가중치뿐이라 자체 완결이다** — 748바이트 JSON이다.
> 커널이 늘면(RBF) 서포트 벡터를 담아야 하니 커지지만 그때도 `dataset/`은 필요 없다.

해석기는 알고리즘 등록부와 같은 방식으로 등록한다. `if format === 'onnx'` 분기를 만들지 않는다.

**"전처리" 열을 코드가 읽는 자리가 `model.includesPreprocessing`이다.** 형식 이름을 보고
갈라서는 안 된다 — 그게 바로 윗줄에서 금지한 분기다. 모델 하나하나가 자기 사정을 들고 있고,
포맷 계층은 그 불리언만 본다.

이 필드가 정하는 것은 하나다 — **이 모델을 쓰려면 전처리기가 필요한가.**

- `false`(자체 JSON 전부): 전처리기가 파일에 없으면 그 모델로 예측할 수 없다. 그래서
  전처리기는 그 실험 모델 전체의 전제이고, 예산에서 밀리면 실험이 통째로 빠진다(§4.2).
- `true`(`onnx-v1`): 전처리가 그래프 안에 있으므로 **전처리기가 없어도 혼자 선다.**
  전처리기 유무로 이 모델까지 떼어내면 멀쩡한 모델이 사라진다.

지금은 전부 `false`라 두 경우가 같아 보인다. **그래서 지금 적어 둔다** — 이미지 단계에서 `true`가
처음 들어올 때 이 규칙이 없으면, 전처리기가 없는 파일에서 ONNX 모델이 조용히 떨어지고
아무도 이유를 모른다.

**`format` 하나가 payload 스키마 하나를 결정해야 한다.** 로지스틱 회귀와 나이브 베이즈를
한 이름에 묶었다가 나눴다 — 전자는 클래스별 가중치 행렬이고 후자는 클래스별 평균·분산·
사전확률이라 같은 해석기가 읽을 수 없다. 묶어 두면 그 해석기가 `algorithm`을 보고
갈라져야 하는데, 그건 바로 윗줄에서 금지한 분기를 형식 **안쪽**으로 옮긴 것에 불과하다.

반대로 `mlpx-tree-v1`이 Decision Tree와 Random Forest를 함께 담는 것은 문제가 없다 —
랜덤포레스트는 같은 노드 구조의 트리가 여러 개일 뿐이라 해석기가 하나로 선다.
**기준은 알고리즘 개수가 아니라 payload 스키마가 하나인가다.**

각 형식의 payload는 **만드는 시점에** 여기 적는다. 미리 적어 두면 구현하면서 어긋나고,
안 적으면 다음 사람이 왜 그 모양인지 알 수 없다. 지금 있는 것은 하나다 — §5.3.

### 5.0 해석기가 받는 것 (2026-08-06)

**형식마다 예측에 필요한 것이 다르다.** 나무는 자기 안에 다 들고 있고, KNN은 훈련 행이
있어야 한다. 그래서 해석기 등록부가 **축 둘**을 선언한다.

| 축 | 묻는 것 | 지금 값 |
|---|---|---|
| `includesPreprocessing` | 전처리기가 필요한가 | 자체 JSON은 전부 `false`, `onnx-v1`이 첫 `true` |
| `needsTrainingRows` | **원본 훈련 행이 필요한가** | 참조형만 `true` |

**둘 다 불리언이고, 화면은 형식 이름을 절대 보지 않는다.** "이 모델로 예측할 수 있는가"의
판정이 §5.2의 "이 빌드가 아는 형식인가"에 이 축 하나를 더한 것으로 끝난다 — 형식이 늘어도
그 판정은 안 바뀐다.

```ts
load(file: unknown, context: LoadContext): Predict
```

`LoadContext`는 **전처리를 마친 훈련 행렬과 그 정답**이다. `needsTrainingRows`가 `false`인
해석기는 쳐다보지 않는다. 인자를 두 벌로 나누거나 2단계 로딩으로 만들지 않는 이유는,
**부르는 쪽이 형식마다 다른 호출 방법을 알아야 하는 순간 그게 곧 분기**이기 때문이다.

**행을 만드는 것은 해석기가 아니라 부르는 쪽이다.** 모델의 `trainIndices`로 `dataset/`에서
원본 행을 찾고, 그 실험의 전처리기로 변환한다(§5.1). 해석기가 이 일을 하면 zip과 CSV 파서와
전처리기를 알게 되고, "해석기는 학습 라이브러리를 모른다"(§5.3)와 같은 이유로 그건 경계
위반이다.

**행이 없으면 예측 못 하는 것이지 파일이 깨진 것이 아니다.** `dataset/`이 없는 파일에
참조형 모델이 들어 있을 수 있고(남이 편집했거나 옛 파일이거나), 그때 화면은 그 모델만
끄고 사유를 말한다 — `client.MODEL_NEEDS_DATASET`. §5.2의 "모르는 형식"과 같은 처리다.

### 5.0.1 담지 못한 모델의 사유도 원문을 남긴다 (2026-08-06)

직렬화가 터지면 `modelOmitted: 'engineUnsupported'`만 남고 **원문이 아무 데도 안 남았다.**
실패한 run에는 남의 라이브러리 원문을 `failure.params.detail`로 남기면서
(`open-decisions.md` "학습 실패는 교사가 읽을 수 있게 전달한다") 여기만 비어 있었다.

**`modelOmittedDetail`(선택, 문자열)을 둔다.** `modelOmitted`에 값을 더하지 않는 이유는
§4.2가 어휘를 나누는 기준이 "화면이 서로 다른 지시를 해야 하는가"인데 **학생이 할 일은
같기 때문**이다. 사유는 어휘가 아니라 기술 정보이고, 읽을 사람은 교사와 우리다.

지금 이걸 하는 이유는 **형식이 넷으로 늘기 때문**이다. 하나일 때는 발생 경로가 사실상
0이었지만(우리가 낸 모델을 우리가 읽고 테스트가 엔진 버전을 고정한다) 면적이 네 배가 된다.

### 5.1 참조형 — 데이터를 중복 저장하지 않는다

KNN의 모델은 사실상 훈련 데이터 전체다. 그런데 그 데이터는 **이미 `dataset/`에 있다.**

```jsonc
// model/run-5.json
{
  "format": "mlpx-reference-v1",
  "algorithm": "knn",
  "hyperparameters": { "n_neighbors": 5, "weights": "uniform", "metric": "minkowski", "p": 2 },
  "trainIndices": [0, 3, 5, …]        // dataset/data.csv 의 행 번호
}
```

**행 번호는 헤더를 제외하고 0부터 센다 — `hasHeader`와 무관하게 데이터 행 기준이다.**
파일의 물리적 줄 번호가 아니다. `hasHeader: true`인 파일에서 이걸 헷갈리면 모든 참조가
한 줄씩 밀린 채로 **그럴듯한 예측이 나온다.** 조용히 틀린 결과라 아무도 못 알아챈다.
`ml/split.ts`가 이 번호를 만드는 유일한 자리이고, 쓸 수 없는 행을 걸러내는 일은 부르는
쪽이 한다 — 걸러낸 뒤 0부터 다시 세면 그 번호가 다른 행을 가리킨다.

SVM도 같다. 서포트 벡터는 훈련 데이터의 부분집합이므로 행 번호 + 계수만 담는다.
덕분에 **가장 큰 모델은 KNN이 아니라 Random Forest**가 된다.

**모델 파일의 `trainIndices`와 실험 스냅샷의 `experiment.settings.trainIndices`는 다른 것이다.**
쓰임이 다르므로 중복이 아니다 — 모델 쪽은 **예측**에 필요한 부분집합(SVM은 서포트 벡터만,
KNN은 훈련 데이터 전체라 결과적으로 같아 보일 뿐)이고, 실험 쪽은 **재실행 대조**가 같은 분할을
다시 세우기 위한 기록이다. 하나를 다른 하나에서 유도하지 마라.

#### 이미지에서 행 번호가 가리키는 것 — `rowsHash`

**이미지에는 `dataset/data.csv`가 없다.** 그래서 위 행 번호가 가리키는 것은 파일의 어떤
줄이 아니라 **임베딩 표의 자리**이고, 그 표는 예측할 때마다 **지금 사진들로 다시 세워진다.**
사진이 하나 늘거나 줄거나 **범주를 옮기면** 같은 번호가 다른 사진을 가리킨다.

- **순서는 zip 경로의 코드 단위 오름차순이다.** 로케일 비교를 쓰면 체코에서 `ch`가 한
  글자이고 스웨덴에서 `Ä`가 `z` 뒤라 **같은 파일이 기기마다 다른 좌표계를 갖는다**
  (`open-decisions.md` "이미지의 행 순서를 기기에서 떼고, 그 순서를 파일이 기억한다").
- **그 순서를 스냅샷이 `data.rowsHash`로 기억한다.** 학습에 쓴 행들의 사진 해시를 순서대로
  이어 해싱한 값 하나다. 되세울 때 다시 계산해 **다르면 그 모델은 행을 안 내준다.**
- **선택 항목이다.** 이 필드가 생기기 전 파일에는 없고, 없으면 범주별 장수만 본다.
  **장수는 두 방향 이동을 못 잡는다** — A를 개→고양이로, B를 고양이→개로 옮기면 장수가
  하나도 안 변하는데 순서는 바뀐다.
- **목록을 통째로 안 담는다.** 64자 × 5,000장이면 한 실험이 320KB다. 되세울 때 필요한
  것은 "같은가"뿐이라 값 하나면 된다.

### 5.2 모르는 형식을 만나면 파일을 거부하지 않는다

알고리즘 추가는 **등록부 변경이지 포맷 변경이 아니다.** 그래서 `formatVersion`이 오르지 않고,
같은 버전 파일 안에 이 빌드가 모르는 모델이 들어 있을 수 있다.

```
☑ Random Forest       정확도 96.7%   [예측 가능]
☐ 이미지 분류 모델     정확도 91.2%   ⚠ 이 버전에서는 실행할 수 없습니다
```

`client.MODEL_FORMAT_UNSUPPORTED`. 파일 열기 실패(`PROJECT_FILE_*`)와 성격이 다르다.
**파일은 멀쩡히 열리고 그 모델로 예측만 못 한다.**

같은 이유로 `algorithm` 이름과 `model.format`은 **스키마에서 검증하지 않는다.**

### 5.3 `mlpx-tree-v1` — 결정트리와 랜덤포레스트

**이 형식의 요구는 하나다 — 저장했다가 다시 읽은 모델의 예측이 원본과 하나도 다르지
않아야 한다.** 지표만 대조하면 어긋난 예측이 상쇄로 가려진다.

```jsonc
// model/run-3.json
{
  "format": "mlpx-tree-v1",
  "classes": ["setosa", "versicolor", "virginica"],
  "featureCount": 4,
  "trees": [
    { "nodes": [
      [ 2, 2.45,  1,  2],   // 내부 노드: [열, 임계값, 왼쪽, 오른쪽]
      [-1, 0,    -1, -1],   // 잎:        [-1, 클래스 번호, -1, -1]
      [ 3, 1.75,  3,  4],
      [-1, 1,    -1, -1],
      [-1, 2,    -1, -1]
    ] }
  ]
}
```

판정은 `row[열] < 임계값`이면 왼쪽, 아니면 오른쪽이다.

불변식 넷을 해석기가 강제한다. 어기면 `client.MODEL_FILE_INVALID`이고, §5.2와 마찬가지로
**파일은 멀쩡히 열리고 그 모델로 예측만 못 한다.**

1. **0번이 뿌리다.**
2. **자식 인덱스는 항상 자기보다 크다.** 전위 순서로 적기 때문이고, 그래서 순환이
   구조적으로 불가능하다. 손으로 고친 파일이 브라우저를 얼리지 못한다.
3. **열 번호는 전처리를 마친 행렬의 열 번호다.** `featureCount`와 안 맞는 입력은 거부한다 —
   맞춰서 읽으면 다른 열로 예측하고, 그건 조용히 틀린 숫자다.
4. **잎의 클래스 번호는 `classes`의 인덱스다.** `classes`는 라벨을 **정렬한** 순서다.
   등장 순서로 매기면 행 순서만 바뀌어도 같은 모델이 다른 모델이 된다.

**나무가 여럿이면 다수결이고, 동점이면 그 표수에 먼저 도달한 나무 쪽이 이긴다.**
나무 순서가 판정에 들어가므로 `trees`의 순서에는 의미가 있다. 번호가 작은 클래스가
이기는 규칙이 아니다.

**결정트리는 나무가 하나인 포레스트다.** 그러면 다수결이 그 나무의 답이 되므로 해석기에
알고리즘 분기가 생기지 않는다. §5가 금지한 분기를 형식 **안쪽**으로 옮기지 않는 방법이 이것이다.

담지 않는 것이 셋이고, 전부 이유가 있다.

- **`algorithm`과 `hyperparameters`.** 예측에 안 쓰이고 `runs.json`에 이미 있다. 크기 때문이
  아니라 **해석기가 `algorithm`을 볼 여지를 없애기 위해서다.** 참조형이 이 둘을 담는 것은
  (§5.1) KNN이 예측할 때 `n_neighbors`가 실제로 필요해서이고, 다 자란 나무에는 그런 값이 없다.
- **잎의 클래스별 확률 분포.** 예측에 쓰이는 것은 argmax 하나뿐이라 클래스 수만큼 부풀릴
  이유가 없다.
- **노드의 gain과 표본 수.** 특성 중요도를 계산하는 값이다. **중요도는 학습 시점에 계산해
  `run.featureImportance`에 남긴다. 모델 파일에서 유도하지 않는다.** 적어 두지 않으면
  나중에 "저장된 모델에서 중요도를 다시 뽑자"가 조용히 막다른 길에 닿는다.

**다른 엔진의 포레스트는 이 형식이 아니다.** scikit-learn은 나무별 확률을 평균 내서 고르므로
위의 다수결로는 그 모델을 재현할 수 없다. 그때는 새 형식 이름을 받는다 — 설계 실패가 아니라
"형식 하나 = payload 하나 = 해석 하나"의 귀결이다.

**해석기는 학습 라이브러리를 import하지 않는다.** 직렬화기는 알아도 된다. 이 경계가
"라이브러리를 갈아도 옛 파일은 열린다"의 실체이고, 지금 그 경계를 긋는 이유는 방금
라이브러리 결함으로 데었기 때문이다(`ml/engines/mljs.ts`의 나이브 베이즈).

### 5.4 `mlpx-linear-v1` — 지웠다 (2026-08-15)

**로지스틱 회귀의 첫 형식이었고, 이제 없다.** 절편이 생기면서 `mlpx-linear-v2`가
새 이름을 받았고(§5.4.1) 그때부터 엔진은 v1을 만들지 않았는데, **해석기만 남아
아무것도 안 읽고 있었다.**

**지운 이유는 그 해석기가 함정을 하나 들고 있었기 때문이다** — v1은 점수가 **낮은**
클래스가 이겼다(떼어낸 `ml-logistic-regression`이 one-vs-all에서 대상 클래스를 0으로
두고 학습했다). v2는 표준 규약대로 높은 점수가 이긴다. **같은 파일에서 방향이 반대인
두 규칙**을 배포 뒤까지 들고 갈 이유가 없었다. 근거와 판단은 `open-decisions.md`의
**"`mlpx-linear-v1`을 배포 전에 지운다"**에 있다.

**옛 파일은 이제 안 열린다.** `RELEASED = false`라 그 형식으로 담긴 `.mlpx`는 내부
베타 빌드가 만든 것뿐이고, 그런 파일은 지운다는 것이 이 저장소의 규칙이다
(`CLAUDE.md` §4).

### 5.4.1 `mlpx-linear-v2` — 절편이 있고, 높은 점수가 이긴다 (2026-08-10)

> **정의를 한 번 고쳐 썼다** (같은 날, 1단계-B). 처음에는 v1의 argmin 규약에 절편만
> 더한 모양이었는데, 솔버를 sklearn과 같은 구조(L2 + softmax)로 바꾸면서
> (`open-decisions.md` "로지스틱 회귀 솔버를 sklearn과 같은 구조로 바꾼다") 점수의
> 방향까지 표준으로 돌아왔다. **배포 전에는 형식 이름을 새로 만들지 않고 정의를 고쳐
> 쓴다** — 밖에 나간 v2 파일이 없다.

```jsonc
// model/run-7.json
{
  "format": "mlpx-linear-v2",
  "classes": ["setosa", "versicolor", "virginica"],
  "featureCount": 4,
  "weights": [                       // 클래스마다 한 줄. 길이는 featureCount. 원래 좌표계다
    [-0.72, -1.58,  2.79,  1.37],
    [-2.34,  3.66, -0.71,  2.03],
    [ 2.34,  1.29, -2.97, -2.19]
  ],
  "intercepts": [0.41, -1.02, 0.66]  // 클래스마다 하나. weights와 같은 순서
}
```

**v1과 반대로, 점수가 높은 클래스가 이긴다.** `score_k = weights[k]·x + intercepts[k]`
이고 예측은 **argmax**, 확률은 **softmax**다 — sklearn `predict`·`predict_proba`와
같은 식이다. v1의 "낮은 쪽이 이긴다"는 떼어낸 라이브러리의 규약이었고, 그 라이브러리와
함께 갔다.

- **동점이면 정렬 순서가 앞선 클래스다** — argmax가 첫 최댓값을 고르고 클래스는
  정렬돼 있다. KNN 득표 동점(§5.6 규칙 3)과 같은 규약이다.
- **확률은 언제나 있다.** softmax는 로그합지수(log-sum-exp)로 안정화하면 어떤 유한한
  점수에서도 정의된다 — v1의 "전부 포화하면 확률이 없다"는 그 라이브러리의 일대다
  정규화가 만든 특수 경우였고, v2에는 그 자리가 없다.
- **이진 분류도 줄이 두 개다.** 학습은 sklearn과 같이 binomial(시그모이드) 목적함수로
  가중치 한 벌 `(w, b)`를 풀고, 저장할 때 `[−w/2, +w/2]`(절편도 같이) 두 줄로 나눈다.
  `softmax([−s/2, +s/2]) = sigmoid(s)`가 정확히 성립하므로 **해석기는 클래스 수를
  가르지 않는다** — 형식 하나 = 해석 하나(§5)가 유지된다.

불변식은 §5.4의 1·2에 둘이 더해진다 (3·4는 v1 전용이다).

5. **`intercepts`의 길이 = `classes`의 길이.** 어긋나면 어느 절편이 어느 클래스인지
   알 수 없다.
6. **가중치는 원래 좌표계다.** 전처리를 마친 행렬에 그대로 곱한다 — 엔진 내부의
   어떤 변환도 파일에 새어 나오지 않는다.

**학습 쪽 예측도 이 형식의 해석기를 그대로 쓴다** — 참조형(§5.6)·SVM(§5.8)과 같은
방식이고, 그래서 "저장했다 읽은 모델의 예측이 원본과 같다"가 테스트가 아니라 구조로
보장된다.

### 5.5 `mlpx-naive-bayes-v1` — 가우시안 나이브 베이즈 (2026-08-06)

```jsonc
// model/run-9.json
{
  "format": "mlpx-naive-bayes-v1",
  "classes": ["setosa", "versicolor", "virginica"],
  "featureCount": 4,
  "logPriors": [-1.0986, -1.0986, -1.0986],   // 클래스마다. 이미 로그다
  "means":     [[5.0, 3.4, 1.5, 0.2], …],     // 클래스 × 특성
  "variances": [[0.12, 0.14, 0.03, 0.01], …]  // 평활을 **더한 뒤의** 값
}
```

**이 형식은 우리가 계산한 값을 그대로 담는다.** 이 알고리즘만 라이브러리가 아니라 저장소
안에서 계산하기 때문이고(`open-decisions.md` "가우시안 나이브 베이즈는 의존성을 빼고
우리가 구현한다"), 그래서 직렬화기가 남의 구조를 추측할 일이 없다.

**로그 공간에서 끝까지 간다.** `logPriors`가 이미 로그인 것도, 점수를 확률로 되돌리지
않는 것도 같은 이유다 — `exp`를 한 번 왕복하면 지수 합이 대략 −745 아래에서 0으로
언더플로해서 **모든 클래스가 같아진다.** 비교만 하면 되므로 되돌릴 이유가 없다.

**평활을 더한 뒤의 분산을 담는다.** 평활 계수를 따로 담고 읽을 때 더하는 방법도 있지만,
그러면 그 계수의 정의(전체 훈련 데이터 분산의 최댓값 × 1e-9)가 파일에 없는 채로 재현에
필요해진다. **재현에 필요한 값은 파일 안에 있어야 한다.**

**정규화 상수 `log(2π·분산)`을 식에서 빼면 안 된다** (2026-08-06). 상수라서 지워도
된다고 보기 쉬운데 **그건 클래스마다 분산이 같을 때 얘기다.** 여기서는 클래스마다 다르므로
클래스마다 다른 값이 되고, 빼면 답이 갈린다. 입력이 두 클래스의 평균과 정확히 같을 때
거리 항이 0이라 **이 상수만 남고 분산이 작은 쪽이 이긴다.**

실제로 저장소 주석이 "argmax에는 영향이 없다"고 적어 두고 있었고 **그게 틀렸다.**
붓꽃로 왕복 대조를 해도 안 잡혔다 — 그 데이터에서는 답이 안 뒤집혔기 때문이다.
`tests/models.spec.ts`가 갈리는 경우를 손으로 만들어 못 박았다.

불변식을 해석기가 강제한다. 어기면 `client.MODEL_FILE_INVALID`다.

1. `logPriors`·`means`·`variances`의 줄 수가 전부 `classes`의 길이와 같다.
2. `means`와 `variances`의 줄 길이가 `featureCount`다.
3. **분산이 0 이하인 열은 점수에서 건너뛴다.** 평활이 0을 막지만 훈련 데이터 전체가 상수인
   극단이 남고, 0으로 나누면 **모든 클래스가 NaN**이 되어 비교가 통째로 무너진다.
4. **동점이면 번호가 작은 클래스가 이긴다.** 엄격한 `>`로 갱신한다.

### 5.6 `mlpx-reference-v1` — KNN (2026-08-06)

```jsonc
// model/run-11.json
{
  "format": "mlpx-reference-v1",
  "k": 5,
  "classes": ["setosa", "versicolor", "virginica"],
  "featureCount": 4,
  "trainIndices": [0, 3, 5, …]     // dataset/data.csv 의 행 번호 (§5.1)
}
```

**이 형식만 `needsTrainingRows: true`다** (§5.0). 모델이 사실상 훈련 데이터이고 그 데이터는
이미 `dataset/`에 있으므로 행 번호만 담는다.

#### KNN은 우리가 구현한다 (2026-08-06)

**`ml-knn` 의존성을 뺐다.** 성능이 아니라 **재현 때문**이다.

그 구현의 예측은 k개 이웃을 훑어 최다 득표를 고르는데 **동점이면 먼저 나온 쪽이 이긴다.**
그런데 그 "먼저"의 순서가 KDTree가 이진 힙에 담아 둔 **내부 배열 순서**다 — 거리순도
행 번호순도 아니다. 즉 **동점을 가르는 것이 자료구조의 내부 상태**이고, 파일에서 읽은
모델이 그것을 재현하려면 그들의 KDTree와 BinaryHeap을 통째로 옮겨 와야 한다. 얻는 것은
"라이브러리와 같은 동점 처리"뿐인데 **그 동점 처리에는 아무 근거가 없다.**

그래서 규칙을 우리가 정한다. 가우시안 나이브 베이즈를 직접 구현한 것과 같은 판단이고,
가르는 기준도 같다 — **학습 알고리즘이 있는가.** KNN은 학습이 없다(거리 재고, k개 고르고,
표를 센다). SVM은 SMO가 있어서 라이브러리 몫으로 남는다(`open-decisions.md` "순수 JS
서포트 벡터 머신을 넣는다").

**그 결과 학습할 때와 파일에서 읽었을 때가 같은 코드를 쓴다.** 재현이 테스트로 확인하는
성질이 아니라 **구조로 보장되는 성질**이 된다.

#### 동점 규칙 셋 — 어떤 입력에도 답이 하나로 정해진다

1. **k개 이웃을 거리순으로 고른다.** 거리가 같으면 **행 번호가 작은 쪽**이 먼저다.
2. **최다 득표 클래스가 이긴다.**
3. **득표가 같으면 정렬 순서가 앞선 클래스가 이긴다** — sklearn `KNeighborsClassifier`와
   같은 답이다(득표 배열의 argmax가 첫 최댓값을 고르고, 클래스는 정렬돼 있다).
   **"정렬"은 라벨을 문자열로 본 사전순이다** — 이 도구는 라벨을 언제나 문자열로
   다루므로(`ml/preprocess.ts` "3과 '3'을 가르지 않는다") `"1" < "10" < "2"`다.
   sklearn과 같은 답이 되는 것은 **양쪽 다 라벨을 문자열로 받을 때**다. 앞으로 들어올
   엔진(pyodide-sklearn)이 라벨을 숫자 dtype으로 받으면 `classes_`가 `1, 2, 10` 순서가
   되어 **바로 이 동점에서 두 엔진이 갈린다** — 그 엔진을 붙이는 사람은 라벨을
   문자열로 넘겨야 한다.

> 규칙 3은 원래 "그중 가장 가까운 이웃을 가진 클래스"였다 (2026-08-10에 바꿨다,
> V2 감사 1단계-A). 그쪽이 KNN이 하려는 일과 결이 같고 설명도 더 잘 됐지만, **1만 행
> 실측에서 sklearn과 2000행 중 9행이 갈렸고 전부 이 규칙 차이였다** (2-2 득표 동점).
> 이 도구는 발판이라 나란히 설 sklearn 엔진과 같은 표에서 다른 답을 내면 학생은 그것을
> 엔진 차이로 읽는다 — 규약에서 고를 것이 있으면 sklearn을 따른다 (CLAUDE.md §2).
> 규칙 1은 그대로다 — 이웃 **선택**의 동점은 sklearn이 규약을 정의하지 않는 자리다
> (자료구조에 따라 다르다). 실측에서 경계 동점은 2000행 중 2행이었고 답은 갈리지 않았다.

거리는 **제곱근을 씌우지 않은 제곱 거리**로 비교한다. 순서가 같고 `Math.sqrt`가 만드는
반올림 차이가 없어 **동점 판정이 더 정확해진다.**

#### k번째까지만 고른다 — 완전 정렬하지 않는다

**필요한 것은 k개이지 전체 순서가 아니다.** 크기 k로 제한한 최대 힙에 (거리, 행 번호)를
넣으면 `O(n log k)`이고, 무엇보다 **쿼리마다 n개의 쌍을 할당하던 것이 k개로 줄어든다** —
이 크기에서 실제로 드는 비용은 비교보다 할당이다.

**실측 (2026-08-06, 개발 PC, 같은 전순서·결과 동일 확인).**

| 크기 | 완전 정렬 | 크기 k 힙 |
|---|---|---|
| 2000행 · 특성 4 · k=5 | 205ms | **20ms** |
| 2000행 · 특성 20 · k=5 | 184ms | **15ms** |
| 5000행 · 특성 20 · k=5 | 1347ms | **82ms** |

10~16배다. `n log n → n log k`의 비교 횟수 차이는 4배 남짓이므로 **나머지는 할당에서
온다.** 그리고 이 표는 KNN을 직접 구현한 것이 성능 손해가 아니라는 근거이기도 하다 —
비교 대상인 SVM이 2000행에 10.4초다(`open-decisions.md` "순수 JS 서포트 벡터 머신을 넣는다").

**힙에 넣는 순서도 (거리, 행 번호)의 사전식 전순서다.** 그래야 규칙 1이 힙에서도 그대로
성립한다 — 전순서로 고른 k개 집합은 유일하므로 완전 정렬한 결과와 **반드시 같다.**

득표 집계에는 이웃의 순서가 필요 없다. 클래스마다 **개수**만 들고 있으면 규칙 2~3이
그대로 계산된다.

### 5.7 `mlpx-linear-regression-v1` — 선형 회귀 (2026-08-06)

```jsonc
// model/run-13.json
{
  "format": "mlpx-linear-regression-v1",
  "featureCount": 2,
  "coefficients": [2.0, 3.0],   // 특성마다 하나
  "intercept": 1.0
}
```

예측은 `Σ(특성 × 계수) + 절편`이다. 그게 전부다 — **형식 넷 중 가장 단순하다.**

**`classes`가 없다.** 회귀에는 클래스가 없고, 예측이 돌려주는 것은 라벨이 아니라 수치다.
이 차이가 `mlpx-linear-v2`와 이름을 나누는 이유이기도 하다 — **그쪽은 클래스별 가중치
행렬이고 이쪽은 계수 한 줄에 절편 하나라, 같은 해석기가 읽을 수 없다.** §5가 정한 기준
그대로다: 형식 하나 = payload 하나 = 해석 하나.

**절편을 계수 배열에 섞지 않는다.** 라이브러리는 가중치 행렬의 **마지막 줄**에 절편을
두는데, 그 규약을 그대로 담으면 `coefficients.length`가 `featureCount`와 안 맞아
"특성 수가 맞는가"라는 가장 중요한 검사가 헷갈린다.

**이 형식이 늦게 온 이유를 적어 둔다.** 회귀를 V1로 올린 결정(`roadmap.md`)이 이 표까지
따라오지 않아서, 분류 다섯이 전부 담기는 동안 **회귀만 지표는 나오는데 모델이 파일에
없었다.** 그 상태로는 회귀 프로젝트가 예측 화면에서 쓸 모델이 하나도 없다.

### 5.8 `mlpx-svm-v1` — 선형 서포트 벡터 머신 (2026-08-06)

```jsonc
// model/run-17.json
{
  "format": "mlpx-svm-v1",
  "classes": ["setosa", "versicolor", "virginica"],   // 정렬 순서
  "featureCount": 4,
  // 클래스 쌍마다 하나. a·b는 classes의 인덱스이고 **a < b다.**
  "classifiers": [
    { "a": 0, "b": 1, "weights": [0.4, -1.2, 2.0, 0.9], "intercept": -0.3 }
  ]
}
```

예측은 쌍마다 `Σ(특성 × 가중치) + 절편`을 구해 **양수면 `b`, 음수면 `a`에 한 표**를 주고
가장 많이 받은 클래스다. **동점은 결정함수 값의 합으로 가른다** — sklearn `SVC`와 같은
규칙이고, 그래도 남으면 클래스 이름 순이다(결정적이어야 한다).

**다중 클래스는 one-vs-one이다.** 솔버가 이진 분류기이므로 감싸는 것이 필수인데, 방식을
`SVC`와 맞춘다 — 화면에서 순수 JS SVM은 `scikit-learn · 내 컴퓨터`와 **나란히 서므로**
방식이 다르면 학생이 그 차이를 "엔진 차이"로 읽는다. 쌍마다 두 클래스만 보므로 학습
시간에서도 이득이다.

**정규화(whitening)를 payload에 담지 않는다.** 솔버는 학습 전에 열마다 min-max로 펴는데,
선형이라 그 변환을 **가중치와 절편에 접어 넣을 수 있다** — `w'ᵢ = wᵢ/폭ᵢ`,
`b' = b − Σ wᵢ·최솟값ᵢ/폭ᵢ`. 접어 두면 해석기는 원래 좌표계에서 곱하고 더하기만 하면
되고, `minMax`를 담았다가 **예측에서 한 번 더 적용하는 것을 잊는 경로**가 아예 없어진다.
폭이 0인 열(값이 하나뿐)은 1로 둔다 — `ml/preprocess.ts`의 `spread || 1`과 같은 규칙이다.

**해석기는 `mlpx-linear-v2`와 다르다.** 저쪽은 클래스마다 한 줄(one-vs-all)이고 이쪽은
클래스 **쌍**마다 한 줄이라, 같은 배열을 읽어도 뜻이 다르고 투표 규칙이 다르다.
§5가 정한 기준 그대로다 — 형식 하나 = payload 하나 = 해석 하나.

### 5.9 수렴하지 못한 학습은 실패가 아니다 — `run.warning` (2026-08-06)

SMO는 반복 예산 안에 수렴하지 못할 수 있다. **교실 데이터에서는 그게 예외가 아니라
흔한 경우다** (`open-decisions.md` "다시 쟀더니"). 그때 나오는 계수는 쓸모없는 값이
아니라 **덜 다듬어진 값**이고, sklearn도 같은 자리에서 경고만 내고 모델을 준다.

**로지스틱 회귀도 같은 자리를 쓴다** (2026-08-10, V2 감사 1단계-A·B). 처음 발견은
고정 스텝 경사하강이 **수렴 개념 자체가 없어** 덜 배운 모델이 무신호로 저장되던 것이다
— 2만 행 실측에서 기본 스텝으로 정확도 0.78, 같은 목적함수의 최적점은 0.92였다.
1단계-B에서 솔버가 sklearn 구조(L2 + L-BFGS)로 바뀌면서 판정도 sklearn과 같아졌다:
기울기 최대 성분이 `tol` 아래로 내려가면 수렴이고, **`maxIter`에 닿으면
`LOGISTIC_NOT_CONVERGED`가 붙는다** — sklearn이 `ConvergenceWarning`을 내는 그
자리다. L2가 최적점을 유한하게 만들었으므로 이 경고는 정말로 덜 배운 모델에서만 뜬다
(규제 없는 옛 솔버에서는 분리 가능한 데이터가 최적점이 무한대라, 좋은 모델에도 경고가
뜨는 것을 막을 근거 있는 문턱이 존재하지 않았다).

**세 코드는 자리가 같고 주장의 세기가 다르다** (2026-08-11에 고쳐 적는다). 로지스틱은
`max|기울기| ≤ tol`로 판정한다 — 경고가 없으면 최적점 근방이라는 뜻이다. **SMO는
그렇지 않다.**

> **뒤집으면 sklearn보다 시끄럽다** (2026-08-31). scipy `L-BFGS-B`는 정지 조건이
> 둘이라(`gtol`·`ftol`) 스케일이 갈린 데이터에서는 **함수값이 안 줄어든다는 이유로 먼저
> 멈추고 경고를 안 낸다** — 실측에서 그 점의 `max|기울기|`가 `tol`의 1만 배였다. 우리는
> 그 자리에서 경고를 낸다. 보수적인 쪽이고, 학생이 할 일은 **전처리 스케일링**이다
> (`open-decisions.md` "로지스틱 회귀 솔버를 sklearn과 같은 구조로 바꾼다"의 "실물이
> 꺼낸 것"). V3에서 정지 조건을
KKT 위반 기준으로 바꿨지만(`open-decisions.md` #26), 실측하니 그 출구는 좀처럼 안 열리고
**연속 정체(α가 하나도 안 움직인 패스 열 번)가 실질적인 종료 조건**이다(#26-1).
그래서 **`SVM_NOT_CONVERGED`가 없다고 해서 최적점 근방이라는 뜻은 아니다** — 그 코드는
"반복 예산을 다 썼다"만 뜻한다. 같은 낱말을 쓰지만 보증이 다르다.

**K-평균의 `KMEANS_NOT_CONVERGED`도 자리가 같다** (V3). Lloyd 반복이 `max_iter`(300) 안에
중심점을 고정하지 못한 것이고, 중심점도 군집 번호도 정상으로 나온다 — 더 돌리면 미세하게
움직일 뿐이다. sklearn도 같은 자리에서 `ConvergenceWarning`을 낸다.

**sklearn과의 비대칭도 여기서 나온다** (2026-08-11 실측 · sklearn 1.9.0 · 800행 겹침).
`SVC`의 기본값은 `max_iter=-1`이라 libsvm이 **KKT 위반의 최대치가 `tol`(1e-3) 아래로
내려갈 때까지 무조건 돈다** — 이 데이터에서 7,174 반복이 걸렸고 경고는 없었다.
`max_iter`를 조이면 그때는 `ConvergenceWarning`이 뜬다(같은 실측). 즉 **sklearn은
기본값으로 덜 배운 SVM을 주지 않고, 우리는 줄 수 있다.** 우리 예산은 교실 시간의
것이지 정확도의 것이 아니므로, 이 경고는 sklearn에 없는 일을 한다 — 없앨 것이 아니다.

SMO의 정지 조건을 libsvm처럼 KKT 위반 기준으로 바꿀 것인지는 `open-decisions.md` #26이다.

그래서 run에 `warning`을 둔다. **`failure`와 모양이 같고 자리가 다르다.**

```jsonc
{ "id": "run-17", "status": "done", "metrics": { … },
  "warning": { "code": "SVM_NOT_CONVERGED", "params": { "iterations": 10000 } } }
```

- **`status`는 `done`이다.** 지표가 나왔고 모델도 담긴다. 실패로 만들면 학생은 숫자를
  하나도 못 보고, 그건 사실보다 나쁜 상태다.
- **자연어가 아니라 코드다** (CLAUDE.md §1.4). 서버가 학습한 run도 같은 자리를 쓴다.
- **`failure`와 합치지 않는다.** 하나로 두면 "실패했는가"의 판정이 `status`와 그 필드
  둘로 갈라지고, 화면이 성공한 run을 실패 목록에 넣는 경로가 생긴다.

**어휘를 늘리는 변경이지만 `formatVersion`은 안 오른다** — 아직 밖에 v1 파일이 없다
(§9, `open-decisions.md` "전처리도 분할도 끌 수 있다"의 같은 근거). 첫 배포 뒤에는 뒤집힌다.

### 5.10 `mlpx-kmeans-v1` — K-평균 (V3, 2026-08-11)

```jsonc
// model/run-21.json
{
  "format": "mlpx-kmeans-v1",
  "featureCount": 2,
  "k": 3,                          // 군집 수. centroids.length와 같아야 한다
  "centroids": [                   // centroids[c][j] = 군집 c의 특성 j
    [0.5, 0.0],
    [10.5, 10.0],
    [5.0, 5.0]
  ]
}
```

**담기는 것은 중심점뿐이다.** 예측은 입력과 각 중심점의 거리를 재서 가장 가까운 것의
번호를 돌려주는 것이 전부다. 훈련 행이 필요 없으므로 `needsTrainingRows: false`이고,
KNN(§5.6)과 갈리는 자리가 여기다 — 같은 "거리로 답하는" 모델인데 이쪽은 자체 완결이다.

**돌려주는 것은 문자열이다** (`"0"`, `"1"`, …). `Prediction`이 `string | number`이므로
군집 번호를 수치로 돌려주면 부르는 쪽이 "이건 회귀인가 군집인가"를 봐야 한다. 문자열이면
분류와 같은 경로를 탄다.

**불변식 넷을 해석기가 강제한다** (`ml/models/kmeans.ts`의 `loadKMeansModel`). 어기면
`MODEL_FILE_INVALID`다 — 형식은 아는데 내용이 그 형식이 아닌 경우이고, 학생이 할 일은
다시 학습하는 것이다(§5.2).

1. `featureCount`가 정수이고 0보다 크다
2. `k`가 정수이고 0보다 크다
3. `centroids.length === k`
4. 중심점마다 길이가 `featureCount`이고 값이 전부 유한하다

**`classes`가 없다.** 군집화에는 정답 라벨이 없고, 번호는 이름이 아니라 자리다 —
같은 데이터를 다시 학습하면 같은 군집이 다른 번호를 받을 수 있다(`randomState`가
같으면 같지만, 그건 시드가 같아서지 번호에 뜻이 있어서가 아니다).

**빈 군집은 파일에 오지 않는다.** 엔진이 sklearn처럼 재배치하고(`mljs-kmeans.ts`),
데이터보다 군집이 많은 요청은 `CLUSTER_TOO_FEW_ROWS`로 학습 전에 거부한다 — 그 검사가
없으면 데이터에 없는 유령 중심점이 불변식 넷을 전부 만족한 채 이 파일에 담긴다.
