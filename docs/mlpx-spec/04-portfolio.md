# `.mlpx` — 포트폴리오 (§8)

> `mlpx-spec.md`에서 갈라져 나온 절이다. **절 번호는 안 바뀌었다** —
> 저장소가 `mlpx-spec.md §5.9`처럼 번호로 가리키므로 여기서도 원래 번호를 쓴다.
>
> 전체 차례는 허브(`../mlpx-spec.md`)에 있다.

## 8. 포트폴리오 — 양식은 마크다운, 답은 글이다

**양식과 답은 다른 물건이고, 형식도 다르다.**

| | 형식 | 어디서 오나 |
|---|---|---|
| 양식 (문항) | 마크다운 | 밖에서 온다 (§8.7) |
| 답 | 서식 없는 글 | 쓰는 사람 |
| 제출물 (`portfolio/document.md`) | 마크다운 | 우리가 조립한다 (§8.5) |

**답까지 마크다운으로 두면 문법 편집기를 만들게 된다.** 그러면 이 도구를 쓰는 사람이
`##`과 `![]()`를 먼저 배워야 하고, 그건 여기서 가르치려는 것이 아니다. 그래서 양식만
마크다운이고 **쓰는 사람은 마크다운 기호를 한 번도 보지 않는다.**

**수업 전용 도구가 아니다.** 문항은 도와주려고 있는 것이지 채워야 할 숙제가 아니고,
혼자 놀러 온 사람이 "회상 일기"로 쓰는 것도 같은 자격을 갖는다. 이 절의 규칙 여럿이
거기서 나온다 — 빈 양식이 있는 것, 문항을 마음대로 고칠 수 있는 것, 잠그는 장치가
없는 것.

### 8.1 양식 — `#`은 제목, `##`이 문항이다

```markdown
# 3학년 프로젝트 보고서       ← 문서 제목. 문항이 아니다. 없어도 된다

## 이 주제를 고른 이유         ← 문항
데이터를 고른 과정도 함께 쓰세요.   ← 그 문항의 안내문
```

다음 `##`을 만날 때까지가 그 문항의 몫이다. 안내문에는 목록·표·강조가 다 들어간다 —
읽기 전용으로 렌더링되고 답 칸 위에 붙는다.

**렌더링은 살균을 거친다.** 양식은 남이 준 파일이고 남이 준 주소에서도 온다.
raw HTML은 통과시키지 않고 링크 프로토콜을 검사한다 — **어느 입구로 들어왔든 같은
경로를 탄다.** 입구가 늘었다고 방어선이 갈라지면 그 자리가 곧 구멍이다.

**링크는 누를 수 있다.** 교사가 자료 주소를 안내문에 넣는 것은 실제로 있을 일이고,
링크를 죽이면 학생이 주소를 손으로 옮겨 적는다. 대신 셋을 강제한다 — **`http`·`https`만
통과하고, 새 탭에서 열리며, `rel="noopener noreferrer"`가 붙는다.** 새 탭인 이유는
쓰던 글이 있는 탭을 남의 주소가 가져가면 안 되기 때문이다.

**우리가 주소를 링크로 만들지는 않는다**(`linkify`를 켜지 않는다). 글 안의 주소를 링크로
바꾸는 것은 우리 판단이지 쓴 사람의 뜻이 아니다.

**안내문에서 줄바꿈은 줄바꿈이다.** CommonMark은 홑 개행을 공백으로 보지만 **이 화면에서
안내문을 고치는 사람은 마크다운을 모른다** — 엔터를 쳤는데 한 줄로 붙으면 그건 문법이
아니라 고장으로 읽힌다. 문단을 나누려면 빈 줄을 넣는 규칙은 그대로 산다.

**대가는 원본이 접혀 있을 때다.** 80칸에서 손으로 접은 문단은 접은 자리마다 줄이
바뀐다. 그건 **파일에 보이는 그대로 나오는 것**이라 설명할 수 있고, 고치는 방법도 그
파일 안에 있다.

**그림은 안내문에 안 들어간다.** 원격 이미지는 우리 페이지가 남의 서버에 요청을 보내는
것이고, 학교망에서는 깨진 아이콘이 되며, 추적 픽셀과 구분할 방법이 없다. 사진은 답에
붙이는 것이고 그건 파일 안에 담긴다 (§8.6.1). **막는 것은 그리는 일뿐이라** 나중에
풀기 쉽다.

### 8.2 문항 id는 제목 슬러그다

답은 문항 id로 저장되는데(`answers`) 마크다운에는 id가 없다. **제목에서 만든다.**
겹치면 뒤에 번호를 붙이고, 만들 수 없으면(기호만 있는 제목 등) 순번으로 떨어진다.

**순서 번호(`q1`·`q2`)로 하지 않는다.** 문항 순서를 바꾸는 순간 답이 엉뚱한 문항에
조용히 붙는다. 슬러그는 제목을 고치면 답이 떨어져 나가지만, 그건 화면에 보이고
(§8.4) 조용히 틀리지 않는다.

**우리가 내보내는 양식에는 제목 줄에 id를 적는다.** 그래야 제목을 다듬어도 답이 붙어
있고, 마크다운 → 문항 → 마크다운 왕복이 무손실이다. 맨손으로 쓴 양식에는 그것이 없고,
그때는 슬러그로 계산한다 — **둘 다 열려야 한다.**

```markdown
## 이 주제를 고른 이유 {#motivation}
```

**표기는 Pandoc 계열의 관행을 따른다**(kramdown·MkDocs·Quarto가 같은 것을 쓴다).
우리가 지어낸 표기를 쓰지 않는 이유는 낱말을 고를 때와 같다(CLAUDE.md §2) — 여기서만
통하는 규약은 이 저장소 밖에서 아무 뜻도 없다. **처음에는 `<!-- id: … -->` 주석이었다가
바꿨다**(2026-08-14): 주석은 "제목 바로 아래 줄"이라는 자리 규칙을 요구했고, 제목과
id가 다른 줄에 있어 고칠 때 함께 눈에 들어오지 않았다.

**HTML 주석은 양식을 읽을 때 통째로 걷어낸다.** 그것은 양식을 쓴 사람의 메모이지 학생이
읽을 안내문이 아니고, 남겨 두면 `html: false`인 렌더러가 그것을 **글자로** 보여준다
(§8.1).

### 8.3 화면

**빈 프로젝트에서 열어도 화면이 비지 않는다.** 양식이 아직 없으면 둘을 준다.

```
[빈 양식에서 시작]   [양식 가져오기 ▾]
                      ├ (내장 프리셋들)
                      └ 파일에서 가져오기
```

**가져오는 곳이 여럿이므로 버튼을 늘리지 않고 팝오버 하나에 담는다.** §8.7이 모든
출처를 같은 모양으로 만들어 두었기 때문에 이 목록은 등록부에서 그대로 나온다 — 화면이
경로마다 다른 단추를 만들지 않는다. **여기 있는 것이 전부다** — 주소로 받는 길과 서버가
맡아 주는 길은 §8.7에서 접었고, **안 만든 경로를 비활성으로 미리 세워 두지 않는다.**
회색으로라도 서 있으면 그건 없는 기능을 있다고 말하는 것이다.

**줄의 무게는 등록부가 갖는다** (2026-08-15). 목록이 전부 같은 회색이면 그것은 "고를
것이 둘"이 아니라 **"꺼진 것이 둘"로 읽힌다** — 팝오버 패널이 흰 면이라 옅은 회색
단추가 거기서 비활성으로 보였다(사용자가 겪었다). 그렇다고 화면이 "파일 줄이면
파란색"으로 가르면 §8.7이 세워 둔 균일함이 그 자리에서 깨진다. 그래서 **줄이 자기 무게를
들고 온다** — 앞서는 줄은 `파일에서 가져오기`다(§8.7의 "가장 확실하다", 그리고 **유일하게
사용자가 무언가를 내놓는 줄**이다). 화면이 갖는 것은 무게를 단추 모양으로 옮기는 표
하나뿐이다.

**바닥은 프리셋이 아니라 [빈 양식에서 시작]이다.** 프리셋은 `public/`에 있어서
가져오려면 네트워크를 탄다(§8.7). 빈 양식은 문항 하나짜리라 **코드가 만든다** — 파일도
연결도 필요 없으니 무슨 일이 있어도 시작할 수 있다. 그리고 이것이 **문항 없이 자유롭게
쓰고 싶은 사람의 자리**이기도 하다. 별도 모드를 만들지 않는다.

**가져오기는 대체가 아니라 추가다.** 문항을 반쯤 채우다 프리셋을 가져와도 쓰던 문항과
글이 그대로 있고, 가져온 문항이 뒤에 붙는다. **이미 있는 id는 다시 붙이지 않는다** —
그래야 두 번 눌러도 문항이 불어나지 않고, 그 문항에 쓴 글도 안 흔들린다.

문항은 **번호가 붙고 제목이 크고 굵다.** 그 아래 안내문, 그 아래 글 칸이다.
[작성]과 [완성본]을 오간다 — **문법과 결과 사이가 아니라 쓰는 화면과 받는 사람이 볼
화면 사이다.** 나란히 두지 않는 이유는 휴대폰이 기준이기 때문이다.

**프로젝트 요약은 여기 넣지 않는다.** `ProjectSummary`가 도구 막대와 대시보드에서
이미 같은 것을 보여준다. 두 벌이면 한쪽만 고쳐진다.

**문항은 마음대로 고친다** — 더하고, 지우고, 순서를 바꾸고, 받아 온 양식의 문항도
같다. 막을 근거가 없다. 이 도구는 누구의 것도 아닌 놀이터이고, "받은 양식은 받은
대로"를 강제할 권한이 우리에게 없다.

**잠그는 장치는 두지 않는다.** 다 썼다고 표시해 읽기 전용으로 굳히는 버튼은
[완성본] 보기가 이미 하는 일과 겹치고, 무엇보다 **강제력이 없다** — 압축을 풀면
풀린다. 없는 보증을 있는 것처럼 보이게 하는 문구를 만들지 않는다(§7.3).

**체크리스트가 완료로 넘어가는 기준은 "모든 문항에 답이 있는가"다.** 한 글자라도
썼는가가 아니다. 딸려 오는 것 셋을 못 박는다 — 항목을 새로 추가하면 완료가 다시
풀리고(자기가 늘린 것이다), 지금 양식에 없는 문항의 답은 세지 않으며, 양식을 아직
고르지 않았으면 완료가 아니다.

### 8.4 문항을 지우면 그 글도 지운다

**문항을 지우면 그 문항의 답과 첨부까지 함께 지운다. 되돌릴 수 없고, zip 엔트리도
같이 지운다.** 의도가 분명하기 때문이다 — 지우겠다고 누른 것이다. 답과 첨부가
유령으로 파일에 남으면 크기만 먹고 아무도 못 본다.

**글이 사라지는 다른 경로는 없다.** 양식을 통째로 갈아 끼우는 동작 자체가 없기
때문이다 — 가져오기는 대체가 아니라 추가이고(§8.3), 문항 문구를 고치는 것은 id를
안 건드린다. **글을 잃는 방법이 "지우기" 하나뿐인 것이 이 설계의 값이다.**

그래도 **지금 양식에 없는 id의 답을 만나면 버리지 않는다.** 정상 경로로는 안 생기지만
남이 손으로 고친 파일에서는 올 수 있고, 그때 조용히 지우면 그 파일을 준 사람의 글이
말없이 사라진다. 포맷은 이미 견딘다(`answers`가 자유 레코드다) — 화면이 "이전 문항의
답"으로 보여준다.

### 8.5 파일에 남는 모양

```jsonc
{ "template": {
    "locale": "ko",                     // 양식의 언어. 모르면 없다
    "sections": [ { "id": "동기", "title": "이 주제를 선택한 이유",
                    "description": "데이터를 고른 과정도 함께 쓰세요." } ] },
  "answers": { "동기": "…" },
  "attachments": { "동기": ["portfolio/attachments/1.webp"] } }
```

**양식이 무슨 언어인지가 파일에 적힌다** — `template.locale` (2026-08-15).
문항 제목과 안내문의 언어이고, **UI 언어를 바꿔도 안 따라간다** — 이미 ko로 가져온
문항이 en으로 저절로 번역되지는 않기 때문이다. 그래서 `manifest.locale`(머리글의
언어, §2)과 다른 값일 수 있고, 그 둘이 갈린다는 것 자체가 사실이다.

**아는 경우에만 적는다.** 내장 프리셋은 파일 이름이 언어를 갖고 있어서(§8.7) 확실히
알고, **밖에서 받은 `.md`는 모른다** — 그때는 필드를 두지 않는다. UI 언어를 대신
적으면 추측이 사실로 굳는다. 없는 것을 이름으로 말하지 않는다.

**처음 문항이 들어올 때 박고 그 뒤로 안 바뀐다.** 가져오기가 대체가 아니라 추가라서
(§8.3) 언어가 섞인 양식을 만들 수는 있는데, 그때 참인 단일 값은 없다 — 양식의 정체는
그것을 세운 첫 가져오기가 갖는다고 본다. 섞은 사람은 자기가 섞은 것을 안다.

**답을 무엇으로 썼는지가 파일에 적힌다** — `answerFormat`. 지금 값은 `plain-v1`
하나이고, **서식 없는 글이며 사진은 답 아래에 붙는다**는 뜻이다 (§8.3).

**적어 두는 이유는 나중에 편집기를 바꿀 때다** (2026-08-14, 사용자). 형식이 달라지면
**옛 답을 그대로 새 형식으로 읽는 순간 학생이 쓴 별표와 밑줄이 갑자기 서식이 된다.**
파일이 자기 형식을 말하고 있으면 마이그레이션이 그것을 붙잡을 수 있고, 말하지 않으면
추측해야 한다.

**이름에 버전이 들어간다** — 모델 형식 이름과 같은 규칙이다(CLAUDE.md §4). `2`는 무엇이
달랐는지 말하지 않지만 `plain-v1`은 말한다. 그리고 **어휘라서 늘어나는 순간
`FORMAT_VERSION`과 마이그레이션을 요구한다** (§9).

**양식에는 id가 없다.** 가져오기가 대체가 아니라 추가이므로(§8.3) 내장에서 시작해
프리셋을 얹고 문항을 고친 양식은 **어느 이름도 참이 아니다.** 가리킬 대상이 없는 이름을
파일에 남기면 다음 사람이 그것을 믿는다. **양식을 아직 고르지 않았다는 것은 `sections`가
비었다는 것으로 표현된다** — 새 프로젝트가 그 상태고, 그때 화면은 §8.3의 시작 화면을 낸다.

**문항은 언제나 파일에 통째로 박힌다.** 내장 양식이라고 id만 남기지 않는다 — 문항을
하나라도 고치는 순간 그건 더 이상 내장 양식이 아니고, 그때 고친 문구가 저장될 곳이
없어진다. 내장 양식도 밖에서 온 양식과 같은 물건이어야 한다는 뜻이고, 그래서 내장
양식의 문구도 로케일이 아니라 언어별 마크다운 파일에 있다 (§8.7).

문항 문구는 애초에 번역 대상이 아니다 — 쓴 사람의 말이다.

### 8.6 `.md`로 옮길 때 — 구조를 깨는 것만 막는다

`.json`이 원본인 이유는 채점 편의가 아니라 **양식이 가변이기 때문**이다.
`.md`는 도구 없이 파일만 받은 사람이 읽게 하는 용도다.

**머리에 프로젝트 정보를 적는다.** 화면에서는 `ProjectSummary`가 그 일을 하는데,
파일만 받은 사람은 그 화면을 못 본다. 언제 만든 것이고 무슨 데이터로 무엇을 했는지가
첫 줄에 있어야 몇 달 뒤의 자신도 읽을 수 있다.

**적었다면 학번과 이름이 그중 맨 위다** (2026-08-15, 사용자). 이 파일은 제출물이고,
받은 사람이 제일 먼저 찾는 것이 그 둘이다 — 만든 날짜보다 아래에 있으면 훑는 눈이
한 번 더 내려가야 한다. **안 적었으면 자리도 없다** (§3의 `student`는 선택이다) —
빈 칸을 만들면 안 적은 것이 빠뜨린 것으로 보인다.

**읽기 좋은 것이 기준이다.** 답을 코드 블록으로 감싸거나 기호를 전부 이스케이프하면
안전하기는 한데, 읽으라고 만든 파일을 읽기 나쁘게 만든다. 막을 것은 **문항 구조를
깨는 것뿐**이다 — 줄 첫머리의 `#`, 그리고 앞줄을 제목으로 만드는 단독 `---`·`===`.
답에 목록이나 강조가 들어가 그대로 살아나는 것은 사고가 아니라 잘 된 것이다.

**안 쓴 문항도 제목은 남긴다.** 빈 칸이 보이는 것과 문항이 사라지는 것은 다르다 —
받은 파일에 "느낀 점"이 없으면 안 쓴 것인지 문항이 없었던 것인지 알 수 없다.

**렌더링된 `.md`는 저장하는 쪽이 만들어 넘긴다.** 포맷 계층은 `t()`를 모른다 —
i18n을 끌어들이면 zip 왕복 테스트마다 번역을 부팅해야 한다.

### 8.6.1 상한

**글과 첨부를 합쳐 하나의 상한을 둔다.** 값은 `limits.ts`가 갖는다.

상한을 두는 이유는 제약이 아니라 **폭주 방지턱**이다. 사람이 손으로 쓴 글이 거기
닿을 일은 없고, 실제로 걸리는 것은 붙여넣기 한 번에 들어오는 거대한 텍스트나 사진
무더기다. 상한이 없으면 안 걸리는 것이 아니라 **저장이 실패하는 모양으로 터진다** —
그리고 그 실패는 "저장이 안 됩니다"로만 보인다.

문항마다 나누지 않는다. 나누면 어느 칸이 얼마인지를 설명해야 한다.

**첨부는 굽는다 — WebP, 못 구우면 jpg.** 형식과 품질은 훈련용 정본과 같은 상수를
쓴다(§1.2). **크기 규칙은 다르다.** 훈련용은 백본이 정사각형을 요구해 레터박스로
여백을 채우는데, 첨부는 사람이 보는 그림이라 **긴 변 상한을 두고 비율을 지킨다.**
여백을 붙이지 않는다.

**긴 변은 1536px이다** (2026-08-14에 정했다). **우리가 이미 쓰는 눈금이다** — 완성본
본문 폭이 `md`(48rem = 768px)이고 그 두 배이며, 동시에 Tailwind의 가장 큰 브레이크포인트
(`2xl` = 96rem = 1536px)다. 고해상도 화면에서 본문 폭을 꽉 채워도 뭉개지지 않는 가장
작은 값이라는 뜻이고, 값은 `limits.ts`가 갖는다.

**`.md`에는 상대 경로로 적는다.** `portfolio/document.md`에서 본 `attachments/3.webp`이고,
**압축을 푼 자리에서 그대로 맞는다.** 안 적으면 파일만 받은 사람에게는 사진이 아예 없는
것이 된다. 안내문의 원격 이미지를 막은 것과는 다른 자리다(§8.1) — 이건 zip 안의 파일이라
네트워크를 안 탄다.

### 8.7 양식은 어디서 오나

**프로젝트 파일로 나누지 않는다** (§6.3). 나누는 것은 마크다운 하나다.

| 경로 | 무엇 |
|---|---|
| 내장 프리셋 | `public/portfolio/`의 언어별 마크다운 파일을 같은 오리진에서 받는다 |
| 파일 열기 | 받은 `.md`를 연다. **가장 확실하다** — 파일을 나르는 통로는 이미 있다 |

**출처는 다르지만 하는 일은 같다 — 마크다운 문자열 하나를 돌려주는 것.** 그래서
등록부에는 출처마다 그 함수 하나만 등록되고, 파싱·살균·문항 세우기는 한 벌이다.
**내장이라고 특별 취급하지 않는다** — 번들에 넣지 않고 `public/`에 두는 이유가 그것이다.
자가호스팅 백엔드가 서빙하는 경로도 나중에 이 표에 줄 하나로 붙는다.

**내장 프리셋은 지원 언어마다 하나씩 있다.** 없는 언어는 en으로 떨어지는데, **떨어지는
것과 빠뜨린 것을 화면에서 구분할 수 없다.** 그래서 지원 언어 배열과 프리셋 파일 목록이
어긋나면 CI가 운다 (`docs/i18n.md`). 로케일 JSON은 이미 그런 검사를 받고 있는데
`public/`의 마크다운은 아무도 안 보고 있었다.

**프리셋은 파일만 더하면 는다.** 목록은 `public/portfolio/index.json`이 갖는다 — id마다
언어별 이름이 있고, 파일 이름이 그 id에서 나온다.

```jsonc
// public/portfolio/index.json          그리고 파일은 portfolio/hello.ko.md · hello.en.md
{ "hello": { "ko": "회상 일기", "en": "Looking back" } }
```

**이름이 로케일 JSON에 없는 이유는 프리셋이 코드가 아니기 때문이다.** 프리셋을 하나
늘리는 일은 파일 둘과 줄 하나이고, 거기에 코드 수정과 배포가 끼면 그건 더 이상 "자유롭게
고칠 수 있는 양식"이 아니다. 문항 문구가 로케일을 떠난 것과 같은 자리다 (§8.5).

**그래서 `index.json`도 검증을 거친다.** 우리가 배포하지만 자가호스팅에서는 설치한 쪽이
고치는 파일이고, 깨져 있으면 프리셋 줄만 사라지고 나머지 경로는 그대로 산다 — 바닥은
언제나 빈 양식이다 (§8.3).

**주소로 나누는 길은 재 보고 접었다** (2026-08-14). 양식을 압축해 주소에 실을 수는
있는데 **기본 양식 하나가 758자짜리 링크가 된다**(deflate + base64url, 한국어는 UTF-8에서
글자당 3바이트라 압축 여지가 작다). 문자로는 여러 통으로 쪼개지고, QR로는 교실에서
스캔이 까다로우며, 무엇보다 **사람 눈에 수상한 링크로 보인다** — 교사가 학생에게 주기
어려운 물건이다. 그렇게 얻는 것은 파일 열기 대비 한 단계 절약뿐이다.

**짧은 숫자 코드는 서버가 있어야 성립한다.** 코드로 양식을 찾아 주려면 조회하는 서버가
있어야 하는데 공식 배포에는 서버가 없다 (CLAUDE.md §1.1). **그래서 이 자리는 자가호스팅
백엔드(V6)의 일이다** — 서버가 서면 양식을 맡아 두고 짧은 코드를 줄 수 있고, 서버가
없으면 758자다. 서버 없이 만들면 반쪽이라 지금 만들지 않는다.

**URL에서 받는 길은 아예 접었다.** 교사가 CORS가 열린 호스팅에 양식을 올려 둬야 하는데,
그럴 수 있는 교사라면 **그 주소에서 파일을 받아 열기가 더 빠르다**(사용자 판단,
2026-08-14). 문턱은 높고 그 위에 실패 화면과 오류 문구까지 만들어야 한다.

**브라우저끼리 직접 나누는 길도 없다.** 웹 페이지는 포트를 열 수 없고 자기 내부망
주소도 볼 수 없다. WebRTC로 데이터를 직접 주고받는 것은 되지만 **서로를 찾는 데
시그널링 서버가 필요하고**, 그건 우리가 안 띄우기로 한 바로 그것이다.
