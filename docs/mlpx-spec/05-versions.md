# `.mlpx` — 버전·검증·브라우저 저장소 (§9~§11)

> `mlpx-spec.md`에서 갈라져 나온 절이다. **절 번호는 안 바뀌었다** —
> 저장소가 `mlpx-spec.md §5.9`처럼 번호로 가리키므로 여기서도 원래 번호를 쓴다.
>
> 전체 차례는 허브(`../mlpx-spec.md`)에 있다.

## 9. 버전과 마이그레이션

**첫 배포 전에는 버전을 올리지 않는다** (2026-08-05). 아래 규칙들이 지키는 것은 **밖에
나간 파일과 지금 앱 사이의 호환성**인데, 배포 전에는 나간 파일이 하나도 없어 지킬 대상이
없다. 어휘를 늘려도, 필드를 옮겨도, 이름을 바꿔도 마찬가지다 — 실제로 `batches`를
`experiments`로 바꾸면서 안 올렸다(§4). 지금 올리면 아무도 안 겪을 상황을 위해
변환 함수와 왕복 테스트를 영구히 지고 가는 것뿐이다.

**첫 배포 순간 이 문단은 죽는다.** 그 뒤로는 아래가 예외 없이 적용된다.

같은 판단이 `MLJS_ENGINE.version`에도 걸린다. 그쪽이 지키는 것은 "재실행 대조가 옛
파일을 새 엔진으로 검사하지 않게 막는 것"이고, 검사할 옛 파일이 없으면 구분할 대상이 없다.

1. **하위 버전은 조용히 올려서 연다.**
2. **상위 버전은 거부한다** — `PROJECT_FILE_VERSION_TOO_NEW`.
   학교 PC와 집 PC의 앱 버전이 다를 때 조용히 깨지는 것보다 낫다.
3. 마이그레이션 함수는 **순수 함수**. 파일 I/O 없이 객체만 변환한다.
4. 버전을 올리는 커밋에 마이그레이션 함수와 테스트가 함께 온다. **테스트로 강제한다.**

**검사 순서가 설계의 핵심이다.**

```
압축 해제 → manifest 파싱 → formatVersion 확인 → 나머지 엔트리 요구 →
마이그레이션 → zod 검증
                  ↑ 여기가 zod보다 앞이고, 엔트리 존재 검사보다도 앞이다
```

구버전 파일은 현재 스키마를 만족하지 않는 게 당연하다. 순서를 뒤집으면 올려서 열 수 있는
파일이 전부 `PROJECT_FILE_INVALID`가 된다.

**엔트리 존재 검사보다도 앞이어야 한다.** 없으면 못 여는 엔트리는 넷이지만(§1), 그 넷을
먼저 요구하면 **미래의 파일이 `PROJECT_FILE_VERSION_TOO_NEW` 대신 `PROJECT_FILE_ENTRY_MISSING`
으로 거부된다.** v2가 `portfolio/document.json`을 `manifest.json`에 합치기만 해도 그렇게 된다.
학생과 교사가 보는 것은 "앱을 업데이트하세요"가 아니라 "manifest.json이 없습니다"이고,
둘은 파일이 손상됐다고 결론 낸다. 2번 조항이 약속한 "명확한 거부"가 여기서 새어 나간다.

그리고 이 순서 덕분에 **검증 단계에 도달하는 파일은 항상 같은 버전이다.** 그래서 어휘를
엄격하게 막아도 호환성 문제가 생기지 않는다(§10).

마이그레이션은 문서 넷(`manifest`/`settings`/`runs`/`portfolio`)을 묶은 단위로 동작한다.
스키마 변경이 여러 파일에 동시에 걸치는 것이 정상이기 때문이다.
`formatVersion`은 체인이 올린다 — 함수마다 잊지 않기를 기대하지 않는다.

**그래서 zip 엔트리의 구성은 v1에서 동결이다.** 마이그레이션 함수가 받는 것은 JSON 넷이지
엔트리 맵이 아니므로, **엔트리의 이름·추가·병합·데이터셋 경로 변경을 표현할 자리가 없다.**
JSON 안의 필드는 얼마든지 옮길 수 있고 그것이 마이그레이션이 다루는 전부다.

엔트리 구성을 바꿔야 한다면 그건 함수 하나를 추가하는 일이 아니라 **마이그레이션 체계를
다시 설계하는 일**이다(시그니처에 엔트리 맵을 넘길지부터). 그때 결정한다.

### 9.1 v1 → v2 — 백본 id 개정 (2026-08-19)

**첫 마이그레이션이다.** 배포 뒤에 실제로 이 체계를 한 번 돌려 본 자리이기도 하다.

**왜.** 등록부가 MobileNetV2의 입력 범위를 `[-1,1]`로 선언했는데 우리가 받는 것은 TF-Hub
모듈이라 **그래프가 `x*2-1`을 자기 안에서 한다.** 계약은 `[0,1]`이었고, 그래서 컨볼루션이
실제로 받은 값이 `[-3,1]`이었다 — **예외 없이 모든 이미지 프로젝트의 임베딩이 조용히 나쁜
상태로 학생 파일에 담겼다.** 결정문은 `open-decisions.md`의 **"백본 입력 범위가 그래프의
계약과 어긋났다"**에 있다.

**무엇을 바꾸나.** 문서 안의 백본 id 둘뿐이다.

| 자리 | v1 | v2 |
|---|---|---|
| `settings.data.backboneId` | `mobilenet-v2` | `mobilenet-v2-r2` |
| `runs.experiments[].settings.data.backboneId` | `mobilenet-v2` | `mobilenet-v2-r2` |

**옛 id일 때만 바꾼다.** 모르는 id는 그대로 두고 지나간다 — 우리가 만들지 않은 값을 우리
이름으로 덮으면 그 파일은 자기가 어디서 왔는지 말할 수 없게 된다.

**임베딩은 마이그레이션이 안 만진다.** 경로 규칙(§1.3 규칙 2)이 저절로 처리한다 — 문서가
새 id를 가리키는 순간 `embeddings/mobilenet-v2/`는 아무도 안 보는 디렉터리가 되고, 다음
저장에서 "등록부에 없는 백본 id"로 떨어져 나간다. 다음 학습에서 새 좌표계로 다시 뽑힌다.

**어휘는 안 바뀐다.** `backboneId`는 `z.string()`이고 §10의 "어휘"가 아니다 — 그래서
`tests/schema-version.spec.ts`의 v2 지문은 v1과 같은 내용이다. **그래도 버전은 오른다**:
지키는 것이 어휘가 아니라 **같은 문자열이 뜻하는 좌표계**이고, 그것이 파일마다 갈리면
구버전 앱이 새 파일을 조용히 열어 옛 범위로 벡터를 뽑는다.

**고쳐도 안 돌아오는 것.** 이미 나간 `.mlpx` 안의 지표는 그 시점의 숫자로 남는다.
마이그레이션이 하는 일은 "다음부터 맞게"이지 "지난 것을 고침"이 아니다.

## 10. 검증 정책 — 관대함과 엄격함의 경계

**필드는 관대하게, 어휘는 엄격하게.**

| | 규칙 | 이유 |
|---|---|---|
| 모르는 **필드** | 살려서 그대로 다시 쓴다 (`looseObject`) | 지우면 소리 없이 데이터가 사라진다 |
| 모르는 **어휘** | 거부한다 (`z.enum`) | 같은 버전인데 모르는 값이면 깨진 값이다 |
| **사용자 데이터** | 어떤 문자열이든 받는다 | 한글·공백·특수문자가 오는 게 정상이다 |

`looseObject`는 **중첩된 안쪽까지 전부** 적용한다. 최상위만 열어 두면 `metrics` 안의
새 지표가 사라진다.

어휘를 엄격하게 막는 대가는 **어휘가 늘어나는 변경마다 `formatVersion`을 올려야 한다는 것**이다.
`schema.spec.ts`가 어휘 목록을 고정해 두고 있어서 잊고 지나갈 수 없다.
**첫 배포 전에는 이 대가를 치르지 않는다** — 근거는 §9의 머리말에 있다.

예외는 축이 다른 것뿐이다 — `algorithm` 이름과 `model.format`은 등록부에 속하고
등록부 변경은 포맷 변경이 아니다(§5.2).

**파일 파싱은 관대하게, 폼 입력은 엄격하게.** 같은 규칙을 두 곳에 똑같이 적용하지 않는다.
학번 길이 상한은 입력 화면에만 걸린다 — 상한을 넘는 학번이 든 남의 파일도 열려야 한다.

## 11. 브라우저 저장소

프로젝트 보관은 IndexedDB에서 이루어진다. store를 셋으로 나눈다.

| store | 담는 것 | 왜 나눴나 |
|---|---|---|
| `projects` | 문서와 요약(이름·시각·용량) | 목록 화면이 읽는 것 |
| `datasets` | 원본 바이트 | 수십 MB. 목록 뽑을 때 딸려오면 안 된다 |
| `models` | 모델·전처리기 바이트 | Random Forest가 MB 단위다 |

- 저장은 **한 트랜잭션**이다. 모델을 전부 지우고 새로 넣는다(§4.3).
- 쓰기 전에 `navigator.storage.estimate()`로 여유를 확인하고 부족하면
  `STORAGE_QUOTA_EXCEEDED`로 거부한다. `estimate()`가 없는 브라우저에서는
  `QuotaExceededError`를 같은 코드로 바꾼다.
- 언어 선택 저장 실패는 삼키지만 **프로젝트 저장 실패는 삼키지 않는다.**
  학생의 작업물이 날아가는 일이라 화면이 반드시 알아야 한다.
- **우리 쪽 용량 상한은 없다.** 판정하는 주체는 브라우저이고 우리는 묻기만 한다.
  프로젝트 수 상한도 없다 (`open-decisions.md` #7).
- **`navigator.storage.persist()`를 데이터셋이 처음 들어간 저장에서 한 번 부른다.**
  안 부르면 기본값이 "지워도 되는 데이터"이고, iOS Safari는 일정 기간 방문이 없으면
  통째로 지운다. 빈 프로젝트를 만든 시점이 아니라 **표를 올린 시점**인 이유는 그때가
  학생에게 잃을 것이 생긴 순간이기 때문이다. **성공하든 실패하든 저장은 그대로 진행된다** —
  이건 저장의 전제 조건이 아니라 저장된 것을 오래 살게 하는 요청이다.
