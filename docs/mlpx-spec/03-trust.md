# `.mlpx` — 인적사항과 무결성 (§6~§7)

> `mlpx-spec.md`에서 갈라져 나온 절이다. **절 번호는 안 바뀌었다** —
> 저장소가 `mlpx-spec.md §5.9`처럼 번호로 가리키므로 여기서도 원래 번호를 쓴다.
>
> 전체 차례는 허브(`../mlpx-spec.md`)에 있다.

## 6. 인적사항과 표절 흔적

### 6.1 원칙과 충돌하지 않는다

CLAUDE.md §1.1은 "**서버는** 인적사항을 받지 않는다"이지 "파일에 없다"가 아니다.
학번·이름은 `.mlpx` 안에만 존재하고 서버로 가는 경로를 **구조적으로 막는다.**

1. 학습·예측·검증 요청 타입에 `manifest`를 넣을 수 없게 한다
2. 전송 페이로드에 인적사항 키가 있으면 실패하는 테스트를 둔다
3. `privacy.md`에 "`.mlpx` 파일 자체는 개인정보를 담는다"를 명시한다

### 6.2 둘 다 선택 입력

| | 형식 | 필수 |
|---|---|---|
| `studentId` | 자유 문자열 (상한은 `limits.ts`) | 아니오 |
| `name` | 텍스트 (상한은 `limits.ts`) | 아니오 |

숫자 강제는 없다. `1-2-03`, `2026-0101` 같은 학번 체계가 실재한다.

**`required`로 만들지 않는 이유**: 안 쓸 학생은 `0000`을 넣는다.
강제는 입력을 만들지 품질을 만들지 않는다. 반면 교사 시연·독학·동아리에서
"student ID"를 요구받는 건 확실한 장벽이다.

**대신 파일명이 검사 수단이다.**

```
있음 →  10203_홍길동_붓꽃품종분류.mlpx
없음 →  붓꽃품종분류.mlpx
```

학생이 저장 시점에 스스로 알아채고, 교사는 수거 폴더만 봐도 찾아낸다.
`required`는 `0000`을 못 걸러내지만 이건 걸러진다.

파일명은 금지 문자와 공백만 지우고 **한글과 하이픈은 그대로 둔다.**

### 6.3 표절은 이렇게 드러난다

**파일을 열면 `projectId`는 언제나 그대로다.** 여는 쪽에 갈림이 없다 — "이걸 바탕으로
새로 시작"처럼 새 id를 발급하는 선택지를 두지 않는다.

이유가 둘이다. **하나, 그 갈림이 곧 탐지 장치를 끄는 스위치다** — 복사한 파일이 새 id를
얻는 순간 남의 것이었다는 흔적이 사라진다. **둘, 대부분이 안 쓸 기능이다.** 이 도구는
수업 전용이 아니라 놀이터이고, 거기서 "남의 프로젝트를 바탕으로 새로 시작"은 뜻이 옅다.

**id가 유지된다는 것 자체가 신호다.**

- **자기 파일을 다른 기기에서 이어서 함** → 유지. 정상이고, 흔적이 남는 것도 정상이다
- **B가 A의 파일을 복사** → `projectId` 중복. zip을 풀어 고치면 해시가 어긋나지만,
  해시는 다시 계산할 수 있으므로 이건 방지턱이지 증거가 아니다(§7.2)

**그래서 프로젝트 파일 자체를 여러 사람에게 나눠 주는 경로를 만들지 않는다.** 여럿이 같은
파일에서 시작하면 그 파일들이 전부 같은 id를 갖고, 그 순간 위의 신호가 아무것도 못 가린다.

**가장 강한 표절 신호는 암호학이 아니라 파일들을 가로질러 보는 것이다.** 학생은 자기 파일은
고칠 수 있어도 나머지 29개는 못 고친다. `projectId` 중복과 `trainedAt` 간격의 일치 —
이것들은 해시도 서명도 없이 그대로 작동한다.

세 번째 단서는 `trainedAt` 타임스탬프다. 사람이 자판을 두드린 간격이 초 단위까지
두 번 일치할 확률은 없다.

**고아 모델 파일을 탐지 수단으로 쓰지 않는다.** run을 지울 거면 모델 파일도 지우면 그만이라
너무 쉽게 우회되고, 허술한 탐지기를 옆에 두면 교사가 그걸 신뢰하게 된다.

**한계**: B가 A의 데이터·설정만 받아 처음부터 자기가 돌리면 못 잡는다.
그리고 그건 표절인지 자체가 애매하다. **도구는 신호를 보여주고 판단은 교사가 한다.**

## 7. 무결성 — 위협 모델

**왜 필요한가:** `.mlpx`는 zip이고 수행평가 제출물이다. 학생이 압축을 풀어 지표를
고칠 수 있다. "재학습 없이 결과 확인"이 기본 동작이므로 변조 흔적을 볼 수 있어야 한다.

**전제부터 분명히 한다. 브라우저에서 도는 코드로는 위조를 막을 수 없다.**
학생 컴퓨터에서 실행되는 이상 학생이 통제한다. 클라이언트에 내려간 비밀은 비밀이 아니다.
그러므로 목표는 "위조 불가능"이 아니라 **"흔적을 남기고 판단은 교사에게 넘긴다"**이다.

### 7.1 세 층으로 나눈다

| 층 | 잡는 것 | 필요한 것 |
|---|---|---|
| 엔트리별 + 전체 해시 | 손으로 고친 흔적, **어디가** 바뀌었는지 | 없음 |
| 수거 시점 해시 기록 | 제출 이후의 변조 | 교사 앱의 기록 |
| **재실행 대조** | **지표가 이 데이터·설정에서 실제로 나오는지** | 없음 |

**세 층 전부 서버가 필요 없다.** 공식 배포에 서버가 없으므로(CLAUDE.md §1.1) 서버만 할 수
있는 검증은 애초에 설계하지 않는다.

**HMAC 서명은 넣지 않는다.** 자가호스팅 서버가 키를 쥐면 기술적으로는 가능하지만, 서버를
설치해서 쓰는 사람이 극소수일 것이므로 거의 아무도 못 쓰는 경로를 위해 키 관리·환경 변수·
검증 API를 유지할 이유가 없다. `SIGNING_SECRET`도 `core/signing`도 만들지 않는다.

**재실행 대조가 기본값이다.** `randomState`와 `trainIndices`를 항상 저장하는 것이 여기서
값을 한다 — 교사가 파일을 열고 다시 학습하면 지표가 재현되고, 학생이 숫자를 고쳤으면
재현되지 않는다.

앞의 두 층(해시)은 **바이트**를 검사하고 재실행은 **주장**을 검사한다. 데이터를 바꿔치기하면
해시는 통과시킬 수 있어도(다시 계산하면 되므로) 재실행은 통과하지 못한다.

### 7.2 해시 — 무엇을 위한 것인지 정직하게

엔트리별 해시와 그 전체를 덮는 해시를 파일에 남긴다. **이건 위조 방지가 아니라 방지턱이다.**
계산 코드가 오픈소스이고 비밀이 없으므로, 파일을 가진 사람은 고친 뒤 다시 계산할 수 있다.
git이 blob·tree·commit을 전부 해시하면서도 `commit -S`를 따로 두는 이유와 같다.

그럼에도 값이 있다.

- 압축을 풀어 숫자를 고치고 다시 압축하는 시도는 걸린다. 교실에서 실제로 일어나는 시도의
  대부분이 이 수준이다.
- **어디가 바뀌었는지**를 짚어준다. "`runs.json`은 바뀌었고 `dataset/`은 그대로"는 교사에게
  넘길 신호로서 쓸모가 있다.

**해시가 진짜 이빨을 갖는 순간은 신뢰할 수 있는 경로로 받은 값과 비교할 때다.**
교사가 제출물을 수거하는 시점이 그 경로다 — 그때 전체 해시를 기록해 두면 이후의 변조는
확실히 잡힌다. 학생은 자기 파일은 통제해도 교사가 적어둔 값은 통제하지 못한다.

**속도 규칙: 데이터셋은 import 시점에 한 번만 해싱한다.** 정본 바이트는 그 뒤로 바뀌지
않으므로(아래) 다시 계산할 이유가 없다. 저장할 때마다 도는 것은 JSON 넷뿐이고 수 KB다.
`ImportedTable.hash`가 그 한 번이고, `ProjectFile.dataset.hash`가 그 값을 저장까지 나른다 —
**타입이 규칙을 강제한다.**

> `@noble/hashes`의 SHA-256을 쓴다. **`crypto.subtle`을 쓰지 않는다** — 보안 컨텍스트에서만
> 존재하는데 자가호스팅은 `http://192.168.x.x:8000`이 보통이라 없는 셈이다. 분기와 폴백을
> 두면 "어떤 학교에서는 해시가 없다"는 상태가 생기고 화면과 테스트가 그걸 다 알아야 한다.
> 단일 경로로 간다. → `frontend/src/hash.ts`

### 7.2.1 파일에 남는 모양 — `hashes.json`

별도 엔트리다. **자기 자신은 해싱 대상에서 빠진다.**

```jsonc
{
  "algorithm": "sha256",
  "entries": { "manifest.json": "…", "dataset/data.csv": "…", "model/run-1.json": "…" },
  "contentHash": "…"
}
```

`contentHash`는 zip 바이트가 아니라 **엔트리 해시들에서** 나온다 — 경로로 정렬해
`"경로\n해시\n"`를 이어 붙인 것의 SHA-256이다. `JSON.stringify`를 쓰지 않는 이유는 키 순서와
들여쓰기가 값을 바꾸기 때문이다.

그래서 **다시 압축해도 안 변한다.** 부수 효과로 두 제출물의 `contentHash`가 같으면 내용이
같다는 뜻이 되어 §6.3의 신호에 그대로 얹힌다.

**옛 파일에는 없으므로 선택 항목이다.** 없거나 깨져 있으면 "확인할 수 없음"이지 파일 열기
실패가 아니다. 무결성 정보 때문에 학생의 작업물이 안 열리는 일은 없어야 한다.

대조 대상은 **아는 엔트리만**이다 — 고정 엔트리, `settings.data`가 가리키는 정본(있을 때),
`model/` 아래. **이미지는 정본 한 장 한 장이 그 대상이다**(§1.2).
`__MACOSX/` 같은 쓰레기까지 세면 맥에서 압축을 풀었다 다시 압축한 파일이 전부 "고쳐졌음"이
되고, 그러면 아무도 이 표시를 믿지 않는다. 반대로 `model/`을 통째로 보는 이유는 끼어든
고아 모델도 신호이기 때문이다.

**해시가 둘인데 쓰임이 다르다. 섞지 마라.**

| | 무엇인가 | 무엇에 쓰나 |
|---|---|---|
| `contentHash` | 파일 **안**의 값. 엔트리 해시들에서 계산 | 어디가 바뀌었나 · 표절 대조(§6.3) |
| 수거 해시 | 파일 **밖**의 기록. `.mlpx` 바이트 자체 | 제출 이후의 변조 |

**수거 시점에 기록하는 해시는 `.mlpx` 바이트 자체를 해싱한 값이다.** 파일 안에 아무것도
넣을 필요가 없다.

`contentHash`로 통일하지 않는 이유는 하나다 — **교사가 우리 도구 없이 계산할 수 있어야
한다.** 우리 앱으로만 대조할 수 있으면 그 대조는 결국 우리 앱의 보고를 믿는 것이 되고,
§7.2가 말한 "신뢰할 수 있는 경로"의 독립성이 앱 안으로 접혀 들어간다. 재압축 불변이라는
`contentHash`의 장점도 수거 이후에는 값이 없다 — 수거된 파일은 바이트가 변할 이유가
없고, 변했다는 것 자체가 신호다.

```
certutil -hashfile 10203_홍길동_붓꽃품종분류.mlpx SHA256
Get-FileHash 10203_홍길동_붓꽃품종분류.mlpx -Algorithm SHA256   # PowerShell
```

**학교 PC는 윈도우다.** `sha256sum`이라고 적어 두면 이 문단의 근거가 교실에서 성립하지
않는다.

### 7.3 UI 문구 — 과신을 만들지 마라

**"검증됨"이라고 쓰지 않는다.** 도구가 보증할 수 있는 것보다 강한 말이고, 교사가 그 말을
믿기 시작하면 허술한 탐지기가 판단을 대신하게 된다.

정직한 표현은 "고쳐진 흔적 없음", "지표가 재현됨", "재현되지 않음" 수준이다.
어휘의 단일 출처는 `frontend/src/errors.ts`의 `FILE_HASH_STATUSES` / `ENTRY_HASH_STATUSES` /
`REPRODUCTION_STATUSES`다. 파일 전체와 엔트리 하나는 축이 다르므로 열거형도 다르다 —
"이 파일이 고쳐졌는가"와 "이 엔트리가 무엇이 됐는가"는 같은 낱말로 말할 수 없다.

### 7.4 데이터셋 바이트를 가공하지 않는 이유

읽고 쓰면서 인코딩을 바꾸거나 줄바꿈을 정규화하면 해시가 달라져 대조가 전부 무너진다.
그래서 **정본으로 확정된 뒤에는 누구도 손대지 않는다.**

정규화는 정본이 되기 **전에**, 가져오기 시점에 딱 한 번 일어난다(§1.1). 그 이후가 이 규칙의
적용 범위다.

**데이터셋 해시를 문서에 따로 적어 두지 않는다.** 파일에 남는 기록은 `hashes.json`의
엔트리 항목 하나뿐이고(§7.2.1), 여는 쪽은 그 값을 믿는 것이 아니라 zip 안의 바이트에서
다시 계산해 대조한다. 적힌 값을 그대로 읽어 보여주면 그 대조는 자기 자신과의 대조가 된다.

그래서 **참조가 가리키는 본체가 없는 파일은 아예 열지 않는다**(§1). 재계산할 바이트가
없으면 대조도 재학습도 재현도 성립하지 않는다.
